# framing-problems

작업을 시작하기 전에 왜 하려는지, 무엇이 원인인지, 무엇을 바꿀 수 없는지를 "구체화 기록"으로 정리해 사용자와 함께 확정합니다. 스킬은 코드, 문서, 로그, git 기록으로 알 수 있는 사실을 조사해 출처와 함께 보여 주고, 의도와 선택은 사용자에게 묻습니다. 기록이 확정되면 그 기록의 목표와 해법에 따라 작업을 이어 갑니다.

| 항목 | 값 |
|---|---|
| 버킷 | productivity |
| 호출 방식 | Model-invoked (요청하거나 프롬프트·스킬이 지시할 때만) |
| 호출 | `/gongbang:framing-problems [구체화할 요청]` |
| 원문 | [SKILL.md](../../skills/productivity/framing-problems/SKILL.md) |

**목차**: [언제 쓰나](#언제-쓰나) · [준비물](#준비물) · [진행 과정](#진행-과정) · [결과물](#결과물) · [커스텀](#커스텀) · [함께 쓰는 스킬](#함께-쓰는-스킬)

## 언제 쓰나

- 요청이 모호해서 바로 작업하면 원하지 않는 해법이 나올 것 같을 때
- "여기 고쳐줘"처럼 해법만 정해진 요청에서, 그 해법이 실제 원인을 고치는지 먼저 확인하고 싶을 때
- prompt-builder로 만든 프롬프트나 run-flow 같은 다른 스킬이 작업 전 구체화를 지시할 때

일반 작업 요청에는 스스로 실행하지 않습니다. "구체화해 줘"처럼 직접 요청하거나 `/gongbang:framing-problems`로 부르세요.

## 준비물

따로 준비할 것은 없습니다. 아래 도구가 있으면 함께 씁니다.

- **웹 검색 도구**: R4 외부 근거를 채울 때 씁니다. 없으면 그렇다고 알리고 출처를 "모델 지식, 미검증"으로 적습니다.
- **선택지를 보여 주는 질문 도구**: 메시지의 질문이 모두 선택형이면 선택창으로 묻습니다. 없으면 번호 목록으로 묻습니다.

## 진행 과정

1. R1~R6 체크리스트를 보여 줍니다. 한 단계의 칸이 모두 확정될 때마다 체크리스트를 갱신합니다.
2. 코드, 문서, 로그, git 기록, 대화로 답할 수 있는 사실은 스킬이 직접 조사해 출처(파일 경로, 문서 이름, URL)와 함께 보여 줍니다. 여러 파일을 훑는 조사도 다른 에이전트에 맡기지 않고 원본을 직접 읽습니다. 출처 없이 알게 된 내용은 "가설"로 적습니다.
3. 의도, 만족 기준, 선택은 사용자에게 묻습니다. 메시지마다 지금 물을 수 있는 질문, 곧 답이 기대는 칸이 이미 확정된 질문을 모두 묻습니다. 보통 첫 메시지에서 R1·R2·R3을 함께 묻고, R5 해법은 R2 원인, R3 제약, R4 판정(R4를 채울 때)이 확정된 뒤에 묻습니다.
4. 사용자가 "맞다"고 한 칸만 확정합니다. 조사한 사실도 사용자가 맞다고 해야 확정되고, 이 스킬을 부른 프롬프트나 스킬이 사용자 대신 확정할 수 없습니다.
5. R1~R6의 모든 칸이 정해지면 기록 전체를 한 번 보여 주고 확정받습니다.

### 채우는 항목

칸은 정해진 순서 없이, 물을 수 있게 된 것부터 채웁니다.

| 항목 | 채우는 내용 |
|---|---|
| R1 의도·배경 | 왜 하려는지, 계기(특정 사건이나 반복되는 상황), 누가 겪는지. 요청이 해법만 말하면 그 해법으로 무엇이 달라지길 바라는지 묻습니다 |
| R2 이상·현재·원인 | 관찰할 수 있는 기준으로 쓴 이상과, 코드·출력·로그로 확인한 현재를 따로 적습니다. 문제는 "이상은 X인데 현재는 Y다"로 쓰고, 원인은 "확인됨"이나 "가설"로 적습니다 |
| R3 제약·자원 | 바꿀 수 없는 조건(기술, 일정, 조직, 호환성)과 그대로 쓸 기존 코드·도구·문서 |
| R4 외부 근거 | 보안·결제·개인정보·규제처럼 틀리면 비용이 큰 표준이 있는 영역이거나, R3에 따를 기존 방식이 없거나, 사용자가 요청할 때 채웁니다. 알려진 해법과 표준마다 우리 상황에 맞는지(맞음 / 조건부 / 맞지 않음), 그 판단의 근거 칸, 출처 URL을 적습니다. 그 밖에는 "R4 해당 없음: 이유"를 한 줄 적습니다 |
| R5 목표·해법 | 바꿀 원인(목표)과 바꾸는 방법(해법)을 따로 정합니다. 제안 해법, R3 자원을 쓰는 해법, R4에서 온 해법 가운데 2~3개를 비교합니다 |
| R6 부작용·장애물 | 해법이 새로 만드는 비용·위험(건드리는 호출부, 설정, 결과를 쓰는 사람)과 실행을 막는 것(권한, 의존성, 일정). 부작용마다 감수, 완화책, 해법 변경 중 하나를 정합니다 |

- 요청에 해법이 들어 있으면 그 해법을 "R5 제안 해법"에 적어 두고, 그 해법이 풀려는 문제부터 맞춥니다. 조사한 원인이 제안 해법을 뒷받침하면 첫 메시지부터 유력 후보로 추천하고, 뒷받침하지 않으면 그 이유를 보여 줍니다.
- R5 목표로 고른 원인이 "가설"이면 확인 방법(재현, 측정, 로그)을 R6 장애물에 넣습니다. 가설이 틀리면 R2로 돌아갑니다.
- 감수할 수 없는 부작용이 있으면 R5로 돌아갑니다.

### 질문에 답하는 방법

질문 메시지는 진행 줄, 정리와 질문, 확인 요청 순서로 옵니다.

- **진행 줄**: 첫 줄에 다루는 단계와 질문 수가 있습니다. 예: `**R2·R3 · 질문 2개 · 답이 필요합니다**`. 알림만 봐도 답이 필요한지 알 수 있습니다.
- **추천**: 질문마다 ➡️ 추천과 근거가 붙습니다. 근거가 조사한 사실이나 확정한 칸에서 나오지 않고 사용자만 아는 것(의도, 계기, 운영 절차 등)이면 추천 앞에 "추정:"이 붙습니다. 질문에 "네"라고 답하면 그 추천을 받아들입니다.
- **확인 요청**: 마지막 줄에서 확인을 요청합니다. "맞다"고 답하면 정리와 모든 추천을 받아들입니다. 다르게 답하려면 "Q1 b"처럼 질문 번호와 선택지로 알려 주세요.

추천과 다른 답이나 새 정보를 주면, 반영한 정리를 다음 메시지 맨 앞에 넣어 다음 질문과 함께 다시 확인받습니다. 질문이 모두 선택형이면 질문 도구로 묻고, 추천을 첫 선택지에 두어 라벨 끝에 "(추천)"을 붙입니다. 질문이 4개를 넘으면 텍스트로 묻습니다.

### 질문을 줄이거나 멈추기

- **압축 모드**: "질문 줄여 줘"처럼 요청하거나 부른 프롬프트·스킬이 그렇게 지시하면, 조사로 채운 구체화 기록 전체와 모든 단계의 질문을 한 메시지에 보여 줍니다. 진행 줄은 `**R1~R6 한 번에 · 질문 <개수>개 · 답이 필요합니다**`입니다. 확정 전 칸은 "확인 필요"로 표시되고, 한 번 답해서 여러 단계를 확정할 수 있습니다. R6 부작용·장애물과 "가설"인 원인은 질문으로 남습니다.
- **중단**: "그냥 해줘", "그만 묻고 진행해"라고 하면 더 묻지 않고 지금까지의 기록을 보여 줍니다. 못 채운 칸은 "미확인"으로 둡니다. R5 해법이 미확인이면 제안 해법을 따르고 그렇다고 알립니다. "가설"인 원인과 미확인 R6 때문에 생길 수 있는 위험은 한 줄씩 알립니다.

### 확정한 내용 바로잡기

"그게 아니고"처럼 확정한 내용을 바로잡으면 기록을 다음 순서로 고칩니다. 기록을 확정해 다른 작업으로 넘어간 뒤에도 같습니다.

1. 정정이 어느 단계의 전제인지 찾아 그 단계를 다시 확정합니다.
2. 뒤 단계를 차례로 다시 봅니다. "근거" 열에 바뀐 칸이 있는 결정은 다시 판단하고, 나머지도 결론이 여전히 성립하는지 확인합니다. 이미 정한 해법도 다시 판단합니다.
3. 결과를 `R3 유지: 제약이 의도와 무관함`, `R5 변경: 캐시 추가 → 타임아웃 재시도`처럼 한 줄씩 보여 줍니다.

정정이 용어나 문장 표현에 대한 것이면 그 칸만 고칩니다.

## 결과물

**구체화 기록**: 대화에 `항목 | 내용 | 출처 | 근거` 표로 보여 줍니다.

| 열 | 내용 |
|---|---|
| 항목 | R1 의도, R1 계기, R2 이상, R2 현재, R2 문제, R2 원인, R3 제약, R3 자원, R4 근거, R5 제안 해법(채택 / 기각), R5 목표, R5 해법, R6 부작용, R6 장애물. 값이 여럿이면 행을 나눕니다 |
| 내용 | 확정한 값 |
| 출처 | "사용자", 확인한 파일·문서·URL, 또는 "미확인" |
| 근거 | 이 칸의 결정이 기대는 다른 칸. 확정한 내용을 바로잡을 때 다시 볼 칸을 찾는 데 씁니다 |

기록을 확정한 뒤에는 누가 불렀는지에 따라 다음 일이 달라집니다.

- **직접 불렀을 때**: R5 해법을 실행할지 묻고, 답을 받기 전에는 실행하지 않습니다.
- **프롬프트나 다른 스킬이 불렀을 때**: 확정한 R5 목표와 해법에 따라 그 지시의 작업을 이어 갑니다.

## 커스텀

| 바꾸고 싶은 것 | 고칠 곳 |
|---|---|
| 채울 항목(R1~R6)과 각 항목의 기준 | SKILL.md의 "항목" |
| 질문 메시지 형식, 압축 모드, 중단 조건 | SKILL.md의 "질문 방식" |
| 확정한 내용을 바로잡는 순서 | SKILL.md의 "되돌아가기" |
| 기록 표의 항목과 열 | SKILL.md의 "구체화 기록" |
| 기록을 확정한 뒤 할 일 | SKILL.md의 "마무리" |

기록의 항목 이름(R1 의도, R5 해법 등)을 바꾸면 set-brief의 "기록 템플릿"도 고쳐야 합니다. set-brief가 이 이름으로 구체화 기록의 칸을 brief 섹션에 옮깁니다.

Model-invoked라 description이 실행 조건을 정합니다. description을 고치면 Claude가 이 스킬을 고르는 상황도 바뀝니다. 복사해서 고치는 방법은 [커스텀 가이드](../customization.md)를 보세요.

## 함께 쓰는 스킬

- **prompt-builder**: 확정한 구체화 기록을 초안으로 넘기면 그 내용으로 프롬프트를 만듭니다. 사람과 대화하며 진행하는 에이전트 프롬프트나 재사용 템플릿을 만들 때 인터뷰에서 "실행 시 구체화"를 고르면, 완성 프롬프트가 실행될 때 작업 전에 이 스킬을 부릅니다. 프롬프트를 실행하는 환경에도 framing-problems가 설치돼 있어야 합니다.
- **set-brief**: 확정한 구체화 기록을 다른 세션이나 작업자가 이어받을 작업 지시서(brief)로 남깁니다.
- **run-flow**: 2단계(구체화)에서 이 스킬을 부릅니다. 사용자가 칸을 확정할 때마다 run-flow가 상태 파일의 `## 구체화 기록`에 적어 두므로, 흐름이 끊겨도 이미 받은 답을 다시 묻지 않습니다.
