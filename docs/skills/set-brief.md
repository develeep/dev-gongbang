# set-brief

대화에서 확정한 내용을 작업 지시서(brief) 하나로 남겨, 대화를 보지 못한 작업자나 다른 에이전트에게 작업을 넘길 수 있습니다. brief만 읽고 작업해도 대화 맥락을 가진 에이전트와 같은 결과가 나오도록, 스킬은 확인된 사실과 합의한 내용만 적고 대화를 모르는 서브에이전트에게 초안을 읽혀 해석이 갈리는 문장을 고칩니다. brief는 GitHub 이슈나 `docs/context/` 문서로 게시합니다.

> 만드는 중인 스킬입니다. `gongbang-dev`를 설치해야 쓸 수 있고, 동작이 바뀔 수 있습니다.

## 언제 쓰나

- 한 세션에서 끝나지 않는 작업을 다음 세션이나 다른 에이전트에 넘길 때
- framing-problems로 확정한 구체화 기록을 작업 지시서로 바꿀 때

일반 작업 요청이나 대화 요약 요청에는 스스로 실행하지 않습니다. "brief로 남겨 줘"처럼 요청하거나 `/gongbang:set-brief`로 부르세요.

## 준비물

- **남길 내용**: framing-problems로 확정한 구체화 기록이 있으면 그 기록을 기준으로 씁니다. 없으면 대화에서 확인된 사실과 합의한 결정만 모읍니다.
- **GitHub 이슈로 남길 때**: `gh` CLI가 로그인돼 있어야 합니다. 스킬은 `git remote -v`에 github.com이 있고 `gh auth status`가 성공하면 GitHub 이슈를, 아니면 docs 문서를 추천합니다.
- **서브에이전트**: 냉독 검증에 씁니다. 띄울 수 없으면 냉독 검증을 건너뛰고, 사용자 확인 단계에서 그렇다고 알립니다.
- **요구사항 문서(선택)**: analyzing-requirements로 만든 요구사항 문서가 있으면 그 경로와 고른 개발 범위를 brief에 넣고, 요구사항이 빠지지 않았는지 확인합니다.

## 진행 과정

1. **입력 수집**: 구체화 기록과 그 뒤에 한 작업(바꾼 파일, 커밋, 새로 합의한 결정)을 모읍니다. 구체화 기록이 없으면 대화 전체에서 확인된 사실과 합의한 결정만 모읍니다. 요구사항 문서가 있으면 그 경로와 고른 개발 범위도 모읍니다.
2. **저장 위치 선택**: GitHub 이슈와 docs 문서 중 하나를 고릅니다. 추천이 첫 선택지에 있습니다. docs 문서는 `docs/context/`에 두고, 레포 규칙이 작업 문서용 디렉터리를 따로 정해 두었으면 그 디렉터리도 선택지에 나옵니다.
3. **초안 작성**: 템플릿으로 초안을 씁니다.
   - 제목은 "최종 목적"을 한 줄로 쓴 문장입니다. 최종 목적을 한 줄로 쓸 수 없으면 목적이 여럿인 것으로 보고, 쓰기 전에 목적마다 brief를 나눌지 묻습니다.
   - 내용이 없는 섹션과 줄은 지웁니다.
   - 요구사항 문서가 있으면 고른 개발 범위의 요구사항마다 "남은 일"이나 "확인 기준"에 대응하는 줄이 있는지 확인합니다. 대응하는 줄이 없는 요구사항은 합의한 대로 "바꾸지 않는 범위"에 적고, 합의가 없으면 "미확인·위험"에 적습니다.
4. **냉독 검증**: 대화를 모르는 독자에게 초안만 읽혀 해석이 갈리는 문장을 찾습니다.
   - 새 컨텍스트로 서브에이전트 3개를 동시에 띄우고, 대화 내용 없이 초안 전문과 저장소 경로만 줍니다. 에이전트 규칙이나 이 스킬을 부른 쪽이 냉독 검증을 맡을 에이전트를 정해 두었으면 그 에이전트로 띄웁니다.
   - 서브에이전트는 그 저장소에서 작업을 맡았다고 가정하고 다섯 가지에 답합니다. 가장 먼저 할 작업과 시작 위치, 바꿀 범위와 바꾸지 않을 범위, 하지 않을 것, 끝났다고 판정하는 방법, 문서만으로는 정할 수 없어서 질문하거나 추측해야 하는 것입니다.
   - 스킬은 답을 대화에서 합의한 내용과 비교하고 세 답끼리도 비교해, 합의와 어긋나거나 서로 갈린 답의 원인이 된 문장을 고칩니다. 합의가 없어 고칠 수 없는 항목은 "미확인·위험"으로 옮깁니다.
   - 고친 초안으로 한 번 더 검증합니다. 두 번째에도 어긋나는 항목은 고치지 않고 5단계에서 보여 줍니다.
5. **사용자 확인**: 한 메시지에 다음을 보여 주고 확인을 받습니다. 맞다고 하기 전에는 게시하지 않고, 수정 요청을 받으면 반영한 초안을 다시 보여 줍니다.
   - 초안 전문
   - 냉독 검증에서 고친 항목과 남은 어긋남
   - 실행할 외부 작업. 이슈면 이슈를 만들 저장소와 공개 여부, 붙일 라벨, `context` 라벨을 새로 만드는지 여부이고, docs면 저장할 경로입니다.

   공개 저장소면 초안에 비밀값, 내부 URL, 개인 정보가 없는지 확인해 달라고 요청합니다. 이슈는 게시한 뒤 되돌려도 캐시나 알림으로 남기 때문입니다.
6. **게시**: 고른 위치에 게시합니다. 게시 형태는 [결과물](#결과물)에 있습니다. 게시를 마치면 "남은 일"의 크기를 보고 다음 스킬을 안내합니다. 새 컨텍스트 창 하나로 끝나지 않을 크기면 set-ticket으로 나누라고, 한 창으로 끝날 크기면 새 세션에서 run-ticket을 brief 경로나 이슈 번호로 실행하라고 안내합니다. 다른 스킬이 불렀으면 안내하지 않고 brief 경로나 이슈 번호를 그 스킬에 넘깁니다.

## 결과물

**GitHub 이슈**

- `context` 라벨을 붙여 이슈를 만들고 이슈 URL을 알려 줍니다. 라벨이 없으면 `gh label create context --description "맥락 파악서 겸 작업 지시서"`로 먼저 만듭니다.
- `context` 라벨이 brief 목록 역할을 합니다. 다음 세션은 `gh issue list --label context`로 brief를 찾습니다.

**docs 문서**

- 2단계에서 고른 디렉터리(기본 `docs/context/`)에 `YYYY-MM-DD-<slug>.md`로 저장합니다. slug는 제목을 영문 소문자와 하이픈으로 줄인 것입니다. 같은 이름의 파일이 있으면 덮어쓰기 전에 묻습니다. 레포 규칙이 정한 파일 이름(`spec.md` 등)은 쓰지 않습니다.
- 같은 디렉터리의 `README.md`에 `- [YYYY-MM-DD 제목](./YYYY-MM-DD-<slug>.md): 요약 문장` 한 줄을 추가합니다. `README.md`가 없으면 `# Context` 제목과 함께 만듭니다.
- 저장한 파일 목록을 알려 줍니다. 커밋은 하지 않습니다.

**brief 구성**

brief 맨 위에는 `- 기준 커밋:`, `- 작성일: YYYY-MM-DD`, `- 요구사항 문서:` 줄이 있고, 그 아래에 다음 섹션이 옵니다. 구체화 기록이 있으면 오른쪽 열의 칸을 그 섹션으로 옮깁니다.

| 섹션 | 내용 | 옮기는 구체화 기록 칸 |
|---|---|---|
| 요약 | 이슈 요약 | - |
| 배경·의도 | 왜 하는지, 계기 | R1 의도, R1 계기 |
| 최종 목적 | 완료됐을 때 관찰할 수 있는 상태 | R2 이상, R5 목표 |
| 확인된 사실 | 확인된 사실 목록 | R2 현재, R2 문제, "확인됨"인 R2 원인, R3 자원 |
| 합의한 작업 | 해법, 해법 근거, 기각한 해법과 이유, 완료한 일, "남은 일" 체크리스트 | R5 해법, "맞음"·"조건부"인 R4 근거, "기각"인 R5 제안 해법, "맞지 않음"인 R4 근거 |
| 작업 경계 | 바꾸는 범위, 바꾸지 않는 범위, 바꿀 수 없는 조건 | R3 제약(바꿀 수 없는 조건으로) |
| 하면 안 되는 것 | 하면 안 되는 행동과 이유 | - |
| 확인 기준 | 실행할 명령과 기대 결과, 사용자가 관찰할 수 있는 변화를 체크리스트로 | - |
| 미확인·위험 | 가설인 원인과 확인 방법, 부작용과 감수·완화책, 장애물 | "가설"인 R2 원인, R6 부작용, R6 장애물 |

출처가 "모델 지식, 미검증"인 R4 근거는 "해법 근거" 대신 "미확인·위험"에 들어갑니다. 기각한 해법을 함께 적는 이유는 작업자가 이미 기각한 대안을 다시 조사하지 않게 하기 위해서입니다.

brief의 문장은 다음 규칙으로 씁니다.

- 확인된 사실과 합의한 내용만 적습니다. 추측, 추천, 가설은 "미확인·위험"에만 둡니다.
- 사실마다 출처(커밋 해시, URL, "사용자 합의")를 붙입니다. 경로는 맨 위 기준 커밋 시점의 경로입니다.
- "아까 말한", "그 파일"처럼 대화를 가리키는 표현 대신 이름, 경로, 값을 직접 적습니다.
- "빠르게", "깔끔하게"처럼 기준 없는 표현은 대화에서 합의한 수치, 명령, 경로로 바꿉니다. 합의한 기준이 없으면 그 표현을 "미확인·위험"으로 옮깁니다.
- 확인 기준은 구현 방식 대신 외부에서 관찰할 수 있는 동작으로 씁니다. 그래야 다른 방식으로 구현한 작업자도 같은 기준으로 판정할 수 있습니다.

## 커스텀

| 바꾸고 싶은 것 | 고칠 곳 |
|---|---|
| brief 섹션 구성 | SKILL.md의 "기록 템플릿" |
| brief 문장 규칙(출처, 기준 없는 표현) | SKILL.md의 "핵심 규칙" |
| 추천 저장 위치, docs 디렉터리 | SKILL.md의 "2. 저장 위치 선택" |
| docs 파일 이름, 인덱스 줄, 이슈 라벨 | SKILL.md의 "6. 게시와 인덱스 갱신" |
| 냉독 검증 질문과 서브에이전트 수 | SKILL.md의 "4. 냉독 검증" |

섹션 이름, "남은 일"·"바꾸지 않는 범위"·"바꿀 수 없는 조건" 같은 줄 이름, `- 작성일: YYYY-MM-DD` 줄을 바꾸면 set-ticket, run-ticket, run-flow도 함께 고쳐야 합니다. set-ticket과 run-ticket은 이 이름과 `^- 작성일: ` 정규식으로 brief를 찾고 읽고, run-flow도 `- 작성일:` 줄로 brief를 알아봅니다. `context` 라벨 이름을 바꿀 때도 같습니다. 세 스킬 모두 `gh issue list --label context`로 GitHub brief를 찾습니다.

복사해서 고치는 방법은 [커스텀 가이드](../customization.md)를 보세요.

## 함께 쓰는 스킬

- **framing-problems**: 먼저 구체화 기록을 확정하면 그 기록을 기준으로 brief를 씁니다.
- **analyzing-requirements**: 이 스킬로 만든 요구사항 문서가 있으면 그 경로와 고른 개발 범위를 brief에 적고, 요구사항마다 대응하는 줄이 있는지 확인합니다.
- **set-ticket**: "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 brief를 티켓으로 나눕니다.
- **run-ticket**: 한 창으로 끝날 크기면 새 세션에서 brief를 바로 실행합니다. `## 티켓` 섹션이 없는 brief는 brief 전체를 티켓 하나로 봅니다.
- **run-flow**: 3단계(작업 지시서)에서 이 스킬을 부릅니다. 이때는 run-flow 세션이 set-brief의 단계를 모두 직접 하고, 냉독 검증의 독자만 새 컨텍스트로 띄웁니다. 게시가 끝나면 run-flow가 같은 크기 기준으로 4단계(티켓 분할)나 5단계(구현과 리뷰)로 이어 갑니다. 사용자가 티켓으로 나누라고 했으면 크기와 상관없이 4단계로 갑니다.
