# building-skills

SKILL.md 초안이나 작업 자료를 넘기면, Agent Skills 명세에 맞고 실제로 돌려 봤을 때 스킬 없이 할 때보다 나은 스킬로 완성할 수 있습니다. Claude 공식 skill best practice와 Agent Skills 명세를 기준으로 정적 검사, 실행 테스트, 사람 리뷰, 수정을 반복합니다. 스킬에 넣는 절차, 규칙, 판단 기준, 예시는 사용자의 자료와 답변, 승인한 제안에서만 가져옵니다.

| 항목 | 값 |
|---|---|
| 버킷 | productivity |
| 호출 방식 | Model-invoked (스킬을 만들거나 검증·개선해 달라고 할 때) |
| 호출 | `/gongbang:building-skills [스킬 폴더 경로, SKILL.md 초안, 또는 만들 스킬 설명]` |
| 원문 | [SKILL.md](../../skills/productivity/building-skills/SKILL.md) |

**목차**: [언제 쓰나](#언제-쓰나) · [준비물](#준비물) · [진행 과정](#진행-과정) · [결과물](#결과물) · [커스텀](#커스텀) · [함께 쓰는 스킬](#함께-쓰는-스킬)

## 언제 쓰나

입력에 따라 세 모드 중 하나로 진행합니다. 입력만으로 모드가 애매하면 묻습니다.

| 모드 | 이럴 때 | 넘길 입력 |
|---|---|---|
| A. prompt-builder 이어받기 | prompt-builder로 만든 SKILL.md 초안을 테스트하고 다듬을 때 | prompt-builder 출력(설계 요약, SKILL.md 코드블록, 다음 단계) |
| B. 기존 스킬 개선 | 이미 있는 스킬을 고치고, 고치기 전보다 나아졌는지 확인할 때 | 스킬 폴더나 SKILL.md |
| C. 단독 신규 | 자료에서 스킬을 새로 만들 때 | 만들 스킬 설명, 대화 기록, 런북, 코드, 리뷰 코멘트 같은 자료 |

이 스킬은 SKILL.md만 다룹니다. CLAUDE.md를 쓰려면 prompt-builder를 쓰세요.

## 준비물

- Python 3.9 이상. 번들 스크립트는 표준 라이브러리만 씁니다.
- 대표 요청 3개. Model-invoked 스킬이면 비슷하지만 스킬을 쓰면 안 되는 요청(near-miss) 2개도 준비하세요. 대표 요청이 없으면 지어내지 않고 묻습니다. 사용자가 맡기면 초안 3개를 보여 주고 승인한 것만 씁니다.
- 모드 C는 이 작업을 실제로 해낸 대화 기록, 런북·내부 문서, API 명세·설정 파일·코드, 리뷰 코멘트·이슈 중 있는 것을 넘기세요. 요청에 자료가 없으면 스킬이 달라고 합니다. 자료가 하나도 없으면 질문으로만 진행하지만 품질이 떨어집니다.
- 실행 테스트는 서브에이전트로 돌립니다. 서브에이전트를 띄울 수 없는 환경에서는 케이스를 하나씩 직접 실행하고, 엄밀하지 않다고 알린 뒤 기준 실행은 건너뜁니다.
- 검증 3단계(description 측정)는 `claude` CLI(Claude Code)가 있어야 측정합니다. 없으면 쿼리 세트까지만 만들고 측정은 건너뜁니다.

## 진행 과정

1. **입력 파악과 모드 결정**: 입력을 보고 모드를 정합니다. 코드블록으로만 받은 스킬은 작업 폴더에 `<name>/` 폴더를 만들어 파일로 옮깁니다. 모드 B는 고치기 전에 원본을 `<name>-workspace/skill-snapshot/`에 복사해 비교 기준으로 둡니다.
2. **사양 확정**: 사양표(K1~K10)를 채워 `항목 | 값 | 출처 | 상태` 표로 보여 주고, 상태가 모호하거나 없는 항목만 묻습니다. 모드 A에서는 prompt-builder가 이미 확인받은 값을 다시 묻지 않습니다.
3. **작성 또는 보완**: `references/authoring-rules.md`의 작성 규칙대로 SKILL.md와 번들 파일을 쓰거나 고칩니다. 문구 다듬기, 순서 조정, 참조 파일 분리 같은 형식 수정은 바로 하고 무엇을 바꿨는지 알립니다. 절차, 규칙, 판단 기준, gotcha, 예시 같은 내용은 넣을 문장을 그대로 제안해 승인받습니다.
4. **정적 검사**: `scripts/check_skill.py`로 검사하고 ERROR가 없어질 때까지 고칩니다. WARN은 고치거나, 고치지 않을 이유를 한 줄로 알립니다. 스크립트가 못 보는 항목은 사람 검토 체크리스트로 점검하고, 결과를 `항목 | 결과 | 근거` 표로 보여 줍니다.
5. **검증 강도 선택**: 아래 단계 중 하나를 고릅니다. 단계는 누적됩니다.

   | 단계 | 하는 일 | 비용 |
   |---|---|---|
   | 1. 점검 (권장, 기본) | 대표 요청을 스킬을 쓴 실행으로만 돌리고 채점·리뷰 | 서브에이전트 3개 안팎 |
   | 2. 비교 | 1에 더해 기준 실행(모드 A·C는 스킬 없이, 모드 B는 스냅숏)을 함께 돌려 비교. 사용 모델(K7)이 여럿이면 모델마다 실행 | 서브에이전트 6개 이상 |
   | 3. description | 2에 더해 description으로 스킬이 실행되는지 측정하고 다듬음 | `claude -p` 수십 회 이상 |

   User-invoked 스킬은 이름으로 부르므로 선택지에서 3단계를 뺍니다. 테스트 없이 끝내겠다고 하면 9단계로 넘어가고, 실행 검증을 하지 않았다는 사실을 마무리 보고에 남깁니다.
6. **테스트 작성·실행·채점**: 대표 요청마다 테스트 케이스를 스킬 폴더의 `evals/<case-name>/`에 `claude plugin eval`이 읽는 형식으로 만듭니다. 작업 중인 저장소의 CLAUDE.md가 eval 위치를 정해 두었으면 그 위치를 씁니다. 모든 실행을 한 번에 띄우고, 실행이 도는 동안 assertion을 쓰고, 끝나면 채점합니다. 2단계 이상이면 `scripts/aggregate.py`로 결과를 집계합니다. 실행 결과는 스킬 폴더 옆 `<name>-workspace/iteration-N/`에 쌓입니다.

   테스트할 스킬이 사용자에게 질문하면 서브에이전트에는 답할 사람이 없으므로, 케이스마다 예상 답변을 정해 실행에 함께 넘깁니다. 이 답변은 사용자에게 확인받습니다.
7. **사용자 리뷰**: 결과를 분석하기 전에 `scripts/review.py`로 만든 리뷰 페이지(`iteration-N/review.html`)부터 전달합니다. 케이스마다 피드백을 적고 "피드백 내보내기"를 누르면 `feedback.json`이 내려받아집니다. 그 파일을 채팅에 첨부하거나 연결된 폴더에 두세요. 피드백이 비어 있는 케이스는 괜찮다는 뜻으로 받습니다.
8. **진단과 수정**: 실패한 assertion, 피드백, 실행 기록으로 원인을 찾아 수정안을 `번호 | 근거 | 바꿀 문장 전/후 | 형식/내용` 표로 보여 줍니다. 형식 수정은 바로 적용하고, 내용 수정은 번호별로 승인·수정·제외를 받습니다. 고친 뒤 정적 검사를 다시 돌리고 `iteration-<N+1>/`에서 6단계부터 반복합니다. 사용자가 만족하거나, 피드백이 모두 비었거나, 더 나아지지 않으면 멈춥니다.

   검증 3단계를 골랐으면 반복이 끝난 뒤 description을 다듬습니다. 쿼리 20개 안팎(실행돼야 할 것과 실행되면 안 될 것 각 8~10개)을 만들어 확인받고, `scripts/trigger_eval.py`로 측정하며 최대 5회 고칩니다. 측정할 때마다 쿼리 수 × 쿼리당 실행 횟수(`--runs`)만큼 실제 과금되는 실행이 일어나므로, 시작하기 전에 횟수를 알립니다.
9. **마무리와 전달**: 마지막으로 정적 검사를 돌려 ERROR가 없는지 확인한 뒤 전달합니다.

## 결과물

- 완성한 스킬 폴더와 테스트 케이스(`evals/<case-name>/`)
- 스킬 폴더 옆 `<name>-workspace/`: 반복마다 실행 결과, 채점, 리뷰 페이지, 2단계 이상이면 집계(`benchmark.json`, `benchmark.md`)
- 전달 방식은 스킬 구성에 따라 다릅니다.
  - SKILL.md 하나뿐이고 추가 frontmatter가 없으면: `propose_skills` 도구가 있는 환경에서 저장 카드를 띄웁니다.
  - 그 밖에는: `scripts/package.py`로 `<name>.skill` 패키지를 만들어 전달합니다. 사용하는 에이전트의 스킬 폴더(예: Claude Code는 `~/.claude/skills/<name>/`·`.claude/skills/<name>/`, Codex·OMP는 `~/.agents/skills/<name>/`·`.agents/skills/<name>/`)에 복사하는 방법도 알려 줍니다.
- 마무리 보고: 최종 통과율과 반복 횟수(2단계 이상이면 기준 실행과의 차이), 반영한 수정(형식/내용 구분), 남은 WARN·실패·승인받지 못한 수정안. 실행 검증을 건너뛰었거나 일부 모델에서만 시험했으면 그 사실도 적습니다.

claude.ai·Cowork의 `propose_skills` 저장 카드는 `name`, `description`과 본문만 남기고 `disable-model-invocation` 같은 다른 frontmatter 키를 버리며, 번들 파일도 담지 못합니다. 그래서 번들 파일이나 추가 frontmatter가 있는 스킬은 패키지로 전달합니다.

## 커스텀

| 바꾸고 싶은 것 | 고칠 파일 |

| 스킬 작성 규칙과 사람 검토 체크리스트 | `references/authoring-rules.md` |
| 사양표 항목, 모드별 입력 처리 | `references/intake.md` |

스킬을 복사해서 고치는 방법은 [커스텀 가이드](../customization.md)를 보세요.

## 함께 쓰는 스킬

- **prompt-builder**: SKILL.md 초안을 prompt-builder로 만들고 그 출력을 넘기면 모드 A로 이어받습니다. prompt-builder가 이미 확인받은 값은 다시 묻지 않습니다. prompt-builder의 "다음 단계"에 남은 경고(승인받지 못한 보완 제안, 생략하거나 기본값으로 둔 항목, 통과하지 못한 검수 항목)는 실패 원인 후보로 가장 먼저 봅니다.
- 이 저장소의 스킬을 고친 뒤 모드 B로 시험할 수 있습니다. 방법은 [커스텀 가이드](../customization.md#고친-스킬-시험하기)에 있습니다.
