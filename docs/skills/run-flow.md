# run-flow

기획서, 요청, brief 중 하나를 주면 요구사항 정리부터 PR 생성까지 개발 단계를 차례로 이어서 진행합니다. 단계마다 그 단계의 스킬을 대신 불러오므로, 각 스킬이 묻는 확인과 질문에만 답하면 됩니다. 진행 상황은 상태 파일에 남아, 대화가 끊겨도 run-flow를 다시 실행하면 멈춘 단계부터 이어 갑니다.

> 만드는 중인 스킬입니다. `gongbang-dev`를 설치해야 쓸 수 있고, 동작이 바뀔 수 있습니다.

| 항목 | 값 |
|---|---|
| 버킷 | in-progress |
| 호출 방식 | Model-invoked (기획서를 받아 개발하거나 요구사항 정리부터 티켓 분할·구현·리뷰까지 거칠 큰 작업을 맡길 때) |
| 호출 | `/gongbang:run-flow [기획서 경로·링크 \| 요청 \| brief 경로·이슈 번호 \| 상태 파일 \| status]`. 인자를 생략하면 진행 중인 흐름을 이어 갑니다 |
| 원문 | [SKILL.md](../../skills/in-progress/run-flow/SKILL.md) |

## 언제 쓰나

- 기획서나 요청 하나로 PR까지 진행하고, 중간에는 확인과 질문에만 답하고 싶을 때
- 멈춘 흐름을 이어서 끝낼 때. 인자 없이 실행하면 끝나지 않은 흐름을 찾아 이어 갑니다.
- 진행 중인 흐름이 어느 단계에 있는지 볼 때. `status`를 주면 끝나지 않은 흐름마다 제목, 현재 단계, 멈춘 이유, 남은 티켓 수를 보여 주고 끝냅니다.
- run-flow 밖에서 만든 brief와 티켓을 이어 갈 때. brief를 인자로 주면 티켓 상태로 시작 단계를 정합니다.

## 준비물

- 단계 스킬 analyzing-requirements, framing-problems, set-brief, set-ticket, run-ticket. `gongbang`과 `gongbang-dev`를 함께 설치하면 모두 있습니다.
- git 저장소와 `python3`. 시작 단계 판정, 보호 목록, 교차 리뷰 게이트가 `python3` 스크립트입니다.
- GitHub 이슈로 된 brief·티켓을 쓰거나 PR을 만들려면 github.com 원격과 로그인된 `gh` CLI. 없으면 7단계에서 PR 본문만 보여 주고 멈춥니다.
- 교차 리뷰에 쓸 다른 회사 모델. 정하는 방법은 [run-ticket의 교차 리뷰](run-ticket.md#교차-리뷰)에 있습니다. omp를 쓰면 [omp 멀티에이전트 설정](../omp-orchestration.md)으로 교차 리뷰·냉독 에이전트와 위임 규칙을 설치하고, 모델은 직접 고릅니다.
- 선택: 보호 목록의 쓰기 전 차단. [gongbang-mods](../mods.md#run-flow-보호-경로-차단)(Claude Code)나 [omp extension](../omp-orchestration.md#보호-경로-차단)을 설치합니다. 동작은 [보호 목록](#보호-목록)에 있습니다.
- 선택: 병렬 실행. 기본은 run-flow를 실행한 세션이 티켓을 차례로 직접 구현합니다. 워커로 병렬 실행하려면 워커 도구 절차를 지정하거나 규칙에 등록합니다. 조건은 [run-ticket의 여러 티켓 실행](run-ticket.md#여러-티켓-실행)에, 설정 예는 [Orca](../orca-orchestration.md)와 [Paseo](../paseo-orchestration.md) 오케스트레이션 설정에 있습니다.

## 진행 과정

시작할 때 0~7단계 체크리스트를 보여 주고 단계를 마칠 때마다 갱신합니다. 한 단계가 끝나면 다음 단계를 시작한다고 한 줄로 알리고 바로 이어 갑니다. 단계 사이에는 대화 대신 요구사항 문서 경로, brief 경로나 이슈 번호 같은 결과물을 넘깁니다.

0. **시작 단계 고르기**: 인자와 저장소 문서를 보고 [시작 단계](#시작-단계)를 정한 뒤, 고른 단계와 근거를 한 줄로 알리고 [상태 파일](#상태-파일)을 만들거나 이어 씁니다.
1. **요구사항 정리**: analyzing-requirements로 기획서를 요구사항 문서로 정리합니다. 스킬의 질문에 준 답은 받는 즉시 상태 파일에 적어, 문서를 저장하기 전에 끊겨도 다시 묻지 않습니다.
2. **구체화**: 개발 범위가 여럿이면 이번 흐름에서 진행할 범위 하나를 고르게 합니다. brief 하나에는 최종 목적 하나만 담기 때문입니다. 고르지 않은 범위는 상태 파일에 남고, 흐름이 끝난 뒤 요구사항 문서를 인자로 run-flow를 다시 실행하면 진행할 수 있습니다. 그다음 framing-problems로 구체화 기록을 확정합니다. 확정한 칸은 그때마다 상태 파일에 적어, 도중에 끊겨도 다시 묻지 않습니다.
3. **작업 지시서**: set-brief로 brief를 쓰고 게시합니다. set-brief의 단계를 이 세션이 모두 직접 하고, 냉독 검증의 독자 3명만 대화를 모르는 새 컨텍스트로 띄웁니다. 에이전트 규칙이 냉독 검증을 맡을 에이전트를 정해 두었으면 그 에이전트를 씁니다. 초안은 저장소 밖 임시 파일에, 냉독 결과는 그 옆 `<초안 파일 이름>.review.md`에 저장하고 두 경로를 상태 파일에 적으므로, 확인 전에 끊겨도 초안을 다시 만들지 않습니다. 게시한 뒤 다음 단계는 이렇게 정합니다. 사용자가 티켓으로 나누라고 했으면 크기와 상관없이 4단계, 그 밖에는 "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 4단계, 아니면 5단계입니다. 고른 단계와 근거는 상태 파일 `## 결정`에 남습니다.
4. **티켓 분할**: set-ticket으로 티켓을 나눠 게시합니다. 게시가 끝나면 5단계를 이 세션에서 이어 갈지, 새 세션에서 `/gongbang:run-flow <상태 파일>`로 이어 갈지 묻습니다. 새 세션은 지금까지의 대화를 다시 읽지 않아 비용이 줄고, 5단계에 필요한 것은 brief, 티켓, 상태 파일에 모두 있습니다.
5. **구현과 리뷰**: 현재 브랜치가 기본 브랜치면 작업 브랜치 이름을 묻고 만듭니다. 시작 HEAD를 상태 파일에 적고, 그 HEAD로 [보호 목록](#보호-목록)을 만들어 보여 준 뒤, 커밋하지 않은 흐름 문서(상태 파일, 보호 목록, 요구사항 문서, ADR, brief, 티켓, 인덱스 `README.md`)를 커밋 하나로 묶을지 묻습니다. 그다음 run-ticket의 [여러 티켓 실행](run-ticket.md#여러-티켓-실행)으로 끝나지 않은 티켓 전부를 실행합니다. 티켓이 하나이거나 `## 티켓`이 없는 brief여도 같고, 끝나지 않은 티켓이 없으면 통합 리뷰만 합니다. 기본은 이 세션이 차례로 직접 구현하는 것이고, 병렬 실행은 워커 도구 절차를 지정했거나 규칙에 등록해 둔 때만 씁니다.
   - 구현 중 받은 질문의 답과 새로 정한 설계 결정은 그때마다 상태 파일 `## 구현 중 결정`에 적어 뒤 티켓에 그대로 씁니다.
   - 완료 기준을 통과하지 못한 티켓이 나오면 흐름이 멈춥니다. 그 티켓, 시도 횟수, 실패 원인을 `- 멈춘 이유:`에 적고 티켓을 다시 나눌지(4단계로 돌아감) 묻습니다. 더 강한 모델이 필요하면 세션 모델을 바꾼 뒤 상태 파일을 인자로 다시 실행합니다.
   - 통합 리뷰 결과는 받는 즉시 리뷰한 HEAD, [코드 지문](#상태-파일)과 함께 `## 리뷰`에 적습니다. run-ticket 보고에 교차 리뷰 게이트 통과가 없으면 완료로 적지 않고 리뷰를 다시 맡깁니다.
6. **머지·PR 결정**: 먼저 보호 목록을 다시 검사하고, `## 리뷰`의 코드 지문을 지금 값과 비교합니다. 다르면 리뷰한 뒤에 코드가 바뀐 것이므로 그렇다고 알리고 리뷰부터 다시 합니다. 그다음 완료 기준 결과, 고치지 않은 리뷰 지적, 건너뛴 리뷰, 교차 리뷰 대체 표시, 바뀐 파일과 커밋을 모아 보여 주고 하나를 고르게 합니다. 6단계부터 시작해 run-ticket 보고가 없으면 상태 파일, 티켓의 완료 기록, git 기록에서 모읍니다.
   - **PR 만들기**: 커밋 메시지와, 기본 브랜치에 있으면 새 작업 브랜치 이름을 정하고 7단계로 갑니다. 커밋하기 전에 [보호 목록을 닫습니다](#보호-목록).
   - **고치기**: 고친 뒤 run-ticket으로 리뷰 단계만 다시 하고, 새 결과와 코드 지문을 적고 6단계로 돌아옵니다.
   - **멈추기**: 지금 상태와 남은 일을 보고하고 끝냅니다.
7. **PR 만들기**: 6단계에서 정한 대로 작업 브랜치를 만들고 커밋한 뒤 남은 변경이 없는지 확인합니다. PR 본문은 diff 전문 대신 brief, 바뀐 파일 목록(`git diff --stat`), 완료 기록, 리뷰 기록으로 이 세션이 직접 씁니다. 바꾼 이유, 바꾼 내용, 확인 방법 순서로 쓰고, 레포에 PR 템플릿이 있으면 그 형식을 따릅니다. 교차 리뷰를 대체했으면 그 표시와 수행한 모델도 확인 방법에 옮깁니다. 본문을 확인받은 뒤에야 push하고 `gh pr create`로 PR을 만듭니다.

각 단계 스킬이 묻는 확인(요구사항 문서 저장 위치, 구체화 기록 확정, brief 초안과 게시 위치, 티켓 분할안, 병렬 실행 계획)은 줄이거나 대신 답하지 않고 그대로 묻습니다. run-flow가 따로 묻는 것은 개발 범위, ADR로 남길 결정, 작업 브랜치 이름, 보호 목록에서 뺄 파일, 흐름 문서 커밋, 4단계 뒤의 세션 선택, 6단계의 선택, PR 본문 확인입니다. push와 PR은 되돌려도 원격 기록과 알림이 남으므로 6단계에서 고른 뒤에만 합니다.

### 시작 단계

`scripts/start_stage.py`가 저장소의 docs 문서를 보고 아래 표대로 판정합니다. 요청 문장, 링크, GitHub 이슈, `## 티켓`이 없는 brief의 크기처럼 스크립트가 정하지 못하는 것은 이 세션이 같은 표로 정합니다.

| 인자 | 시작 단계 |
|---|---|
| `status` | 단계를 시작하지 않습니다. 끝나지 않은 흐름의 목록만 보여 주고, 상태 파일도 고치지 않습니다 |
| 상태 파일 | 그 파일의 `- 현재 단계:` |
| `## 티켓`이 없는 brief | "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 4, 아니면 5 |
| 끝나지 않은 티켓이 있는 brief, 또는 그 티켓 | 5 |
| 티켓이 모두 끝난 brief | 통합 리뷰를 아직 안 했으면(`- 통합 리뷰: 안 함`) 5, 그 밖에는 6 |
| 흐름 밖에서 진행한 작업을 흐름으로 정리해 달라는 요청 | 끝나지 않은 brief마다 지금 단계를 판정해 상태 파일을 만든 뒤 이어 갈지 묻습니다 |
| 요구사항 문서(`## 개발 범위`와 `## 요구사항`이 있는 MD), 요청 문장 | 2 |
| 기획서: 위에 맞지 않는 PDF·PPT·MD 파일, SharePoint·OneDrive 링크 | 1 |
| 폴더 | 그 폴더 안에서 "없음"처럼 찾습니다 |
| 없음 | 끝나지 않은 상태 파일, 없으면 끝나지 않은 brief를 찾습니다. 여럿이면 목록을 보여 주고 고르게 하고, 하나도 없으면 무엇을 진행할지 묻습니다 |

- brief는 `- 작성일: YYYY-MM-DD` 줄이 있는 문서이고, 티켓은 brief의 `## 티켓` 링크가 가리키는 문서입니다. docs 티켓은 `- 상태: done`, GitHub 티켓은 closed면 끝난 것입니다. 레포 규칙이나 상태 파일 `## 결정`이 완료 표시를 다른 값으로 정했으면 그 값도 끝난 것으로 봅니다.
- 인자로 준 brief나 요구사항 문서를 적은 끝나지 않은 상태 파일이 있으면 그 파일을 이어 씁니다. 끝난 상태 파일에는 이어 쓰지 않고 새로 만듭니다.
- 구체화 기록은 있고 brief는 없는 흐름은, 기록이 확정됐으면 3단계부터, 확정 전이면 2단계부터 이어 갑니다.
- 상태 파일은 `docs/context/run-flow/` 밖(brief 옆 등)에 둬도 `- 현재 단계:` 줄로 찾고, `.scratch`처럼 심볼릭 링크로 붙인 폴더도 따라갑니다. GitHub brief는 `context` 라벨이 붙은 열린 이슈에서 찾습니다.

### 상태 파일

흐름마다 `docs/context/run-flow/YYYY-MM-DD-<slug>.md`에 상태 파일을 두고 단계가 바뀔 때마다 고칩니다. 대화가 끊기거나 압축돼도 이 파일을 열거나 `/gongbang:run-flow status`를 실행하면 어느 단계에서 무엇이 남았는지 볼 수 있습니다. 맨 위에 현재 단계와 멈춘 이유(이어 가는 방법 포함)가 있고, 그 아래 단계 체크리스트, 결과물 위치(요구사항 문서, 개발 범위, brief, brief 초안, brief 냉독 결과, ADR, 브랜치, 시작 HEAD, 보호 목록, 병렬 실행일 때만 채우는 워커 식별자, PR), 사용자 결정, 요구사항 답변, 구체화 기록, 구현 중 결정, 리뷰 기록이 들어갑니다. 형식은 `assets/state-file.md`입니다.

- 답, 결정, 리뷰 결과는 단계가 끝나기를 기다리지 않고 생긴 때에 바로 적습니다. 리뷰를 여러 개 함께 돌리면 결과가 하나 올 때마다 적습니다.
- 상태 파일이 brief·티켓 상태와 어긋나면 brief·티켓에 맞춰 고칩니다. 티켓은 통합 리뷰보다 먼저 done이 되므로, 티켓이 모두 끝났어도 통합 리뷰가 기록되지 않았으면 5단계의 리뷰부터 이어 갑니다.
- 7단계를 마치면 현재 단계가 `완료`가 되고, 끝난 상태 파일에는 다시 쓰지 않습니다. 같은 요구사항 문서로 다른 개발 범위를 진행하면 새 상태 파일이 생깁니다.

리뷰와 보고는 시작 HEAD 이후의 커밋, 커밋하지 않은 변경, 새 파일을 모두 봅니다. 코드 지문은 `scripts/code_fingerprint.sh`가 계산하는, 흐름 문서를 뺀 작업 트리의 tree 해시입니다. 커밋하지 않은 변경과 새 파일이 들어가고 흐름 문서만 바뀌면 값이 그대로여서, 6단계는 이 값으로 리뷰한 코드와 지금 코드가 같은지 봅니다.

### 보호 목록

구현하는 세션이 기존 테스트를 고쳐서 통과하는 것을 막습니다. 보호 목록은 5단계를 시작한 HEAD의 테스트와 판정용 사례(eval 사례, 채점 기준, 기대 출력), 이번 흐름에서 수락한 테스트의 목록입니다. 이 세션, 서브에이전트, 워커 모두 목록의 파일을 고치지 않고, 새 테스트 파일은 만들 수 있습니다. 목록은 상태 파일의 `- 현재 단계:`가 `완료`가 아닌 동안 켜져 있고, 상태 파일이 없어진 목록도 켜진 것으로 봅니다.

`scripts/protected_paths.py`가 목록을 만들고 고칩니다.

- **만들기(`init`)**: 5단계를 시작할 때 시작 HEAD의 테스트 파일을 찾아 `docs/context/run-flow/<상태 파일 이름>.protected`에 적습니다. `test`·`tests`·`__tests__`·`spec` 폴더 안의 파일과 `test_*.py`, `*_test.go`, `*.test.ts`, `*.spec.js`, `*Test.java`, `*_spec.rb` 같은 이름이 들어갑니다. 레포 규칙이 정한 다른 테스트나 판정용 사례는 `--path`로 더합니다. 목록이 이미 있으면 바꾸지 않습니다. 같은 내용의 사본을 git 공통 디렉터리(보통 `.git/gongbang-protected/`)에 둬서, 목록 파일을 셸로 고친 것도 찾습니다.
- **바꾸기(`add`, `remove`)**: 티켓을 수락하면 그 티켓이 새로 만든 테스트를 더합니다. brief나 티켓이 목록의 기존 테스트를 고치라고 하면 5단계를 시작할 때 그 파일을 보여 주고, 사용자가 정한 파일만 뺍니다.
- **쓰기 전 차단**(선택): gongbang-mods나 omp extension을 설치하면 쓰기 도구가 목록의 파일을 고치려 할 때 호출 전에 막고 이유를 돌려줍니다. 셸 명령(`sed -i`, 리다이렉트)으로 쓰는 것은 막지 못합니다.
- **수락 전 검사(`verify`)**: 티켓을 수락하기 전과 6단계에 들어갈 때 작업 트리, 인덱스, HEAD, 병렬 실행이면 워커의 티켓 브랜치까지 시작 내용과 비교합니다. 바뀐 파일, 지운 파일, `--path`로 더한 폴더에 새로 생긴 파일이 있거나 검사 자체가 실패하면 수락하지 않고, 바뀐 파일을 되돌리지 않고 보여 준 뒤 멈춥니다. 요구사항이 바뀌어 기존 테스트를 고쳐야 하면 사용자가 정한 뒤 그 파일을 빼고 이어 갑니다.
- **닫기(`close`)**: 목록은 흐름 문서로 커밋되므로, 지우지 않고 머지하면 기본 브랜치에서도 켜진 채 남아 기존 테스트 쓰기를 막습니다. 그래서 6단계에서 PR 만들기를 고르면 `verify`를 한 번 더 돌리고 통과하면 목록과 사본을 지웁니다. 이 삭제는 PR 커밋에 들어갑니다.
- **사본이 없을 때(`--reseal`)**: 다른 clone에서 이어 가 사본이 없으면, 목록이 셸로 바뀌었는지 알 수 없어 `init`이 멈춥니다. 목록을 보여 주고 사용자가 맞다고 하면 `--reseal`로 사본을 다시 만듭니다.

### ADR

2단계와 6단계에서 되돌리기 어렵고, 맥락 없이 보면 의아하고, 실제 대안 사이에서 고른 결정만 ADR 후보로 보여 줍니다. 고른 것만 레포의 ADR 폴더(없으면 `docs/adr/NNNN-<slug>.md`)에 남기고 상태 파일에 링크합니다. 2단계에서 남긴 ADR은 set-ticket이 읽어 티켓에 반영합니다.

### 요구사항이 바뀌면

진행 중에 요구사항이 바뀌었다고 알리면 새 흐름을 만들지 않고 같은 상태 파일에서 1단계로 돌아갑니다. 이전 요구사항 문서는 `<이름>-<이전 날짜>.md`로 옮기고, 구체화 기록은 바뀐 칸만 묻습니다. brief는 고칠지 새로 쓸지 묻고, 끝난 티켓은 그대로 둔 채 남은 일만 다시 나눕니다.

## 결과물

- 상태 파일, 요구사항 문서, brief, 티켓, ADR
- 구현 코드와 커밋. 보호 목록은 PR 커밋에서 지워집니다.
- GitHub PR. 머지는 사용자가 합니다.
- 마무리 보고: 단계별 결과물, PR URL, 고치지 않은 리뷰 지적
