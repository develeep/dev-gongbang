# run-flow

기획서, 요청, brief 중 하나를 받아 요구사항 정리부터 PR 생성까지 개발 단계를 차례로 이어서 진행합니다. 단계마다 그 단계의 스킬을 대신 불러오므로, 단계마다 스킬을 실행하지 않고 각 스킬이 묻는 확인과 질문에만 답하면 됩니다.

> 만드는 중인 스킬입니다. `gongbang-dev`를 설치해야 쓸 수 있고, 동작이 바뀔 수 있습니다.

## 언제 쓰나

- 기획서나 요청 하나로 PR까지 진행하고, 중간에는 확인과 질문에만 답하고 싶을 때
- 진행하다 멈춘 흐름을 이어서 끝낼 때. 인자 없이 실행하면 끝나지 않은 상태 파일을, 없으면 끝나지 않은 brief를 찾아 이어 갑니다.
- 진행 중인 흐름이 어느 단계에 있는지 볼 때. `status`를 주면 끝나지 않은 흐름마다 현재 단계, 멈춘 이유, 남은 티켓 수만 보여 주고 끝냅니다.
- 여러 기능을 동시에 진행할 때. 기능마다 Orca 작업 공간을 따로 만들고 각각 run-flow를 실행합니다.

## 준비물

- 단계 스킬: analyzing-requirements, framing-problems, set-brief, set-ticket, run-ticket. `gongbang`과 `gongbang-dev`를 함께 설치하면 모두 있습니다.
- 여러 티켓을 병렬로 실행하려면 Orca가 실행 중이고 `orchestration` 스킬이 설치돼 있어야 합니다. 없으면 티켓을 차례로 실행합니다.
- PR을 만들려면 github.com 원격과 로그인된 `gh` CLI가 있어야 합니다. 없으면 PR 본문만 보여 주고 멈춥니다.
- 단계마다 모델을 나눠 쓰려면 [omp 멀티에이전트 설정](../omp-orchestration.md)을 설치합니다.

## 진행 과정

0. 인자로 시작 단계를 고르고 상태 파일을 만듭니다. 상태 파일이면 그 파일의 현재 단계, brief면 티켓 상태에 따라 4~6단계, 요구사항 문서나 요청 문장이면 2단계, 기획서면 1단계부터 시작합니다. 상태 파일과 brief도 MD 문서라 기획서보다 먼저 판단합니다. 인자가 없으면 끝나지 않은 상태 파일을, 없으면 끝나지 않은 brief를 찾고, 여럿이면 목록을 보여 주고 고르게 합니다.
1. **요구사항 정리**: analyzing-requirements로 기획서를 요구사항 문서로 정리합니다.
2. **구체화**: 개발 범위가 여럿이면 이번에 진행할 범위 하나를 고른 뒤, framing-problems로 구체화 기록을 확정하고 상태 파일에 옮깁니다. brief를 쓰기 전에 흐름이 끊겨도 이 기록으로 3단계부터 이어 갑니다.
3. **작업 지시서**: set-brief로 brief를 남깁니다. 초안 작성과 냉독 검증은 상태 파일의 구체화 기록을 받은 서브에이전트가 맡고, 저장 위치 선택, 초안 확인, 게시는 run-flow가 직접 합니다. 남은 일이 한 세션에 끝나지 않을 크기면 4단계로, 아니면 5단계로 갑니다.
4. **티켓 분할**: set-ticket으로 티켓을 나눠 게시합니다.
5. **구현과 리뷰**: 현재 브랜치가 기본 브랜치면 먼저 작업 브랜치 이름을 묻고 만듭니다. 그다음 run-ticket으로 남은 티켓 전부를 실행합니다. Orca가 있으면 티켓마다 워커를 띄워 병렬로 실행합니다. 티켓이 하나여도 새 컨텍스트의 워커나 서브에이전트에게 맡겨, 대화 없이 brief와 티켓만 보고 구현하게 합니다. 완료 기준을 통과하지 못한 티켓이 나오면 멈추고, 티켓을 다시 나눌지 묻습니다.
6. **머지·PR 결정**: 완료 기준 결과, 리뷰 지적, 바뀐 파일과 커밋을 모아 보여 주고 PR 만들기, 고치기, 멈추기 중 하나를 고르게 합니다. 6단계부터 시작해 run-ticket 보고가 없으면 티켓의 완료 기록과 git 기록에서 모읍니다.
7. **PR 만들기**: 필요하면 작업 브랜치를 만들고 커밋한 뒤, PR 본문을 써서 push하고 PR을 만듭니다.

각 단계 스킬이 묻는 확인(구체화 기록 확정, 요구사항 문서 저장 위치, brief 초안과 게시 위치, 티켓 분할안, Orca 실행 계획)은 그대로 묻습니다. run-flow가 없애는 것은 단계가 끝날 때마다 다음 스킬을 직접 실행하던 일입니다.

### 상태 파일과 ADR

흐름마다 `docs/context/run-flow/YYYY-MM-DD-<slug>.md`에 상태 파일을 두고 단계가 바뀔 때마다 고칩니다. 현재 단계, 멈춘 이유, 단계 체크리스트, 결과물 위치(요구사항 문서, brief, ADR, 브랜치, PR), 사용자 결정, 확정한 구체화 기록이 들어갑니다. 대화가 끊기거나 압축돼도 이 파일을 열거나 `/run-flow status`로 어느 단계인지 확인할 수 있습니다. 5단계 진행 상황은 티켓 상태가 기준이고, 상태 파일이 어긋나면 티켓 상태에 맞춰 고칩니다.

2단계와 6단계에서 되돌리기 어렵고, 맥락 없이 보면 의아하고, 실제 대안 중에서 고른 결정만 ADR 후보로 보여 줍니다. 고른 것만 레포의 ADR 폴더(없으면 `docs/adr/NNNN-<slug>.md`)에 남기고 상태 파일에 링크합니다.

## 결과물

- 상태 파일, 요구사항 문서, brief, 티켓, ADR, 구현 코드와 커밋
- GitHub PR. 머지는 사용자가 합니다.
- 마무리 보고: 단계별 결과물 위치, PR URL, 고치지 않은 리뷰 지적

## 함께 쓰는 스킬

- **analyzing-requirements**, **framing-problems**, **set-brief**, **set-ticket**, **run-ticket**: 단계마다 불러오는 스킬입니다. set-brief, set-ticket, run-ticket은 run-flow가 불러올 수 있도록, 사용자나 다른 스킬이 지시할 때만 쓰는 Model-invoked입니다.
- **orchestration**(Orca): 5단계의 병렬 실행과 교차 리뷰 워커에 씁니다.
