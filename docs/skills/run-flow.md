# run-flow

기획서, 요청, brief 중 하나를 받아 요구사항 정리부터 PR 생성까지 개발 단계를 차례로 이어서 진행합니다. 단계마다 그 단계의 스킬을 대신 불러오므로, 단계마다 스킬을 실행하지 않고 각 스킬이 묻는 확인과 질문에만 답하면 됩니다.

> 만드는 중인 스킬입니다. `gongbang-dev`를 설치해야 쓸 수 있고, 동작이 바뀔 수 있습니다.

## 언제 쓰나

- 기획서나 요청 하나로 PR까지 진행하고, 중간에는 확인과 질문에만 답하고 싶을 때
- 진행하다 멈춘 흐름을 이어서 끝낼 때. 인자 없이 실행하면 끝나지 않은 상태 파일을, 없으면 끝나지 않은 brief를 찾아 이어 갑니다.
- 진행 중인 흐름이 어느 단계에 있는지 볼 때. `status`를 주면 끝나지 않은 흐름마다 현재 단계, 멈춘 이유, 남은 티켓 수만 보여 주고 끝냅니다.
- 여러 기능을 동시에 진행할 때. 기능마다 worktree를 따로 만들고 각각 run-flow를 실행합니다.

## 준비물

- 단계 스킬: analyzing-requirements, framing-problems, set-brief, set-ticket, run-ticket. `gongbang`과 `gongbang-dev`를 함께 설치하면 모두 있습니다.
- 티켓은 기본적으로 run-flow를 실행한 세션이 차례로 직접 구현합니다. 병렬 실행은 선택 기능입니다. 여러 티켓을 병렬로 실행하려면 사용자가 워커 도구 절차를 정해 주거나 레포·에이전트 규칙(CLAUDE.md, AGENTS.md)에 지정돼 있어야 합니다. 워커 도구 절차는 워커를 띄우는 도구 하나로 워커를 다루는 방법을 적은 문서입니다. 쓸 수 있는 절차가 없거나, 함께 시작할 수 있는 티켓이 둘 이상이 아니거나, 통합 브랜치를 공유하는 티켓이 있으면 티켓을 차례로 실행합니다.
- 선택 설정 예: [Orca 오케스트레이션 설정](../orca-orchestration.md), [Paseo 오케스트레이션 설정](../paseo-orchestration.md). 각 문서에 도구 설치와 절차를 규칙 파일에 등록하는 방법이 있습니다.
- PR을 만들려면 github.com 원격과 로그인된 `gh` CLI가 있어야 합니다. 없으면 PR 본문만 보여 주고 멈춥니다.
- omp를 쓰면 [omp 멀티에이전트 설정](../omp-orchestration.md)으로 교차 리뷰·냉독 에이전트와 위임 규칙을 설치합니다. 모델은 레포가 정하지 않고 사용자가 고릅니다.

## 진행 과정

0. 인자로 시작 단계를 고르고 상태 파일을 만듭니다. 상태 파일이면 그 파일의 현재 단계, brief면 티켓 상태에 따라 4~6단계, 요구사항 문서나 요청 문장이면 2단계, 기획서면 1단계부터 시작합니다. 상태 파일과 brief도 MD 문서라 기획서보다 먼저 판단합니다. 인자가 없으면 끝나지 않은 상태 파일을, 없으면 끝나지 않은 brief를 찾고, 여럿이면 목록을 보여 주고 고르게 합니다. 폴더를 넘기면 그 안에서 같은 방법으로 찾습니다. 흐름 밖에서 진행한 작업을 흐름으로 정리해 달라고 하면 brief마다 지금 단계를 판정해 상태 파일을 만든 뒤 이어 갈지 묻습니다. 레포 규칙이나 상태 파일이 완료 표시를 `done` 대신 다른 값으로 정했으면 그 값도 끝난 것으로 봅니다.
1. **요구사항 정리**: analyzing-requirements로 기획서를 요구사항 문서로 정리합니다. 스킬의 질문에 준 답은 받는 즉시 상태 파일에 적어, 문서를 저장하기 전에 끊겨도 다시 묻지 않습니다.
2. **구체화**: 개발 범위가 여럿이면 이번에 진행할 범위 하나를 고르고, 고르지 않은 범위는 상태 파일에 적어 둡니다. 그다음 framing-problems로 구체화 기록을 확정합니다. 확정한 칸은 그때마다 상태 파일에 적으므로, 도중에 끊겨도 받은 답을 다시 묻지 않습니다. brief를 쓰기 전에 흐름이 끊겨도 이 기록으로 3단계부터 이어 갑니다.
3. **작업 지시서**: set-brief로 brief를 남깁니다. 저장 위치 선택, 초안 작성, 냉독 검증, 초안 확인, 게시를 run-flow를 실행한 세션이 모두 직접 하고, 냉독 검증의 독자 3명만 대화를 모르는 새 컨텍스트로 띄웁니다. 에이전트 규칙이 냉독 검증을 맡을 에이전트를 정해 두었으면 그 에이전트를 씁니다. 초안은 저장소 밖 임시 파일에 씁니다. 초안 파일 경로와 냉독 검증 결과 파일 경로를 상태 파일에 적어, 확인 전에 끊겨도 초안을 다시 만들지 않고 남은 어긋남을 그대로 보여 줍니다. 티켓으로 나누라고 했으면 크기와 상관없이 4단계로 갑니다. 그 밖에는 남은 일이 한 세션에 끝나지 않을 크기면 4단계로, 아니면 5단계로 갑니다.
4. **티켓 분할**: set-ticket으로 티켓을 나눠 게시합니다. 게시가 끝나면 5단계를 이 세션에서 이어 갈지, 새 세션에서 `/run-flow <상태 파일>`로 이어 갈지 묻습니다. 새 세션은 지금까지의 대화를 다시 읽지 않아 비용이 줄어듭니다.
5. **구현과 리뷰**: 현재 브랜치가 기본 브랜치면 먼저 작업 브랜치 이름을 묻고 만듭니다. 시작 HEAD를 상태 파일에 적고, 시작 HEAD에 있던 테스트와 판정용 사례로 보호 목록을 만든 뒤, 커밋하지 않은 흐름 문서(상태 파일, 보호 목록, 요구사항 문서, ADR, brief, 티켓)를 커밋 하나로 묶을지 묻습니다. 그다음 run-ticket으로 남은 티켓 전부를 실행합니다. 쓸 수 있는 워커 도구 절차가 있고, 함께 시작할 수 있는 티켓이 둘 이상이며, 통합 브랜치를 공유하는 티켓이 없으면 티켓마다 워커를 띄워 병렬로 실행합니다. 그 밖에는 이 세션이 티켓을 차례로 직접 구현합니다. 구현 중 받은 질문에 준 답과 새로 정한 결정은 그때마다 상태 파일에 적어 뒤 티켓에 그대로 씁니다. 병렬로 실행하면 워커 식별자도 상태 파일에 적습니다. 레포 규칙이 티켓 실행에 다른 스킬을 지정했으면, 그 스킬이 구현을 맡기지 않고 교차 리뷰를 건너뛰지 않는다는 것을 확인할 수 있을 때만 쓰고, 확인할 수 없으면 run-ticket을 씁니다. 완료 기준을 통과하지 못한 티켓이 나오면 멈추고, 시도 횟수와 실패 원인을 상태 파일에 적은 뒤 티켓을 다시 나눌지 묻습니다. 통합 리뷰 결과는 받는 즉시 리뷰한 HEAD, 코드 지문과 함께 상태 파일에 적습니다. 리뷰 대상은 시작 HEAD 이후의 커밋, 커밋하지 않은 변경, 새 파일 전부입니다. 티켓을 수락하기 전마다 보호 목록의 파일이 바뀌지 않았는지 검사하고, 수락한 티켓이 새로 만든 테스트를 목록에 더합니다.
6. **머지·PR 결정**: 먼저 보호 목록을 다시 검사하고, 상태 파일에 적힌 코드 지문을 지금 값과 비교합니다. 다르면 리뷰한 뒤에 코드가 바뀐 것이므로 알리고 리뷰부터 다시 합니다. 그다음 완료 기준 결과, 리뷰 지적, 바뀐 파일과 커밋을 모아 보여 주고 PR 만들기, 고치기, 멈추기 중 하나를 고르게 합니다. PR 만들기를 고르면 커밋하기 전에 보호 목록을 닫습니다. 6단계부터 시작해 run-ticket 보고가 없으면 상태 파일의 리뷰 기록, 티켓의 완료 기록, git 기록에서 모읍니다.
7. **PR 만들기**: 필요하면 작업 브랜치를 만들고 커밋한 뒤 남은 변경이 없는지 확인하고, PR 본문을 써서 보여 주고 확인받은 뒤 push하고 PR을 만듭니다. PR 본문은 이 세션이 diff 전문 대신 brief, 변경 파일 목록, 완료 기록, 리뷰 기록으로 직접 씁니다. 교차 리뷰를 같은 회사 모델 등으로 대체했으면 그 표시와 수행한 모델을 본문에 옮깁니다.

각 단계 스킬이 묻는 확인(구체화 기록 확정, 요구사항 문서 저장 위치, brief 초안과 게시 위치, 티켓 분할안, 병렬 실행 계획)은 그대로 묻습니다. run-flow가 직접 묻는 것은 작업 브랜치 이름, 흐름 문서 커밋, 4단계 뒤의 세션 선택, 6단계의 선택, 7단계의 PR 본문 확인입니다. run-flow가 없애는 것은 단계가 끝날 때마다 다음 스킬을 직접 실행하던 일입니다.

### 상태 파일과 ADR

흐름마다 `docs/context/run-flow/YYYY-MM-DD-<slug>.md`에 상태 파일을 두고 단계가 바뀔 때마다 고칩니다. 현재 단계, 멈춘 이유, 단계 체크리스트, 결과물 위치(요구사항 문서, brief, brief 초안, brief 냉독 결과, ADR, 브랜치, 시작 HEAD, 병렬 실행일 때만 채우는 워커 식별자, PR), 사용자 결정, 요구사항 답변, 구체화 기록, 구현 중 결정, 리뷰 기록이 들어갑니다. 코드 지문은 `scripts/code_fingerprint.sh`가 계산하는, 흐름 문서를 뺀 작업 트리의 tree 해시로, 커밋하지 않은 변경과 새 파일까지 들어가고 흐름 문서만 바뀌면 그대로입니다. 5단계부터 6단계에서 PR 만들기를 고를 때까지 같은 이름의 `.protected` 파일에 보호 목록이 있습니다. 이어 가는 세션도 이 목록을 그대로 씁니다. 자세한 동작은 아래 "보호 목록"에 있습니다. 대화가 끊기거나 압축돼도 이 파일을 열거나 `/run-flow status`로 어느 단계인지 확인할 수 있습니다. 5단계 진행 상황은 티켓 상태가 기준이고, 상태 파일이 어긋나면 티켓 상태에 맞춰 고칩니다. 다만 티켓이 모두 끝났어도 통합 리뷰가 기록되지 않았으면 5단계의 리뷰부터 이어 갑니다. 끝난 흐름의 상태 파일은 다시 쓰지 않으므로, 같은 요구사항 문서로 다른 개발 범위를 진행하면 새 상태 파일이 생깁니다.

상태 파일을 brief 옆 등 다른 곳에 두기로 할 수도 있습니다. 인자 없이 실행하면 `- 현재 단계:` 줄로 상태 파일을 찾고, brief와 상태 파일을 찾을 때 `.scratch`처럼 심볼릭 링크로 붙인 폴더도 따라갑니다. 리뷰를 여러 개 함께 돌리면 결과가 하나 올 때마다 상태 파일에 적습니다. 진행 중에 요구사항이 바뀌면 새 흐름을 만들지 않고 같은 상태 파일에서 1단계로 돌아가, 구체화 기록은 바뀐 칸만 묻고 brief와 남은 티켓을 고칩니다.

2단계와 6단계에서 되돌리기 어렵고, 맥락 없이 보면 의아하고, 실제 대안 중에서 고른 결정만 ADR 후보로 보여 줍니다. 고른 것만 레포의 ADR 폴더(없으면 `docs/adr/NNNN-<slug>.md`)에 남기고 상태 파일에 링크합니다.

### 보호 목록

구현하는 세션이 기존 테스트를 고쳐 통과하는 것을 막습니다. 5단계를 시작할 때 `scripts/protected_paths.py init`이 시작 HEAD의 테스트 파일(`tests/`·`test/`·`__tests__/`·`spec/` 폴더 안의 파일, `test_*.py`, `*_test.go`, `*.test.ts`, `*.spec.js`, `*Test.java` 같은 이름)을 찾아 `docs/context/run-flow/<상태 파일 이름>.protected`에 적습니다. 레포 규칙이 정한 다른 테스트나 판정용 사례(eval 사례, 채점 기준, 기대 출력)는 `--path`로 더합니다. 같은 내용을 git 공통 디렉터리(`.git/gongbang-protected/`)에도 둬서, 목록 파일 자체를 셸로 고친 것도 찾습니다.

- **쓰기 전 차단**: [gongbang-mods](../mods.md#run-flow-보호-경로-차단)(Claude Code)와 [omp extension](../omp-orchestration.md#보호-경로-차단)을 설치하면 Write·Edit 같은 쓰기 도구가 목록의 파일을 고치려 할 때 호출 전에 막고 이유를 돌려줍니다. 서브에이전트와 워커도 같습니다. 상대 경로, 절대 경로, 심볼릭 링크 경로, 저장소 안의 git worktree 경로를 모두 실제 경로로 풀어 비교합니다. 새 파일과 목록 밖의 파일 쓰기는 그대로 됩니다.
- **수락 전 검사**: 셸 명령(`sed -i`, 리다이렉트)으로 쓰는 것은 차단하지 못합니다. 그래서 run-ticket이 티켓을 수락하기 전과 6단계에 들어갈 때 `protected_paths.py verify`가 작업 트리, 인덱스(stage한 내용), HEAD, 병렬 실행이면 워커의 티켓 브랜치까지 시작 내용과 비교합니다. 바뀐 파일, 지운 파일, 보호 폴더에 새로 생긴 파일이 있거나 검사 자체가 실패하면 수락하지 않고 멈춥니다. 바뀐 파일은 되돌리지 않고 보여 줍니다.
- **켜지는 때**: 상태 파일의 `- 현재 단계:`가 `완료`가 아닌 동안입니다. 끝난 흐름과 흐름 밖의 작업은 막지 않고, 쓰기 전 차단도 `python3`를 실행하지 않습니다. 상태 파일이 없어진 목록은 켜진 것으로 봅니다.
- **닫기**: 목록은 흐름 문서로 커밋되므로, 지우지 않고 머지하면 기본 브랜치에서도 켜진 채 남아 기존 테스트 쓰기를 막습니다. 그래서 6단계에서 PR 만들기를 고르면 `close`가 `verify`를 한 번 더 돌리고, 통과하면 목록과 사본을 지웁니다. 이 삭제는 PR 커밋에 들어갑니다.
- **목록 바꾸기**: 5단계를 시작할 때 brief나 티켓이 목록에 든 기존 테스트를 고치라고 하면 그 파일을 보여 주고, 사용자가 정한 파일만 `remove`로 뺍니다. 수락한 테스트는 `add`로 더합니다. 구현 중에 기존 테스트를 바꿔야 하는 요구사항 변경이 생기면 흐름이 멈추고, 사용자가 정한 뒤 `remove`로 뺍니다. 다른 clone에서 이어 가 사본이 없으면 `init`이 멈추고, 목록을 확인받은 뒤 `--reseal`로 사본을 다시 만듭니다.
- 쓰기 전 차단을 설치하지 않았으면 수락 전 검사만 남습니다. eval 러너처럼 차단이 켜져 있는지 모르는 환경에서는 도구 호출 기록만으로 차단을 판정하지 않습니다. 거부된 호출도 기록에 남기 때문입니다. 차단을 확인하려면 거부된 도구 결과의 이유와 파일이 그대로인지를 함께 봅니다.

## 결과물

- 상태 파일, 요구사항 문서, brief, 티켓, ADR, 구현 코드와 커밋
- GitHub PR. 머지는 사용자가 합니다.
- 마무리 보고: 단계별 결과물 위치, PR URL, 고치지 않은 리뷰 지적
