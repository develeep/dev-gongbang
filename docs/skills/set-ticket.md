# set-ticket

set-brief로 남긴 brief가 한 번에 작업하기에 클 때, 혼자 검증할 수 있는 작은 티켓으로 나눌 수 있습니다. 티켓은 대화도 brief 작성 과정도 보지 못한 작업자가 그 티켓 하나만 읽고 끝낼 수 있게 씁니다. 스킬은 티켓을 GitHub sub-issue나 docs 파일로 게시하고, 원래 brief에 티켓 목록을 연결합니다.

> 만드는 중인 스킬입니다. `gongbang-dev`를 설치해야 쓸 수 있고, 동작이 바뀔 수 있습니다.

| 호출 방식 | Model-invoked (요청하거나 run-flow 같은 스킬이 지시할 때만) |
| 호출 | `/gongbang:set-ticket [brief 이슈 번호·URL 또는 docs 경로]` |

## 언제 쓰나

- brief의 "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 만큼 클 때
- set-brief가 게시를 마치고 set-ticket으로 나누라고 안내했을 때

brief가 없는 일반 작업 분할이나 할 일 목록 요청에는 스스로 실행하지 않습니다. "이 brief를 티켓으로 나눠 줘"처럼 요청하거나 `/gongbang:set-ticket`으로 부르세요.

## 준비물

- **set-brief로 만든 brief**: 인자로 이슈 번호·URL이나 docs 경로를 줍니다. 인자가 없으면 다음 순서로 찾습니다.
  1. 이 대화가 set-brief 게시로 끝났으면 그때 만든 brief
  2. `context` 라벨이 붙은 가장 최근 이슈와, `- 작성일:` 줄이 있는 문서 중 작성일이 가장 늦은 문서를 비교해 더 최근 것. 이미 `## 티켓` 섹션이 있거나 "남은 일"에 빈 체크박스가 없는 brief는 나눴거나 끝난 것이므로 건너뜁니다.

  docs brief는 저장소 전체에서 `- 작성일:` 줄로 찾으므로, `docs/context/` 밖이나 `.gitignore`에 걸린 폴더에 둔 brief도 찾습니다. 찾은 brief로 바로 진행하고 어떤 brief를 골랐는지 한 줄로 알립니다. 하나도 없으면 그렇다고 알리고 멈춥니다.
- **GitHub brief면**: `gh` CLI가 로그인돼 있어야 합니다. 티켓 이슈를 만들고, sub-issue와 막힘 관계를 `gh api`로 연결합니다.

## 진행 과정

1. **brief 찾기**: brief를 끝까지 읽습니다. GitHub brief는 `gh issue view <번호> --comments`로 코멘트까지 읽습니다.
2. **코드베이스 탐색**: 이 대화에서 아직 코드를 보지 않았으면 brief가 다루는 영역의 현재 상태를 살펴봅니다. 저장소에 용어집이나 ADR이 있으면 티켓 제목과 설명에 그 용어를 쓰고 ADR을 따릅니다. 구현을 쉽게 만드는 선행 리팩터링(prefactoring)도 찾습니다.
3. **분할안 작성**: brief의 "남은 일"을 아래 [분할 기준](#분할-기준)으로 티켓으로 나눕니다. 선행 리팩터링이 있으면 첫 티켓으로 둡니다.
4. **분할안 확인**: 분할안을 번호 목록으로 보여 줍니다. 티켓마다 제목, 막힘 관계(먼저 끝나야 하는 티켓 번호, 없으면 "없음"), 만들 것, 완료 기준이 있습니다. 그리고 단위 크기가 맞는지(너무 큼 / 너무 작음), 막힘 관계가 맞는지, 합치거나 더 나눌 티켓이 있는지 묻습니다. 승인할 때까지 고쳐서 다시 보여 줍니다.
5. **게시와 brief 연결**: brief가 있는 곳에 막힘 관계 순서대로 티켓을 만들고, brief 끝에 `## 티켓` 섹션을 덧붙입니다. 막는 티켓을 먼저 만들어야 막힘 관계에 실제 번호를 쓸 수 있습니다. GitHub에서는 게시 전에 brief에 이미 연결된 sub-issue와 `## 티켓` 섹션을 확인해, 분할안과 제목이 같은 티켓은 다시 만들지 않고 빠진 연결만 합니다. 그래서 게시 도중 끊긴 뒤 다시 실행해도 같은 티켓이 두 번 생기지 않습니다.

게시를 마치면 새 세션에서 run-ticket으로 티켓을 하나씩 실행하라고 안내합니다. 다른 스킬이 불렀으면 안내하지 않고 그 스킬로 돌아갑니다.

### 분할 기준

- **수직 슬라이스**: 티켓 하나가 한 계층만 다루지 않고 필요한 모든 계층(스키마, API, UI, 테스트)을 좁게 관통합니다. 끝낸 티켓은 혼자서 시연하거나 검증할 수 있어야 합니다.
- **크기**: 티켓 하나는 새 컨텍스트 창 하나로 끝낼 수 있어야 합니다. 세션이 끊기거나 새 세션에서 이어 가면, 작업자는 이전 티켓의 대화 없이 그 티켓과 앞 티켓의 완료 기록만 읽고 시작하기 때문입니다. 병렬 실행을 고르면 티켓마다 워커가 이렇게 시작합니다.
- **만들 것**: 구현할 파일 경로와 코드 대신 동작으로 씁니다. 구현 경로와 코드는 빨리 낡기 때문입니다. 바뀌는 이름(필드, 타입, 열, 함수)과, 완료 기준을 확인할 명령과 기대 결과는 적습니다. 프로토타입 코드가 결정(상태 기계, 스키마, 타입 형태)을 글보다 정확히 담으면 결정이 담긴 부분만 넣고 프로토타입에서 왔다고 적습니다.
- **완료 기준**: brief "확인 기준" 중 그 티켓만 끝나도 확인할 수 있는 항목은 문구 그대로 옮깁니다. 나머지는 run-ticket이 마지막 티켓을 끝낼 때 brief에서 실행합니다.
- **막힘 관계**: 그 티켓을 시작하기 전에 끝나야 하는 티켓입니다. 막는 티켓이 없으면 바로 시작할 수 있습니다.
- **산출물**: 한 티켓의 결과(예: 수정 전 동작 체크리스트, 측정값)를 다른 티켓이 쓰면, 만드는 티켓의 "만들 것"에 "결과를 이 티켓의 산출물로 남긴다"를 적고, 쓰는 티켓의 완료 기준에 "NN 티켓의 산출물"을 적어 만드는 티켓에 막히게 합니다. 티켓마다 새 세션에서 실행되므로 이렇게 적어야 뒤 티켓이 결과를 찾습니다. 다른 티켓의 결과는 경로 대신 이 표현으로 가리킵니다. run-ticket은 산출물을 docs 티켓의 `## 산출물` 섹션이나 GitHub 티켓의 완료 코멘트에 남깁니다.
- **제한요소**: brief의 "하면 안 되는 것", "바꾸지 않는 범위", "바꿀 수 없는 조건" 중 그 티켓과 관련된 항목을 brief 문구 그대로 옮깁니다. 관련 여부가 애매하면 옮깁니다.
- **문장**: "앞서 정한 방식대로", "위 티켓처럼", "깔끔하게"처럼 대화 맥락이 있어야 판단할 수 있는 말 대신 이름, 값, 티켓 번호를 직접 적습니다.

### 넓은 리팩터링 나누기

열 이름 변경이나 공유 타입 변경처럼 기계적인 변경 하나가 코드 전체로 퍼져서 어떤 슬라이스도 혼자서는 초록(CI 통과) 상태가 될 수 없으면, 수직 슬라이스 대신 expand–contract 순서로 나눕니다.

1. **expand**: 옛 형태 옆에 새 형태를 추가해 아무것도 깨지지 않게 합니다.
2. **migrate**: 호출부를 패키지나 디렉터리 단위로 묶어 옮깁니다. 묶음마다 티켓 하나이고, 모두 expand 티켓에 막힙니다. 옛 형태가 남아 있으므로 묶음마다 CI가 초록입니다.
3. **contract**: 호출부가 남지 않으면 옛 형태를 지웁니다. 모든 migrate 티켓에 막힙니다.

묶음끼리도 혼자 초록이 될 수 없으면 순서는 그대로 두고, 묶음들이 통합 브랜치 하나를 공유하게 한 뒤 마지막 "통합 및 검증" 티켓이 모든 묶음 티켓에 막히게 합니다. 초록은 그 마지막 티켓에서만 약속합니다. 이때 묶음 티켓과 "통합 및 검증" 티켓의 막힘 관계 줄 끝에 `(통합 브랜치 공유)`를 적고, 묶음 티켓의 완료 기준에는 그 묶음만으로 통과할 수 있는 검사만 둡니다. run-ticket은 이 표시를 보고 티켓별 worktree 대신 한 작업 트리에서 차례로 실행하고, 묶음 티켓에서는 전체 테스트를 돌리지 않습니다.

## 결과물

**GitHub 이슈**

- 티켓마다 `ready-for-agent` 라벨을 붙인 이슈를 만듭니다. 라벨이 없으면 먼저 만듭니다.
- 티켓 이슈를 brief의 sub-issue로 연결합니다. 연결에 실패하면 티켓 본문 맨 위에 `Part of #<brief 번호>`를 넣습니다.
- 막힘 관계를 이슈 의존성(blocked by)으로 연결합니다. 연결에 실패하면 티켓 본문에 "막힘 관계" 섹션을 넣습니다.
- brief 본문 끝에 `## 티켓` 섹션을 덧붙이고 `- [ ] #<번호> <제목>`을 막힘 관계 순서로 적습니다.
- 티켓 URL 목록을 알려 줍니다.

티켓 본문에는 부모, 만들 것, 완료 기준, 막힘 관계(네이티브 연결에 실패했을 때만), 하면 안 되는 것, 작업 경계(바꾸지 않는 범위, 바꿀 수 없는 조건) 섹션이 있습니다. 내용이 없는 섹션은 지웁니다. GitHub 티켓은 닫히면 끝난 것입니다.

**docs 문서**

- brief와 같은 디렉터리에 brief 파일 이름에서 `.md`를 뺀 폴더를 만듭니다. 예: `docs/context/YYYY-MM-DD-<brief-slug>/`. 레포 규칙이 정한 티켓 폴더 이름(`issues/` 등)은 쓰지 않습니다.
- 티켓 하나를 `NN-<slug>.md` 파일 하나로 저장합니다. NN은 `01`부터 막힘 관계 순서로 매기고, slug는 제목을 영문 소문자와 하이픈으로 줄인 것입니다. 같은 이름의 파일이 있으면 덮어쓰기 전에 묻습니다.
- brief 문서 끝에 `## 티켓` 섹션을 덧붙이고 `- [ ] [NN: <제목>](./YYYY-MM-DD-<brief-slug>/NN-<slug>.md)`를 적습니다.
- 저장하고 고친 파일 목록을 알려 줍니다. 커밋은 하지 않습니다.

티켓 파일은 `# NN: <제목>` 제목 아래 `- 부모:`, `- 막힘 관계:`, `- 상태: ready-for-agent` 줄이 있고, 그 아래 만들 것, 완료 기준, 하면 안 되는 것, 작업 경계 섹션이 있습니다. 내용이 없는 섹션은 지웁니다. run-ticket이 티켓을 끝내면 상태를 `done`으로 바꾸고 `## 완료 기록`을 붙입니다.

**brief**

brief는 닫지 않고, `## 티켓` 섹션을 덧붙이는 것 외에는 고치지 않습니다. 티켓이 brief 문구를 옮겨 쓰고 brief를 부모로 가리키므로, brief를 고치면 티켓과 어긋나고 닫으면 작업자가 전체 맥락을 찾지 못합니다.

## 커스텀

| 바꾸고 싶은 것 | 고칠 곳 |
|---|---|
| 티켓 섹션 구성 | SKILL.md의 "이슈 티켓 템플릿", "docs 티켓 템플릿" |
| 분할 기준(수직 슬라이스, 티켓 크기, 만들 것 쓰는 법) | SKILL.md의 "핵심 규칙", "3. 분할안 작성" |
| 분할안을 보여 줄 때 묻는 질문 | SKILL.md의 "4. 분할안 확인" |
| 라벨 이름, docs 티켓 폴더와 파일 이름 | SKILL.md의 "5. 게시와 brief 연결" |

티켓 템플릿의 섹션 이름, `- 상태:` 줄, brief에 덧붙이는 `## 티켓` 섹션, 막힘 관계의 `(통합 브랜치 공유)` 표시를 바꾸면 run-ticket도 함께 고쳐야 합니다. run-ticket이 이 이름과 표시로 티켓을 찾고 완료 여부와 실행 방법을 정합니다. run-flow도 `## 티켓` 섹션과 `- 상태: done`으로 끝나지 않은 티켓을 찾습니다.

복사해서 고치는 방법은 [커스텀 가이드](../customization.md)를 보세요.

## 함께 쓰는 스킬

- **set-brief**: 나눌 brief를 만듭니다. 게시를 마친 뒤 "남은 일"이 크면 이 스킬로 나누라고 안내합니다.
- **run-ticket**: 게시한 티켓을 하나씩 실행합니다. 마지막 티켓을 끝낼 때 brief의 "확인 기준"을 실행합니다. 사용자가 워커 도구 절차를 지정했거나 레포·에이전트 규칙에 등록해 두었으면 여러 티켓을 병렬로 실행합니다.
- **run-flow**: 4단계(티켓 분할)에서 이 스킬을 부릅니다. 게시가 끝나면 5단계(구현과 리뷰)를 같은 세션에서 이어 갈지, 새 세션에서 이어 갈지 묻습니다. run-flow 2단계에서 남긴 ADR은 이 스킬이 코드베이스를 탐색할 때 읽고 따릅니다.
