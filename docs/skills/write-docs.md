# write-docs

쓸 글의 분야, 독자, 목적, 톤, 자료를 먼저 정하고, 분야에 맞는 원칙으로 쓴 글을 채팅에서 받을 수 있습니다. 새 초안을 쓸 때도, 가져온 초안을 다듬거나 기존 문서를 고칠 때도 씁니다. 사실, 수치, 경로, 이름, 근거는 지어내지 않고, 자료에 없는 값은 `[확인 필요: 무엇]`으로 표시합니다.

| 항목 | 값 |
|---|---|
| 버킷 | productivity |
| 호출 방식 | Model-invoked (문서나 업무 메시지를 쓰거나 다듬어 달라고 할 때) |
| 호출 | `/gongbang:write-docs [쓰거나 고칠 글에 대한 요청]` |
| 원문 | [SKILL.md](../../skills/productivity/write-docs/SKILL.md) |

## 언제 쓰나

- README, 가이드, API 문서 같은 기술 문서를 쓸 때
- 개념이나 배경을 설명하는 글, 의견 글을 쓸 때
- 대화, 조언, 이야기처럼 사람에게 보내는 글을 다듬을 때
- 작업 보고, PR 설명, 슬랙 메시지처럼 동료에게 보내는 업무 메시지를 쓸 때
- 기존 문서를 문장만 고치거나 구조까지 고칠 때

## 준비물

- 글에 담을 자료(사실, 코드, 문서, 링크). 요청에 없으면 스킬이 따로 묻습니다.
- 고칠 원본이 있으면 첨부나 경로로 넘기세요. SharePoint·OneDrive 같은 링크는 그 링크를 읽을 커넥터나 MCP 도구가 연결돼 있어야 합니다. 원본이나 자료를 읽지 못하면 쓰기를 시작하지 않고, 파일을 직접 붙여 넣거나 커넥터를 연결하라고 안내합니다.

## 진행 과정

1. **요청 파악**: 요청, 가져온 초안, 고칠 파일에서 분야, 독자, 목적, 톤, 자료, 수정 범위를 찾습니다. 수정 작업이면 원본을 끝까지 읽습니다. 이미 분명한 항목은 묻지 않고 `확인됨: 독자 - 사내 백엔드 개발자 (요청에 있음)`처럼 한 줄로 되짚습니다.
2. **빈 항목 질문**: 비어 있거나 해석이 둘 이상인 항목만 묻습니다. 선택지에 없는 답은 직접 입력할 수 있습니다.
   - 분야: 기술 문서 / 업무 메시지 / 설명·의견 / 대화·조언·이야기
   - 기술 문서 유형(기술 문서를 골랐을 때): 학습 / 문제 해결 / 참조 / 설명
   - 수정 범위(초안 다듬기나 문서 수정일 때): 문장만 / 구조까지

   자료처럼 길게 답할 항목은 선택 질문의 답을 받은 뒤 따로 묻습니다.
3. **원칙 읽기**: 모든 분야에서 `reference/clear-writing.md`를 읽고, 기술 문서는 `reference/tech-writing.md`도 읽습니다. 새 초안이거나 수정 범위가 "구조까지"면 다음 구조를 글의 뼈대로 씁니다. 수정 범위가 "문장만"이면 원본 구조를 그대로 둡니다.
   - 기술 문서: 고른 유형의 권장 구조
   - 업무 메시지: 결론이나 상태 → 근거 → 남은 일과 요청

   두 원칙이 부딪치면 기술 문서는 `tech-writing.md`를, 나머지 분야는 `clear-writing.md`를 따릅니다. 지어내지 않는다는 원칙은 분야와 상관없이 가장 앞섭니다.
4. **쓰기**: 받은 자료로만 씁니다. 초안을 다듬거나 문서를 고칠 때는 사실의 의미와 글쓴이의 목소리를 지키고, 수정 범위가 "문장만"이면 섹션 순서와 제목을 바꾸지 않습니다. 자료에 없는 사실이 결과에 크게 영향을 주면 묻고, 그렇지 않으면 그 자리에 `[확인 필요: 타임아웃 기본값]`처럼 무엇이 빠졌는지 표시합니다.
5. **검토**: 결과를 내기 전에 문장마다 누가 무엇을 하는지 독자가 알 수 있는지 확인합니다. 문맥에서 분명한 주어는 생략해도 됩니다. 먼저 아래 세 패턴을 고칩니다.
   - 행동을 명사로 바꿔 행위자를 감춘 문장: "DB 서버 재시작이 이루어졌습니다"
   - 흔한 이름 대신 단어를 이어 붙여 새로 지은 어색한 말: "세션 진입 경계"
   - 요점이 주절에 없는 문장

   그다음 SKILL.md "주의할 점"의 나머지 패턴을 찾아 고칩니다. 독자가 꺼낸 적 없는 대안을 부정하는 "X가 아니라 Y다" 틀, 지어낸 구체성, 대상 없는 지시어, 빠진 논리 연결, 해독해야 하는 은유, 작은 사실마다 끊어 늘어놓는 리듬, 압축한 명사 나열입니다. 기술 문서면 다음도 확인합니다.
   - 제목 바로 아래에 개요가 있는지
   - 같은 개념을 같은 용어로 쓰고, 영문 용어와 한글 용어를 섞지 않았는지
   - 약어를 처음 쓸 때 전체 이름을 풀어 적었는지
   - "다음으로", "앞서 설명했듯이" 같은 메타 담화가 남았는지
   - "~을 통해", "~을 수행합니다" 같은 번역체가 남았는지
6. **전달**: 결과를 채팅에 보여 줍니다. 기존 파일을 고친 경우에도 수정본을 채팅에 먼저 보여 주고, 승인하면 파일에 반영합니다.
7. **수정 반복**: 고칠 점을 말하면 4~6단계를 다시 합니다. 분야가 바뀌면 3단계에서 원칙부터 다시 고릅니다.

## 결과물

- 채팅에 보여 주는 글. 기존 파일은 승인한 뒤에 반영합니다.
- `[확인 필요]` 표시가 있으면 결과 아래에 그 목록을 한 줄씩 적어 채울 수 있게 합니다.

검토했다는 안내나 문체 보고서는 붙이지 않습니다.

## 커스텀

| 바꾸고 싶은 것 | 고칠 파일 |
|---|---|
| 기술 문서 유형과 권장 구조, 정보 구조 원칙, 문장 원칙 (기본은 토스 테크니컬 라이팅 가이드) | `reference/tech-writing.md` |
| 모든 분야에 적용하는 읽히는 글 원칙, 업무 메시지 구조, 대비 예시 | `reference/clear-writing.md` |
| 쓸 때 피하고 검토에서 다시 찾는 패턴 | SKILL.md의 "주의할 점" |
| 분야와 질문 선택지 | SKILL.md의 "1. 요청 파악", "2. 빈 항목 질문" |
| 기술 문서 검토 항목 | SKILL.md의 "5. 검토" |

팀의 스타일 가이드를 쓰려면 `reference/tech-writing.md`를 그 가이드로 바꾸세요. 기술 문서에서는 이 파일이 `clear-writing.md`와 부딪칠 때 앞섭니다. 문서 유형 네 가지는 SKILL.md 2단계의 질문에, 기술 문서 검토 항목은 5단계에 따로 적혀 있으므로, 바꾼 가이드와 맞지 않으면 SKILL.md도 함께 고치세요. 스킬을 복사해서 고치는 방법은 [커스텀 가이드](../customization.md)를 보세요.
