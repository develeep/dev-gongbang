# write-docs

새 글 초안을 쓰거나, 가져온 초안을 다듬거나, 기존 문서를 고친다. 쓰기 전에 분야, 독자, 목적, 톤, 자료를 정하고, 분야에 맞는 원칙으로 쓴다. 사실, 수치, 경로, 이름, 근거는 지어내지 않고, 빠진 값은 `[확인 필요: 무엇]`으로 표시한다.

## 언제 쓰나

- README, 가이드, API 문서 같은 기술 문서를 쓴다.
- 개념이나 배경을 설명하는 글, 의견 글을 쓴다.
- 대화, 조언, 이야기처럼 사람에게 보내는 글을 다듬는다.
- 기존 문서를 문장만 고치거나 구조까지 고친다.

## 준비물

- 글에 담을 자료(사실, 코드, 문서, 링크)
- 고칠 원본이 있으면 첨부나 경로로 넘긴다. SharePoint·OneDrive 링크는 그 링크를 읽을 커넥터나 MCP 도구가 연결돼 있어야 한다. 읽지 못하면 쓰기를 시작하지 않는다.

## 진행 과정

1. 요청과 원본에서 분야, 독자, 목적, 톤, 자료, 수정 범위를 찾는다. 이미 분명한 항목은 한 줄로 되짚는다.
2. 비어 있거나 해석이 둘 이상인 항목만 묻는다.
   - 분야: 기술 문서 / 설명 / 의견 / 대화·조언·이야기
   - 기술 문서 유형: 학습 / 문제 해결 / 참조 / 설명
   - 수정 범위: 문장만 / 구조까지
   - 자료처럼 길게 답할 항목은 선택 질문 뒤에 따로 묻는다.
3. 분야에 맞는 원칙을 읽는다. 기술 문서는 고른 유형의 권장 구조를 뼈대로 쓴다. 수정 범위가 "문장만"이면 원본 구조를 그대로 둔다.
4. 받은 자료로만 쓴다.
5. 자주 나오는 패턴을 찾아 고친다. "X가 아니라 Y다" 틀, 지어낸 구체성, 대상 없는 지시어, 압축한 명사 나열 등이다.
6. 결과를 채팅에 보여 준다. 기존 파일을 고친 경우에도 승인을 받은 뒤에 파일에 반영한다.
7. 피드백을 받으면 4~6단계를 반복한다.

## 결과물

- 채팅에 보여 주는 글. 승인하면 파일에 반영한다.
- `[확인 필요]` 표시가 있으면 결과 아래에 그 목록을 한 줄씩 적는다.

## 커스텀

| 바꾸고 싶은 것 | 고칠 파일 |
|---|---|
| 기술 문서 유형, 권장 구조, 문장 원칙 (기본은 토스 테크니컬 라이팅 가이드) | `reference/tech-writing.md` |
| 모든 분야에 적용하는 읽히는 글 원칙과 예시 | `reference/clear-writing.md` |
| 쓸 때 피하고 검토에서 다시 찾는 패턴 | SKILL.md의 "주의할 점" |

팀의 스타일 가이드를 쓰려면 `reference/tech-writing.md`를 그 가이드로 바꾼다. 이 파일과 부딪치는 `clear-writing.md` 원칙은 기술 문서에서 `tech-writing.md`에 밀린다. 복사해서 고치는 방법은 [커스텀 가이드](../customization.md)를 본다.
