# analyzing-requirements

기획서 링크나 파일을 넘기면 요구사항, 서비스·개발 영역별 개발 범위, 기획서 섹션별 내용을 정리한 마크다운 문서를 받을 수 있습니다. 개발자나 에이전트는 기획서 대신 이 문서를 읽으므로, 스킬은 기획서에 없는 내용을 채우지 않고 모호한 부분을 쓰기 전에 묻습니다.

## 언제 쓰나

- 기획서 링크나 파일을 받아 요구사항을 정리하거나 분석할 때
- 개발을 시작하기 전에 서비스와 개발 영역(web, api 등)별로 무엇을 만들지 나눌 때

기획서를 주며 "요구사항 정리해 줘", "기획서 정리해 줘"처럼 요청하면 이름을 입력하지 않아도 Claude가 이 스킬을 고를 수 있습니다.

## 준비물

- **기획서**: PDF, PPT(X), MD 파일(첨부나 경로), 또는 SharePoint·OneDrive 같은 링크. 인자나 요청에 기획서가 없으면 링크나 경로를 묻습니다.
- **링크를 읽을 도구**: 링크로 줄 때는 그 링크를 읽을 수 있는 커넥터나 MCP 도구가 연결돼 있어야 합니다. 기획서를 읽지 못하면 정리를 시작하지 않고, 그 링크를 읽을 커넥터나 MCP 도구를 연결하라고 안내합니다.

## 진행 과정

1. **기획서 읽기**: 기획서를 끝까지 읽고 섹션 구성과 등장하는 서비스, 개발 영역을 파악합니다.
2. **모호한 부분 질문**: 모호한 부분을 번호 목록으로 한 메시지에 모아 묻고, 질문마다 무엇이 왜 모호한지 적습니다. 기획서에서 서비스명이나 개발 영역을 알 수 없으면 여기서 묻습니다. 답을 받은 뒤 다음 단계로 넘어갑니다.
3. **문서 작성**: [결과물](#결과물)의 템플릿으로 문서를 씁니다. 문서에는 기획서에 적힌 것과 사용자가 답한 것만 씁니다. 답을 받지 못한 항목은 해당 자리에 `확인 필요`로 표시하고, 문서 끝 "확인 필요" 목록에도 모읍니다.
4. **검증**: 문서의 항목마다 기획서나 사용자 답에 근거가 있는지 확인합니다. 근거가 없으면 지우거나 `확인 필요`로 바꾸고, 바꾼 문서를 다시 확인합니다. 그다음 거꾸로 기획서의 섹션을 하나씩 짚어 문서에 대응하는 섹션이나 `확인 필요` 항목이 있는지 보고, 없는 섹션은 문서에 넣습니다. 첫 확인은 쓴 항목의 근거만 보므로, 큰 기획서에서 통째로 빠진 섹션은 이 거꾸로 확인으로 찾습니다.
5. **저장**: 저장할 경로를 묻고, 받은 경로에 마크다운 파일로 저장합니다.

## 결과물

마크다운 문서 하나를 다음 템플릿으로 씁니다.

```markdown
# <기획서 제목> 요구사항

## 개발 범위

| 서비스 | 개발 영역 | 내용 |
|---|---|---|
| <서비스명> | <web, api 등> | <이 영역에서 개발할 것> |

## 요구사항

- <요구사항>

## <기획서에 있는 섹션>

<섹션 내용>

## 확인 필요

- <항목>: <무엇이 정해지지 않았는지>
```

- **개발 범위**: 항상 넣습니다. 서비스명과 개발 영역(web, api 등)으로 나눕니다.
- **요구사항**: 항상 넣습니다.
- **기획서에 있는 섹션**: as-is, to-be, 화면 목록, 기능 목록, 일정처럼 기획서에 있는 섹션만 기획서 순서대로 넣습니다. 기획서에 없는 섹션은 만들지 않습니다.
- **확인 필요**: 답을 받지 못한 항목과, 그 항목에서 무엇이 정해지지 않았는지 적습니다. 본문의 해당 자리에도 `확인 필요`로 표시해, 읽는 사람이 정해지지 않은 부분을 알아볼 수 있게 합니다.

출처로 슬라이드 경로나 번호는 적지 않습니다.

## 커스텀

| 바꾸고 싶은 것 | 고칠 곳 |
|---|---|
| 문서 템플릿, 항상 넣을 섹션 | SKILL.md의 "3. 문서 작성" |
| 읽을 수 있는 입력 형식 | SKILL.md의 "입력" |
| 문서에 쓸 내용과 `확인 필요` 표시 규칙 | SKILL.md의 "규칙" |
| 근거를 확인하는 방법 | SKILL.md의 "4. 검증" |

`## 개발 범위`와 `## 요구사항` 섹션 이름을 바꾸면 run-flow도 함께 고쳐야 합니다. run-flow는 이 두 섹션이 있는 MD 파일을 요구사항 문서로 알아보고 2단계(구체화)부터 시작합니다.

Model-invoked라 description이 실행 조건을 정합니다. description을 고치면 Claude가 이 스킬을 고르는 상황도 바뀝니다. 복사해서 고치는 방법은 [커스텀 가이드](../customization.md)를 보세요.

## 함께 쓰는 스킬

- **run-flow**: 기획서로 흐름을 시작하면 1단계(요구사항 정리)에서 이 스킬을 부르고, 저장한 요구사항 문서를 2단계(구체화)로 넘깁니다. 개발 범위가 여럿이면 이번 흐름에서 진행할 범위 하나를 고르게 하고, 고른 범위를 framing-problems로 구체화합니다. 이 스킬이 물어 받은 답은 run-flow가 상태 파일 `## 요구사항 답변`에 바로 적어 두므로, 문서를 저장하기 전에 흐름이 끊겨도 답이 남습니다.
- **set-brief**: 요구사항 문서의 경로와 고른 개발 범위를 brief에 적고, 그 범위의 요구사항마다 brief의 "남은 일"이나 "확인 기준"에 대응하는 줄이 있는지 확인합니다.
