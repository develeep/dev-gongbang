# run-ticket

set-ticket이 만든 티켓 하나를 새 세션에서 구현하고 리뷰한 뒤, 티켓 상태와 brief 체크박스를 갱신합니다. brief를 만든 대화 없이 brief, 티켓, 앞 티켓의 완료 기록만 근거로 삼습니다. 커밋은 하지 않습니다. 여러 티켓을 요청했고 함께 시작할 수 있는 티켓이 둘 이상이면 Orca 워커로 티켓마다 worktree를 나눠 병렬로 실행하고, 이때만 티켓 브랜치에 커밋해 머지합니다.

> 만드는 중인 스킬입니다. `gongbang-dev`를 설치해야 쓸 수 있고, 동작이 바뀔 수 있습니다.

## 언제 쓰나

- set-ticket으로 나눈 티켓을 하나씩 실행할 때
- 티켓으로 나누지 않은 작은 brief를 실행할 때. 이때는 brief 전체를 티켓 하나로 봅니다.
- "남은 티켓 전부"처럼 여러 티켓을 한 번에 실행할 때. Orca를 쓸 수 있고 함께 시작할 수 있는 티켓이 둘 이상이면 병렬로, 아니면 차례로 실행합니다.

## 준비물

- set-brief·set-ticket으로 만든 brief와 티켓
- GitHub 티켓이면 `gh` CLI가 로그인돼 있어야 합니다.
- 작업 트리에 brief·티켓 밖의 변경이 있으면 커밋하고 진행할지 묻습니다. 그대로 진행하면 리뷰에 이전 변경이 섞입니다.
- 여러 티켓을 병렬로 실행하려면 Orca가 실행 중이고 `orchestration` 스킬이 설치돼 있어야 합니다. 없으면 차례로 실행합니다.
- 교차 리뷰에는 다른 회사 모델을 쓰는 리뷰 에이전트(예: [omp 멀티에이전트 설정](../omp-orchestration.md)의 reviewer)나 Orca가 필요합니다. 둘 다 없으면 건너뛰고 보고에 적습니다.

## 진행 과정

1. 티켓을 고릅니다. 인자가 없으면 끝나지 않은 티켓이 남은 brief 중 가장 최근 것에서, 막힘 관계가 풀린 티켓 중 번호가 가장 앞선 것을 고릅니다.
2. 티켓과 brief 전문, 같은 brief의 끝난 티켓의 완료 기록, 레포의 CLAUDE.md·AGENTS.md를 읽습니다.
3. "만들 것"을 구현합니다. 에이전트 규칙이 티켓 구현을 맡을 에이전트를 정해 두었으면 brief, 티켓, 레포 규칙 경로, 검증 명령, 앞 티켓 산출물을 넘겨 맡깁니다. 티켓 범위 밖의 문제는 고치지 않고 보고에 남깁니다.
4. 완료 기준을 하나씩 명령이나 관찰로 확인합니다. 화면에서 봐야 하는 기준은 에이전트 규칙이 정한 UI 확인 에이전트가 있으면 맡깁니다. 통과하지 못하면 고치고, 고칠 수 없으면 멈추고 보고합니다.
5. 리뷰합니다. 코드 리뷰(레포 규칙이 지정한 리뷰 스킬, `code-review` 스킬, 직접 리뷰 순서로 처음 맞는 방법), check-guidelines 규칙 검사, 다른 회사 모델의 교차 리뷰를 함께 돌리고, 결과를 모두 받은 뒤 완료 기록으로 넘어갑니다. 교차 리뷰를 실제로 수행한 모델이 이 세션과 같은 회사면 건너뛴 것으로 보고합니다. 변경이 인증, 권한, 결제, 개인정보를 다루고 에이전트 규칙이 보안 리뷰 에이전트를 정해 두었으면 보안 리뷰도 맡깁니다.
6. 티켓 상태를 done으로 바꾸거나 이슈를 닫고, brief 체크박스를 갱신하고, 완료 기록을 남깁니다. 마지막 티켓이면 brief의 "확인 기준"을 실행하고 brief를 닫습니다. 여러 티켓 실행에서는 이 일을 마무리 리뷰 뒤에 한 번 합니다.

티켓과 레포 규칙이 충돌하면 진행하기 전에 묻습니다. 우선순위는 티켓의 "하면 안 되는 것"·"작업 경계", 레포 규칙, 스킬의 기본 동작 순입니다.

### 여러 티켓 실행

번호 범위나 "남은 티켓 전부"를 요청하면 실행 방법이 갈립니다. Orca를 쓸 수 있고, 함께 시작할 수 있는 티켓이 둘 이상이고, 통합 브랜치를 공유하는 티켓이 없으면 Orca 병렬 실행을, 하나라도 아니면 차례 실행을 합니다.

**Orca 병렬 실행**: 티켓마다 Orca 워커를 띄워 현재 브랜치에서 갈라진 child worktree에서 구현시킵니다.

1. 작업 트리가 깨끗해야 합니다. 커밋하지 않은 brief·티켓 문서는 워커가 읽지 못하므로 커밋할지 묻습니다.
2. 실행 묶음, 머지할 브랜치, 동시 워커 수(기본 3개), 시작 HEAD를 보여 주고 승인을 받습니다. 현재 브랜치가 기본 브랜치면 작업 브랜치를 만들지 함께 묻습니다.
3. brief 하나에 Orca Run 하나를, 티켓마다 Task를 만들고 막힘 관계를 Task deps로 겁니다. 이어 받은 Run에 끝났지만 머지하지 않은 Task가 있으면 다시 띄우지 않고 머지부터 합니다.
4. 막는 티켓이 모두 머지된 티켓부터 워커를 띄웁니다. 워커는 티켓을 구현해 티켓 브랜치에 커밋하고 결과를 보고합니다.
5. 끝난 브랜치를 현재 브랜치로 합친 뒤 머지 커밋을 만들기 전에 레포 검증 명령(타입 검사, 린트, 테스트)을 돌립니다. 통과하면 완료 기록을 머지 커밋에 넣고 worktree를 지웁니다. 실패하면 머지를 되돌리고 새 워커를 띄우지 않고 멈춥니다. 머지한 티켓이 다른 티켓을 막으면 막힌 티켓을 띄우기 전에 그 머지에 교차 리뷰만 먼저 합니다. 충돌하면 워커에게 리베이스를 맡기고, 다시 충돌하면 멈추고 알립니다. 실패한 티켓과 그 티켓에 막힌 티켓은 실행하지 않습니다.
6. 모두 끝나면 시작 HEAD부터 지금까지를 한 번 리뷰하고, brief의 "확인 기준"을 실행한 뒤 결과와 커밋 목록을 보고합니다. push, PR, 기본 브랜치 머지는 사용자가 정합니다.

**차례 실행**: 티켓마다 서브에이전트를 하나씩 차례로 띄웁니다. 같은 작업 트리를 고치므로 병렬로 띄우지 않고 커밋하지 않습니다. 완료 기준을 통과하지 못한 티켓이 나오면 멈추고, 모두 끝나면 전체 변경을 한 번 리뷰한 뒤 brief의 "확인 기준"을 실행합니다.

## 결과물

- 구현한 코드 변경. 커밋하지 않습니다. Orca 병렬 실행에서는 티켓마다 머지 커밋이 생깁니다.
- 티켓에 붙는 완료 기록: 완료일, 커밋 정보(커밋 안 함과 작업 시작 HEAD, Orca 병렬 실행이면 머지한 티켓 브랜치와 커밋), 바꾼 파일, 확인한 명령과 결과, 확인 못 한 기준, 고치지 않은 지적. 다른 티켓이 쓸 결과는 `## 산출물`에 남깁니다.
- 보고: 끝낸 티켓, 완료 기준 결과, 바꾼 파일, 산출물 위치, 고치지 않은 리뷰 지적, 건너뛴 리뷰, 다음 티켓

## 함께 쓰는 스킬

- **set-brief**, **set-ticket**: 실행할 brief와 티켓을 만듭니다.
- **run-flow**: 5단계에서 이 스킬로 brief의 남은 티켓을 실행합니다.
- **code-review** 스킬이 설치돼 있으면 5단계 코드 리뷰에 씁니다.
- **check-guidelines**: 5단계 규칙 검사에 씁니다.
- **orchestration**(Orca): 여러 티켓 병렬 실행과 교차 리뷰 워커에 씁니다.
