# run-ticket

set-ticket이 만든 티켓 하나를 새 세션에서 구현하고 리뷰한 뒤, 티켓 상태와 brief 체크박스를 갱신합니다. brief를 만든 대화 없이 brief, 티켓, 앞 티켓의 완료 기록만 근거로 삼습니다. 커밋은 하지 않습니다. 여러 티켓을 요청했고 함께 시작할 수 있는 티켓이 둘 이상이며 레포·에이전트 규칙이 워커 도구 절차를 지정해 두었으면, 그 절차로 티켓마다 워커를 띄워 worktree를 나눠 병렬로 실행하고 이때만 티켓 브랜치에 커밋해 머지합니다. 지정된 절차가 없으면 차례로 실행합니다.

> 만드는 중인 스킬입니다. `gongbang-dev`를 설치해야 쓸 수 있고, 동작이 바뀔 수 있습니다.

## 언제 쓰나

- set-ticket으로 나눈 티켓을 하나씩 실행할 때
- 티켓으로 나누지 않은 작은 brief를 실행할 때. 이때는 brief 전체를 티켓 하나로 봅니다.
- "남은 티켓 전부"처럼 여러 티켓을 한 번에 실행할 때. 쓸 수 있는 워커 도구 절차가 있고 함께 시작할 수 있는 티켓이 둘 이상이면 병렬로, 아니면 차례로 실행합니다.

## 준비물

- set-brief·set-ticket으로 만든 brief와 티켓
- GitHub 티켓이면 `gh` CLI가 로그인돼 있어야 합니다.
- 작업 트리에 brief·티켓 밖의 변경이 있으면 커밋하고 진행할지 묻습니다. 그대로 진행하면 리뷰에 이전 변경이 섞입니다. 끝난 티켓의 "바꾼 파일"에 없는 변경은 끊긴 티켓의 미완성 변경일 수 있어 따로 보여 주고, 되돌릴지 이어서 쓸지 묻습니다.
- 여러 티켓을 병렬로 실행하려면 워커 도구 절차가 지정돼 있어야 합니다. 워커 도구 절차는 워커를 띄우는 도구 하나로 워커를 만들고, 기다리고, 정리하는 방법을 적은 문서입니다. 아래 순서로 절차를 보고, 그 절차의 사용 조건을 만족하는 첫 절차를 씁니다. 지정된 절차가 없거나 모두 쓸 수 없으면 차례로 실행합니다.
  1. 사용자나 부른 쪽이 정한 도구의 절차
  2. 레포·에이전트 규칙(CLAUDE.md, AGENTS.md)이 지정한 절차. 여럿이면 규칙에 적힌 순서로 봅니다.
- 선택 설정 예: [Orca 오케스트레이션 설정](../orca-orchestration.md), [Paseo 오케스트레이션 설정](../paseo-orchestration.md). 각 문서에 도구 설치와 절차를 규칙 파일에 등록하는 방법이 있습니다.
- 교차 리뷰는 이번 변경을 구현한 모델과 다른 회사의 모델이 하는 리뷰입니다. 구현한 모델은 구현을 맡긴 에이전트나 워커의 모델이고, 이 세션이 직접 구현했으면 이 세션의 모델입니다. 교차 리뷰에는 다른 회사 모델을 쓰는 리뷰 에이전트(예: [omp 멀티에이전트 설정](../omp-orchestration.md)의 reviewer)나 교차 리뷰 워커를 정해 둔 워커 도구 절차가 필요합니다. 모두 없으면 건너뛰고 보고에 적습니다. 리뷰 에이전트가 구현한 모델과 같은 회사 모델로 확인되면 워커 도구 절차로 다시 맡깁니다.

## 진행 과정

1. 티켓을 고릅니다. 인자가 없으면 끝나지 않은 티켓이 남은 brief 중 가장 최근 것에서, 막힘 관계가 풀린 티켓 중 번호가 가장 앞선 것을 고릅니다.
2. 티켓과 brief 전문, 같은 brief의 끝난 티켓의 완료 기록, 레포의 CLAUDE.md·AGENTS.md를 읽습니다.
3. "만들 것"을 구현합니다. 에이전트 규칙이 티켓 구현을 맡을 에이전트를 정해 두었으면 brief, 티켓, 레포 규칙 경로, 검증 명령, 앞 티켓 산출물을 넘겨 맡깁니다. 티켓 범위 밖의 문제는 고치지 않고 보고에 남깁니다.
4. 완료 기준을 하나씩 명령이나 관찰로 확인합니다. 구현을 에이전트에 맡겼으면 그 에이전트가 통과했다고 보고해도 이 세션이 다시 확인합니다. 통과 보고를 그대로 믿지 않기 위한 확인입니다. 화면에서 봐야 하는 기준은 에이전트 규칙이 정한 UI 확인 에이전트가 있으면 맡깁니다. 통과하지 못하면 고칩니다. 고칠 수 없으면 에이전트 규칙이 정한 실패 처리(다시 맡기기, 다른 에이전트로 올리기)를 먼저 따르고, 그래도 통과하지 못하면 시도한 에이전트와 횟수를 보고하고 멈춥니다.
5. 리뷰합니다. 코드 리뷰(레포 규칙이 지정한 리뷰 스킬, `code-review` 스킬, 직접 리뷰 순서로 처음 맞는 방법), check-guidelines 규칙 검사, 다른 회사 모델의 교차 리뷰를 함께 돌리고, 결과를 모두 받은 뒤 완료 기록으로 넘어갑니다. 교차 리뷰는 에이전트 규칙이 정한 에이전트, 워커 도구 절차의 "교차 리뷰 워커"대로 이 작업 트리에 띄운 다른 회사 모델의 워커 순서로 처음 되는 방법에 맡깁니다. 절차가 여럿이면 사용자나 부른 쪽이 정한 도구의 절차를 먼저, 그다음 규칙에 적힌 순서로 해 봅니다. 교차 리뷰를 실제로 수행한 모델이 구현한 모델과 같은 회사면 다음 방법으로 다시 맡기고, 남은 방법이 없을 때만 건너뛴 것으로 보고합니다. 변경이 인증, 권한, 결제, 개인정보를 다루고 에이전트 규칙이 보안 리뷰 에이전트를 정해 두었으면 보안 리뷰도 맡깁니다.
6. 티켓 상태를 done으로 바꾸거나 이슈를 닫고, brief 체크박스를 갱신하고, 완료 기록을 남깁니다. 레포 규칙이나 run-flow 상태 파일이 완료 표시를 다른 값으로 정했으면 done 대신 그 값을 씁니다. 마지막 티켓이면 brief의 "확인 기준"을 실행하고 brief를 닫습니다. 여러 티켓 실행에서는 이 일을 통합 리뷰 뒤에 한 번 합니다.

티켓과 레포 규칙이 충돌하면 진행하기 전에 묻습니다. 우선순위는 티켓의 "하면 안 되는 것"·"작업 경계", 레포 규칙, 스킬의 기본 동작 순입니다.

### 여러 티켓 실행

번호 범위나 "남은 티켓 전부"를 요청하면 실행 방법이 갈립니다. 함께 시작할 수 있는 티켓이 둘 이상이고, 통합 브랜치를 공유하는 티켓이 없고, 쓸 수 있는 워커 도구 절차가 있으면 병렬 실행을, 하나라도 아니면 차례 실행을 합니다.

**병렬 실행**: 티켓마다 워커를 띄워 현재 브랜치에서 갈라진 worktree에서 구현시킵니다. 이 세션은 조정자로서 막힘 관계 순서를 지키고, 끝난 브랜치를 머지하고, 완료 기록을 남깁니다.

1. 작업 트리가 깨끗해야 합니다. 커밋하지 않은 brief·티켓 문서는 워커가 읽지 못하므로 커밋할지 묻습니다. 이어 받는 실행이면 끊긴 머지 복구(3번)를 이 검사보다 먼저 합니다.
2. 실행 묶음, 워커를 띄울 도구, 머지할 브랜치, 동시 워커 수(기본 3개), 시작 HEAD를 보여 주고 승인을 받습니다. 현재 브랜치가 기본 브랜치면 작업 브랜치를 만들지 함께 묻습니다.
3. 앞선 실행의 워커가 남아 있으면 새로 만들지 않고 이어 받습니다. 끝났지만 머지하지 않은 티켓이 있으면 다시 띄우지 않고 머지부터 합니다. 실행 중인 워커는 새로 띄우지 않고 상태를 확인하며 기다립니다. 막는 티켓이 끝났는데 완료 기록에 교차 리뷰 줄이 없으면 교차 리뷰부터 합니다. 워커 식별자는 생기자마자 보고하고, 부른 쪽이 기록 파일을 넘겼으면 거기에 적습니다.
4. 막는 티켓이 모두 머지된 티켓부터 워커를 띄웁니다. 워커는 티켓을 구현해 티켓 브랜치에 커밋하고 결과를 보고합니다. 워커 질문에 준 답과 앞서 내린 결정은 뒤에 띄우는 워커의 지시에 넣습니다.
5. 끝난 브랜치를 현재 브랜치로 합친 뒤 머지 커밋을 만들기 전에 레포 검증 명령(타입 검사, 린트, 테스트)을 돌립니다. 통과하면 완료 기록을 머지 커밋에 넣고 워커와 worktree를 정리합니다. GitHub 티켓은 머지 커밋을 만든 뒤에 닫습니다. 실패하면 머지를 되돌리고 새 워커를 띄우지 않고 멈춥니다. 에이전트 규칙이 고치지 않고 원인 보고만 하는 에이전트를 정해 두었으면 멈추기 전에 원인 보고를 받아 함께 보여 줍니다. 머지한 티켓이 다른 티켓을 막으면 막힌 티켓을 띄우기 전에 그 머지에 교차 리뷰만 먼저 하고, 했다는 줄을 완료 기록에 남깁니다. 충돌하면 워커에게 리베이스를 맡기고, 다시 충돌하면 멈추고 알립니다. 실패한 티켓과 그 티켓에 막힌 티켓은 실행하지 않습니다.
6. 모두 끝나면 시작 HEAD부터 지금까지를 한 번 리뷰하고, brief의 "확인 기준"을 실행한 뒤 결과와 커밋 목록을 보고합니다. push, PR, 기본 브랜치 머지는 사용자가 정합니다.

워커를 만들고, 기다리고, 정리하는 방법은 고른 워커 도구 절차가 정합니다. 절차는 다음 항목을 그 도구의 방법으로 채웁니다. 항목의 조건은 `references/multi-ticket.md`의 "워커 도구 절차"에 있습니다.

| 항목 | 절차가 정하는 것 |
|---|---|
| 사용 조건 | 이 세션에서 그 도구로 워커를 띄울 수 있는지 확인하는 방법 |
| 워커 만들기 | 워커를 띄울 때 현재 브랜치의 로컬 ref에서 갈라진 새 worktree와 새 브랜치를 만드는 방법, 워커 spec을 넘기는 방법, 워커의 모델과 effort를 정하는 순서 |
| 기다리기 | 워커가 끝나거나, 묻거나, 멈추거나, 권한을 요청했을 때 알림을 받는 방법. 상태를 되풀이해 조회하지 않습니다. |
| 끝 판정 | 알림과 마지막 보고를 통과, 질문, 실패로 가르는 방법. 보고한 커밋이 티켓 브랜치에 있을 때만 통과입니다. |
| 같은 워커에 보내기 | 질문 답과 리베이스 요청을 새 워커가 아닌 그 워커에 보내는 방법 |
| 이어 받기 | 기록한 워커 식별자로 남은 워커를 찾아 상태와 마지막 보고를 읽는 방법 |
| 정리 | 머지한 뒤 워커를 닫고 worktree와 머지된 티켓 브랜치를 지우는 방법. 실패한 티켓의 것은 남깁니다. |
| 워커 식별자 | 기록할 값과 형식. 도구 이름과 워커를 찾는 데 필요한 ID를 담습니다. |
| 교차 리뷰 워커 | 다른 회사 모델의 워커를 지금 작업 트리에 읽기 전용으로 띄우는 방법, 그 모델과 effort, 보고를 받는 방법 |

**차례 실행**: 티켓마다 서브에이전트를 하나씩 차례로 띄웁니다. 에이전트 규칙이 구현 에이전트를 정해 두었으면 그 에이전트로 띄웁니다. 같은 작업 트리를 고치므로 병렬로 띄우지 않고 커밋하지 않습니다. 레포 규칙이 코드를 고치기 전에 사용자 승인을 요구하면 서브에이전트에는 제안 diff만 만들게 하고, 승인을 받아 이 세션이 적용합니다. 완료 기준을 통과하지 못한 티켓이 나오면 에이전트 규칙의 실패 처리를 따른 뒤 그래도 실패하면 멈추고, 모두 끝나면 전체 변경을 한 번 리뷰한 뒤 brief의 "확인 기준"을 실행합니다. 레포 규칙이나 사용자 결정으로 도중에 커밋했으면 그 커밋도 리뷰 대상에 넣습니다.

## 결과물

- 구현한 코드 변경. 커밋하지 않습니다. 병렬 실행에서는 티켓마다 머지 커밋이 생깁니다.
- 티켓에 붙는 완료 기록: 완료일, 커밋 정보(커밋 안 함과 작업 시작 HEAD, 병렬 실행이면 머지한 티켓 브랜치와 커밋), 바꾼 파일, 확인한 명령과 결과, 확인 못 한 기준, 고치지 않은 지적. 다른 티켓이 쓸 결과는 `## 산출물`에 남깁니다.
- 보고: 끝낸 티켓, 완료 기준 결과, 바꾼 파일, 산출물 위치, 고치지 않은 리뷰 지적, 건너뛴 리뷰, 다음 티켓

## 함께 쓰는 스킬

- **set-brief**, **set-ticket**: 실행할 brief와 티켓을 만듭니다.
- **run-flow**: 5단계에서 이 스킬로 brief의 남은 티켓을 실행합니다.
- **code-review** 스킬이 설치돼 있으면 5단계 코드 리뷰에 씁니다.
- **check-guidelines**: 5단계 규칙 검사에 씁니다.
