# run-ticket

set-brief·set-ticket으로 남긴 티켓 하나를 이 세션이 직접 구현하고, 완료 기준을 확인하고, 리뷰한 뒤 티켓 상태와 brief 체크박스를 갱신합니다. 리뷰에는 구현한 모델과 다른 회사 모델의 교차 리뷰가 늘 들어가고, 리뷰한 코드와 지금 코드가 같은지 게이트로 확인합니다. 커밋은 하지 않습니다. 여러 티켓을 요청하면 차례로 실행하고, 워커 도구 절차를 지정하면 워커로 병렬 실행할 수도 있습니다.

> 만드는 중인 스킬입니다. `gongbang-dev`를 설치해야 쓸 수 있고, 동작이 바뀔 수 있습니다.

## 언제 쓰나

- set-ticket으로 나눈 티켓을 하나씩 실행할 때
- 티켓으로 나누지 않은 작은 brief를 실행할 때. brief 전체를 티켓 하나로 보고, "남은 일"을 만들 것으로, "확인 기준"을 완료 기준으로 씁니다.
- "남은 티켓 전부"나 번호 범위처럼 여러 티켓을 한 번에 실행할 때. [여러 티켓 실행](#여러-티켓-실행)을 보세요.

run-flow는 5단계에서 이 스킬로 남은 티켓을 실행합니다. brief·티켓 문서가 없는 일반 구현 요청에는 스스로 실행되지 않습니다.

## 준비물

- set-brief·set-ticket으로 만든 brief와 티켓. docs brief는 `- 작성일: YYYY-MM-DD` 줄로 찾고 `.gitignore`에 걸린 폴더(`.scratch/` 등)도 봅니다. GitHub brief는 `context` 라벨이 붙은 열린 이슈에서 찾습니다.
- GitHub 이슈로 된 brief·티켓이면 github.com 원격과 로그인된 `gh` CLI
- `python3`. 교차 리뷰의 코드 지문과 완료 게이트가 `scripts/cross_review.py`입니다.
- 교차 리뷰에 쓸 다른 회사 모델. 실행할 때 지정하거나 레포·에이전트 규칙, 하네스 설정, 저장된 에이전트 프로필(예: [omp 멀티에이전트 설정](../omp-orchestration.md))에 적어 둡니다. 없으면 쓸 수 있는 모델에서 고르고, 다른 회사 모델이 없으면 대체합니다. 순서는 [교차 리뷰](#교차-리뷰)에 있습니다.
- 선택: 병렬 실행에 쓸 워커 도구 절차. [여러 티켓 실행](#여러-티켓-실행)과 [Orca](../orca-orchestration.md), [Paseo](../paseo-orchestration.md) 오케스트레이션 설정을 보세요.

## 진행 과정

시작할 때 1~6단계 체크리스트를 보여 주고 단계를 마칠 때마다 갱신합니다.

1. **티켓 고르기**: 인자가 티켓이면 그 티켓을, brief면 그 안에서 고릅니다. 인자가 없으면 끝나지 않은 티켓이 남은 brief 가운데 작성일이 가장 늦은 것에서, 막힘 관계가 풀린 티켓 가운데 번호가 가장 앞선 것을 고릅니다. 가리키는 문서가 없거나 둘 이상이면 후보를 보여 주고 묻고, 고른 티켓이 이미 done이거나 막혀 있으면 알리고 진행할지 묻습니다. 고를 brief가 없으면 알리고 멈춥니다. 그다음 작업 트리를 확인합니다. brief·티켓 문서 밖의 변경이 있으면 커밋하고 진행할지 묻습니다. 그대로 진행하면 리뷰에 이전 변경이 섞입니다. 어느 끝난 티켓의 "바꾼 파일"에도 없는 변경은 끊긴 티켓의 미완성 변경일 수 있어 따로 보여 주고, 되돌릴지 이어서 쓸지 묻습니다.
2. **맥락 읽기**: 티켓과 brief 전문, 같은 brief의 끝난 티켓의 완료 기록과 산출물, 레포 규칙(CLAUDE.md·AGENTS.md와 거기서 가리키는 문서, `.claude/skills/`)을 읽고 검증 명령과 커밋 규칙을 확인합니다. run-flow에서 이어 실행해 brief를 만든 대화가 세션에 남아 있어도 brief, 티켓, 앞 티켓의 완료 기록만 근거로 삼습니다. 완료 기준이 참조하는 앞 티켓의 산출물을 찾을 수 없으면 다시 만들지 않고 멈춥니다.
3. **구현**: "만들 것"을 이 세션이 직접 구현합니다. 서브에이전트나 다른 에이전트에 맡기지 않고, 예외는 병렬 실행의 워커뿐입니다. 테스트는 레포 규칙이 요구하거나 바꾸는 동작에 이미 테스트가 있을 때 함께 씁니다. 티켓 범위 밖의 문제는 고치지 않고 보고에 남깁니다. run-flow가 보호 경로 검사를 넘겼으면 [보호 목록](run-flow.md#보호-목록)의 파일은 셸로도 고치지 않고, 그 파일을 고쳐야만 통과할 수 있으면 멈추고 묻습니다.
4. **완료 기준 확인**: 완료 기준을 하나씩 명령이나 관찰로 확인하고, 전체 테스트 스위트가 있으면 마지막에 한 번 돌립니다. 막힘 관계에 `(통합 브랜치 공유)`가 붙은 티켓은 전체 스위트를 돌리지 않고, 마지막 "통합 및 검증" 티켓에서만 전체 통과를 확인합니다. 화면에서 봐야 하는 기준도 이 세션이 직접 확인합니다. 브라우저를 다루거나 화면을 캡처할 수단이 있으면 화면을 열어 보고 근거(연 주소, 한 조작, 캡처 경로)를 남기고, 확인하지 못한 항목은 통과로 치지 않고 "확인 못 한 것"에 적습니다.

   통과하지 못한 기준은 같은 세션에서 원인을 정리해 고치고 다시 확인합니다. 시도마다 무엇을 바꿨고 왜 실패했는지 적어 같은 방법을 되풀이하지 않습니다. 최초 시도를 포함해 3회째에도 통과하지 못하면 티켓 상태를 바꾸지 않고 멈춥니다. 통과하지 못한 기준, 시도 횟수, 실패 원인을 보고하고(run-flow가 불렀으면 상태 파일의 `- 멈춘 이유:`에도 적습니다), 티켓을 다시 나눌지 묻습니다. 더 강한 모델이 필요하면 세션 모델을 바꿔 다시 실행할 수 있습니다.
5. **리뷰**: 이 세션이 코드 리뷰와 규칙 검사를 차례로 직접 하고, 티켓 범위 안의 지적을 고쳐 4단계를 다시 확인한 뒤 [교차 리뷰](#교차-리뷰)를 한 번 맡깁니다. 새 컨텍스트에 맡기는 리뷰는 교차 리뷰 하나입니다.
   - **코드 리뷰**: 레포 규칙이 지정한 리뷰 스킬, `code-review`(또는 `<플러그인>:code-review`) 스킬, 직접 리뷰 가운데 처음 맞는 방법을 씁니다. 리뷰 스킬이 서브에이전트로 하위 리뷰를 띄우라고 해도 이 세션이 차례로 직접 보고, 그렇게 실행할 수 없는 스킬이면 쓰지 않고 직접 리뷰한 뒤 보고에 적습니다.
   - **규칙 검사**: check-guidelines로 바꾼 파일을 검사합니다. 스킬이 없으면 건너뛰고 보고에 적습니다.

   리뷰 범위는 작업 시작 HEAD(부른 쪽이 기준 커밋을 넘겼으면 그 커밋) 이후의 커밋하지 않은 변경과 새 파일입니다. 병렬 실행이면 작업 시작 HEAD부터의 커밋이고, 커밋과 커밋하지 않은 변경이 함께 있으면 둘 다 봅니다.
6. **완료 기록**: 교차 리뷰 결과를 모두 검증한 뒤에 합니다.
   1. run-flow가 보호 경로 검사를 넘겼으면 먼저 `verify`를 돌립니다. 실패하면 티켓을 수락하지 않고, 바뀐 파일을 되돌리지 않고 출력을 보여 준 뒤 멈춥니다. 통과하면 이 티켓이 새로 만든 테스트를 목록에 더합니다.
   2. [완료 기록](#결과물)을 씁니다. docs 티켓은 티켓 파일 끝(`## 티켓`이 없는 brief면 brief 끝)에 붙이고, GitHub 티켓은 임시 파일에 씁니다.
   3. 교차 리뷰 게이트(`scripts/cross_review.py gate`)를 그 기록으로 돌립니다. 기록에 `- 교차 리뷰:` 줄이 없거나 그 줄의 코드 지문이 지금 코드와 다르면 거부되고, 상태를 바꾸지 않은 채 리뷰부터 다시 합니다.
   4. 통과하면 docs 티켓은 `- 상태: done`으로, 통과한 완료 기준은 `- [x]`로 바꾸고, GitHub 티켓은 기록을 코멘트로 남기고 닫습니다. brief의 `## 티켓`(없으면 "남은 일")에서 그 티켓을 체크합니다.
   5. 마지막 티켓이면 brief의 "확인 기준"을 실행해 보고하고 brief를 닫습니다. docs brief는 체크박스가 모두 체크된 것으로 끝났음을 나타냅니다.

   레포 규칙이나 run-flow 상태 파일 `## 결정`이 완료 표시를 `done`과 다르게 정했으면 읽을 때와 쓸 때 모두 그 값을 씁니다. 여러 티켓 실행에서는 교차 리뷰 줄, 게이트, 마지막 티켓의 일을 통합 리뷰 뒤에 한 번 합니다.

레포 규칙이 커밋을 요구해도 커밋하지 않고 사용자에게 맡기며, 예외는 병렬 실행입니다. 티켓과 레포 규칙이 충돌하면 진행하기 전에 묻습니다. 우선순위는 티켓의 "하면 안 되는 것"·"작업 경계", 레포 규칙, 스킬의 기본 동작 순입니다.

### 교차 리뷰

같은 회사의 모델은 같은 실수를 함께 놓치기 쉬워서, 구현한 모델과 다른 회사의 모델에 읽기 전용 리뷰를 맡깁니다. 구현한 모델은 이 세션의 모델이고, 병렬 실행에서는 그 티켓을 구현한 워커의 모델입니다. 리뷰어는 사용자와 대화하지 않고 다음 단계를 정하지 않습니다. 교차 리뷰를 하지 않고 5단계를 끝내는 경로는 없습니다.

- **넘기는 것**: 리뷰할 diff 범위(작업 시작 HEAD와 이번 변경을 읽는 명령), brief 전문(티켓 하나를 리뷰하면 그 티켓 전문도), 볼 기준, 실행할 확인 기준입니다. 기준은 버그, 티켓의 "하면 안 되는 것"·"작업 경계" 위반, 레포 규칙 위반이고, 변경이 인증, 권한, 결제, 개인정보를 다루면 보안을 더합니다. 확인 기준은 티켓의 완료 기준이고, 마지막 티켓이나 통합 리뷰면 brief의 "확인 기준"도 넣습니다. 리뷰어가 명령을 직접 실행해 판정하므로, 구현한 세션의 확인만으로 수락하지 않게 됩니다. 비밀값과 원문 로그는 넘기지 않습니다.
- **권한**: 리뷰어는 파일을 고치거나 커밋하지 않고 저장소 밖에도 쓰지 않습니다. 저장소 파일을 바꾸는 확인 명령(스냅샷 갱신, 포매터의 쓰기 모드 등)은 실행하지 않고 `확인 못 함`으로 둡니다. 이 세션은 부르기 직전과 결과를 받은 직후에 코드 지문을 비교하고, 달라졌으면 그 결과를 쓰지 않고 바뀐 것을 보여 준 뒤 다음 수단에 맡깁니다.
- **돌려받는 것**: 수행한 모델 이름, 지적 목록(기준, 심각도, 파일과 줄, 근거, 고칠 방법), 확인 기준마다 `met`·`unmet`·`확인 못 함`과 실행한 명령, 결과 요약만 받습니다. 요약, 총평, 수정 diff는 받지 않습니다.
- **결과 검증**: 이 세션이 지적을 하나씩 재현하거나 원문과 대조해 `수용`, `기각(사유)`, `범위 밖`으로 적습니다. `unmet` 기준은 명령을 다시 실행하고, 재현되면 고칩니다. 리뷰어 판정이 4단계 결과와 다르면 그 차이를 완료 기록에 적습니다. 수용한 지적을 고친 뒤 4단계를 다시 확인합니다. 지적이 없다는 보고만으로는 수락하지 않습니다.

**모델과 수단**: 모델 이름을 정해 두지 않고, 부를 때마다 아래 순서에서 처음 되는 것을 씁니다. 다른 회사 모델이 없어도 멈추지 않습니다.

1. 사용자나 부른 쪽이 이번 실행에서 지정한 모델이나 수단
2. 레포·에이전트 규칙 파일, 하네스 설정, 저장된 에이전트 프로필이 정해 둔 교차 리뷰 에이전트나 모델, 또는 지정되거나 등록된 워커 도구 절차의 "교차 리뷰 워커"
3. 이 세션에서 쓸 수 있는 provider, 모델, 에이전트 목록에서 고른 다른 회사 모델. 무엇을 골랐는지 알립니다.
4. 같은 회사 모델의 새 컨텍스트 리뷰로 대체. 넘기는 것과 검증은 같습니다.

리뷰는 새 컨텍스트의 읽기 전용 서브에이전트 하나로 부르고, 모델을 정할 수 있으면 4번이어도 정해서 띄웁니다. 워커 도구 절차를 쓰면 그 절차의 "교차 리뷰 워커"대로 지금 작업 트리에 띄웁니다. 응답이 없거나 결과를 읽을 수 없으면 다음 수단에 맡깁니다. 독립 여부는 리뷰어가 적은 이름 대신 호출 도구의 실행 정보나 수단의 설정으로 확인한 실제 모델로 판정합니다. 같은 회사였으면 다음 수단에 맡기고, 남은 수단이 4번뿐이면 그 리뷰를 대체로 칩니다. 새 컨텍스트를 하나도 띄울 수 없으면 이 세션이 diff를 처음부터 다시 읽고 확인 기준을 다시 실행하는 자기 리뷰로 대체합니다.

**코드 지문과 게이트**: `scripts/cross_review.py`가 만듭니다.

- `fingerprint`는 작업 트리의 코드 지문을 냅니다. 커밋하지 않은 변경과 새 파일이 들어가고, tree 해시라서 커밋만 해서는 바뀌지 않습니다. `docs/context/run-flow/`(상태 파일과 보호 목록), `--brief`로 준 brief와 그 티켓 폴더, `--exclude`로 준 경로는 빼므로 완료 기록을 고쳐도 값이 그대로입니다. tree 해시를 구하지 못하면 HEAD, 상태, diff로 만든 지문을 대신 냅니다.
- `record`는 검증과 고침을 마친 뒤의 지문으로 완료 기록의 `- 교차 리뷰:` 줄을 만듭니다. 수행한 모델을 확인할 수 없으면 모델 자리에 `수행 모델 확인 불가: <맡긴 수단>`을 적습니다.
- `gate`는 기록마다 마지막 `- 교차 리뷰:` 줄이 완료나 대체이고 그 지문이 지금 지문과 같을 때만 통과시킵니다.

`- 교차 리뷰:` 줄은 셋 가운데 하나입니다. 대체 리뷰는 독립 검증이 아니므로 보고에도 대체 표시를 적어 사용자가 판단하게 하고, run-flow가 불렀으면 상태 파일의 `- 교차 리뷰 모델:`에도 적습니다.

- 다른 회사 모델: `- 교차 리뷰: 완료 (<수행한 모델>, 코드 지문 <지문>)`
- 같은 회사 모델로 대체: `- 교차 리뷰: 대체 (같은 회사 모델 <수행한 모델>, 코드 지문 <지문>)`
- 자기 리뷰로 대체: `- 교차 리뷰: 대체 (새 컨텍스트 없음, 메인 세션 자기 리뷰, 코드 지문 <지문>)`

### 여러 티켓 실행

번호 범위나 "남은 티켓 전부"를 요청하면 `references/multi-ticket.md`의 절차를 따릅니다. 기본은 이 세션이 티켓을 하나씩 직접 구현하는 **차례 실행**입니다. **병렬 실행**은 사용자나 부른 쪽이 이번 실행에서 워커 도구 절차를 지정했거나 레포·에이전트 규칙에 등록해 둔 때만 고를 수 있고, 다음을 모두 만족해야 합니다. 하나라도 아니면 차례 실행을 합니다.

- 막힘 관계로 함께 시작할 수 있는 티켓이 둘 이상인 때가 있습니다. 막힘 관계가 일렬이면 worktree와 머지 비용만 듭니다.
- 대상 티켓의 막힘 관계에 `(통합 브랜치 공유)`가 없습니다.
- 쓸 수 있는 워커 도구 절차가 있습니다. 사용자나 부른 쪽이 정한 도구의 절차, 규칙이 지정한 절차(여럿이면 적힌 순서) 가운데 "사용 조건"을 만족하는 첫 절차를 씁니다. 이어 받는 실행은 기록에 남은 워커 식별자가 가리키는 도구의 절차를 씁니다.

워커 도구 절차는 워커를 띄우는 도구 하나로 워커를 만들고, 기다리고, 정리하는 방법을 적은 문서입니다. 실행 중에 받은 질문의 답, 새로 정한 설계 결정, 실패한 티켓의 시도 기록, 워커 식별자는 생긴 때에 바로 남깁니다. 부른 쪽이 기록 파일을 넘겼으면(run-flow는 상태 파일) 거기에, 아니면 사용자에게 한 줄로 알리고 마지막 보고에 넣습니다.

**차례 실행**: 작업 트리 확인을 한 번 하고, 막힘 관계와 번호로 정한 순서를 보여 준 뒤 티켓마다 2, 3, 4, 6단계를 합니다. 한 티켓의 완료 기록을 남긴 뒤 다음 티켓을 시작하고, 같은 작업 트리를 고치므로 티켓 둘을 함께 진행하지 않습니다. 완료 기준을 통과하지 못한 티켓이 나오면 4단계 규칙대로 멈추고 뒤 티켓은 시작하지 않습니다. 모두 끝나면 아래 통합 리뷰를 합니다.

**병렬 실행**: 티켓마다 워커가 현재 브랜치에서 갈라진 worktree의 새 브랜치에서 구현하고 커밋합니다. 새 worktree는 커밋된 내용만 보므로 이 경로에서만 커밋이 생깁니다. 이 세션은 조정자로서 막힘 관계 순서를 지키고, 끝난 브랜치를 머지하고, 완료 기록을 남기고, 교차 리뷰를 부릅니다.

1. **준비**: 작업 트리가 깨끗해야 합니다. 커밋하지 않은 것이 brief·티켓 문서뿐이면 커밋할지 묻고, 다른 변경이 있으면 정리한 뒤 다시 실행하라고 알리고 멈춥니다.
2. **계획 승인**: 실행 묶음, 워커를 띄울 도구와 그 절차를 정한 곳, 머지할 브랜치, 동시 워커 수(기본 3개), 작업 시작 HEAD를 보여 주고 승인을 받습니다. 현재 브랜치가 기본 브랜치면 작업 브랜치를 만들지 함께 묻습니다.
3. **이어 받기**: 앞선 실행의 워커가 남아 있으면 새로 띄우지 않고 이어 받습니다. 다시 띄우면 같은 티켓을 두 번 구현하기 때문입니다. 끝났지만 머지하지 않은 티켓은 머지부터 하고, 끊긴 머지는 `git merge --abort`로 되돌린 뒤 처리합니다. 다른 티켓을 막는 done 티켓에 `- 교차 리뷰: 완료 (...)`나 `- 교차 리뷰: 대체 (...)` 줄이 없으면 막힌 티켓을 띄우기 전에 그 교차 리뷰부터 합니다. 앞선 실행이 남긴 `- 교차 리뷰: 건너뜀 (...)` 줄은 리뷰하지 않은 것으로 봅니다.
4. **워커 띄우기**: 막는 티켓이 모두 머지되고 그 교차 리뷰까지 끝난 티켓의 워커를 동시 워커 수까지 띄웁니다. 워커는 run-ticket의 2, 3, 4단계만 하고, 통과하면 티켓 브랜치에 커밋한 뒤 완료 기준 결과, 바꾼 파일, 산출물, 브랜치, 커밋 해시를 보고합니다. 보호 목록의 파일은 셸로도 고치지 않습니다. 이미 내린 결정과 워커 질문에 준 답은 뒤에 띄우는 워커의 지시에 넣습니다.
5. **워커가 끝나면** 결과에 따라 처리합니다.
   - **통과**: `git merge --no-ff --no-commit`으로 합치고, 머지 커밋을 만들기 전에 레포 검증 명령(타입 검사, 린트, 테스트)을 돌립니다. 앞서 머지한 티켓과 어긋나는 변경은 여기서 드러납니다. 이어서 보호 경로 검사(`verify --rev <티켓 브랜치>`)를 돌리고, 새 테스트를 목록에 더한 뒤 완료 기록과 함께 머지 커밋을 만듭니다. 완료 기록의 커밋 줄은 ``- 커밋: 티켓 브랜치 `<브랜치>`의 `<해시>`를 머지``입니다. GitHub 티켓은 머지 커밋을 만든 뒤에 닫고, 절차의 "정리"대로 워커와 worktree를 정리합니다.
   - **검증이나 보호 경로 검사 실패**: 머지를 되돌리고 새 워커를 띄우지 않고 멈춥니다. 그 티켓의 worktree는 남깁니다. 통합 검증이 실패했으면 멈추기 전에 이 세션이 실패 출력과 양쪽 변경을 읽고, 어느 쪽 변경에서 생긴 실패로 보이는지 근거와 함께 보여 줍니다.
   - **막는 티켓의 교차 리뷰**: 머지한 티켓이 다른 티켓을 막으면, 막힌 티켓을 띄우기 전에 그 머지 커밋의 diff(`HEAD^..HEAD`)에 교차 리뷰만 합니다. 결함 위에 뒤 티켓이 쌓이면 고칠 범위가 커지기 때문입니다. 수용한 지적을 고치고 `- 교차 리뷰:` 줄을 그 티켓의 완료 기록에 더해 함께 커밋합니다.
   - **머지 충돌**: 머지를 되돌리고 그 워커에게 현재 브랜치 위로 리베이스해 다시 확인하라고 보냅니다. 다시 충돌하면 그 티켓을 멈추고 알립니다.
   - **실패**: 그 티켓과 그 티켓에 막힌 티켓은 띄우지 않습니다. 실행 중인 워커는 끝까지 기다려 머지합니다.
   - **질문**: brief와 티켓으로 답할 수 있으면 답하고, 아니면 사용자에게 물어 같은 워커에 전합니다.
6. 모든 워커가 끝나면 아래 통합 리뷰를 하고, 티켓별 결과와 만든 커밋 목록을 보고합니다. push, PR, 기본 브랜치 머지는 사용자가 정합니다.

**통합 리뷰**: 모든 티켓이 끝나면 작업 시작 HEAD 이후의 전체 변경(커밋, 커밋하지 않은 변경, 새 파일)에 5단계 리뷰를 한 번 하고, 고친 부분이 걸친 티켓의 완료 기준을 다시 확인합니다. 병렬 실행이면 고친 내용을 커밋합니다. 보호 경로 검사를 넘겨받았으면 `verify`를 다시 돌립니다. 교차 리뷰 줄은 리뷰한 변경에 든 티켓마다 완료 기록에 더합니다(차례 실행에서 다시 리뷰했으면 새 줄로 바꿉니다). 병렬 실행에서는 막는 티켓의 리뷰로 줄이 이미 있는 티켓에도 더하는데, 뒤 티켓이 머지되면서 그 줄의 지문이 맞지 않게 됐고 게이트는 마지막 줄을 보기 때문입니다. 그 티켓들 모두로 게이트를 한 번 돌리고, 거부되면 줄이 없거나 지문이 다른 티켓의 변경을 다시 리뷰합니다. 통과하면 모든 티켓을 합친 상태에서 brief의 "확인 기준"을 실행하고 brief를 닫습니다.

**워커 도구 절차가 정할 것**: 워커를 띄우는 명령과 알림 방식은 도구마다 달라 고른 절차를 따릅니다. 절차는 다음 항목을 그 도구의 방법으로 채웁니다. 항목마다 지킬 조건은 `references/multi-ticket.md`의 "워커 도구 절차"에, 예는 [`extras/orca/worker-procedure.md`](../../extras/orca/worker-procedure.md)와 [`extras/paseo/worker-procedure.md`](../../extras/paseo/worker-procedure.md)에 있습니다.

- **사용 조건**: 이 세션에서 그 도구로 워커를 띄울 수 있는지 확인하는 방법
- **워커 만들기**: 워커를 띄울 때 현재 브랜치의 로컬 ref에서 새 worktree와 브랜치를 만드는 방법, 워커의 모델과 effort를 정하는 순서
- **기다리기**: 워커가 끝나거나, 묻거나, 멈추거나, 권한을 요청했을 때 알림을 받는 방법. 상태를 되풀이해 조회하지 않습니다.
- **끝 판정**: 알림과 마지막 보고를 통과, 질문, 실패로 가르는 방법. 보고한 커밋이 티켓 브랜치에 있을 때만 통과입니다.
- **같은 워커에 보내기**, **이어 받기**, **정리**, **워커 식별자**: 답과 리베이스 요청을 그 워커에 보내는 방법, 기록한 식별자로 남은 워커를 찾는 방법, 머지한 뒤 워커와 worktree를 정리하는 방법(실패한 티켓의 것은 남김), 기록할 도구 이름과 ID
- **교차 리뷰 워커**: 다른 회사 모델의 워커를 지금 작업 트리에 읽기 전용으로 띄워 교차 리뷰를 맡기는 방법. 모델은 절차에 고정하지 않고, 다른 회사 모델을 고를 수 없으면 띄우지 않습니다.

## 결과물

- 구현한 코드 변경. 커밋하지 않습니다. 병렬 실행에서는 티켓마다 머지 커밋이 생깁니다.
- 완료 기록: 아래 형식으로 티켓에 붙습니다(GitHub 티켓은 코멘트). 해당 없는 줄은 지웁니다. `## 산출물`에는 "만들 것"이나 완료 기준이 남기라고 한 결과와 다른 티켓이 "NN 티켓의 산출물"로 참조하는 결과를 내용 그대로나 저장소 경로로 적고, 없으면 섹션을 지웁니다.

  ```markdown
  ## 완료 기록
  - 완료일: YYYY-MM-DD
  - 커밋: 안 함 (작업 시작 HEAD `<해시>`)
  - 바꾼 파일: `<경로>`, `<경로>`
  - 확인한 것: `<명령>` → <결과> (확인한 HEAD `<해시>`, 커밋 전이면 "작업 트리")
  - 확인 못 한 것: <기준>: <이유>
  - 교차 리뷰: 완료 (<수행한 모델>, 코드 지문 <지문>)
  - 교차 리뷰 지적: <지적>: <수용 / 기각(사유) / 범위 밖>
  - 교차 리뷰 기준 판정: <기준>: <met / unmet / 확인 못 함> (4단계 결과와 다르면 그 차이)
  - 고치지 않은 지적: <지적>: <이유>

  ## 산출물
  <내용 또는 저장소 경로>
  ```
- 보고: 끝낸 티켓, 완료 기준 결과, 바꾼 파일, 산출물 위치, 교차 리뷰를 수행한 모델과 대체 표시, 교차 리뷰 지적과 기준 판정, 게이트 결과, 고치지 않은 리뷰 지적, 건너뛴 리뷰와 이유(규칙 검사를 하지 못했거나 리뷰 스킬을 쓰지 않은 경우), 다음 티켓, 커밋은 사용자가 한다는 안내

## 함께 쓰는 스킬

- **set-brief**, **set-ticket**: 실행할 brief와 티켓을 만듭니다.
- **run-flow**: 5단계에서 이 스킬로 brief의 남은 티켓을 실행하고, 상태 파일과 보호 경로 검사 명령을 넘깁니다.
- **code-review** 스킬이 설치돼 있으면 5단계 코드 리뷰에 씁니다.
- **check-guidelines**: 5단계 규칙 검사에 씁니다.
