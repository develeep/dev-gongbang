# dev-gongbang 오케스트레이션 강화 계획

[설계안](./2026-11-19-multi-agent-orchestration.md)과 [원칙 문서](./2026-11-19-multi-agent-orchestration-principles.md)를 현재 구현(`skills/in-progress/{run-flow,run-ticket,set-ticket,set-brief}`, `extras/omp/`, `extras/paseo/`)과 대조해 세운 계획입니다. 2026-11-20에 Codex(gpt-6.2-sol, 설계 충실도)와 Claude Code(claude-opus-5-5, 사실 정확성)가 리뷰했고, 지적은 모두 수용해 반영했습니다. 본문의 "설계 N행"은 설계안의 줄 번호입니다.

이미 있는 것: 단계 순서(run-flow 0~7), 상태 파일, 코드 지문(`run-flow/scripts/code_fingerprint.sh`), 교차 리뷰, 실패 시 승격(implementer 2회 → hard-implementer), 검증 명령 실행(run-ticket 3·4단계, 병렬 머지), 같은 제목의 티켓 재생성 방지(set-ticket 93행).

## 사용자 결정 (2026-11-20)

## 모든 단계에 공통인 끝나는 조건

- eval 사례를 새로 더합니다. 일어나야 하는 경우와 일어나지 말아야 하는 경우를 함께 둡니다. 사례는 실제 원격과 상태 기록을 건드리지 않게 격리하고, 판정은 실행한 명령과 작업 상태처럼 관찰한 결과로 합니다(설계 457~462행).
- 수락, 상한, 승인, 권한 경로를 바꾸는 단계(P4, P5, P6, P7, P9)는 관련된 기존 사례도 다시 돌립니다. 바뀐 동작과 반대로 단언하는 기존 사례는 고쳐 씁니다.
- 스킬 동작이 바뀌면 `docs/skills/<스킬>.md`를, `extras/`가 바뀌면 `docs/{omp,orca,paseo}-orchestration.md`를 고칩니다. 영어판(`docs/en/`)도 같은 커밋에서 고칩니다.
- `skills/`를 바꾼 단계는 `plugin.json` 버전을 올리고 릴리스 절을 따릅니다. `gongbang-dev`는 버전이 없어 `plugin.json` 버전을 씁니다.
- `extras/paseo/playbooks/`를 고치면 `.paseo/plugins/playbooks/`에 복사해 검증한 뒤 복사본을 지웁니다. mod를 고치면 `gongbang-mods` 버전을 올리고 `claude plugin validate`와 `claude plugin test`를 돌립니다.
- `scripts/check.py`를 통과시킵니다.

### P1. 역할 정의와 인계 계약

- 역할마다 통과 조건을 한 문장으로 적습니다(설계 112~128행). 대상은 implementer, hard-implementer, test-writer, ui-checker, code-reviewer, cold-reader, doc-writer, root-cause와 Paseo 프로필·역할입니다.
- 구현이 자기 작업의 테스트를 씁니다. 레포 규칙이 테스트를 쓰지 않는다고 정했으면 그 규칙을 따르고, 그 사실을 완료 기록에 적습니다. test-writer는 테스트가 작업의 목적일 때와, 조정자가 틀렸다고 판정한 기존 테스트를 고칠 때만 부릅니다.
- 넘기는 것(설계 133~143행): 명세와 작업 전문, 이미 내린 결정과 근거, 앞선 작업의 산출물, 작업 공간 절대 경로와 수정해도 되는 경로, 규칙 문서와 검증 명령, 시도 번호와 상한("3회 중 2번째"). 다시 맡길 때는 이전 실패 분류, 충족하지 못한 완료 기준, 리뷰 지적을 함께 넘깁니다. 필수 입력이 없으면 부르기 전에 멈춥니다.
- 다른 회사 모델에는 그 일에 필요한 범위만 넘깁니다. 비밀값, 불필요한 개인정보, 원문 로그는 프롬프트와 읽을 수 있는 범위에서 뺍니다. 빼고는 맡길 수 없으면 맡기지 않고 사용자에게 넘깁니다.
- 돌려받는 것(설계 145~159행): `통과/실패`, 받은 시도 번호, 기준별 `충족/미충족/미확인/해당 없음(이유)`(항목을 지우지 않음), 항목별 근거, 바꾼 파일과 브랜치·커밋, 수행한 모델(모르면 `확인 불가`), 실패 분류와 원본 오류 발췌, 완화·대체로 처리한 것, 범위 밖 문제. 판정에 쓰는 값만 정해진 목록에서 고르고, 나머지 맥락은 글로 넘깁니다.
- 고칠 파일: `extras/omp/agents/*.md`, `extras/omp/AGENTS.md`의 "넘기는 것" 절, run-ticket 3·4·6단계와 완료 기록 템플릿, `multi-ticket.md`의 워커 지시와 차례 실행 지시, `extras/paseo/config.json`의 notes, `extras/paseo/playbooks/roles/*`
- eval: 확인 못 한 기준을 `미확인`으로 남기는지, 해당 없는 항목을 지우지 않는지, 다른 회사 리뷰에 `.env` 내용을 넘기지 않는지

### P2. 상태 파일 스키마

- `assets/state-file.md`에 설계 270~284행의 섹션을 모두 둡니다: 진행, 결과물, 결정, 시도, 수락, 리뷰, 승인, 바깥 쓰기, 명세 버전, 사람 정정, 판정 기록, 게시 뒤 관찰, 변경 후보. 각 섹션에 무엇을 적는지는 P5~P12가 정합니다.
- 생긴 때에 바로 적습니다. 사실의 출처는 하나씩입니다. 코드와 병합은 git, 게시와 이슈는 원격, 진행과 결정은 상태 파일을 따르고, 서로 어긋나면 다음 단계로 가지 않고 대조합니다.
- 비밀값과 원문 로그는 적지 않습니다. 이어 가는 데 필요한 기록(수락, 승인, 시도 결과)을 남기지 못했으면 그 단계를 끝난 것으로 치지 않고 멈춥니다.
- 고칠 파일: `run-flow/assets/state-file.md`, run-flow "상태 파일" 절, `evals/run-flow/state-created`

### P3. 티켓 템플릿과 작업 사이 계약

- 이슈 티켓과 docs 티켓 템플릿에 세 칸을 더합니다: `- 필수: 필수/선택`, `## 수정 범위`(허용 경로 glob), `## 주고받는 것`(이름, 필수·선택 항목, 상태값, 오류 형식. 관련 티켓에 같은 문구로 적음).
- 공유 진입점(등록, 공통 스키마, 설정)은 한 티켓에만 주거나 통합 티켓에 둡니다. 구현 중 계약을 바꿔야 하면 작업자는 고치지 않고 조정자에게 돌려보냅니다.
- brief와 티켓 목록의 지문을 명세 버전으로 씁니다. 개정되면 새 지문을 상태 파일 "명세 버전"에 적습니다.
- 고칠 파일: `set-ticket/SKILL.md`(템플릿 2종, 3단계 분할, 4단계 확인 질문), `docs/customization.md`의 티켓 형식 줄
- eval: 공유 진입점을 두 티켓에 주지 않는지, 수정 범위 칸이 비지 않는지

### P4. 쓰기 권한 강제

- 읽기만 하는 역할에서 쓰기 도구를 뺍니다. 대상은 code-reviewer, reviewer, ui-checker, cold-reader, doc-writer, root-cause이고, `tools:`에서 edit와 write를 뺍니다. bash로 쓰는 것은 막을 수 없으므로 P5에서 호출 전후의 코드 지문을 비교해 잡습니다. Paseo 역할은 이미 `readonly: true`를 쓰고 있으므로(`roles/ticket-reviewer`) 다른 읽기 전용 역할에도 같은 값을 둡니다.
- 보호 경로에 쓰는 것을 막습니다. 보호 경로는 시작 HEAD에 있던 테스트 파일, 앞서 수락된 작업의 테스트, 판정용 사례입니다.
  - **목록 파일**: 조정자가 5단계를 시작할 때 `docs/context/run-flow/<slug>.protected`를 만듭니다. 한 줄에 경로나 glob 하나를 적습니다. 작업을 하나 수락할 때마다 그 작업의 테스트를 더합니다. 조정자가 틀렸다고 판정한 테스트는 test-writer에 맡기기 전에 목록에서 빼고, test-writer의 결과를 수락하면 다시 넣습니다.
  - **워커에게 보이게 하기**: 목록 파일은 흐름 문서라 run-flow 5단계에서 함께 커밋됩니다. 목록을 고치면 머지 커밋에 함께 넣습니다. 그래야 worktree를 나눈 워커도 목록을 읽습니다.
  - **켜지는 조건**: 차단 코드는 git 루트의 `docs/context/run-flow/*.protected` 가운데, 같은 이름의 상태 파일이 `- 현재 단계: 완료`가 아닌 것만 읽습니다. 그런 파일이 없으면 아무것도 막지 않으므로, 흐름 밖의 작업에는 영향이 없습니다.
  - **누가 실행했는지는 가리지 않습니다**: 목록에 있는 경로는 조정자, 워커, 서브에이전트 모두 고칠 수 없습니다. 조정자가 직접 구현할 때도 구현 역할이므로 막는 것이 맞습니다. 병합은 git이 하므로 도구 차단에 걸리지 않습니다. test-writer에게는 목록에서 뺀 파일만 열립니다. 그래서 워커 세션을 따로 가려낼 필요가 없습니다.
  - **omp**: `extras/omp/extensions/`에 extension을 새로 두고, `~/.omp/agent/extensions/`에 설치합니다. `tool_call` 핸들러가 `write`(path), `edit`(input의 `[PATH#TAG]` 머리줄), `ast_edit`(path)의 대상이 목록에 있으면 `{ block: true, reason }`을 돌려줍니다.
  - **Claude Code**: `mods/gongbang-mods/hooks/`에 PreToolUse mod를 더해 `Write`, `Edit`, `MultiEdit`, `NotebookEdit`의 `file_path`를 검사합니다.
  - **bash로 쓰는 것**(`sed -i`, 리다이렉트)은 막지 못합니다. P5의 사후 검사가 잡습니다.
  - Codex 워커는 리뷰만 맡으므로 차단 대상이 아닙니다. 리뷰 전후의 코드 지문 비교로 잡습니다.
- 판정용 사례는 구현 역할이 읽을 수 있는 범위와 지시문에 두지 않습니다.
- 고칠 파일: `extras/omp/agents/*.md`, `extras/omp/extensions/`(새로 만듦), `mods/gongbang-mods/hooks/`, `types/index.d.ts`, `extras/paseo/playbooks/roles/*`, `extras/setup.sh`, run-flow 5단계와 `assets/`, `docs/mods.md`, `docs/omp-orchestration.md`
- eval: 목록에 있는 테스트를 고치려 하면 막히는지, 목록에서 뺀 테스트는 test-writer가 고칠 수 있는지, 끝난 흐름의 목록 파일은 아무것도 막지 않는지

### P5. 수락 검사와 조정자 판정

- **순서**: 구현이 자체 확인을 합니다. 병렬 워커는 그다음 커밋하고, 브랜치와 커밋을 보고합니다. 그 뒤 조정자가 결정적 검사를 하고, 마지막으로 조정자가 판정합니다.
- 단독 실행과 차례 실행은 핵심 규칙 3대로 커밋하지 않습니다. 이 경우 검사 대상은 시작 HEAD 대비 작업 트리 diff와 새 파일이고, 커밋 계보 검사는 건너뜁니다.
- **결정적 검사** `run-ticket/scripts/accept_check.py`:
  - 커밋 모드면 보고된 커밋이 있고 시작 HEAD에서 이어졌는지 봅니다.
  - 바뀐 파일이 모두 수정 범위 안인지 봅니다.
  - 보호 경로가 바뀌지 않았는지 봅니다. P4를 보조하는 검사입니다.
  - 맡기지 않은 작업 공간과, 읽기만 하는 역할을 부르기 전후의 코드 지문이 같은지 봅니다.
  - 시도 번호가 이번 차례와 같은지 봅니다.
  - 검증 명령을 돌립니다.
  - 스크립트 안에 assert 자체 검사를 둡니다.
- **조정자 판정**(설계 173~178행):
  - 근거 없는 `충족`을 거부합니다.
  - 필수 기준이 `미충족`이거나 `미확인`이면 수락하지 않습니다.
  - 완화·대체와 선택 기준의 `미확인`은 승인 항목으로 올립니다.
  - 수락한 명세 버전을 상태 파일 "수락"에 적습니다.
  - 코드가 아닌 결과(명세, 작업 목록, 화면 확인, 게시 글)는 그 단계의 끝나는 조건과 필수 항목으로 판정합니다.
- **검사 결과별 처리**(설계 180~184행):
  - 범위 위반은 되돌리지 않고 멈춘 뒤 사용자에게 알립니다.
  - 검증 실패나 `미충족`은 `완료 기준 실패`로 P7에 넘깁니다.
  - 시도 번호가 다르거나 커밋이 없으면 결과를 받지 않고, 작업 공간을 조회해 한 일을 확인합니다.
- 리뷰는 결정적 검사가 통과한 뒤에만 부릅니다.
- 고칠 파일: run-ticket 핵심 규칙 3과 4단계, `multi-ticket.md`의 병렬 실행 5번과 차례 실행 절, `extras/paseo/playbooks/run-ticket.yaml`(review 앞에 검사 단계를 둠), 커밋 여부를 단언하는 eval(`mark-done`, `multi-sequential`, `no-ticket-brief-done`, `scratch-brief`)
- eval: 허용 경로 밖을 고친 구현이 수락되지 않는지, 근거 없는 `충족`이 거부되는지

### P6. 리뷰

- **기준별 호출**: 버그, 규칙 위반, 불필요한 코드를 늘 따로 부릅니다. 인증, 권한, 결제, 개인정보를 다루는 변경에는 보안 리뷰를 더합니다. 한 호출에 기준을 섞지 않습니다. 각 기준에 맞는 리뷰 도구는 이 단계에서 정합니다.
- **독립성**:
  - 보안을 뺀 모든 기준은 다른 회사 모델이 리뷰합니다.
  - 독립인지는 실제로 수행한 모델과, 그 범위를 구현한 **모든** 모델을 비교해 판정합니다. `확인 불가`면 독립이 아닙니다.
  - 보안 리뷰는 사용자 결정에 따라 Claude로 하고, 독립성 판정에서 예외로 기록합니다.
  - `config.yml`의 `retry.fallbackChains.review`를 지웁니다.
- **지시와 수용**:
  - 리뷰어에게는 기준 하나, 볼 범위, 명세를 넘기고 반대 근거와 재현 방법을 찾게 합니다.
  - 재현되거나 원문 근거가 있는 지적만 고칩니다.
  - 지적마다 `수용/기각(사유)/범위 밖`을 상태 파일 "판정 기록"에 적습니다.
  - 구현이 새로 쓴 테스트가 기준을 제대로 시험하는지는 리뷰가 봅니다. 테스트만 통과시키는 특수 처리는 "불필요한 코드" 기준에서 봅니다.
- **고친 뒤**: 검증 명령 전체를 다시 돌리고, 바뀐 범위를 다시 리뷰합니다. 파일이 그대로여도 작업 사이 계약이 바뀌었으면 바뀐 범위로 봅니다. 범위를 가를 수 없으면 전체를 다시 리뷰합니다. 재리뷰도 그 기준의 3회 안에 셉니다.
- **유효성**: 리뷰마다 수행한 모델, 본 코드의 지문, 본 범위를 기록합니다.
- **필수 리뷰가 실패한 경우**: 응답이 없거나, 결과를 읽을 수 없거나, 독립이 아니었거나, 상한에 닿으면 수락하지 않고 사용자에게 넘깁니다. 이를 대신할 수 있는 것은 사용자가 그 기준으로 직접 검토하고 그렇게 기록한 경우뿐입니다. "건너뛰고 진행"은 없앱니다.
- **병렬 실행**: 다른 티켓을 막는 티켓은 필수 기준의 리뷰가 모두 수락된 뒤에 뒤 티켓을 띄웁니다. 지금은 교차 리뷰 하나만 합니다.
- 고칠 파일: run-ticket 5단계, `multi-ticket.md`(막는 티켓의 리뷰, 통합 리뷰), `extras/omp/agents/code-reviewer.md`, `extras/omp/config.yml`, `extras/omp/AGENTS.md` 위임 표와 교차 리뷰 절, `run-flow/references/merge-stage.md`, run-flow 5단계의 `## 리뷰` 기록, `extras/paseo/config.json`(cross-review, skill-review, security-review의 notes), `extras/paseo/playbooks/run-ticket.yaml` review 단계와 `roles/ticket-reviewer`, `docs/orca-orchestration.md`의 리뷰 건너뜀 동작
- 고쳐 쓸 eval: `review-fallback-no-skill`(건너뛰고 done으로 바꾸는 것을 PASS로 판정함), `mark-done`
- eval: 결과 없이 끝난 리뷰가 수락을 막는지, 고친 뒤 재리뷰를 부르는지, 같은 회사 모델의 리뷰를 독립으로 치지 않는지

### P7. 실패 처리, 상한, `parked`

- **분류**: 종료 코드, 타임아웃, 요청 한도 응답, 권한 오류처럼 관찰할 수 있는 신호로 먼저 가르고, 모호할 때만 모델이 판단합니다. 분류별 처리는 설계 190~196행의 표를 따릅니다. `명세 모호`는 P10으로 보내고, `환경·설정`과 `분류 불명`은 사람에게 넘깁니다.
- **세는 단위**: 한 작업을 같은 목적으로 맡긴 횟수입니다. 목적은 구현, 리뷰 기준 하나, 게시 결정의 "고치기", 명세 작성입니다. 최초 호출, 실패 뒤의 재시도, 일시적 오류 재시도, 재리뷰를 모두 셉니다. 최초 시도를 포함해 3회입니다.
  - 구현으로 시작한 작업은 세 번째 시도를 hard-implementer에 맡깁니다.
  - 구현 워커가 한 번 실패한 뒤 hard-implementer로 올리는 것은 그대로 둡니다. 이 경로는 3회를 넘지 않습니다.
- **`parked`**:
  - 세 번째 시도가 실패하면 `- 상태: parked`로 두고, 사유, 마지막 시도 번호, 산출물 위치를 남깁니다.
  - 그 작업에 기대는 작업은 시작하지 않고, 기대지 않는 작업은 계속합니다.
  - 원인이 풀렸다는 근거가 있고 사용자가 추가 시도를 허용했을 때만, 실패한 검사부터 다시 맡깁니다. 횟수는 초기화하지 않습니다.
  - 상태값을 더하므로 세 스킬의 상태 판정을 함께 고칩니다(`docs/customization.md` 77행 규칙): set-ticket 150행, run-flow 68·72행(끝난 티켓 판정, 남은 티켓 수), run-ticket 1단계.
- **무응답**: 응답 없이 끝난 역할은 실패로 단정하지 않습니다. 작업 공간과 브랜치를 먼저 조회합니다.
- **동시 호출**: 구현, 리뷰, 냉독 독자를 모두 합쳐 10개까지 띄우고, 넘는 호출은 기다립니다. 워커는 기본 3개로 유지합니다. 기다리는 시간은 실행 환경의 타임아웃에 맡깁니다.
- **Paseo**: `run-ticket.yaml`은 지금 구현을 최대 4회 돌립니다(아래 "확인한 것"). `retries: 0`과 `max_loops: 2`, 또는 `retries: 1`과 `max_loops: 1`로 바꿔 3회 안으로 맞춥니다. 루프 상한에 닿으면 Paseo가 한 번 더 돌릴지 사람에게 묻는 gate를 엽니다. 이 gate에서 승인하는 것은 `parked`의 "추가 시도 허용"과 같은 뜻으로 봅니다. `config.json` hard-implementer 프로필 notes의 승격 횟수도 맞춥니다.
- 고칠 파일: `extras/omp/AGENTS.md` "실패했을 때", run-ticket 4단계와 1단계, `multi-ticket.md`, `set-ticket/SKILL.md`, `run-flow/SKILL.md`, `extras/paseo/playbooks/run-ticket.yaml`, `extras/paseo/config.json`, `docs/{omp,paseo}-orchestration.md`의 승격 횟수 줄, `docs/customization.md`
- eval: 상한에 닿으면 `parked`가 되는지, `환경·설정` 실패를 다시 맡기지 않는지, `parked`에 기대는 티켓을 띄우지 않는지

### P8. 비용: 결과 재사용과 모델 라우팅

- **재사용**:
  - 입력이 같으면 결과를 다시 만들지 않습니다. 입력이 같다는 것은 코드 지문, 명세 버전, 실행한 명령이나 리뷰 기준이 모두 같다는 뜻입니다.
  - 실행 환경(의존성, 설정, 화면에 쓰는 데이터)이 바뀌었으면 재사용하지 않습니다.
  - 재사용하는 것: 검증 명령 결과, 리뷰 결과(바뀌지 않은 범위만), 탐색 결과, 화면 확인 결과
  - 재사용하지 않는 것: 리뷰 지적을 고친 뒤와 작업을 합친 뒤의 검증 명령, 원격 상태
  - 재사용했으면 그 사실과 원래 결과의 위치를 "수락"에 적습니다.
- **라우팅**: doc-writer와 Paseo pr-body를 강한 모델로 올립니다. 고정 사례로 품질이 유지된다고 확인되면 다시 낮춥니다. 대체 모델로 넘어갔으면 그 사실을 "시도"에 적습니다.
- 고칠 파일: run-ticket 4·5단계, `multi-ticket.md`, `extras/omp/config.yml`, `extras/omp/agents/doc-writer.md`, `extras/paseo/config.json`
- eval: 같은 지문에서 검증 명령을 다시 돌리지 않는지, 고친 뒤에는 다시 돌리는지

### P9. 바깥에 쓰는 일과 승인

- **대상**: set-brief와 set-ticket의 이슈 생성, run-ticket과 `multi-ticket.md`의 코멘트·close·본문 수정, push, PR 생성
- **절차**(설계 246~253행):
  1. 상태 파일에 작업 식별자, 대상, 승인한 내용의 지문을 `예정`으로 적습니다.
  2. 본문에 `<!-- gongbang-op:<식별자> -->`를 넣어 씁니다.
  3. 원격을 조회해 식별자와 내용이 일치하는지 본 뒤 `확인`으로 적습니다.
  4. 재개할 때 `예정`만 남아 있으면 원격을 먼저 조회합니다. 일치하는 것이 있으면 `확인`으로 적고, 없다고 확인되면 다시 대조한 뒤 쓰고, 그 밖에는 멈춥니다.
  5. 같은 식별자의 쓰기는 한 세션에서만 합니다.
  - set-ticket이 이미 하는 제목 대조는 식별자 대조로 바꿉니다.
- **승인**:
  - 바깥에 쓰는 일은 건별로 명시적으로 승인받습니다.
  - PR은 기준 브랜치, 코드 지문, 본문 해시를 승인 기록에 남기고 쓰기 직전에 대조합니다. 달라졌으면 쓰지 않고 다시 묻습니다.
  - "응", "좋아"처럼 무엇을 승인하는지 알 수 없는 답은 승인으로 치지 않습니다.
  - 기본 브랜치 병합은 따로 승인받습니다.
  - 사람에게 보여 줄 때는 조치가 필요한 항목을 맨 앞에 둡니다.
- **6단계**: PR 본문을 6단계 결정 **전에** 씁니다. 필수 작업이 `parked`면 6단계로 가지 않습니다. 사용자가 그 작업을 이번 범위에서 빼기로 정한 경우에만 진행하고, 뺀 사실을 PR 본문에 적습니다.
- 고칠 파일: `run-flow/references/{merge-stage,pr-stage}.md`, run-flow 6·7단계, set-brief 게시 절, set-ticket 5단계, run-ticket 6단계, `multi-ticket.md` 50·62행 부근
- eval: `예정`만 남은 채 재개하면 다시 쓰지 않고 조회부터 하는지, 승인 뒤 코드가 바뀌면 다시 묻는지, 애매한 답에 push하지 않는지

### P10. 피드백 루프 1: 앞 단계 재개와 판정 기준 (설계의 넣는 순서 1)

- **결함 보고**: 구현, 리뷰, 테스트 작성이 보고합니다. 조정자가 병렬 결과의 어긋남에서 직접 찾은 결함도 같은 경로로 다룹니다. 보고에는 막힌 완료 기준과, 명세 원문 인용이나 빠진 결정이 있어야 합니다. 원문이 두 가지로 읽히면 두 해석을 함께 적습니다.
- **판정 기준은 승인된 명세 하나입니다**: 조정자가 구현, 테스트, 검사를 명세 문장과 대조해 어긋난 쪽만 고치게 합니다. 명세가 답하지 않으면 재개합니다.
- **재개**:
  - 조정자가 결함이 처음 생긴 단계를 1~4 중에서 가립니다.
  - 1·2단계로 가는 결함은 사람이 확정합니다. 3·4단계는 그 단계의 역할을 다시 불러 자체 검증을 다시 거치게 합니다.
  - 개정된 부분에 기댄 수락만 `재수락 필요`로 표시합니다. 기댔는지 알 수 없으면 재사용을 보류합니다.
  - 시도 이력과 상한은 초기화하지 않습니다.
  - 자동 재개는 1회이고, 설정할 수 있는 시작값으로 둡니다. 같은 결함이 다시 나오거나 영향 범위를 모르면 사람에게 넘깁니다.
- `requirement-change.md`를 이 경로의 1단계 재개로 합칩니다.
- 고칠 파일: run-flow(새 reference 파일 하나), run-ticket 4·5단계, `multi-ticket.md` "질문"과 "실패", `extras/omp/AGENTS.md`
- eval: `명세 모호` 실패를 구현에 다시 맡기지 않고 3단계로 보내는지, 원문 인용이 없는 결함 보고는 재개하지 않는지

### P11. 피드백 루프 2: 기록만 하는 루프 (설계의 넣는 순서 2)

- **사람 정정**: 원문 그대로 "사람 정정"에 적고, 이후 재작업에 넘깁니다. 이번 결과에 필요한 정정은 바로 반영합니다. 앞으로도 적용할지 모호한 것만 흐름 끝에 한 번 묶어 묻고, "앞으로도"라고 답한 것만 변경 후보로 보냅니다.
- **게시 뒤 관찰**: 앞서 게시한 변경과 같은 코드 영역의 흐름을 열 때, 그 게시의 식별자로 원격을 조회합니다. 검사 결과, 사람의 리뷰, 병합이나 되돌림, 연결된 문제 보고를 기록하고, `관찰 없음`과 `조회 실패`를 나눠 적습니다. 원인 연결은 사람이 확인합니다. 자동으로 되돌리거나 다시 돌리지 않습니다.
- 고칠 파일: run-flow 0·6·7단계
- eval: 조회하지 못한 경우를 `관찰 없음`으로 적지 않는지

### P12. 피드백 루프 3: 흐름 변경과 지표 (설계의 넣는 순서 3)

- **변경 후보**:
  - 후보가 되는 조건: 서로 독립인 두 흐름에서 같은 원인이 확인됨, 사람의 지속 적용 요청, 중대한 누락 한 건(보안, 데이터 손실, 바깥 쓰기, 승인 우회)
  - 원인은 넷으로 가릅니다: 규칙 없음, 인계 누락, 지켜지지 않음, 리뷰 오류. 고치는 순서는 결정적 검사, 사례, 지시문입니다.
  - 바꿀 대상의 담당 역할이 후보를 만들고, 리뷰 역할이 기준 하나로 검토하고, 사람이 승인합니다. 조정자는 제안만 하고 스스로 채택하지 않습니다.
  - 상태 파일 "변경 후보"에 출처 흐름, 가설, 바꿀 것 하나, 기대하는 변화, 되돌릴 조건, 버전을 적습니다. 처리는 `채택/기각/보류`입니다.
  - 채택하면 dev-gongbang PR과 eval 사례로 반영합니다. 채택 뒤 미리 정한 구간에서 `유지/복귀/보류`로 닫습니다. 보류는 한 번만 하고, 같은 항목을 두 번 되돌렸으면 동결합니다.
- **검증자 교정**: 기준별로 기각된 지적과 게시 뒤 놓친 결함의 표본을 사람이 함께 읽고, 리뷰 지시를 바꿀지 정합니다.
- **고정 사례**: 재현되는 실패는 사람이 채택하면 eval 사례가 됩니다. 판정용 사례는 구현 역할에 보이지 않게 두고, 후보를 만드는 데 쓴 사례와 나눕니다.
- **지표**: `flow_metrics.py`가 상태 파일에서 설계 295~302행의 지표를 흐름별로 셉니다. 각 지표의 기록은 P5(검사 차단), P6(리뷰 지적, 독립성 실패), P7(시도, `parked`), P9(중복 쓰기), P10(결함 보고), P11(게시 뒤 결함)이 만듭니다. 지표는 원인을 찾는 단서로만 쓰고 목표로 삼지 않습니다.
- 고칠 파일: run-flow `status`, 새 스크립트(assert 자체 검사 포함), `assets/state-file.md`
- eval: 한 흐름의 사건만으로는 후보를 만들지 않는지(중대한 누락은 예외)
