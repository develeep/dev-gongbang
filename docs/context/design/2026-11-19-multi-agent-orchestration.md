# 멀티 에이전트 오케스트레이션 설계안

코딩 에이전트 여러 개로 요구사항 정리부터 게시까지 개발 흐름을 진행하는 방법을 정한 설계입니다. 이 문서를 읽으면 흐름의 단계, 역할마다 맡는 일과 권한, 결과를 수락하는 조건, 실패와 반복을 다루는 규칙을 알 수 있습니다.

## 이 문서를 읽는 법

- **독자**: 이 설계를 구현 계획으로 옮기는 에이전트나 사람입니다. 설계를 만든 대화는 몰라도 읽을 수 있게 썼습니다.
- **범위**: 무엇을 어떤 규칙으로 하는지만 정합니다. 어떤 파일과 도구로 구현할지는 읽는 쪽이 정합니다.
- **전제**: 코드는 버전 관리 도구로 관리하고, 결과를 올릴 원격 저장소가 있습니다. 그 밖의 도구는 전제하지 않습니다.
- **원칙 문서**: 규칙의 이유는 [원칙 문서](./2026-11-19-multi-agent-orchestration-principles.md)에 있습니다. 본문의 "(원칙 N)"은 그 문서의 번호입니다. 설계의 규칙과 원칙이 어긋나 보이면 한쪽을 고르지 말고 사용자에게 묻습니다.
- **규칙의 세기**는 둘로 나뉩니다.
  - 정해진 규칙: "~합니다"로 쓴 문장입니다. 그대로 따릅니다.
  - 시작값: 측정해서 정한 값이 아닌 숫자입니다. "시작값"으로 표시했습니다. 구현할 때 고칠 수 있는 설정으로 둡니다. 반복 3회와 동시 호출 10은 시작값이 아니라 사용자가 정한 값입니다.
- **문서에 없는 값**이 필요하면 지어내지 말고 사용자에게 묻습니다. 측정하거나 실행해 확인하지 않은 내용은 마지막 절 "확인하지 않은 것"에 모았습니다.
- **백틱으로 감싼 값**(`parked`, `미확인` 등)은 글자 그대로 씁니다. "정해진 값" 절에 모두 있습니다.

## 지켜야 할 결정

사용자가 정한 것입니다. 구현 계획에서 바꾸지 않습니다.

- 역할 하나는 한 가지 일만 맡고, 역할마다 통과 조건이 하나입니다. 그 결과를 완성하는 자체 검증(명세의 냉독 검증, 구현의 테스트)은 같은 역할에 둡니다.
- 테스트 작성은 테스트가 작업의 목적일 때만 따로 나눕니다.
- 호출이 늘어도 완성도가 먼저입니다.
- 모델 라우팅과 결과 재사용을 넣습니다. 예산은 두지 않습니다.
- 어떤 반복도 3회를 넘기지 않고, 상한은 중요한 것만 둡니다.
- 동시에 실행하는 호출은 10개까지 둡니다.
- 역할에 맡긴 뒤 기다리는 시간은 실행 환경의 타임아웃에 맡깁니다.
- 비공개 변경 내용을 다른 회사 모델에 넘겨도 됩니다.
- 흐름을 바꿀 때는 새로 더한 사례만 돌립니다. 모든 흐름이 지나는 경로를 바꿀 때만 관련된 기존 사례도 돌립니다.
- 구현 계획은 이 문서에 두지 않습니다.

## 용어

| 용어 | 뜻 |
|---|---|
| 흐름 | 요구사항 하나를 1단계부터 7단계까지 진행하는 한 번의 실행 |
| 사용자 | 흐름을 맡기고 승인하는 사람. 본문의 "사람"은 사용자를 가리킵니다 |
| 조정자 | 사용자와 대화하는 세션. 단계를 잇고, 역할을 부르고, 결과를 수락할지 정합니다 |
| 역할 | 조정자가 일 하나를 맡기는 에이전트의 종류. 구현, 리뷰 등 |
| 호출 | 역할을 한 번 부르는 것. 같은 역할을 여러 번 부를 수 있습니다 |
| 명세 | 3단계의 결과. 맥락 없는 작업자가 그것만 읽고 작업할 수 있는 지시서 |
| 작업 | 4단계에서 명세를 나눈 단위. 혼자 검증할 수 있는 크기입니다 |
| 완료 기준 | 작업이 끝났는지 판정하는 항목. 작업마다 여러 개 있습니다 |
| 통과 조건 | 역할의 결과가 맞는지 조정자가 판정하는 기준. 역할마다 하나입니다 |
| 자체 검증 | 역할이 자기 결과를 완성하려고 스스로 하는 확인 |
| 냉독 검증 | 명세를 처음 보는 독자에게 읽혀 잘못 읽히는 곳을 찾는 확인 |
| 수락 | 조정자가 역할의 결과를 받아들여 다음으로 넘기는 판정 |
| 결정적 검사 | 모델 없이 코드로 실행하는 검사. 같은 입력에 같은 결과가 나옵니다 |
| 검증 명령 | 타입 검사, 린트, 테스트처럼 대상 저장소가 정한 확인 명령 |
| 작업 공간 | 역할이 파일을 고치는 디렉터리. 병렬일 때 작업마다 따로 둡니다 |
| 코드 지문 | 작업 공간에 있는 코드 전체의 해시. 코드가 같은지 비교할 때 씁니다 |
| 리뷰 기준 | 리뷰가 보는 관점 하나. 버그, 규칙 위반, 불필요한 코드, 보안 |
| 독립 리뷰 | 구현을 실제로 수행한 모델과 다른 회사의 모델이 한 리뷰 |
| 바깥에 쓰는 일 | 게시, 이슈 생성, 코멘트처럼 원격에 남아 되돌려도 기록이 남는 일 |
| 상태 기록 | 대화 밖에 두는 흐름의 기록. 이것만 읽고 흐름을 이어 갈 수 있어야 합니다 |
| 시도 | 한 작업을 역할에 한 번 맡긴 것. 번호를 붙입니다 |
| 상한 | 반복할 수 있는 최대 횟수 |
| 완화·대체 | 테스트를 건너뛰거나, 타임아웃과 임계값을 조정하거나, 가짜 구현이나 대체 경로를 써서 통과시킨 것 |
| 고정 사례 | 흐름이 바르게 동작하는지 확인하려고 정해 둔 시험 사례 |
| 판정용 사례 | 고정 사례 가운데 변경을 채택할지 판정하는 데 쓰는 것. 구현 역할에 보이지 않게 둡니다 |
| 흐름 변경 | 역할, 지시문, 모델, 상한, 검사처럼 다음 흐름부터 적용되는 것을 바꾸는 일 |
| 변경 후보 | 흐름 변경으로 올릴지 검토하는 제안 |

## 정해진 값

| 쓰는 곳 | 값 | 뜻 |
|---|---|---|
| 역할의 결과 | `통과` / `실패` | 역할이 스스로 판단한 결과. 수락은 아닙니다 |
| 완료 기준 항목 | `충족` / `미충족` / `미확인` / `해당 없음(이유)` | `미확인`은 확인하지 못했다는 뜻이고 `충족`이 아닙니다 |
| 실패 분류 | `명세 모호` / `완료 기준 실패` / `일시적 오류` / `환경·설정` / `분류 불명` | "실패 처리" 절 |
| 시도의 결과 | `통과` / `실패` / `parked` | `parked`는 상한에 닿아 자동 진행을 멈추고 보관한 상태 |
| 수행한 모델 | 모델 이름 / `확인 불가` | `확인 불가`면 독립 리뷰로 치지 않습니다 |
| 리뷰 지적의 판정 | `수용` / `기각(사유)` / `범위 밖` | "피드백 루프" 절 |
| 바깥 쓰기의 상태 | `예정` / `확인` | `예정`은 쓰기 전에 적고, `확인`은 원격에서 본 뒤에 적습니다 |
| 수락의 효력 | `재수락 필요` | 명세가 개정돼 다시 수락해야 하는 작업 |
| 변경 후보의 처리 | `채택` / `기각` / `보류` | |
| 채택한 변경의 판정 | `유지` / `복귀` / `보류` | |

## 구조

조정자 하나가 흐름을 이끌고, 역할마다 한 가지 일을 맡습니다. 역할끼리는 직접 주고받지 않고 조정자를 거칩니다.

```
사용자 ── 조정자 ──┬─ 명세 작성
                   ├─ 구현 ─────── (병렬일 때 작업 공간을 나눔)
                   ├─ 테스트 작성 ── (테스트가 작업의 목적일 때만)
                   ├─ 화면 확인
                   ├─ 리뷰 ─────── (기준 하나에 호출 하나, 다른 회사 모델)
                   └─ 게시 문서 작성
        상태 기록 (대화 밖)   결정적 검사 (코드)
```

- 조정자는 사용자와 대화하는 세션입니다. 단계를 잇고, 결과를 수락할지 정하고, 바깥에 쓰는 일을 실행합니다. 조정 전용 에이전트를 따로 두지 않습니다(원칙 2).
- 조건이 분명한 판정은 코드가 합니다. 모델은 판단이 필요한 자리에만 씁니다(원칙 1, 14).

## 단계

| 단계 | 하는 일 | 끝나는 조건 |
|---|---|---|
| 1. 요구사항 정리 | 받은 자료에서 요구사항과 범위를 뽑습니다 | 범위가 문서로 남음 |
| 2. 문제 구체화 | 목적, 범위, 하지 않을 것, 완료 판단 기준을 사용자와 확정합니다 | 사용자가 기록을 확정 |
| 3. 명세 작성 | 맥락 없는 작업자가 그것만 읽고 작업할 수 있는 명세를 씁니다 | 냉독 검증을 통과한 명세 |
| 4. 작업 분할 | 조정자가 혼자 검증할 수 있는 작업으로 나누고, 의존 순서와 필수·선택을 정합니다 | 작업마다 완료 기준, 수정 범위, 주고받는 것이 적힘 |
| 5. 구현과 검증 | 작업마다 구현(그 작업의 테스트 포함), 수락 검사, 리뷰를 합니다 | 필수 작업이 모두 수락되고 합친 결과가 검증됨 |
| 6. 게시 결정 | 결과, 남은 문제, 게시할 글을 보여 주고 사용자가 고릅니다 | 게시, 고치기, 멈추기 중 하나 |
| 7. 게시 | 승인한 내용을 바깥에 올립니다 | 원격에서 결과를 확인 |

순서가 미리 정해진 흐름이므로 모델이 다음 단계를 고르지 않습니다(원칙 1). 앞 단계로 돌아가는 길은 "피드백 루프"의 앞 단계 재개 하나뿐이고, 근거가 있을 때만 열립니다.

## 역할

| 역할 | 맡는 일 | 통과 조건 | 자체 검증 | 쓰기 권한 |
|---|---|---|---|---|
| 조정자 | 흐름의 진행, 작업 분할, 수락 판정 | (사용자가 판정합니다) | 결정적 검사 실행 | 상태 기록, 병합, 바깥 쓰기 |
| 명세 작성 | 명세 | 처음 보는 독자가 이것만 읽고 무엇을 만들고 어떻게 확인할지 잘못 읽지 않는다 | 맥락 없는 독자에게 읽혀 보는 냉독 검증 | 초안 파일만 |
| 구현 | 완료 기준을 만족하는 코드 변경과 그것을 확인하는 테스트 | 이 작업의 완료 기준을 만족한다 | 완료 기준 확인, 테스트 작성과 실행 | 맡은 작업 공간의 허용된 경로. 기존 테스트와 판정용 사례는 제외 |
| 어려운 구현 | 앞선 시도가 실패했거나 처음부터 어렵다고 판단한 작업의 코드 변경 | 구현과 같음 | 실패 재현과 원인 정리, 완료 기준 확인 | 구현과 같음 |
| 테스트 작성 | 테스트가 목적인 작업의 테스트 코드, 틀렸다고 판정된 기존 테스트의 수정 | 명세의 기준을 빠짐없이 시험한다 | 테스트 실행 | 테스트 파일만 |
| 화면 확인 | 항목별 화면 확인 결과 | 요구한 항목마다 화면에서 본 근거가 있다 | 없음 | 없음 |
| 리뷰 | 기준 하나에 대한 지적 목록 | 맡은 범위를 그 기준으로 모두 보았고, 어긋나는 곳이 있으면 근거와 함께 짚었다 | 없음 | 없음 |
| 게시 문서 작성 | 변경을 설명한 글. 게시 결정 전에 씁니다 | 글이 실제 변경과 맞는다 | 없음 | 없음 |

- 역할 하나는 한 가지 일만 맡습니다. 역할마다 통과 조건이 하나여야 하고, 둘이면 역할이나 호출을 나눕니다(원칙 3).
- 구현은 자기 작업의 테스트를 함께 씁니다. 그 테스트는 "완료 기준을 만족한다"는 것의 근거이므로 같은 통과 조건에 속합니다. 구현이 자기 작업 안에서 테스트부터 쓰는 것도 구현의 일입니다. 테스트 작성 역할은 작업 분할에서 테스트 자체를 결과로 정한 작업에만 부릅니다. 기존 코드에 테스트를 보강하는 작업이 그 예입니다.
- 구현은 새 테스트를 더할 수 있지만 기존 테스트, 다른 역할이 먼저 쓴 테스트, 판정용 사례는 고칠 수 없습니다. 고쳐야 한다고 판단하면 고치지 않고 근거와 함께 보고합니다. 자기를 채점하는 것을 스스로 고치면 통과가 의미를 잃습니다(원칙 22). 조정자가 기존 테스트가 틀렸다고 판정하면 테스트 작성 역할이 고치고 조정자가 수락합니다.
- 명세 작성의 냉독 검증, 구현의 완료 기준 확인, 어려운 구현의 원인 정리는 그 결과를 완성하는 과정이므로 나누지 않습니다. 냉독을 새 컨텍스트의 독자에게 맡기더라도 고치고 완성하는 책임은 명세 작성에 남습니다.
- 리뷰는 기준마다 따로 부릅니다. 항상 필수인 기준은 버그, 규칙 위반, 불필요한 코드 셋입니다. 인증, 권한, 결제, 개인정보를 다루는 변경에는 보안 기준이 필수로 더해집니다. 한 번의 호출에 기준을 섞지 않습니다(원칙 3, 4).
- 역할을 정의할 때는 통과 조건을 서술문 한 문장으로 적습니다. 한 문장으로 적을 수 없으면 역할을 나눕니다.
- 쓰기 권한은 지시문이 아니라 도구 설정으로 제한합니다. 리뷰와 화면 확인에는 쓰기 도구를 주지 않고, 바깥 쓰기는 조정자만 합니다(원칙 14).

## 인계

### 조정자가 넘기는 것

- 명세 전문과 작업 전문. 요약하지 않습니다(원칙 6)
- 이미 내린 결정과 그 근거
- 앞선 작업의 산출물
- 작업 공간의 절대 경로와 수정해도 되는 경로
- 규칙 문서의 위치와 검증 명령. 역할은 넘겨받지 않은 규칙을 모릅니다
- 시도 번호와 상한 (예: 3회 중 2번째)
- 다시 맡길 때는 이전 실패 분류, 충족하지 못한 완료 기준, 리뷰 지적
- 다른 회사 모델에 넘길 때는 그 일에 필요한 범위만 넘기고 비밀값, 불필요한 개인정보, 원문 로그는 뺍니다. 비공개 변경 내용을 넘기는 것 자체는 허용합니다
- 비밀값을 빼는 것이 전문으로 넘기는 것보다 먼저입니다. 역할이 읽을 수 있는 파일의 범위에도 같은 규칙을 적용합니다. 비밀값을 빼고는 일을 맡길 수 없으면 맡기지 않고 멈춰 사용자에게 넘깁니다

### 역할이 돌려주는 것

| 항목 | 값 |
|---|---|
| 결과 | `통과` / `실패` |
| 시도 번호 | 받은 시도 번호 그대로 |
| 완료 기준 항목별 상태 | `충족` / `미충족` / `미확인` / `해당 없음(이유)`. 항목을 지우지 않습니다(원칙 7) |
| 항목별 근거 | 실행한 명령과 출력 요지, 또는 관찰한 것 |
| 바꾼 것 | 파일 목록, 브랜치와 커밋 |
| 수행한 모델 | 실제로 돈 모델. 모르면 `확인 불가` |
| 실패했으면 | 실패 분류와 원본 오류 발췌 |
| 완화·대체로 처리한 것 | 건너뛴 테스트, 조정한 타임아웃과 임계값, 가짜 구현, 대체 경로(원칙 8) |
| 범위 밖 문제 | 발견했지만 고치지 않은 것 |

맥락은 글로 넘기고, 위 표에서 판정에 쓰는 값(결과, 항목 상태, 실패 분류)만 정해진 목록에서 고릅니다(원칙 6).

## 수락

역할이 보고한 `통과`는 참고입니다. 조정자는 결정적 검사, 조정자의 판정, 필수 리뷰("리뷰" 절)가 모두 통과했을 때 수락합니다(원칙 5). 검사만 통과한 결과는 아직 수락된 것이 아닙니다. 코드 변경이 아닌 결과(명세, 작업 목록, 화면 확인, 게시 글)는 그 단계의 끝나는 조건과 필수 항목을 확인한 뒤에 다음 단계로 넘깁니다.

**결정적 검사 (코드로 실행)**

- 보고된 브랜치와 커밋이 있고, 작업을 시작한 지점에서 이어졌는지
- 시도 번호가 이번 차례와 같은지. 이전 시도의 결과는 받지 않습니다
- 바뀐 파일이 모두 허용된 경로 안인지. 기존 테스트와 판정용 사례가 바뀌지 않았는지
- 맡기지 않은 작업 공간이 실행 전과 같은지
- 검증 명령(타입 검사, 린트, 테스트)이 통과하는지

**조정자의 판정**

- 근거 없는 항목이 `충족`으로 적혀 있지 않은지
- `미확인`과 완화·대체 처리가 사람이 볼 목록에 올라갔는지
- `미충족`이 있거나 필수 항목이 `미확인`이면 수락하지 않습니다
- 어느 명세 버전을 기준으로 수락했는지 기록합니다

검사 결과에 따라 처리가 갈립니다.

- 범위를 벗어난 변경(허용 경로 밖의 파일, 기존 테스트나 판정용 사례, 맡기지 않은 작업 공간)이 있으면 다시 맡기지 않고 멈춰 사용자에게 알립니다. 자동으로 되돌리지 않습니다. 되돌리면서 다른 변경을 지울 수 있기 때문입니다.
- 검증 명령이 실패했거나 `미충족`이 있으면 `완료 기준 실패`로 보고 "실패 처리"대로 다시 맡깁니다.
- 시도 번호가 다르거나 보고된 커밋이 없으면 그 결과를 받지 않고, 작업 공간을 조회해 한 일을 확인합니다.

## 실패 처리

분류는 종료 코드, 타임아웃, 요청 한도 응답, 권한 오류처럼 관찰할 수 있는 신호로 먼저 하고, 신호가 모호할 때만 모델이 판단합니다(원칙 9).

| 실패 분류 | 뜻 | 처리 |
|---|---|---|
| `명세 모호` | 명세나 작업이 모호하거나 너무 큼 | 구현을 다시 맡기지 않습니다. 원문 인용이 붙은 결함이면 앞 단계 재개로 보내고, 작업이 너무 큰 것이면 다시 나누자고 제안합니다 |
| `완료 기준 실패` | 구현이 기준을 만족하지 못함 | 실패 보고를 넘겨 다시 맡깁니다. 구현으로 시작한 작업은 세 번째 시도를 어려운 구현에 맡기고, 어려운 구현으로 시작한 작업은 같은 역할로 이어 갑니다. 3회에 닿으면 `parked` |
| `일시적 오류` | 한도, 일시 장애, 도구 실패 | 부작용이 없다고 확인되면 같은 역할로 다시 맡깁니다. 이 재시도도 3회 안에 셉니다. 다시 실패하면 멈춰 사용자에게 넘깁니다 |
| `환경·설정` | 누락된 설정, 권한, 의존성 | 구현을 다시 맡기지 않고 사람에게 넘깁니다 |
| `분류 불명` | 위에 들지 않거나 판정할 수 없음 | 멈춥니다 |

응답 없이 끝난 역할은 실패로 단정하지 않습니다. 작업 공간과 브랜치를 먼저 조회해 한 일을 확인한 뒤 이어 갈지 새 시도로 할지 정합니다(원칙 11).

## 상한

| 반복 | 상한 | 값의 성격 | 닿으면 |
|---|---|---|---|
| 같은 일을 다시 맡기기 | 최초 포함 3회 | 사용자 결정 | 그 작업을 `parked`로 둡니다. 그 작업에 기대는 작업은 시작하지 않고, 기대지 않는 작업은 계속합니다 |
| 앞 단계 재개 | 자동 1회 | 시작값 | 사용자가 새 근거를 보고 정합니다 |
| 동시 호출 | 10 | 사용자 결정 | 넘는 호출은 기다립니다 |

- 어떤 반복도 3회를 넘기지 않습니다. 표에 없는 반복도 같습니다.
- 세는 단위는 "한 작업을 같은 목적으로 역할에 맡긴 횟수"입니다. 목적은 구현, 리뷰 기준 하나, 게시 결정의 "고치기", 명세 작성으로 나눕니다. 최초 호출, 실패 뒤의 재시도, 일시적 오류 재시도, 판정 재확인의 재리뷰를 모두 셉니다. 3회 밖에 덧붙는 호출은 없습니다.
- 세 번째 시도가 통과하면 수락하고, 실패하면 `parked`로 둡니다.
- 횟수는 앞 단계 재개 뒤에도, `parked`를 재개할 때도 초기화하지 않습니다. `parked`인 작업은 사용자가 추가 시도를 허용했을 때만 다시 맡깁니다.
- 동시 호출은 동시에 실행 중인 모든 역할 호출입니다. 구현, 리뷰, 냉독 독자가 모두 듭니다.
- `parked`는 상한에 닿아 자동 진행을 멈춘 작업의 표시입니다. 버리지 않고 사유, 마지막 시도 번호, 산출물 위치를 상태 기록에 남깁니다(원칙 10).
- 시작값은 측정값이 아닙니다. 시도 기록이 쌓이면 조정하되 3회를 넘기지 않습니다.
- 역할에 맡긴 뒤 기다리는 시간은 따로 정하지 않고 실행 환경의 타임아웃에 맡깁니다.

## 리뷰

- **순서**: 결정적 검사가 통과한 뒤에만 리뷰를 부릅니다. 코드로 걸러지는 문제에 모델 호출을 쓰지 않습니다.
- **독립성**: 리뷰는 구현을 실제로 수행한 모델과 다른 회사의 모델로 합니다. 구현이 대체 모델로 넘어갔을 수 있으므로, 구현 보고의 "수행한 모델"과 리뷰를 실제로 수행한 모델을 비교합니다. 여러 모델이 구현한 변경을 함께 리뷰할 때는 그 범위를 구현한 모든 모델과 다른 회사여야 합니다. 같은 회사였거나 어느 한쪽을 확인할 수 없으면 독립 리뷰로 치지 않습니다(원칙 13). 다른 회사 모델을 쓰는 것은 설계상의 선택이고, 효과는 측정하지 않았습니다.
- **지시**: 기준 하나, 볼 범위, 명세를 넘기고 반대 근거와 재현 방법을 찾으라고 합니다.
- **지적의 수용**: 재현되거나 코드와 규칙의 원문 근거가 있는 지적만 고칩니다. 범위 밖 지적은 고치지 않고 남깁니다.
- **고친 뒤**: 검증 명령 전체를 다시 돌리고, 바뀐 범위를 다시 리뷰합니다.
- **유효성**: 리뷰마다 본 코드의 지문과 본 범위를 기록합니다. 지문이 달라졌으면 이전 리뷰는 바뀌지 않은 범위에만 유효하고, 바뀐 범위의 재리뷰가 끝나야 지금 코드에 대한 리뷰가 됩니다. 파일이 그대로여도 그 파일이 기대는 작업 사이의 계약이 바뀌었으면 바뀐 범위로 봅니다. 어디가 바뀌었는지 가를 수 없으면 전체를 다시 리뷰합니다.
- **필수**: 필수 기준의 리뷰가 응답하지 않거나, 결과를 읽을 수 없거나, 독립이 아니었거나, 상한에 닿으면 통과가 아닙니다. 그 작업은 수락하지 않고 사용자에게 넘깁니다(원칙 12). 사용자의 승인만으로 빠진 리뷰를 덮지 않습니다. 사용자가 그 기준으로 직접 검토하고 그렇게 기록한 경우에만 대신합니다.
- **보안**: 인증, 권한, 결제, 개인정보를 다루는 변경은 보안 기준의 리뷰가 필수입니다. 독립성, 재리뷰, 필수 규칙이 다른 기준과 같이 적용됩니다.

## 사람 승인

| 구분 | 대상 |
|---|---|
| 명시적으로 승인받음 | 문제 구체화의 확정, 병렬 실행 계획, 바깥에 쓰는 일 전부(게시, 이슈 생성, 코멘트) |
| 묶어서 한 번에 확인 | 저장 위치, 브랜치 이름, 흐름 문서의 커밋 |
| 승인 항목으로 올림 | 완화·대체로 처리한 것, 선택 항목의 `미확인`, 건너뛴 선택 작업, 사용자가 대신 검토한 리뷰 |

- 바깥에 쓰는 일을 승인하면 그때의 대상과 내용을 기록합니다. 게시면 기준 브랜치, 코드 지문, 게시할 글을 기록합니다. 쓰기 직전에 코드로 대조해, 달라졌으면 쓰지 않고 다시 묻습니다(원칙 16).
- 필수 작업이 `parked`면 6단계로 가지 않습니다. 사용자가 그 작업을 이번 범위에서 빼기로 정한 경우에만 진행하고, 뺀 사실을 게시할 글에 적습니다.
- 병합은 사람이 정하고 조정자가 실행합니다. 병렬 실행 계획의 승인은 작업 브랜치 안의 병합까지만 포함합니다. 기본 브랜치로의 병합과 게시는 따로 승인받습니다.
- "응", "좋아"처럼 무엇을 승인하는지 알 수 없는 답은 승인으로 치지 않습니다.
- 사람에게 보여 줄 때는 조치가 필요한 항목을 맨 앞에 둡니다.

## 바깥에 쓰는 일

게시, 이슈 생성, 코멘트처럼 되돌려도 기록이 남는 일에 적용합니다(원칙 11).

1. 쓰기 전에 상태 기록에 작업 식별자, 대상, 승인한 내용의 지문을 `예정`으로 적습니다. 식별자는 승인한 대상과 내용에 묶인 고유한 값입니다. 이 기록에 실패하면 쓰지 않습니다.
2. 쓴 것에는 그 식별자를 넣습니다. 원격이 같은 식별자의 중복 실행을 막아 주면 그 기능을 씁니다. 제목처럼 다른 작업과 겹칠 수 있는 값만으로는 찾지 않습니다.
3. 쓴 뒤에는 원격을 조회해 식별자와 내용이 일치하는지 본 다음 `확인`으로 적습니다. 응답이 성공이었다는 것만으로 `확인`으로 적지 않습니다.
4. 재개할 때 `예정`만 있고 `확인`이 없으면 원격을 먼저 조회해 셋 중 하나로 가릅니다.
   - 식별자와 내용이 일치하는 것이 있음: 다시 쓰지 않고 `확인`으로 적습니다.
   - 없다는 것이 확인됨: 아직 쓰지 않은 것입니다. 대상과 내용이 승인한 것과 같은지 다시 대조한 뒤에 씁니다.
   - 조회할 수 없거나, 일치하지 않는 것이 있거나, 판단할 수 없음: 다시 쓰지 않고 멈춥니다.
5. 같은 식별자의 쓰기는 한 번에 한 곳에서만 실행합니다. 두 세션이 같은 흐름을 동시에 재개하지 않습니다.

## 병렬 실행

- 서로 기다리지 않는 작업이 둘 이상일 때만 병렬로 돌립니다. 그렇지 않으면 차례로 합니다(원칙 17).
- 나누기 전에 작업끼리 주고받는 것(이름, 필수·선택 항목, 상태값, 오류 형식)을 정해 관련 작업에 같은 문구로 적습니다. 구현 중 바꿔야 하면 작업자가 고치지 않고 조정자에게 돌려보냅니다.
- 작업마다 수정해도 되는 경로를 정합니다. 여러 작업이 건드려야 하는 공유 진입점(등록, 공통 스키마, 설정)은 한 작업에만 주거나 통합 작업에 둡니다.
- 작업자마다 작업 공간을 나눕니다. 병합은 조정자만 합니다.
- 합칠 때마다 검증 명령을 다시 돌리고, 모두 합친 뒤 명세의 확인 기준을 전체에 대해 확인합니다. 개별 통과는 전체 통과가 아닙니다.
- 다른 작업을 막는 작업은 수락된 뒤에 뒤 작업을 시작합니다. 수락에는 필수 리뷰가 포함됩니다. 결함 위에 뒤 작업이 쌓이면 고칠 범위가 커집니다.
- 작업마다 필수인지 선택인지 정합니다. 필수 작업이 실패하면 그 결과에 기대는 작업을 진행하지 않습니다. 선택 작업은 빠졌다는 사실과 영향을 보고에 적을 때만 건너뜁니다. 성공한 작업의 결과는 보존하고 실패한 작업만 다시 돌립니다.
- 병렬로 나온 결과가 서로 어긋나면 조정자가 명세를 기준으로 판정합니다. 명세가 답하지 않으면 앞 단계 재개로 보냅니다.

## 상태 기록

대화 밖에 두고, 생긴 때에 바로 적습니다. 이 기록만 읽고 이어 갈 수 있어야 합니다(원칙 15).

| 기록 | 내용 |
|---|---|
| 진행 | 현재 단계, 멈춘 이유와 이어 가는 방법 |
| 결과물 | 요구사항, 명세, 작업 목록, 브랜치, 시작 지점 |
| 결정 | 사용자 답, 구현 중 정한 것과 근거, 걸리는 작업 |
| 시도 | 작업, 역할, 수행한 모델(대체 모델로 넘어갔으면 그 사실), 시도 번호와 상한, 결과(`통과` / `실패` / `parked`), 실패 분류. `parked`면 사유와 산출물 위치 |
| 수락 | 작업별로 수락한 명세 버전, 검사 결과, 리뷰 기록의 위치. 결과를 재사용했으면 그 사실과 원래 결과의 위치 |
| 리뷰 | 기준별 지적과 고침 여부, 수행한 모델, 리뷰가 본 코드 지문과 범위, 사용자가 대신 검토한 리뷰 |
| 승인 | 승인한 대상과 내용. 게시면 기준 브랜치, 코드 지문, 게시할 글 |
| 바깥 쓰기 | 작업 식별자, 대상, 승인한 내용의 지문, `예정` 또는 `확인`, 결과 위치 |
| 명세 버전 | 명세와 작업 목록의 지문, 개정 사유, `재수락 필요`인 작업 |
| 사람 정정 | 사람이 고치거나 거부한 것의 원문, 이번만인지 앞으로도인지 |
| 판정 기록 | 리뷰 지적별 `수용` / `기각(사유)` / `범위 밖`, 결함 보고와 판정 재확인의 결과 |
| 게시 뒤 관찰 | 게시한 것의 검사 결과, 사람의 리뷰, 병합이나 되돌림, 연결된 문제 보고 |
| 변경 후보 | 출처 흐름, 원인 분류, 가설, 바꿀 것 하나, 기대하는 변화, 되돌릴 조건, 처리 결과(`채택` / `기각` / `보류`), 채택 뒤의 판정(`유지` / `복귀` / `보류`) |

- 사실의 출처는 하나씩입니다. 코드와 병합은 버전 관리, 게시와 이슈는 원격, 진행과 결정은 상태 기록을 따릅니다. 서로 어긋나면 다음 단계로 가지 않고 대조합니다.
- 비밀값과 원문 로그는 적지 않습니다.
- 형식은 사람이 읽을 수 있는 글이면 됩니다. 저장소나 큐가 필요해지는 것은 여러 흐름을 동시에 조회해야 할 때입니다(원칙 2).
- 수락, 승인, 시도 결과처럼 이어 가는 데 필요한 기록을 남기지 못했으면 그 단계를 끝난 것으로 치지 않고 멈춥니다(원칙 12).

## 지표

상태 기록에서 코드로 셉니다. 모델은 옮겨 적고 설명만 합니다(원칙 18).

- 작업 수, 첫 시도에 통과한 작업 수, 어려운 구현으로 올라간 작업 수, `parked` 수
- 리뷰 기준별 지적 수와 고친 수
- 리뷰가 같은 회사 모델로 돌아 독립 리뷰로 치지 못한 횟수
- 사람이 개입한 횟수와 사유
- 호출 수와 사용량, 수락한 결과 하나당 든 사용량, 재사용한 결과의 수
- 흐름을 시작해 수락하기까지 걸린 시간
- 중복으로 실행된 바깥 쓰기 수, 권한과 결정적 검사에 막힌 횟수
- 결함 보고 수와 기각된 수, 리뷰 지적의 수용과 기각 수, 게시 뒤 발견된 결함 수

지표는 원인을 찾는 단서로만 씁니다. 목표로 삼으면 첫 시도 통과율을 올리려고 완료 기준이 느슨해지는 식으로 숫자만 좋아집니다(원칙 22).

흐름마다 따로 봅니다. 표본이 적어 평균은 의미가 없습니다.

## 피드백 루프

구현 재시도, 리뷰 지적 수정과 재리뷰, 게시 결정의 "고치기"는 모두 같은 단계에서 같은 결과를 다시 만드는 루프입니다. 이 절은 세 방향의 루프를 더합니다: 앞 단계로 돌아가는 길, 검증 쪽이 틀렸는지 가리는 길, 다음 흐름으로 이어지는 길. 근거 자료는 [원칙 문서](./2026-11-19-multi-agent-orchestration-principles.md)의 "피드백 루프 관련 자료"에 있습니다.

두 가지를 지킵니다. 작업을 고치는 루프와 흐름을 고치는 루프를 섞지 않습니다. 흐름 사이에서는 기록만 자동으로 하고, 바꾸는 일은 사례 확인과 사람 승인을 거쳐 한 번에 하나만 합니다(원칙 21).

### 루프 목록

| 루프 | 신호 | 판정 | 바뀌는 것 | 멈춤 |
|---|---|---|---|---|
| 역할 안 자체 검증 (같은 단계 안) | 실행 결과, 냉독 독자의 오독 | 그 역할. 수락은 아닙니다 | 그 결과 | 상한 3회 |
| 수락 재작업 (같은 단계 안) | 결정적 검사 실패, 리뷰 지적 | 조정자와 코드 | 같은 결과 | 상한 3회. 닿으면 `parked` |
| 앞 단계 재개 | 원문 인용이 붙은 결함 보고 | 조정자가 결함이 처음 생긴 단계를 가립니다. 결정이 바뀌면 사람이 확정합니다 | 그 단계의 결과, 그것에 기댄 수락의 효력 | 자동 1회. 같은 결함이 다시 나오거나 영향 범위를 모르면 사람 |
| 판정 재확인 | 명세 인용과 관찰 결과로 된 반례 | 조정자의 대조. 남으면 독립 리뷰 1회 | 틀린 쪽(구현, 테스트, 검사) | 1회. 반례가 없으면 열지 않습니다 |
| 사람 정정 보존 | 사람이 고치거나 거부한 것 | 이번만인지 앞으로도인지는 사람 | 결정 기록. "앞으로도"는 변경 후보 | 재검증과 필요한 재승인 |
| 게시 뒤 관찰 | 게시한 것의 검사 결과, 사람 리뷰, 되돌림, 문제 보고 | 조정자가 기록, 원인 연결은 사람 | 관찰 기록. 새 흐름의 입력이나 변경 후보 | 기록하면 끝. 자동 행동 없음 |
| 검증자 교정 | 기준별 기각된 지적, 게시 뒤 놓친 결함 | 사람의 표본 검토 | 리뷰 기준의 변경 후보 | 후보를 채택하거나 기각 |
| 변경 후보와 흐름 변경 | 두 흐름에서 확인된 같은 원인, 지속 적용 요청, 중대한 누락 한 건 | 고정 사례, 독립 리뷰, 사람 승인 | 다음 흐름의 검사, 인계, 사례, 지시문, 상한 가운데 하나 | 유지, 복귀, 보류 가운데 하나로 닫음 |

### 적용 지점과 장단점

**1. 앞 단계 재개** (3~6단계의 실패 처리, 병렬 실행, 수락)

- 방안
  - 구현, 리뷰, 테스트 작성 역할이 결함을 보고합니다. 조정자가 병렬 결과의 어긋남에서 직접 발견한 결함도 같은 경로로 다룹니다. 보고에는 막힌 완료 기준과, 명세 원문 인용이나 명세에 빠진 결정이 무엇인지가 있어야 합니다. 원문이 두 가지로 읽히면 두 해석을 함께 적습니다.
  - 조정자가 결함이 처음 생긴 단계를 엽니다. 요구사항을 잘못 뽑았으면 1, 의도가 정해지지 않았으면 2, 확정된 의도를 명세가 잘못 옮겼으면 3, 분할이나 작업 사이 계약만 틀렸으면 4입니다.
  - 1·2단계로 가는 결함은 사람이 확정합니다. 3·4단계는 그 단계의 역할을 다시 불러 자체 검증을 다시 거칩니다.
  - 재개는 코드를 되돌리는 일이 아니라 수락의 효력을 다시 확인하는 일입니다. 개정된 부분에 기댄 수락만 `재수락 필요`로 표시하고, 기댔는지 알 수 없으면 재사용을 보류합니다. 시도 이력과 상한은 초기화하지 않습니다.
- 장점: 구현을 다시 시켜도 풀리지 않는 문제를 고치고, 영향 없는 작업은 살립니다. 구현이 모호한 부분을 임의로 메우는 일을 막습니다.
- 단점과 막는 장치
  - 이미 수락한 작업을 다시 검증하는 비용과 지연이 듭니다.
  - 어려운 작업을 명세 탓으로 넘기는 회피 경로가 됩니다. 원문 인용을 필수로 하고, 기각된 보고의 수를 봅니다.
  - 명세가 계속 흔들립니다. 자동 재개는 1회이고, 상한을 초기화하지 않아 재개가 상한을 돌아가는 길이 되지 않습니다.

**2. 판정 재확인** (5단계의 수락과 리뷰)

- 방안
  - 판정의 기준은 승인된 명세 하나입니다. 테스트와 구현이 어긋나면 조정자가 명세 문장과 대조해 어긋난 쪽만 고치게 하고, 명세가 답하지 않으면 앞 단계 재개로 보냅니다.
  - 검사나 리뷰가 맞는 결과를 거절했다는 반례가 있을 때만, 다른 회사 모델의 리뷰를 기준 하나로 한 번 더 부릅니다. 이 호출도 그 기준의 3회 안에 셉니다.
  - 구현 역할은 기존 테스트와 판정용 사례를 고칠 수 없게 권한으로 막습니다. 구현이 새로 쓴 테스트가 기준을 제대로 시험하는지는 리뷰가 봅니다. 테스트만 통과시키는 특수 처리는 "불필요한 코드" 리뷰에서 봅니다.
- 장점: 맞는 구현을 틀린 테스트에 맞춰 망가뜨리는 일과, 두 역할이 서로를 고치려 오가는 일을 줄입니다.
- 단점과 막는 장치
  - 원하는 판정이 나올 때까지 다시 부르면 수락이 무력해집니다. 반례 없이는 열지 않고, 반례 하나에 한 번만 부릅니다.
  - 명세와의 대조도 모델 판단이라 틀릴 수 있습니다. 가를 수 없으면 멈춰 사용자에게 넘깁니다.

**3. 사람 정정 보존** (2·6단계의 사람 승인, `parked`의 재개)

- 방안
  - 사람이 고치거나 거부한 것을 원문 그대로 기록하고 이후 재작업에 넘깁니다.
  - 이번 결과에 필요한 정정은 바로 반영합니다. 앞으로도 적용할지가 모호한 정정만 흐름 끝에 묶어 한 번 묻습니다. "앞으로도"라고 답한 것만 변경 후보가 됩니다.
  - `parked`는 멈춘 원인이 풀렸다는 근거가 있고 사용자가 추가 시도를 허용했을 때 해당 검사부터 재개합니다. 같은 근거로 자동 재개하지 않습니다.
- 장점: 사용자의 수정이 대화에만 남아 사라지거나 `parked`가 방치되는 일을 줄입니다.
- 단점과 막는 장치
  - 질문이 늘어 승인 피로가 생깁니다. 묶어서 한 번 묻습니다.
  - 한 번의 선호가 규칙으로 굳습니다. "이번만"은 규칙으로 저장하지 않습니다.

**4. 게시 뒤 관찰** (7단계 뒤)

- 방안: 앞서 게시한 변경과 같은 코드 영역을 다루는 흐름을 열 때, 조정자가 그 게시의 작업 식별자로 원격을 조회해 검사 결과, 사람의 리뷰, 병합이나 되돌림, 연결된 문제 보고를 기록합니다. 사용자가 원인 연결을 확인한 뒤 제품 문제는 새 흐름으로, 수락 절차의 문제는 변경 후보로 보냅니다.
- 장점: 이 설계에서 실제 결과를 보는 유일한 신호입니다. 리뷰가 놓친 결함을 알 수 있는 출처입니다.
- 단점과 막는 장치
  - 신호가 늦고, 엉뚱한 흐름에 원인을 돌릴 수 있습니다. 원인 연결은 사람이 확인합니다.
  - 보고가 없다는 것을 성공으로 읽을 수 있습니다. 조회했는데 보고가 없으면 "관찰 없음"으로, 조회하지 못했으면 "조회 실패"로 나눠 적습니다.
  - 자동으로 되돌리거나 다시 돌리면 사람 승인을 건너뜁니다. 기록만 합니다.

**5. 검증자 교정** (리뷰, 지표)

- 방안: 리뷰 지적마다 `수용` / `기각(사유)` / `범위 밖`을 남깁니다. 흐름 사이에 사람이 기준별로 기각된 지적과 게시 뒤 놓친 결함의 표본을 함께 읽고, 리뷰 지시를 고칠지 정합니다. 고칠 때는 다른 흐름 변경과 같은 확인과 승인을 거칩니다.
- 장점: 잡음 지적이 줄어 사람이 볼 항목이 줄고, 다른 회사 모델의 리뷰가 실제로 결함을 더 잡는지 가릴 재료가 생깁니다.
- 단점과 막는 장치
  - 기각 수만 줄이면 리뷰가 소극적이 되어 결함을 놓칩니다. 기각된 지적과 놓친 결함을 반드시 함께 봅니다.
  - 표본이 적어 판단이 흔들립니다. 리뷰 기준은 같은 원인이 두 흐름에서 확인된 뒤에 바꿉니다. 중대한 누락과 사용자의 지속 적용 요청은 한 건으로도 후보가 됩니다("6. 변경 후보와 흐름 변경").

**6. 변경 후보와 흐름 변경** (지표, 상한, "흐름을 바꿀 때")

- 방안
  - 후보가 되는 조건: 같은 원인이 서로 독립인 두 흐름에서 확인됨, 사람의 지속 적용 요청, 중대한 누락 한 건. 중대한 누락은 보안, 데이터 손실, 바깥 쓰기, 승인 우회에 한정하고 반복을 기다리지 않습니다.
  - 조정자가 원인을 넷으로 가릅니다. 규칙이 없었으면 결정적 검사를 먼저 만들고, 안 되면 사례, 그래도 안 되면 지시문을 고칩니다. 규칙이 있었는데 넘겨지지 않았으면 인계를 고칩니다. 넘겨졌는데 지켜지지 않았으면 지시문을 더하지 않고 코드나 권한으로 강제합니다. 리뷰가 틀렸으면 검증자 교정으로 보냅니다.
  - 상설 회고 역할은 두지 않습니다. 바꿀 대상의 담당 역할이 후보를 만들고, 리뷰 역할이 기준 하나로 검토하고, 사람이 승인합니다. 담당 역할이 없는 대상(상한, 조정 규칙)은 조정자가 제안하되 스스로 채택하지 않습니다.
  - 후보에는 출처 흐름, 가설, 바꿀 것 하나, 기대하는 변화, 되돌릴 조건을 적고 버전을 남깁니다. 진행 중인 흐름은 기존 버전을 유지합니다.
  - 채택한 뒤 미리 정한 구간에서 유지, 복귀, 보류 가운데 하나로 닫습니다. 보류는 한 번만 하고, 다음에도 판정할 수 없으면 복귀합니다. 같은 항목을 두 번 되돌렸으면 동결하고 사람이 다시 설계합니다.
  - 재현되는 실패(`parked`, 명세 결함, 게시 뒤 결함)는 사람이 채택하면 고정 사례가 됩니다. 사례에는 일어나야 하는 경우와 일어나지 말아야 하는 경우를 함께 둡니다. 판정용 사례의 입력과 정답은 구현 역할과 지시문에 보이지 않게 두고, 후보를 만드는 데 쓴 사례와 나눕니다.
- 장점: 시작값으로 둔 상한과 역할 설계를 관찰로 고칩니다. 같은 문제를 다음 리뷰에서 다시 찾는 대신 더 앞에서 막습니다.
- 단점과 막는 장치
  - 마지막 흐름 하나에 맞춰 흐름이 흔들립니다. 두 흐름 조건과 한 번에 하나만 바꾸는 규칙으로 막습니다.
  - 지시문이 길어져 오히려 지켜지지 않습니다. 지시문은 마지막 수단이고, 더할 때 출처와 날짜를 붙이고 지울 문구를 함께 찾습니다.
  - 조정자가 자기 흐름을 평가하면 자기 승인이 됩니다. 고정 사례와 사람 승인으로 정합니다.
  - 작은 변경이 다른 역할의 동작을 바꿉니다. 사례로 확인하고 되돌릴 조건을 미리 적습니다.
  - 비교 실행과 사용자 검토의 비용이 듭니다. 후보가 되는 조건을 만족한 사건이 있을 때만 엽니다.

### 넣지 않는 루프

| 루프 | 이유 |
|---|---|
| 에이전트가 스스로 쓰고 다음 흐름에 읽는 장기 메모리 | 잘못된 기록이 이후 흐름에 계속 검색됩니다. 흐름 사이의 기억은 사람이 승인한 규칙과 사례로만 남깁니다 |
| 지시문과 규칙의 자동 갱신 | 확인과 승인을 건너뜁니다. 반복해서 다시 쓰면 세부가 깎여 나갑니다 |
| 바깥 신호 없는 자기 비평의 반복 | 새 근거 없이 같은 모델에 다시 생각하게 하면 나빠질 수 있습니다 |
| 통과할 때까지 도는 개선, 통과할 때까지 리뷰를 바꾸는 경로 | 끝나지 않거나 수락을 무력하게 합니다 |
| 지표에 따른 상한의 자동 조정 | 숫자만 좋아지고 값이 오르내립니다 |
| 리뷰와 구현이 직접 주고받는 토론 | 반복과 비용의 변동이 크고 판정자가 사라집니다 |
| 게시 뒤 결함에 대한 자동 재실행과 자동 되돌림 | 바깥에 쓰는 일은 사람 승인 대상입니다 |

### 넣는 순서

1. 결함을 앞 단계로 돌리는 루프와 권한: 앞 단계 재개, 명세를 판정 기준으로 삼기, 구현의 기존 테스트 수정 차단
2. 기록만 하는 루프: 사람 정정, 리뷰 판정, 게시 뒤 관찰
3. 기록으로 흐름을 바꾸는 루프: 사례 채택, 변경 후보와 흐름 변경. 후보만 두면 쌓이기만 하고 변경만 두면 지표가 흐름을 흔들므로 함께 넣습니다
4. 판정 재확인의 독립 재판정: 검사가 맞는 결과를 거절한 사례가 확인된 뒤

3번은 흐름이 적으면 "두 흐름" 조건에 닿지 않아 사실상 사람의 판단에 맡겨집니다.

## 비용 통제

필요한 호출은 아끼지 않고, 필요 없는 호출을 없앱니다(원칙 4, 23). 예산은 두지 않습니다. 끝나지 않는 실행은 반복 상한과 동시 호출 수로 막습니다.

**모델 라우팅**

- 역할마다 모델과 추론 강도를 정합니다. 판단이 모호하거나 결과가 중요한 일(명세 작성, 구현, 리뷰, 조정)에는 강한 모델을, 정해진 형식으로 옮기는 일(탐색, 게시 글, 형식 변환)에는 작은 모델을 씁니다.
- 가장 강한 모델로 기준을 먼저 잡습니다. 작은 모델로 내리는 것은 고정 사례에서 품질이 유지된다고 확인된 역할에만 합니다. 확인 없이 내리지 않습니다.
- 실패에 따른 승격(구현에서 어려운 구현으로)은 이미 있는 라우팅입니다. 처음부터 어려운 작업은 바로 어려운 구현에 맡깁니다.
- 모델을 쓸 수 없어 대체 모델로 넘어가면 그 사실을 기록합니다. 리뷰의 독립성 판정이 실제로 수행한 모델에 달려 있기 때문입니다.
- 라우팅을 바꾸는 것도 흐름 변경입니다. 사례로 확인하고 한 번에 하나만 바꿉니다.

**결과 재사용(캐싱)**

- 입력이 같으면 결과를 다시 만들지 않습니다. 같다는 것은 코드 지문, 명세 버전, 실행한 명령이나 기준이 모두 같다는 뜻입니다. 셋이 같아도 실행 환경(의존성, 설정, 화면에 쓰는 데이터)이 달라졌으면 재사용하지 않습니다.
- 재사용하는 것: 검증 명령의 결과, 리뷰 결과, 탐색 결과, 화면 확인 결과. 리뷰는 예외로, 코드 지문이 달라져도 바뀌지 않은 범위에는 재사용합니다("리뷰"의 유효성).
- 다시 실행하라고 정한 곳에서는 재사용하지 않습니다. 리뷰 지적을 고친 뒤와 작업을 합친 뒤의 검증 명령이 여기에 듭니다.
- 재사용하지 않는 것: 원격의 상태(게시 여부, 병합 여부)와 바깥 서비스의 응답. 매번 다시 조회합니다.
- 재사용했으면 그렇게 기록합니다. 재사용한 결과를 새로 확인한 것처럼 보고하지 않습니다(원칙 7).
- 여러 작업에 같은 명세를 넘길 때는 명세 전문을 인계의 맨 앞에 같은 글자로 둡니다. 모델 제공자가 입력 캐시를 지원하면 그 부분의 비용이 줄어듭니다. 지원 여부는 실행 환경에 달려 있습니다.

**호출을 줄이는 순서**

- 필수 입력이 없으면 모델을 부르기 전에 멈춥니다.
- 코드로 가를 수 있는 것은 코드로 먼저 가릅니다. 결정적 검사가 통과한 뒤에만 리뷰를 부릅니다.
- 받는 쪽에 필요한 것만 넘깁니다. 명세와 작업은 전문으로 넘기되 조정자의 대화 기록은 넘기지 않고, 큰 변경은 전문 대신 범위를 넘겨 필요한 파일만 읽게 합니다.
- 동시 호출 수를 제한합니다.

**장단점**

- 장점: 낭비가 줄어 같은 사용량으로 리뷰와 재시도에 더 쓸 수 있습니다. 수락한 결과당 사용량으로 흐름 변경의 효과를 비교할 수 있습니다.
- 단점과 막는 장치
  - 작은 모델로 내린 역할이 결함을 놓칩니다. 사례로 확인한 역할만 내리고, 놓친 결함이 나오면 되돌립니다.
  - 오래된 결과를 재사용합니다. 지문이 다르면 무효로 하고, 원격 상태는 재사용하지 않습니다.
  - 넘기는 맥락을 줄이다 필요한 결정이 빠집니다. 명세 전문과 이미 내린 결정은 줄이지 않습니다(원칙 6).

## 흐름을 바꿀 때

역할, 지시문, 모델을 바꾸면 고정된 사례로 확인합니다(원칙 19).

- 사례에는 실패 경로를 넣습니다: 허용 경로 밖을 고친 구현, 결과 없이 끝난 리뷰, 상한 도달, `예정`만 남은 채 재개, 승인 뒤 코드가 바뀐 경우.
- 판정은 실행한 명령의 횟수나 작업의 상태처럼 관찰한 결과로 합니다.
- 바꿀 때는 새로 더한 사례만 돌립니다. 예외로, 상한, 수락, 승인, 권한처럼 모든 흐름이 지나는 경로를 바꿀 때는 관련된 기존 사례도 다시 돌립니다. 그 밖의 변경은 이전에 통과하던 동작이 그대로인지 이 방식으로 확인되지 않습니다.
- 사례를 돌릴 때 실제 원격과 상태 기록을 건드리지 않게 격리합니다.

## 기본으로 넣지 않는 것

필요가 측정되면 넣습니다(원칙 2).

| 항목 | 넣지 않는 이유 | 넣게 되는 조건 |
|---|---|---|
| 조정 전용 에이전트 | 사용자와 이야기하는 세션이 조정자입니다 | 조정자의 컨텍스트가 흐름 하나를 담지 못할 때 |
| 그래프 실행 엔진, 큐 | 단계 순서가 고정돼 있습니다 | 흐름이 동적으로 갈라지거나 사람 없이 돌 때 |
| 데이터베이스 | 흐름 하나의 상태는 문서 하나로 충분합니다 | 여러 흐름을 가로질러 조회할 때 |
| 모든 인계의 스키마 | 읽는 쪽이 모델과 사람이라 맥락 손실 위험이 더 큽니다 | 인계를 코드가 읽어 처리할 때 |
| 전용 관측 서비스 | 상태 기록과 세션 기록으로 추적됩니다 | 흐름 수가 늘어 건별로 볼 수 없을 때 |
| 예산과 비용·시간 상한 | 사용자가 두지 않기로 정했습니다. 사용량은 측정만 합니다 | 넣지 않습니다 |
| 자동 병합 | 병합은 사람이 정합니다 | 넣지 않습니다 |
| 에이전트끼리의 토론 | 반복과 비용의 변동이 큽니다 | 넣지 않습니다 |

## 확인하지 않은 것

- 앞 단계의 자동 재개 횟수는 측정값이 아닙니다. 반복 3회와 동시 호출 10은 사용자가 정한 값이고, 적정한지 측정하지 않았습니다.
- 다른 회사 모델의 리뷰가 결함을 더 잡는지는 측정하지 않았습니다.
- 바깥에 쓰는 일의 재개 절차는 실제로 끊어 보고 확인하지 않았습니다.
- 수행한 모델을 역할이 항상 알 수 있는지는 실행 환경에 달려 있습니다. 알 수 없으면 `확인 불가`로 적고 독립 리뷰로 치지 않습니다.
- 피드백 루프의 조건(자동 재개 1회, 두 흐름)과 효과는 측정하지 않았습니다.
