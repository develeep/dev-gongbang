## 원칙

### 1. 워크플로우를 먼저 정하고 에이전트는 나중에 정한다

목표, 입력, 결정 지점, 끝나는 조건을 먼저 적습니다. 에이전트는 그 흐름에서 판단이 필요한 자리에만 둡니다. 경로 선택, 권한 확인, 상태 전이, 계산처럼 조건이 분명한 일은 코드와 규칙으로 처리합니다.

- 근거: [Agentix Labs](https://www.agentixlabs.com/blog/general/how-it-teams-run-multi-agent-orchestration-in-production/), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents), [Microsoft](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)
- 회고: 모든 일을 모델에 맡기면 비용과 지연이 늘어난다고 정리했습니다(66일차). 입력이 빠진 요청은 조건 분기로 먼저 걸렀습니다(68일차).

### 2. 가장 단순한 구조에서 시작하고, 나아진다는 것이 확인될 때만 더한다

에이전트, 실행 엔진, 저장소, 관측 도구는 필요가 측정된 뒤에 넣습니다. 에이전트가 늘면 호출, 상태 전이, 지연, 실패 경로가 함께 늡니다.

- 근거: Anthropic, [OpenAI](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf), Microsoft가 모두 같은 순서를 권합니다.
- 회고: 한 에이전트로 충분하면 늘리지 않는다고 정리했고(39일차), 패턴을 쓰려고 시나리오를 키우지 말라고 했습니다(56일차). 최종 프로젝트에서는 단일 에이전트와 역할 분리를 비교해 본 뒤 정하기로 했습니다(89일차).
- 2026-11-25 적용: 위임의 필요가 측정된 적이 없어 기본 구조를 메인 단일 루프로 접었습니다(원칙 25, 접기:62, :411).

### 3. ~~역할 하나는 한 가지 일만 맡는다~~ (폐기)

**폐기 (2026-11-25, 사용자 결정 3)**: 이 문서는 "사용자"로 적힌 원칙을 바꾸지 않는다고 적었지만, 원칙 3은 사용자 자신이 2026-11-25에 폐기했습니다(접기:414). 판정 기준으로 역할과 호출을 나누는 것은 Anthropic 글의 "경계는 컨텍스트 기준으로 긋고, 문제 유형으로 나누면 인계마다 내용이 빠진다"(A12, A13, 접기:521-522)와 맞지 않고, 메인 단일 루프(원칙 25)에서는 나눌 역할이 없습니다(접기:437). 이 원칙에서 나온 "기준 하나에 리뷰 호출 하나"(개정 전 설계:127, 강화:131)도 근거를 잃었고, 교차 리뷰는 한 호출에 기준 목록을 받습니다(접기:440). 본문 가운데 "작성과 그 작성물을 완성하는 검증은 나누지 않는다"는 폐기하지 않고 2026-11-26 사용자 결정 12에 따라 원칙 24로 옮겼습니다(접기:428, :438). 아래 인용은 폐기 전 본문이고 기록으로만 남깁니다.

> 역할마다 통과 조건이 하나여야 합니다. 통과 조건은 그 역할의 결과가 맞는지 조정자가 판정하는 기준을 서술문 한 문장으로 적은 것입니다. 구현이면 "이 작업의 완료 기준을 만족한다", 버그 리뷰면 "맡은 범위를 버그 기준으로 모두 보았고, 버그가 있으면 근거와 함께 짚었다"입니다. 통과 조건이 둘이 되면 역할이나 호출을 나눕니다. 그 조건을 만족시키려고 스스로 하는 검증은 같은 역할에 둡니다.
>
> - 한 역할이 여러 일을 맡으면 조정자가 그 결과를 검토하기 어렵습니다. 버그, 규칙 위반, 불필요한 코드 가운데 무엇을 기준으로 봐야 하는지가 섞이기 때문입니다.
> - 나누는 기준은 결과물의 개수가 아닙니다. 코드와 그 테스트는 파일이 달라도 "완료 기준을 만족한다"는 한 조건에 속합니다. 리뷰 보고서는 하나여도 버그, 규칙 위반, 불필요한 코드를 함께 보면 통과 조건이 셋입니다.
> - 작성과 그 작성물을 완성하는 검증은 나누지 않습니다. 명세의 냉독 검증과 구현의 테스트가 여기에 듭니다. 테스트는 그 자체가 작업의 목적일 때만 따로 맡깁니다. (원칙 24로 옮김)
> - 근거: 사용자가 정한 원칙입니다. 회고도 에이전트 수보다 목적과 책임의 경계가 중요하다고 정리했습니다(52일차).

### 4. 호출 수보다 완성도가 먼저다

완성도에 필요한 호출과 확인은 아끼지 않습니다. 지금 완성도를 위해 쓰는 것은 검증 명령, 교차 리뷰, 냉독 독자, 상한 안의 재시도입니다. 교차 리뷰가 한 호출에서 기준을 놓친다는 것이 측정되면 같은 수단을 기준별로 나눠 다시 부릅니다(접기:263).

- 수단 문장 정리 (2026-11-26, 사용자 결정 12): 개정 전에는 "에이전트 종류를 늘리는 대신 같은 역할을 일 하나씩 여러 번 부릅니다"라는 수단을 적었습니다. 메인 단일 루프에서는 부를 역할이 없어 이 문장을 지웠습니다(접기:428, :439). 목표 문장은 바뀌지 않았습니다.
- 근거: 사용자가 정한 원칙입니다.
- 원칙 2와의 관계: 원칙 2는 구조의 종류를 늘리지 말라는 것이고, 이 원칙은 필요한 확인을 아끼지 말라는 것입니다.
- 원칙 23과의 관계: 필요 없는 호출을 없애는 것은 이 원칙과 부딪히지 않습니다.

### 5. 만든 쪽의 "통과"는 수락이 아니다

자체 검증은 결과물을 완성하는 용도입니다. 다음 단계로 넘길지는 메인 세션이 결정적 검사와 독립 리뷰로 정합니다. 중요한 결과물은 만든 쪽이 아닌 쪽이 검증합니다. 메인 단일 루프에서는 만든 쪽이 메인 세션이므로 그 검증이 교차 리뷰입니다(접기:248). 교차 리뷰가 지적이 없다고 보고해도 그것은 수락의 근거가 아니라 입력 하나이고, 메인 세션은 지적마다 재현하거나 원문과 대조합니다(접기:40).

- 근거: Agentix Labs(자기 승인 금지), Microsoft(반복 상한이 있는 작성-검토 구조)
- 회고: 에이전트가 테스트했다고 보고해도 실제 결과와 변경을 확인하라고 했습니다(65일차).

### 6. 맥락은 전문으로 넘기고, 형식은 판정에 쓰는 값에만 고정한다

받는 쪽에는 명세 전문과 이미 내린 결정을 넘깁니다. 개정 뒤 받는 쪽은 교차 리뷰, 냉독 독자, 선택 경로의 워커이고, 계획을 쓴 메인 세션이 실행하므로 단계 사이의 인계는 줄었습니다(접기:76). 고정 형식은 다음 행동을 정하는 값(실패 분류, 완료 기준 상태, 리뷰 판정)에만 씁니다.

- 근거: [Cognition](https://cognition.ai/blog/dont-build-multi-agents)은 압축된 메시지가 행동에 담긴 결정을 잃는다고 보고, 실행 기록까지 넘기라고 합니다. Agentix Labs는 불완전한 인계를 자동으로 거절하고 어디서 막히는지 볼 수 있다는 이유로 타입 계약을 권하지만, 효과를 비교한 실험은 없습니다. 둘은 양자택일이 아니어서, 판정에 쓰는 필수 값은 검증하고 나머지는 원문으로 넘깁니다.
- 회고: 형식 검증만으로는 부족했습니다. 입력에 없던 항목이 추가돼도 형식 검사는 통과했습니다(54일차).

### 7. 실행됨과 완료는 다르다

완료는 관찰한 결과로만 판정합니다. 확인하지 못한 것은 완료로 적지 않고, 해당 없는 것과 빠뜨린 것을 구분합니다.

- 회고: 헬스체크가 정상인데 실제 검색은 실패했습니다(46일차). 에이전트가 해당 없는 항목을 지워 검증이 실패했습니다(56일차). 확인하지 못한 것을 0이나 정상으로 바꾸지 않았습니다(79, 85일차).

### 8. 완화와 해결을 구분한다

테스트를 건너뛰거나, 타임아웃과 임계값을 조정하거나, 가짜 구현이나 대체 경로로 통과시킨 것은 해결이 아닙니다. 그렇게 처리한 곳은 표시하고 사람이 판단하게 합니다.

- 회고: 타임아웃을 늘리면 오류는 줄어도 원인은 남고(77일차), 한도를 올리면 경고만 사라졌습니다(79일차). 구조화 분석이 실패한 뒤 대체 경로만 돌았습니다(29일차).

### 9. 실패는 종류에 따라 다르게 처리한다

같은 요청을 반복해서 풀리는 실패와 풀리지 않는 실패를 나눕니다. 명세가 모호한 실패, 환경과 설정의 실패는 구현을 다시 시켜도 풀리지 않습니다. 분류는 관찰할 수 있는 신호로 먼저 하고, 모호할 때만 모델이 판단합니다.

- 근거: [LangGraph](https://docs.langchain.com/oss/python/langgraph/fault-tolerance), OpenAI(실패 임계치를 넘으면 사람에게)
- 회고: 일시적 오류와 영구적 오류를 나눴습니다(76일차). 환경변수 누락, 틀린 작업 디렉터리, 막힌 포트는 코드를 고쳐서 풀리지 않았습니다(29, 46~51일차).

### 10. 모든 반복에 상한을 두고, 닿으면 버리지 않고 사람에게 넘긴다

재시도, 수정과 재리뷰 같은 루프에는 횟수 상한과 상한에 닿았을 때의 처리를 정합니다. 어떤 반복도 3회를 넘기지 않고, 상한은 중요한 것만 따로 둡니다. 상한의 숫자가 최초 시도를 포함하는지도 적습니다. 상한에 닿은 작업은 사유와 산출물을 남긴 채 보관합니다.

- 근거: Microsoft(검증 루프의 반복 상한), Agentix Labs(전이 횟수 상한)
- 회고: 재처리 3회 뒤 사람이 확인하도록 보관했습니다(76일차). "재시도 3회"가 최초 호출을 포함하는지 해석이 갈렸습니다(61일차).

### 11. 응답이 없다는 것은 실패가 아니라 "결과를 모른다"는 것이다

바깥에 쓰는 일(게시, 생성, 전송)은 쓰기 전에 의도를 기록하고, 다시 시도하기 전에 실제 결과를 조회합니다. 작업자가 응답 없이 끝났을 때도 한 일을 먼저 확인합니다.

- 근거: LangGraph(재시도는 한 번 이상 실행될 수 있음), Agentix Labs(요청, 시작, 완료, 확인을 구분)
- 회고: 일부가 저장됐는데 요청은 오류로 끝났고, 확인 없이 배치를 다시 넣어 3건이어야 할 것이 8건 저장됐습니다(76일차).

### 12. 검토되지 않은 것은 통과시키지 않는다

검증자가 응답하지 않거나, 결과를 읽을 수 없거나, 상한에 닿으면 통과가 아니라 중단입니다. 상태 기록에 실패하면 다음 단계, 특히 바깥에 쓰는 일로 넘어가지 않습니다.

- 교차 리뷰 (2026-11-25, 사용자 결정 6): 교차 리뷰가 응답하지 않거나 결과를 읽을 수 없으면 통과로 치지 않고 다음 수단에 다시 맡깁니다. 다른 회사 모델을 구하지 못한 것은 중단 사유가 아니라 원칙 13의 대체 조건입니다. 대체 리뷰도 결과를 받은 뒤에야 넘어가고, 리뷰를 건너뛰고 넘어가는 경로는 없습니다(접기:47, :351).
- 회고: 리뷰어가 응답하지 않으면 게시하지 않았습니다(69일차). 판정 모델이 형식 오류를 내면 통과시키지 않고 따로 처리했습니다(78일차).

### 13. 독립 검증은 실제로 독립이어야 한다

검증자는 만든 쪽과 다른 회사의 모델을 씁니다. 같은 회사의 모델은 같은 실수를 함께 놓치기 쉽습니다. 독립인지는 계획한 모델이 아니라 실제로 수행한 모델로 판정합니다. 검증자에게는 보완 제안이 아니라 반대 근거를 찾게 하고, 지적은 재현되거나 원문 근거가 있는 것만 수용합니다.

- 모델 (2026-11-25, 사용자 결정 1): 검증자의 모델을 레포가 고정하지 않습니다. 조건은 "이번 변경을 실제로 구현한 모델과 다른 회사"뿐이고, 사용자가 지정한 것, 사용자 설정에 적힌 것, 환경에서 쓸 수 있는 것 순서로 그때 고릅니다(접기:41-44).
- 다른 회사 모델이 없을 때 (2026-11-25 결정 6, 2026-11-26 결정 14): 멈추지 않고 같은 회사 모델의 새 컨텍스트 리뷰로 대체합니다. 새 컨텍스트를 하나도 띄울 수 없으면 메인 세션의 자기 리뷰로 대체합니다. 어느 대체도 독립 검증으로 치지 않고, 대체했다는 것과 수행 모델을 완료 기록에 적어 사용자가 보게 합니다. 자기 리뷰는 같은 회사 대체보다 약하다는 것을 기록 문구로 구분합니다(접기:45, :47, :430).

- 회고: 서로 다른 모델이 같은 말을 해도 사실이 되지는 않는다고 했고(75일차), 교차 검토는 기존 대안과 반대 근거를 찾는 일이라고 했습니다(88일차).
- 한계: 회고는 "다른 회사" 모델을 말하지 않습니다. 회사를 나누는 것은 이 설계의 선택이고, 결함을 더 잡는지는 측정하지 않았습니다.

### 14. 안전 규칙은 지시문이 아니라 코드와 권한으로 강제한다

지시문에 적은 금지는 항상 지켜지지 않습니다. 넘겨도 되는지의 검사는 스크립트로 하고, 하면 안 되는 일은 도구 권한으로 막습니다. 새 컨텍스트에 맡기는 호출에는 필요한 권한만 줍니다. 교차 리뷰는 읽기 전용이고, 도구로 막지 못하는 쓰기(bash)는 메인 세션이 호출 전후의 코드 지문을 비교해 잡습니다(접기:38, :429). 메인 세션이 직접 구현하므로 기존 테스트를 고치지 못하게 막는 장치가 더 필요해졌습니다(접기:443, :425).

- 근거: [OWASP](https://genai.owasp.org/resource/agentic-ai-threats-and-mitigations/)(도구 오용, 권한 탈취), Agentix Labs(최소 권한)
- 회고: 권한을 로직으로 보장했고, 읽기 전용 원칙을 코드 수준에서 막았습니다(59, 67, 79일차).

### 15. 상태는 모델 컨텍스트 밖에 둔다

진행 단계, 결정, 시도, 승인, 바깥에 쓴 일은 대화가 아닌 곳에 생긴 때에 바로 기록합니다. 대화가 끊기거나 압축돼도 그 기록만으로 이어 갈 수 있어야 합니다. 비밀값은 기록하지 않습니다.

- 근거: Agentix Labs, [Anthropic 리서치 시스템](https://www.anthropic.com/engineering/multi-agent-research-system)(오류가 난 지점에서 재개)
- 회고: 어디서 멈췄는지, 실패한 단계부터 다시 돌릴 수 있는지를 상태 기록으로 판단했습니다(58일차).

### 16. 사람의 승인은 되돌리기 어려운 일 앞에 두고, 승인한 것이 바뀌면 다시 받는다

승인 지점이 많으면 검토자가 지쳐 승인이 형식이 됩니다. 되돌릴 수 있는 확인은 묶고, 바깥에 쓰는 일은 명시적으로 승인받습니다. 애매한 답은 승인으로 치지 않습니다.

- 근거: OWASP(검토자 과부하), Agentix Labs(승인 게이트의 위치)
- 회고: "응", "그래"처럼 무엇을 승인하는지 애매한 답은 다시 확인하라고 했습니다(39일차).

### 17. 병렬은 독립인 작업에만 쓰고, 나누기 전에 경계를 고정한다

병렬은 기본 흐름이 아니라, 사용자가 고를 때(워커 도구 절차를 지정하거나 레포·에이전트 규칙에 등록했을 때)만 쓰는 선택 경로입니다. 고르지 않으면 메인 세션이 작업을 차례로 합니다(2026-11-25 사용자 결정 8, 접기:28, :419). 서로 기다리지 않는 작업만 함께 돌립니다. 나누기 전에 작업끼리 주고받는 것과 각자 고쳐도 되는 범위를 정합니다. 합친 뒤에는 전체를 다시 검증합니다.

- 근거: Anthropic은 코딩 작업이 리서치보다 병렬화할 부분이 적다고 씁니다.
- 회고: 테스트 431개가 통과했는데 두 쪽의 필수 항목이 달라 연결에서 깨졌습니다(61일차). 병렬로 돈 에이전트는 서로의 결과를 몰라 결과가 어긋날 수 있다고 했습니다(53일차).

### 18. 숫자는 코드가 세고 모델은 설명한다

시도 횟수, 통과 수, 비용 같은 숫자는 기록에서 코드로 집계합니다. 평균은 문제 구간을 가리므로 건별로 봅니다.

- 회고: 검증 코드가 보고서의 숫자를 원본과 대조했습니다(77일차). 숫자가 어느 지표에 속하는지도 확인해야 한다고 했습니다(79일차). 전체 오류율은 3.15%였지만 하루는 22.86%였습니다(77일차).

### 19. 흐름을 바꾸면 고정된 사례로 다시 확인한다

역할, 지시문, 모델을 바꾸면 정해 둔 사례로 확인합니다. 사례에는 정상 경로뿐 아니라 실패 경로(검증자 무응답, 상한 도달, 중단 뒤 재개)를 넣습니다. 판정은 "말했다"가 아니라 관찰한 결과로 합니다.

- 사용자가 정한 범위: 바꿀 때 돌리는 것은 새로 더한 사례입니다. 상한, 수락, 승인, 권한처럼 모든 흐름이 지나는 경로를 바꿀 때만 관련된 기존 사례도 다시 돌립니다. 그 밖의 변경에서는 이전에 통과하던 동작이 그대로인지 확인되지 않습니다.
- 접기의 예외 (2026-11-25, 사용자 결정 4): 위임을 접거나 남기는 변경은 접는 단계마다 기존 동작 사례와 run-flow e2e 사례를 여러 번(3회) 돌려 사례별로 전후를 비교합니다. 접은 쪽이 낮으면 그 위임을 되돌려 남길지 사용자에게 묻습니다(접기:364-384, :415). 2026-11-26 첫 적용 실행에서는 사용자 지시로 새 e2e 사례와 바뀐 run-ticket 사례만 기준선과 최종에서 1회씩 돌렸고, 단계별 전체 비교는 남은 일입니다(결정 10, 접기:426).
- 근거: Anthropic(작은 평가 세트로 시작), Agentix Labs(단계적 도입)
- 회고: 고정 질문 세트로 릴리스를 검증하고, 기록이 없으면 배포를 막았습니다(74일차).

### 20. 결함은 생긴 단계에서 고친다

구현을 다시 시켜도 풀리지 않는 결함(모호한 명세, 어긋난 계약, 빠진 결정)은 그것이 처음 생긴 단계로 돌려보냅니다. 구현이나 테스트가 기준을 몰래 바꿔 메우지 않습니다. 다툼의 기준은 승인된 명세 하나이고, 명세가 답하지 않으면 명세를 고칩니다. 돌아가도 이미 쓴 시도 횟수와 상한은 그대로 둡니다.

- 근거: [Anthropic의 평가 글](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)은 여러 번 시도해 모두 실패하면 대개 과제나 채점이 잘못된 것이고, 명세의 모호함이 지표의 잡음이 된다고 씁니다. [LangGraph](https://docs.langchain.com/oss/python/langgraph/interrupts)는 멈춘 지점에서 사람의 결정을 받아 이어 가는 방식을 다룹니다.
- 회고: 계약이 어긋나면 재시도로 풀리지 않았습니다(61일차). 실패하면 재시도, 대체, 다시 계획하기 가운데 고르고 필요하면 사용자에게 넘겼습니다(60일차).

### 21. 기록은 증거이고, 승인된 것만 규칙이 된다

흐름에서 나온 지적, 사람의 정정, 게시 뒤의 결과는 자동으로 기록합니다. 그 기록이 다음 흐름의 규칙, 지시문, 상한을 바꾸려면 사례로 확인하고 사람이 승인해야 합니다. 한 번에 하나만 바꾸고, 버전과 되돌릴 조건을 남깁니다. 에이전트가 스스로 쓴 기억이나 지시문을 다음 흐름이 그대로 읽게 하지 않습니다.

- 근거
  - 고쳐야 할 이유: [Google SRE](https://sre.google/sre-book/postmortem-culture/)는 검토되지 않은 사후 분석은 없었던 것과 같다고 보고, 조치 항목을 끝까지 닫습니다. [Anthropic 리서치 시스템](https://www.anthropic.com/engineering/multi-agent-research-system)은 실패 사례를 주면 모델이 원인을 진단해 개선안을 낸다고 씁니다.
  - 자동으로 두면 안 되는 이유: 지시문을 반복해서 다시 쓰면 세부가 깎여 나갑니다([ACE](https://arxiv.org/abs/2510.04618), 초록). 잘못 심긴 기억은 이후 실행에서 계속 검색됩니다([MINJA](https://arxiv.org/abs/2503.03704), 초록). 맥락 파일은 성공률을 대체로 올리지 못하고 비용을 늘렸습니다([Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988), 초록). [Anthropic의 컨텍스트 글](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)은 예외 사례를 지시문에 쌓지 말라고 합니다.
  - 바깥 신호 없는 자기 수정의 한계: 외부 피드백 없이 스스로 고치면 나빠질 수 있고([Huang 외](https://arxiv.org/abs/2310.01798), 초록), 자가 수리의 병목은 피드백의 질입니다([Olausson 외](https://arxiv.org/abs/2306.09896), 초록).
- 회고: 프롬프트나 모델을 바꾸면 정상이던 질문이 깨질 수 있어 고정 질문으로 확인했습니다(74, 79일차). 변경 전후는 같은 조건에서 비교했습니다(77일차).
- 반대 근거: 자동 반성과 자동 갱신이 벤치마크에서 이득을 낸 연구도 있습니다([Reflexion](https://arxiv.org/abs/2303.11366), 초록). 이 설계가 자동 갱신을 뺀 것은 개발 흐름에서 오염과 회귀를 막을 수단이 승인과 사례뿐이라는 판단이고, 측정한 결과가 아닙니다.

### 22. 검증하는 쪽도 검증하고, 지표를 목표로 삼지 않는다

테스트, 리뷰, 검사도 틀립니다. 검증이 맞는 결과를 거절했다는 반례가 있으면 다시 판정하고, 기각된 지적과 놓친 결함을 함께 봐서 검증 기준을 고칩니다. 만드는 쪽은 자기를 채점하는 것, 곧 기존 테스트와 판정용 사례를 고칠 수 없게 합니다. 스스로 더한 테스트가 기준을 제대로 시험하는지는 리뷰가 봅니다. 지표는 원인을 찾는 단서로만 쓰고 목표로 삼지 않습니다.

- 근거
  - 채점의 오류: Anthropic의 평가 글은 실행 기록을 읽어야 채점이 맞는 해법을 거절했는지 알 수 있고, 모델 채점은 사람의 판단에 맞춰 보정하라고 씁니다.
  - 자기 평가의 편향: 모델 평가자는 자기가 만든 것을 알아보고 더 높게 칩니다([Panickssery 외](https://arxiv.org/abs/2404.13076), 초록).
  - 채점을 속이는 행동: [METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)은 채점 방식이 보이는 과제에서 채점을 속이는 행동이 훨씬 잦았고 지시로는 막히지 않았다고 보고합니다. 서로 다른 벤치마크 사이의 관찰이라 채점 공개만의 효과로 읽을 수는 없습니다.
  - 지표의 목표화: [DORA](https://dora.dev/guides/dora-metrics-four-keys/)는 지표를 목표로 삼는 것을 경고합니다.
- 회고: 기준이 너무 엄격하면 쓸 데이터까지 거절하고 너무 느슨하면 나쁜 데이터가 들어옵니다(78일차). 오류가 없어도 같은 문의가 반복되면 품질 신호입니다(77일차).

### 23. 비용은 필요 없는 호출을 없애서 줄이고, 품질이 확인된 곳에서만 모델을 낮춘다

줄이는 순서는 필요 없는 호출을 없애는 것이 먼저입니다: 필수 입력이 없으면 부르기 전에 멈추고, 코드로 가를 수 있는 것은 코드로 가르고, 입력이 같은 결과는 다시 만들지 않습니다. 모델은 레포가 역할별로 정해 배포하지 않고 사용자 설정과 환경에서 고릅니다(2026-11-25 사용자 결정 1, 접기:412). 작은 모델로 바꾸는 것도 사용자의 선택이고, 바꿀 때는 사례로 품질이 유지되는지 확인합니다. 비용은 호출 하나가 아니라 수락한 결과 하나를 기준으로 봅니다. 예산은 두지 않고, 끝나지 않는 실행은 반복 상한으로 막습니다.

- 근거: [Agentix Labs](https://www.agentixlabs.com/blog/general/how-it-teams-run-multi-agent-orchestration-in-production/)는 평가가 품질을 확인한 곳에서 작은 모델을 쓰고, 다음 일에 필요한 정보만 넘기고, 신선도가 허용하는 도구 결과를 캐시하고, 필수 데이터가 없으면 일찍 멈추고, 병렬 분기를 제한하라고 합니다. 싸게 돌았지만 여러 번 고쳐야 하는 실행은 경제적이지 않고, 비싼 검증이 재작업을 막아 전체 비용을 낮출 수 있다고도 씁니다. [OpenAI](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)는 가장 강한 모델로 기준을 잡은 뒤 작은 모델로 바꿔 보라고 합니다.
- 회고: 측정이 먼저이고 최적화가 그다음입니다. 모델 라우팅은 품질이 유지되는지 평가가 필요하다고 했습니다(75일차). 규칙 검사를 통과한 것에만 모델을 불렀습니다(78일차).
- 따르지 않은 것: Agentix Labs는 흐름마다 예산을 주고 단계와 에이전트에 한도를 나누라고도 합니다. 사용자가 예산을 두지 않기로 정했습니다.
- 원칙 4와의 관계: 이 원칙은 품질을 깎지 않습니다. 아낀 만큼을 검증과 재시도에 씁니다.

### 24. 작성과 그것을 완성하는 검증은 나누지 않는다

결과물을 완성하는 검증은 그것을 쓴 쪽이 함께 합니다. 명세의 냉독 검증과 구현의 테스트가 여기에 듭니다. 냉독을 새 컨텍스트의 독자에게 맡겨도 답을 비교하고 원인 문장을 고치는 책임은 명세를 쓴 메인 세션에 남습니다(접기:53). 테스트는 구현하는 쪽이 함께 씁니다.

- 원칙 5와의 관계: 완성하는 검증은 수락이 아닙니다. 수락은 결정적 검사와 교차 리뷰를 거칩니다.
- 출처: 사용자. 2026-11-19에 원칙 3 본문에 있던 문장입니다(개정 전 원칙:63). 같은 날 분리를 넓혔다가 3분 뒤 되돌린 커밋(`ff0ae29`, `ebf0f73`)이 나누면 뒤 에이전트가 맥락을 다시 쌓아야 한다는 이유를 적었고, Anthropic 글의 A13·A21과 같은 주장입니다(접기:438). 원칙 3이 폐기되면서 2026-11-26 사용자 결정 12에 따라 독립 원칙으로 옮겼습니다(접기:428).

### 25. 메인 세션 하나가 흐름을 진행하고, 새 컨텍스트는 정한 예외에만 쓴다

메인 세션(모델 하나, 컨텍스트 창 하나)이 요구사항 정리부터 게시까지 직접 하고, 계획을 쓴 세션이 실행합니다. 새 컨텍스트에 맡기는 것은 다른 회사 모델의 교차 리뷰와 명세의 냉독 독자 둘뿐입니다. 둘 다 메인 세션이 도구처럼 부르고, 간결한 결과를 받아 같은 대화에서 검증합니다. 병렬 워커는 사용자가 고를 때만 쓰는 선택 경로입니다(원칙 17).

- 위임을 더 남기려면 접은 쪽이 고정 사례에서 더 낮게 나와야 하고, 남기는 것은 예외를 늘리는 일이라 사용자에게 묻습니다(접기:383).
- 근거: Anthropic 「에이전트 구축: 서브 에이전트를 메인 에이전트 루프에 통합해야 하는 시점」은 위임을 측정된 컨텍스트 저하, 버릴 수 있는 새 창의 병렬, 도구 선택 실패나 지침 충돌의 세 조건에만 남기고, 남긴 것은 메인이 도구로 부르라고 합니다(A9~A12, A40, 접기:518-521, :537). 냉독은 새 창이자 블랙박스 검증이고(접기:55), 교차 리뷰는 블랙박스 검증입니다(접기:62).
- 출처: 사용자. 2026-11-25 결정 0, 2, 8입니다(접기:411, :413, :419).

## 자료 사이의 어긋남

- **기준 문서의 근거**: Agentix Labs의 글은 컨설팅 회사의 글이라 수치와 실험이 없습니다. 에이전트 추가 전 5문항과 지표 목록은 출처 없는 휴리스틱입니다. 방향만 가져왔습니다.
- **타입 인계와 맥락 공유**: 기준 문서는 모든 인계를 타입으로 만들라고 하고, Cognition은 전체 맥락을 공유하라고 합니다. 원칙 6으로 절충했습니다.
- **독립 검증의 가치**: 기준 문서는 근거 없이 "대개 값어치가 있다"고 합니다. [MAST 논문](https://arxiv.org/abs/2503.13657)은 검증 자체를 실패 범주로 꼽습니다(초록만 확인). 그래서 검증에도 상한과 무응답 처리를 둡니다(원칙 10, 12).
- **비용**: 기준 문서는 예산, 모델 라우팅, 캐싱을 권합니다. 캐싱은 원칙 23으로 받았고, 예산은 사용자가 두지 않기로 정했습니다. 사용량은 측정만 합니다. 모델 라우팅도 원칙 23으로 받았다가, 2026-11-25에 사용자가 모델을 역할별로 고정하지 않기로 정해 대체됐습니다(접기:447).
- **위임의 범위**: 기준 문서와 Cognition은 각각 타입 인계와 맥락 공유를 말하지만, 2026-11-25에 더한 Anthropic의 접기 글은 위임 자체를 세 조건으로 줄이라고 합니다. 원칙 25로 받았습니다.
