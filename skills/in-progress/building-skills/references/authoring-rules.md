출처 (확인일 2026-10-27):

## 1. 폴더 구조와 frontmatter

```
skill-name/
├── SKILL.md          # 필수: frontmatter + 지시
├── scripts/          # 선택: 실행 코드
├── references/       # 선택: 필요할 때 읽는 문서
├── assets/           # 선택: 템플릿, 이미지, 데이터
└── evals/            # 선택: 테스트 케이스
```

명세 필드:

| 필드 | 필수 | 제약 |
|---|---|---|
| `name` | ● | 2절 참고 [자동] |
| `description` | ● | 1~1,024자, XML 태그 불가 [자동] |
| `license` | | 라이선스 이름이나 번들 파일 이름 |
| `compatibility` | | 1~500자 [자동]. 특정 제품, 시스템 패키지, 네트워크가 필요할 때만 쓴다. 대부분 필요 없다 |
| `metadata` | | 문자열 키 → 문자열 값 [자동] |
| `allowed-tools` | | 공백으로 구분한 사전 승인 도구 (실험적) |

Claude Code 확장 필드(다른 클라이언트는 무시할 수 있다): `disable-model-invocation`(true면 이름으로만 호출, description이 모델 컨텍스트에 들어가지 않음), `argument-hint`, `user-invocable`, `model`, `context` 등. 쓸 때는 저장 경로에서 살아남는지 확인한다(SKILL.md "주의할 점" 참고).

## 2. name

- 1~64자, 소문자·숫자·하이픈만, 하이픈으로 시작·끝나지 않음, 연속 하이픈(`--`) 없음, 부모 폴더 이름과 같음 [자동]
- "anthropic", "claude" 포함 불가, XML 태그 불가 [자동]
- 동명사형 권장: `processing-pdfs`, `analyzing-spreadsheets`. 명사구(`pdf-processing`)도 괜찮다
- `helper`, `utils`, `tools`, `documents`, `data`처럼 모호하거나 지나치게 일반적인 이름은 피한다 [자동]
- 한 묶음의 스킬끼리 이름 패턴을 맞춘다

## 3. description

description은 스킬이 호출될지를 거의 혼자 결정한다. 모델은 100개가 넘는 스킬 가운데 이것만 보고 고른다.

공통:
- 3인칭으로 쓴다. 시스템 프롬프트에 들어가므로 "도와드립니다", "I can", "You can use this" 같은 1·2인칭은 시점이 어긋난다 [자동, 휴리스틱]
- 무엇을 하는지는 구체적인 동사와 대상으로 쓴다. "문서를 처리한다"가 아니라 "PDF에서 텍스트와 표를 추출하고, 양식을 채우고, 여러 파일을 합친다"
- 내부 구현이 아니라 사용자가 이루려는 것을 쓴다. 모델은 사용자 요청과 맞춰 본다
- 몇 문장에서 짧은 문단 정도. 최적화하다 보면 길어지므로 1,024자를 넘지 않는지 계속 본다

K10=Model-invoked:
- "~할 때 사용한다" 형태로 언제 쓰는지 쓴다. 트리거 문구를 나열하기보다 사용자가 처한 상황과 의도를 쓴다 [자동: 언제 문구 유무]
- 약간 적극적으로 쓴다. Claude는 스킬을 덜 부르는 경향이 있다. 사용자가 분야 이름을 대지 않는 경우도 포함한다("CSV라고 말하지 않아도 표 데이터 파일을 다루면")
- near-miss 요청(K8)에서 경계를 한 문장 넣는다. 인접 스킬이 있으면 그쪽이 맡는 일을 밝힌다
- 단순한 한 단계 작업("이 PDF 읽어줘")은 description이 완벽해도 호출되지 않을 수 있다. 모델이 혼자 할 수 있으면 스킬을 찾지 않는다

K10=User-invoked:
- `disable-model-invocation: true`를 넣는다
- description은 사람이 목록에서 읽는 요약으로 쓴다. 다만 frontmatter가 잘리는 저장 경로에 대비해 "사용자가 이름으로 부르거나 명시적으로 요청할 때만 사용한다"를 한 문장 넣는다. 저장소 규칙이 User-invoked description 형식을 따로 정해 두었으면(예: 트리거 문구 금지) 그 규칙을 따른다

## 4. 본문: 무엇을 넣고 뺄까

- **모델이 모르는 것만 넣는다.** 프로젝트 관례, 도메인 절차, 상식과 다른 예외, 써야 할 도구와 API. PDF가 무엇인지, HTTP가 어떻게 동작하는지는 쓰지 않는다
- **gotcha가 가장 값지다.** 합리적인 가정을 뒤집는 환경 사실을 구체적으로 쓴다("`users` 테이블은 soft delete라 `deleted_at IS NULL` 조건이 필요하다"). "에러를 적절히 처리한다" 같은 일반론은 gotcha가 아니다. gotcha는 모델이 그 상황을 만나기 전에 읽도록 참조 파일이 아니라 SKILL.md에 둔다
- **적당한 상세도.** 모든 예외를 다루려 하면 모델이 관련 없는 지시를 따라가다 시간을 버린다. 단계별 지침과 동작하는 예시 하나가 방대한 문서보다 낫다
- **선언보다 절차.** 특정 사례의 답("orders와 customers를 customer_id로 조인")이 아니라 같은 부류의 문제에 쓸 방법("스키마 파일에서 관련 테이블을 찾고, `_id` 외래키 관례로 조인한다")을 쓴다. 출력 템플릿, "PII 출력 금지" 같은 구체 제약은 괜찮다
- **시간에 민감한 정보 금지.** "2025년 8월 이전에는 옛 API"처럼 쓰지 않는다. 옛 방식은 `<details>`로 접은 "이전 패턴" 절에 둔다 [자동, 휴리스틱]
- **용어 일관성.** 한 개념은 한 용어로만 부른다("필드"면 계속 "필드")
- **예시는 구체적으로.** 추상적인 자리표시자보다 실제 모양의 입출력 쌍 2~3개

## 5. 본문: 지시의 형태

**자유도를 작업의 취약성에 맞춘다(K4).** 부분마다 따로 정해도 된다.

| 자유도 | 언제 | 형태 |
|---|---|---|
| 높음 | 여러 방법이 맞고 상황 판단이 중요 | 휴리스틱을 글로, 이유와 함께 |
| 중간 | 선호 패턴이 있고 약간의 변형은 괜찮음 | 의사코드, 파라미터 있는 템플릿·스크립트 |
| 낮음 | 깨지기 쉽고 일관성이 중요하며 순서가 고정 | 정확한 명령, "명령을 바꾸거나 플래그를 더하지 않는다" |

**이유를 설명한다.** "항상 X, 절대 Y"보다 "Y는 Z를 일으키므로 X를 한다"가 잘 지켜진다. 이유를 이해한 모델은 상황에 맞게 판단한다. 대문자 `MUST`, `CRITICAL`, `ALWAYS`, `NEVER`가 많으면 과잉 반응을 부른다 [자동, 개수]. 실제로 자주 어기는 규칙만 강하게 쓴다.

**메뉴 대신 기본값.** 도구나 방법이 여럿이면 기본값 하나와 예외 경로 하나를 준다. "pypdf, pdfplumber, PyMuPDF 중에서..."가 아니라 "pdfplumber를 쓴다. OCR이 필요한 스캔본은 pdf2image + pytesseract"

**자주 쓰는 패턴** (필요한 것만):
- **출력 템플릿**: 형식이 중요하면 글로 설명하지 말고 템플릿을 준다. 엄격해야 하면 "이 구조를 그대로 쓴다", 유연하면 "기본 형식이며 필요에 맞게 조정한다". 긴 템플릿은 `assets/`에 둔다
- **체크리스트**: 단계가 많거나 의존 관계가 있으면 복사해 체크할 수 있는 목록을 준다
- **검증 루프**: 작업 → 검증(스크립트, 참조 체크리스트, 자체 점검) → 수정 → 통과할 때까지 반복. "검증이 통과해야 다음으로 간다"
- **계획-검증-실행**: 일괄·파괴적 작업은 중간 계획 파일(`changes.json`)을 만들고, 원본 기준으로 검증한 뒤 실행한다. 검증 오류는 고칠 수 있게 구체적으로("필드 'signature_date' 없음. 있는 필드: customer_name, signature_date_signed")
- **조건부 워크플로**: "새로 만드나? → 생성 절차 / 고치나? → 수정 절차". 각 절차가 길면 참조 파일로 나눈다

**경로와 도구 이름.** 경로는 `/`로 쓴다 [자동]. MCP 도구는 `서버명:도구명`으로 쓴다. 설치를 가정하지 말고 필요한 패키지와 설치 명령을 적는다.

## 6. 점진적 공개와 참조 파일

로딩은 세 단계다: name·description(~100토큰, 항상) → SKILL.md 본문(호출 시) → 번들 파일(필요할 때).

- SKILL.md 본문은 500줄, 약 5,000토큰 이하 [자동]. 넘을 것 같으면 세부를 참조 파일로 옮긴다
- 참조는 SKILL.md에서 한 단계 깊이로만 연결한다. SKILL.md → a.md → b.md처럼 이어지면 모델이 일부만 읽고 놓친다 [자동]
- 참조 링크마다 언제 읽을지 조건을 쓴다. "API가 200이 아니면 `references/api-errors.md`를 읽는다"는 쓸모 있고, "자세한 건 references/ 참고"는 모델이 언제 읽을지 모른다 [자동, 휴리스틱]
- 100줄이 넘는 참조 파일은 맨 위에 목차를 둔다. 일부만 읽어도 전체 범위가 보이게 [자동]
- 여러 도메인을 다루면 도메인별 파일로 나눈다(`references/aws.md`, `gcp.md`). 모델은 필요한 파일만 읽는다
- 파일 이름은 내용을 드러내게(`form_validation_rules.md`, `doc2.md` 아님)
- 어디서도 언급하지 않는 파일은 쓰이지 않는다 [자동]. 모델이 같은 파일을 반복해 읽으면 그 내용은 SKILL.md에 있어야 한다는 신호다

## 7. 스크립트

모델이 실행마다 같은 코드를 새로 짜면 스크립트로 묶을 신호다. 미리 만든 스크립트는 생성 코드보다 믿을 만하고, 실행해도 내용은 컨텍스트에 들어가지 않고 출력만 들어간다.

- **실행인지 참조인지 밝힌다.** "`scripts/analyze.py`를 실행한다" / "추출 알고리즘은 `scripts/analyze.py`를 참고한다"
- **문제를 떠넘기지 않는다.** 예상되는 오류는 스크립트가 처리한다. 처리하지 못하면 무엇이 틀렸고 무엇을 기대했고 무엇을 해 볼지 알려 준다
- **상수에 근거를 단다.** `TIMEOUT = 47`이 아니라 `# 요청은 보통 30초 안에 끝난다` 같은 주석과 함께
- **대화형 입력 금지.** 에이전트는 TTY 프롬프트에 답하지 못해 멈춘다. 입력은 인자, 환경 변수, stdin으로 받는다
- **`--help`를 둔다.** 짧은 설명, 옵션, 예시. 모델이 인터페이스를 배우는 주된 통로다
- **구조화 출력.** 데이터는 stdout에 JSON·CSV로, 진행·경고는 stderr로. 출력이 커질 수 있으면 기본은 요약, 전체는 `--output` 파일로
- **멱등성, `--dry-run`, 의미 있는 종료 코드.** 재시도해도 안전하게, 파괴적 작업은 미리보기와 명시적 확인 플래그로
- **의존성.** 필요한 패키지를 SKILL.md에 적는다. Python은 PEP 723 인라인 메타데이터(`# /// script`)와 `uv run`으로 자체 완결할 수 있다. 버전은 고정한다. 런타임 요구는 `compatibility`에 적는다. Claude API 실행 환경은 네트워크와 런타임 설치가 없다는 점도 고려한다
- **경로**: 스크립트 경로는 스킬 폴더 기준 상대 경로로 쓴다

## 8. 사람 검토 체크리스트

`check_skill.py`가 못 보는 항목이다. 4단계와 8단계에서 점검한다.

- [ ] description의 "무엇"이 구체적이고 사용자가 실제로 쓸 말과 맞닿아 있다
- [ ] Model-invoked면 near-miss 경계가 있고, 인접 스킬과 겹치지 않는다
- [ ] 모든 문단이 "이게 없으면 모델이 틀린다"를 통과한다. 모델이 이미 아는 설명이 없다
- [ ] 내용마다 출처(사용자 자료·답변·승인 제안)가 있다. 조용히 지어낸 규칙·기준·예시가 없다
- [ ] 자유도가 K4와 맞고, 취약한 부분만 엄격하다
- [ ] 강한 규칙마다 이유가 있다
- [ ] K9 gotcha가 SKILL.md "주의할 점"에 있고 구체적이다
- [ ] 도구·방법은 기본값 하나 + 예외 경로 하나다
- [ ] 같은 개념에 같은 용어를 쓴다
- [ ] 예시가 구체적이고, 특정 사례의 답이 아니라 방법을 가르친다
- [ ] 복잡한 작업에 체크리스트와 검증 루프가 있다
- [ ] 스크립트는 실행/참조 구분, 오류 처리, 근거 있는 상수, 의존성 명시가 되어 있다
- [ ] 대표 요청 3개 이상(K8)이 정해져 있고, K7의 모든 모델에서 시험할 계획이 있다
