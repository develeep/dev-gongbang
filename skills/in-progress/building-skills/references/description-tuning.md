# description 실행 여부 측정과 다듬기

K10=Model-invoked이고 사용자가 검증 3단계를 골랐을 때만 한다. `claude` CLI(Claude Code)가 필요하다. `which claude`로 확인하고, 없으면 쿼리 세트까지만 만들어 전달하고 측정은 Claude Code에서 하라고 안내한다.

## 1. 쿼리 세트 만들기

약 20개: 실행돼야 할 것 8~10개, 실행되면 안 될 것 8~10개. `[{"query": "...", "should_trigger": true}, ...]` 형식으로 `<workspace>/trigger-queries.json`에 둔다.

**실행돼야 할 것**: 말투(격식, 구어, 오타·약어), 명시성(분야 이름을 대는 것 / 필요만 말하는 것), 상세도(짧은 것 / 경로·컬럼명·배경이 있는 것), 복잡도(한 단계 / 더 큰 작업 속에 묻힌 것)를 섞는다. 가장 쓸모 있는 것은 스킬이 도움이 되지만 연결이 요청에 드러나지 않는 것이다.

**실행되면 안 될 것**: K8 near-miss 요청을 반드시 넣고, 같은 키워드나 개념을 공유하지만 다른 일이 필요한 요청으로 채운다. "피보나치 함수 짜줘" 같은 무관한 요청은 아무것도 시험하지 않는다.

모델은 혼자 할 수 있는 단순한 요청에는 스킬을 찾지 않는다. 쿼리는 스킬이 실제로 도움이 될 만큼 구체적이어야 한다. 실제 사용자처럼 파일 경로, "팀장이 시켜서" 같은 배경, 구체적인 값을 넣는다.

세트를 표로 보여 주고 사용자에게 확인받는다. 쿼리가 나쁘면 description도 나빠진다.

## 2. 측정

```bash
python3 scripts/trigger_eval.py --skill <skill-folder> --queries <workspace>/trigger-queries.json \
  --runs 3 --split 0.4 --model <배포 모델 ID> --out <workspace>/trigger-iter-1.json
```

- 쿼리마다 `--runs`번 돌려 실행 비율을 낸다. 0.5 이상이면 "실행됨"
- `--split 0.4`는 고정 시드로 40%를 검증 세트로 떼어 둔다. 세트 구성은 반복 내내 같다
- 모델은 K7의 배포 모델로 한다. 세션 모델과 다르면 결과가 다를 수 있다
- 실제 billed 실행이 쿼리 수 × runs 번 일어난다. 시작 전에 횟수를 알린다
- 같은 스킬(또는 이전 판)이 사용자 스킬로 이미 설치돼 있으면 모델이 설치본을 골라 실행률이 낮게 나온다. 결과의 `first_tools`에 `Skill`이 있는데 실패로 잡힌 쿼리가 많으면 이것부터 의심하고, 측정하는 동안 설치본을 빼 두라고 안내한다

stdout에 요약 JSON(학습·검증 세트별 통과율, 실패 쿼리 목록)이 나온다.

## 3. 다듬기 반복 (최대 5회)

1. **학습 세트의 실패만** 본다. 검증 세트 결과는 수정에 쓰지 않는다
2. 실행돼야 하는데 안 된 것이 많으면 범위가 좁다. 쓰임새를 넓게 쓴다. 실행되면 안 되는데 된 것이 많으면 범위가 넓다. 하지 않는 일과 인접 스킬과의 경계를 쓴다
3. 실패한 쿼리의 단어를 그대로 넣지 않는다. 그 쿼리들이 대표하는 상황이나 개념을 쓴다. 이것이 과적합을 막는다
4. 몇 번 해도 안 나아지면 문장을 조금씩 고치지 말고 구조가 다른 문장으로 바꿔 본다
5. 1,024자를 넘지 않는지 `scripts/check_skill.py`로 확인한다
6. `--out`을 `trigger-iter-<N>.json`으로 바꿔 다시 측정한다

학습 세트가 모두 통과하거나 더 나아지지 않으면 멈춘다. **검증 세트 통과율이 가장 높은 판**을 고른다. 마지막 판이 아닐 수 있다.

## 4. 적용

고른 description을 SKILL.md에 넣고, 이전/이후 문장과 반복별 학습·검증 통과율을 표로 보여 준다. 시간이 되면 최적화에 쓰지 않은 새 쿼리 5~10개로 한 번 더 측정한다.
