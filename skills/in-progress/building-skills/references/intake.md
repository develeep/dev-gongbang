## 사양표 (K1~K10)

prompt-builder의 SKILL.md 인터뷰 항목과 같은 ID를 쓴다. 그래야 prompt-builder 결과를 그대로 옮겨 오고, 진단할 때 원인을 같은 항목으로 거슬러 올라갈 수 있다.

| ID | 항목 | 필수 | 쓰는 곳 |
|---|---|---|---|
| K10 | 호출 방식: User-invoked(이름으로 부를 때만) / Model-invoked(모델이 상황 보고) | ● | description 형식, 검증 3단계 가능 여부 |
| K2 | 이름 (소문자·숫자·하이픈, 64자 이하, 동명사형 권장) | ● | frontmatter, 폴더 이름 |
| K3 | 하는 일과 트리거 상황 | ● | description, 본문 도입 |
| K4 | 자유도: 높음(판단 중요) / 중간(선호 패턴) / 낮음(순서 고정, 실수 위험) | ● | 지시 형태 |
| K5 | 반드시 따를 단계와 검증 루프 | ○ | 워크플로, 체크리스트 |
| K6 | 번들 파일 (참조 문서, 스크립트, 템플릿) | ○ | 폴더 구조 |
| K7 | 사용 모델 (Haiku / Sonnet / Opus / Fable, 다중) | ● | 테스트 모델 |
| K8 | 대표 요청 3개, Model-invoked면 near-miss 요청 2개 | ● | 테스트 케이스, description 경계 |
| K9 | 자주 틀리는 점, 상식과 다른 환경 사실 (gotcha) | ○ | "주의할 점" 절, assertion |
| K1 | 대상 (SKILL.md / CLAUDE.md) | ● | 이 스킬은 SKILL.md만 다룬다. CLAUDE.md면 prompt-builder를 안내한다 |

● 항목이 비면 질문한다. ○ 항목은 "생략"도 답이다.

## 모드 A. prompt-builder 이어받기

prompt-builder 출력은 네 부분(설계 요약, 완성 프롬프트 코드블록, 실행 설정 권고, 다음 단계)으로 되어 있다.

1. 대화, 붙여넣은 텍스트, 사용자가 알려 준 경로에서 출력을 찾는다. 코드블록 위의 `### <상대 경로>` 제목은 번들 파일 경로다.
2. 사양표를 아래 출처에서 채운다.

   | 가져올 것 | 출처 |
   |---|---|
   | K10, K4, K6, K7 | 설계 요약의 "반영한 결정", 인터뷰 답변 |
   | K2, K3 | SKILL.md frontmatter |
   | K5 | SKILL.md의 워크플로·체크리스트 |
   | K8 | 인터뷰 답변, 부록, "다음 단계" |
   | K9 | SKILL.md의 "주의할 점" 절 |
   | 실패 원인 후보 | "다음 단계"의 경고 줄 (승인받지 못한 보완 제안, 생략·기본값 항목, 통과 못 한 검수 항목) |

3. 대화에 출력이 없고 SKILL.md 파일만 있으면, 그 파일에서 읽을 수 있는 것만 채우고 나머지는 모드 C의 질문으로 받는다.
4. prompt-builder가 이미 사용자에게 확인받은 값은 다시 묻지 않는다. 표에 "확인됨(prompt-builder)"으로 적는다.
5. "다음 단계"의 승인받지 못한 보완 제안은 이 단계에서 다시 보여 주고 넣을지 묻는다. 보통 품질 문제의 원인이 여기 있다.

## 모드 B. 기존 스킬 개선

1. 스킬 폴더 전체를 읽는다. SKILL.md, 번들 파일, `evals/`(있으면)까지.
2. 이름과 폴더 이름은 바꾸지 않는다. 사용자가 원하면 바꾸되, 이미 설치된 스킬과 이름이 달라진다는 점을 알린다.
3. 사양표를 SKILL.md에서 역으로 채운다. K10은 `disable-model-invocation` 유무와 description 문장으로 판단한다.
4. 사용자가 고치고 싶은 점(불만, 실패 사례)을 묻는다. 이것이 테스트 케이스의 1순위 재료다.
5. 기존 `evals/`가 있으면 그 케이스를 그대로 쓴다.

## 모드 C. 단독 신규

LLM의 일반 지식으로 쓴 스킬은 모호한 절차가 되기 쉽다. 사용자의 실제 자료에서 이 작업에만 있는 지식을 뽑는 데 시간을 쓴다.

1. **자료를 받는다.** 요청에 자료가 없으면 아래 중 있는 것을 달라고 한다. 하나도 없으면 질문으로만 진행할 수 있지만 품질이 떨어진다고 알린다.
   - 이 작업을 실제로 해낸 대화 기록 (이번 대화 포함)
   - 런북, 내부 문서, 스타일 가이드, 장애 회고
   - API 명세, 스키마, 설정 파일, 관련 코드
   - 리뷰 코멘트, 이슈, 수정 커밋
2. **자료에서 뽑는다.** 각 항목에 출처(파일·대화 위치)를 붙인다.
   - 효과가 있었던 단계와 그 순서 → K5
   - 사용자가 바로잡은 곳 ("X 말고 Y 써", "Z 경우 확인해") → K9 gotcha
   - 입력과 출력의 실제 모양 → 출력 형식, 예시
   - 모델이 몰랐던 프로젝트 고유 사실 (테이블명, 필드 별칭, 엔드포인트 동작) → K9 또는 참조 파일
   - 반복해서 새로 짠 코드 → K6 스크립트 후보
3. **스킬 범위를 정한다.** 함수처럼 하나의 일관된 작업 단위를 고른다. 너무 좁으면 한 작업에 스킬 여러 개가 뜨고, 너무 넓으면 정확히 호출되지 않는다. 자료가 두 작업에 걸쳐 있으면 나눌지 묻는다.
4. **사양표를 보여 준다.** 뽑은 값과 출처를 함께 보여 주고 확인받는다. 비어 있는 ● 항목만 묻는다.
5. 이 작업을 스킬 없이도 Claude가 이미 잘한다면 스킬이 값을 더하지 못할 수 있다고 알리고, 검증 2단계(비교)를 권한다.

## 질문 방식

- 선택형(K10, K4, K7)은 AskUserQuestion으로 한 번에 최대 4문항 묻는다. 도구가 없으면 번호 목록 텍스트로 묻고 선택지를 (a)(b)(c)로 적는다.
- 서술형(K2, K3, K5, K8, K9)은 번호를 붙여 한 메시지에 모아 묻는다.
- "알아서", "적당히" 같은 답에는 후보 2~3개를 보여 주고 고르게 한다. 후보는 형식의 선택지여야 하고 도메인 내용을 지어내면 안 된다.
- 답끼리 충돌하면 충돌을 보여 주고 어느 쪽을 우선할지 묻는다.
