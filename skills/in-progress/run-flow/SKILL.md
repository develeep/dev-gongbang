# Run Flow

이 세션은 조정자다. 개발 단계를 순서대로 진행하면서, 단계가 끝날 때마다 다음 단계를 이어서 시작한다. 단계 안의 일은 그 단계의 스킬이 정한 대로 하고, 이 스킬은 시작 단계를 고르고 단계 사이를 잇는다.

## 핵심 규칙

1. **단계의 일과 확인은 그 단계의 스킬을 따른다.** 스킬을 불러와 그 지시를 따르고, 스킬이 사용자에게 묻는 확인과 질문은 줄이거나 대신 답하지 않고 그대로 묻는다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다.
2. **단계가 끝나면 바로 다음 단계를 시작한다.** 단계 스킬이 끝에서 "다음에 무엇을 실행하라"고 안내하는 부분은 건너뛰고, 다음 단계를 시작한다고 한 줄로 알린다. 4단계 끝의 세션 선택만 예외다.
3. **단계 사이에는 대화 대신 결과물을 넘긴다.** 요구사항 문서 경로, brief 경로나 이슈 번호를 다음 단계 스킬에 준다. 흐름이 끊긴 뒤 다시 실행해도 이 결과물과 상태 파일로 이어 갈 단계를 찾는다.
4. **push와 PR 생성은 6단계에서 사용자가 고른 뒤에만 한다.** push와 PR은 되돌려도 원격 기록과 알림이 남는다.

## 상태 파일

흐름마다 상태 파일 하나를 `docs/context/run-flow/YYYY-MM-DD-<slug>.md`에 두고, 단계가 바뀔 때마다 고친다. 대화가 끊기거나 컨텍스트가 압축돼도 이 파일만 읽으면 어느 단계에서 무엇이 남았는지 알 수 있다. 날짜는 흐름을 시작한 날이고, slug는 요청 문장이나 기획서·brief 제목을 영문 소문자와 하이픈으로 줄인 것이며 흐름이 끝날 때까지 바꾸지 않는다.

- 0단계에서 시작 단계를 고르면 바로 만든다. 이어 가는 흐름이면 새로 만들지 않고 그 파일을 고친다. 6단계부터 시작하는 흐름은 `## 리뷰`를 `- 통합 리뷰: 기록 없음`으로 만든다. 이 흐름 밖에서 구현한 변경이라 리뷰했는지 알 수 없다.
- 단계를 시작할 때 `- 현재 단계:`를 고치고, 마칠 때 `## 단계` 체크리스트와 `## 결과물`·`## 결정`을 고친다. 대화에 보여 주는 체크리스트는 이 `## 단계`와 같다. 7단계를 마치면 `- 현재 단계:`를 `완료`로 고친다.
- 흐름이 멈추면 `- 멈춘 이유:`에 이유와 이어 갈 명령(`/run-flow <상태 파일>`)을 적는다.
- 상태 파일과 brief·티켓 상태가 어긋나면 brief·티켓을 따르고 상태 파일을 고친다. 티켓 상태는 다른 worktree의 워커가 run-ticket으로 바꾸기 때문이다. 다만 티켓이 모두 끝났어도 `## 리뷰`가 `- 통합 리뷰: 안 함`이면 5단계는 끝난 것이 아니다. 티켓은 리뷰보다 먼저 done이 된다.
- 상태 파일과 ADR에는 `- 작성일:` 줄을 쓰지 않는다. brief를 찾는 `^- 작성일: ` grep이 저장소 전체를 보므로 brief로 잘못 잡힌다.

```markdown
# <요청 한 줄 요약. brief가 생기면 brief 제목으로 바꾼다>

- 시작일: YYYY-MM-DD
- 현재 단계: 2. 구체화
- 멈춘 이유: 없음

## 단계
(대화 체크리스트와 같은 0~7 목록)

## 결과물
- 요구사항 문서:
- 개발 범위:
- brief:
- brief 초안:
- ADR:
- 브랜치:
- 시작 HEAD:
- PR:

## 결정
- 2단계: 개발 범위 "<고른 범위>" 선택. 고르지 않은 범위: <범위>, <범위>
- 6단계: PR 만들기

## 구체화 기록
(2단계에서 확정한 기록 전문. 확정하는 중에는 첫 줄에 `(확정 전)`을 둔다)

## 구현 중 결정
- <5단계에서 워커 질문에 준 답, 새로 정한 설계 결정>: <근거>

## 리뷰
- 통합 리뷰: 안 함
- brief 확인 기준: <기준>: <통과 / 실패>
- <리뷰 이름>: <지적>: <고침 / 고치지 않음과 이유>
- 건너뛴 리뷰: <리뷰 이름>: <이유>
- 범위 밖 문제: <문제>
```

## ADR

2단계와 6단계에서 결정 중 세 조건을 모두 만족하는 것만 ADR 후보로 보여 주고, 사용자가 고른 것만 남긴다. 조건: 되돌리기 어렵다, 맥락 없이 보면 왜 그렇게 했는지 의아하다, 실제 대안 사이에서 이유를 갖고 골랐다. 하나라도 아니면 후보로 올리지 않는다. 후보가 없으면 묻지 않고 넘어간다.

저장 위치는 레포에 ADR 폴더와 형식이 있으면 그것을, 없으면 `docs/adr/NNNN-<slug>.md`(NNNN은 기존 번호 다음)를 쓰고, 상태 파일 `## 결과물`의 ADR에 링크를 적는다. set-ticket이 저장소의 ADR을 읽고 따르므로 2단계에서 남긴 ADR은 티켓에 반영된다.

```markdown
# NNNN. <결정 한 줄>

- 날짜: YYYY-MM-DD
- 상태: 채택
- 흐름: <상태 파일 경로>

## 맥락
## 결정
## 고려한 대안
## 결과
```

## 단계

아래 체크리스트를 시작할 때 한 번 보여 주고, 단계를 마칠 때마다 갱신한다. 0단계에서 건너뛴 단계는 `- [-]`로 표시한다.

```
흐름 진행:
- [ ] 0. 시작 단계 고르기
- [ ] 1. 요구사항 정리
- [ ] 2. 구체화
- [ ] 3. 작업 지시서
- [ ] 4. 티켓 분할
- [ ] 5. 구현과 리뷰
- [ ] 6. 머지·PR 결정
- [ ] 7. PR 만들기
```

### 0. 시작 단계 고르기

인자를 아래 표의 위 행부터 차례로 맞춰 보고 처음 맞는 행의 단계를 고른다. 고른 단계와 근거를 한 줄로 알린 뒤 바로 시작한다. 상태 파일, brief, 티켓도 MD 문서라 기획서 행보다 먼저 맞춰 본다.

- brief는 `- 작성일: YYYY-MM-DD` 줄이 있는 문서이고, 티켓은 brief의 `## 티켓` 섹션 링크가 가리키는 문서다.
- docs 티켓은 `- 상태: done`이면, GitHub 티켓은 closed이면 끝난 것이다. `## 티켓` 섹션이 없는 brief는 "남은 일"에 빈 체크박스가 없으면 끝난 것이다.

| 인자 | 시작 단계 |
|---|---|
| `status` | 끝나지 않은 흐름(상태 파일의 `- 현재 단계:`가 `완료`가 아닌 것)마다 제목, 현재 단계, 멈춘 이유, 남은 티켓 수를 보여 주고 끝낸다. 상태 파일을 고치거나 단계를 시작하지 않는다 |
| 상태 파일 | `- 현재 단계:`의 단계부터 이어 간다 |
| `## 티켓` 섹션이 없는 brief | "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 4, 아니면 5 |
| 끝나지 않은 티켓이 있는 brief, 또는 그 brief의 티켓 | 5 |
| 티켓이 모두 끝난 brief | 이 brief를 `## 결과물`에 적은 끝나지 않은 상태 파일의 `## 리뷰`가 `- 통합 리뷰: 안 함`이면 5, 그 밖에는 6 |
| 요구사항 문서(`## 개발 범위`와 `## 요구사항`이 있는 MD), 요청 문장 | 2 |
| 기획서: 위 행에 맞지 않는 PDF·PPT·MD 파일, SharePoint·OneDrive 링크 | 1 |
| 없음 | 끝나지 않은 상태 파일을 먼저 찾는다. 하나면 그 단계부터, 여럿이면 목록에서 고르게 한다. 없으면 끝나지 않은 brief를 찾는다. 하나면 위 표대로 이어 가고, 여럿이면 제목과 남은 티켓 수를 목록으로 보여 주고 고르게 한다. 없으면 무엇을 진행할지 묻는다 |

- 인자가 brief나 요구사항 문서이고 그것을 `## 결과물`에 적은 끝나지 않은 상태 파일이 있으면 그 파일을 이어 쓴다. 끝난 상태 파일만 있으면 새 상태 파일을 만든다. 끝난 흐름에 이어 쓰면 두 흐름의 결정과 결과물이 섞인다.
- `## 구체화 기록`이 있고 brief가 없는 흐름은, 기록에 `(확정 전)`이 없으면 3단계부터 이어 가며 그 기록을 set-brief에 넘긴다. `(확정 전)`이 있으면 2단계부터 이어 가며, 적힌 칸을 사용자가 이미 확정한 칸이라고 알려 framing-problems에 넘긴다.

인자가 없을 때 brief는 docs에서 `command grep -rlE --include='*.md' --exclude-dir=.git --exclude-dir=node_modules '^- 작성일: [0-9]{4}-[0-9]{2}-[0-9]{2}' .`로, GitHub에서 `git remote -v`에 github.com이 있고 `gh auth status`가 성공하면 `gh issue list --label context --state open`으로 찾는다.

### 1. 요구사항 정리

`analyzing-requirements` 스킬을 불러와 기획서를 넘긴다. 스킬이 저장한 요구사항 문서의 경로를 2단계에 넘긴다.

### 2. 구체화

요구사항 문서의 개발 범위가 여럿이면 이번 흐름에서 진행할 범위 하나를 먼저 고르게 한다. brief 하나에는 최종 목적 하나만 담기 때문이다. 같은 요구사항 문서를 `## 결과물`에 적은 끝난 상태 파일이 있으면, 그 `## 결정`의 고른 범위를 "이미 진행함"으로 표시해 보여 준다. 고르지 않은 범위는 `## 결정`에 적고, 흐름이 끝난 뒤 요구사항 문서를 인자로 run-flow를 다시 실행하면 된다고 알린다.

`framing-problems` 스킬을 불러와 고른 범위나 요청을 넘기고, 기록이 확정되면 run-flow 3단계로 이어 간다고 함께 지시한다. 사용자가 칸을 확정할 때마다 그 칸을 상태 파일 `## 구체화 기록`에 적고 첫 줄에 `(확정 전)`을 둔다. 도중에 끊겨도 받은 답을 다시 묻지 않기 위해서다. 기록 전체가 확정되면 전문으로 바꾸고 `(확정 전)`을 지운 뒤, "ADR" 절대로 ADR 후보를 고른다.

### 3. 작업 지시서

`set-brief` 스킬을 불러와 그 단계대로 brief를 남기되, 초안 작성과 냉독 검증(set-brief 1·3·4단계)은 새 컨텍스트의 서브에이전트에 맡긴다. 에이전트 규칙이 brief 초안을 맡을 에이전트를 정해 두었으면 그 에이전트로 띄운다. 이 단계는 출력이 길고 검증 결과가 쌓여, 메인 세션이 하면 이후 모든 턴이 그 내용을 다시 읽는다. 구체화 기록이 상태 파일에 있으므로 서브에이전트는 대화 없이 초안을 쓸 수 있다.

1. set-brief 2단계(저장 위치)는 직접 묻는다. 상태 파일 `- brief 초안:`에 적힌 파일이 남아 있으면 2번을 건너뛰고, 3번에서 냉독 검증 결과는 이전 세션에 있어 보여 줄 수 없다고 알린다.
2. 서브에이전트에 set-brief의 1·3·4단계를 맡긴다. 넘길 것: set-brief 스킬 이름, 상태 파일 경로(`## 구체화 기록`이 합의한 내용이다), 구체화를 확정한 뒤에 바꾼 파일과 커밋, 고른 저장 위치, 초안을 쓸 저장소 밖 임시 파일 경로, 에이전트 규칙이 냉독 검증을 맡을 에이전트를 정해 두었으면 그 이름. 저장소 안에 두면 초안의 `- 작성일:` 줄 때문에 brief로 잡힌다. 사용자에게 물어야 할 일(목적이 여럿인 경우 등)은 묻지 말고 돌려 달라고 한다. 돌려받을 것: 임시 파일 경로, 냉독 검증에서 고친 항목과 남은 어긋남, 돌려준 질문. 돌려받은 임시 파일 경로를 상태 파일 `- brief 초안:`에 적는다. 서브에이전트를 띄울 수 없으면 같은 세션에서 차례로 한다.
3. 돌려받은 결과로 set-brief 5단계(사용자 확인)와 6단계(게시)를 직접 한다. 본문은 임시 파일을 그대로 쓴다(docs면 그 파일을 옮기고, 이슈면 `--body-file`로 넘긴다). 수정 요청은 임시 파일을 고쳐 반영한다. 게시한 뒤 `- brief 초안:` 값을 지운다.

게시가 끝나면 brief의 경로나 이슈 번호를 받는다. set-brief의 "티켓 분할 안내"에 쓰인 크기 기준으로, "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 4단계로, 아니면 5단계로 간다.

### 4. 티켓 분할

`set-ticket` 스킬을 불러와 brief를 넘긴다.

게시가 끝나면 5단계를 이 세션에서 이어 갈지, 새 세션에서 `/run-flow <상태 파일>`로 이어 갈지 묻는다. 새 세션은 지금까지의 대화를 다시 읽지 않아 비용이 줄고, 5단계에 필요한 것은 brief, 티켓, 상태 파일에 모두 있다. 새 세션을 고르면 `- 현재 단계:`를 5단계로, `- 멈춘 이유:`를 "새 세션에서 이어 감"과 이어 갈 명령으로 고치고 끝낸다.

### 5. 구현과 리뷰

현재 브랜치가 기본 브랜치(`main` 등)면 먼저 만들 작업 브랜치 이름을 묻고 만든다. 이 단계와 run-ticket의 Orca 병렬 실행이 흐름 문서를 현재 브랜치에 커밋하므로, 그대로 두면 기본 브랜치에 커밋이 생긴다.

run-ticket을 부르기 전에 두 가지를 차례로 한다.

1. 상태 파일 `## 결과물`의 `- 시작 HEAD:`가 비어 있으면 `git rev-parse HEAD` 값을 적는다. 이미 있으면 그대로 둔다. 6·7단계와 리뷰는 이 값부터 HEAD까지를 이번 흐름의 변경으로 본다.
2. 커밋하지 않은 흐름 문서(상태 파일, 요구사항 문서, ADR, brief, 티켓, 인덱스 `README.md`)가 있으면 레포 커밋 규칙대로 쓴 메시지를 보여 주고, 커밋 하나로 묶을지 묻는다. run-ticket의 Orca 병렬 실행은 작업 트리가 깨끗해야 시작하고, 워커의 worktree는 커밋된 문서만 읽는다. 흐름 문서가 아닌 변경은 이 커밋에 넣지 않는다.

`run-ticket` 스킬을 불러와 이 brief의 끝나지 않은 티켓 전부를 "여러 티켓 실행"으로 실행하게 한다. 티켓이 하나이거나 `## 티켓` 섹션이 없는 brief여도 같은 방법을 쓴다. 구현을 새 컨텍스트의 워커나 서브에이전트가 맡아야 이 대화 없이 brief와 티켓만 보고 작업한다. 끝나지 않은 티켓이 없으면 구현은 끝났고 리뷰만 남은 것이므로, 시작 HEAD부터 HEAD까지에 "여러 티켓 실행"의 마무리 리뷰만 하게 한다.

- 레포 규칙이 티켓 실행에 다른 스킬을 쓰라고 정해 두었으면 그 스킬을 불러와 따른다. 불러올 수 없는 User-invoked 스킬이면 흐름을 멈추고, 그 스킬을 실행한 뒤 brief를 인자로 run-flow를 다시 실행하라고 알린다.
- run-ticket이 멈추면 흐름도 멈춘다. 완료 기준을 통과하지 못한 티켓이 있으면 실패 보고를 보여 주고, 그 티켓을 다시 나눌지(4단계로 돌아감) 묻는다.
- run-ticket이 끝나면 그 보고를 상태 파일에 옮긴 뒤 6단계로 간다. `## 리뷰`에는 `- 통합 리뷰: 완료 (<리뷰한 HEAD 해시>)`, brief "확인 기준" 결과, 리뷰별 지적과 고침 여부, 건너뛴 리뷰와 이유, 범위 밖 문제를 적는다. `## 구현 중 결정`에는 워커 질문에 준 답과 구현 중 새로 정한 설계 결정을 적는다. 보고는 대화에만 있어, 옮기지 않으면 대화가 끊기거나 압축될 때 사라진다.

### 6. 머지·PR 결정

run-ticket의 보고에서 티켓별 완료 기준 결과, 고치지 않은 리뷰 지적, 건너뛴 리뷰, 바뀐 파일과 커밋을 한 메시지로 모아 보여 주고 셋 중 하나를 고르게 한다. 6단계부터 시작해 run-ticket의 보고가 없으면 상태 파일의 `## 리뷰`·`## 구현 중 결정`, 티켓의 `## 완료 기록`(GitHub 티켓은 완료 코멘트), 상태 파일의 시작 HEAD(없으면 완료 기록의 작업 시작 HEAD)부터의 `git log`·`git diff --stat`에서 모은다. `## 리뷰`가 `- 통합 리뷰: 기록 없음`이면 통합 리뷰 기록이 없다고 함께 보여 준다. 구현 중 새로 정한 설계 결정이 있으면 고르기 전에 "ADR" 절대로 ADR 후보를 고른다.

- **PR 만들기**: 다음을 함께 정한다. 커밋하지 않은 변경이 있으면 레포 커밋 규칙대로 커밋 하나로 묶고 그 메시지를 보여 준다. 현재 브랜치가 기본 브랜치면 새로 만들 작업 브랜치 이름을 정한다.
- **고치기**: 받은 지시대로 고친 뒤 `run-ticket` 스킬을 불러와 시작 HEAD부터 HEAD까지에 5단계 리뷰만 다시 하게 하고, 결과로 상태 파일 `## 리뷰`를 고친 뒤 이 단계로 돌아온다.
- **멈추기**: 지금 상태와 남은 일을 보고하고 끝낸다.

### 7. PR 만들기

1. 6단계에서 정한 대로 작업 브랜치를 만들고 커밋한다. 커밋한 뒤 `git status --porcelain`이 비었는지 확인하고, 남은 변경이 있으면 보여 주고 커밋에 넣을지 묻는다.
2. PR 본문을 쓴다. 레포나 에이전트 규칙이 PR 설명을 맡을 에이전트를 정해 두었으면 그 에이전트에 맡기고, 아니면 직접 쓴다. 넘길 것: brief, `git diff --stat <기본 브랜치>...HEAD` 출력, 티켓의 `## 완료 기록`, 상태 파일의 `## 리뷰`. diff 전문은 넘기지 않고 필요한 파일만 읽게 한다. 큰 diff는 작성자의 컨텍스트에 다 들어가지 않는다. 바꾼 이유, 바꾼 내용, 확인 방법 순서로 쓰고, 레포에 PR 템플릿(`.github/pull_request_template.md` 등)이 있으면 그 형식을 따른다. 확인 방법에는 brief의 "확인 기준"과 완료 기록의 "확인한 것"을 옮긴다.
3. `git push -u origin <브랜치>`로 올리고, 본문을 임시 파일에 저장해 `gh pr create --base <기본 브랜치> --title "<제목>" --body-file <임시 파일>`로 PR을 만든 뒤 임시 파일을 지운다. 제목은 레포 규칙이 정한 형식을 따르고, 없으면 brief 제목을 쓴다. github.com 원격이 없거나 `gh auth status`가 실패하면 PR 본문을 보여 주고 멈춘다.
4. 한 메시지로 보고한다. 단계별 결과물(요구사항 문서, brief, 티켓, 커밋), PR URL, 고치지 않은 리뷰 지적, 머지는 사용자가 한다는 안내.
