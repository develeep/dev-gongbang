# Run Flow

이 세션은 조정자다. 개발 단계를 순서대로 진행하면서, 단계가 끝날 때마다 다음 단계를 이어서 시작한다. 단계 안의 일은 그 단계의 스킬이 정한 대로 하고, 이 스킬은 시작 단계를 고르고 단계 사이를 잇는다.

## 핵심 규칙

1. **단계의 일과 확인은 그 단계의 스킬을 따른다.** 스킬을 불러와 그 지시를 따르고, 스킬이 사용자에게 묻는 확인과 질문은 줄이거나 대신 답하지 않고 그대로 묻는다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다.
2. **단계가 끝나면 바로 다음 단계를 시작한다.** 단계 스킬이 끝에서 "다음에 무엇을 실행하라"고 안내하는 부분은 건너뛰고, 다음 단계를 시작한다고 한 줄로 알린다.
3. **단계 사이에는 대화 대신 결과물을 넘긴다.** 요구사항 문서 경로, brief 경로나 이슈 번호를 다음 단계 스킬에 준다. 흐름이 끊긴 뒤 다시 실행해도 이 결과물로 이어 갈 단계를 찾는다. 구체화 기록은 대화에만 있으므로, brief를 게시하기 전에 흐름이 끊기면 처음 인자로 다시 시작한다.
4. **push와 PR 생성은 6단계에서 사용자가 고른 뒤에만 한다.** push와 PR은 되돌려도 원격 기록과 알림이 남는다.

## 단계

아래 체크리스트를 시작할 때 한 번 보여 주고, 단계를 마칠 때마다 갱신한다. 0단계에서 건너뛴 단계는 `- [-]`로 표시한다.

```
흐름 진행:
- [ ] 0. 시작 단계 고르기
- [ ] 1. 요구사항 정리
- [ ] 2. 구체화
- [ ] 3. 작업 지시서
- [ ] 4. 티켓 분할
- [ ] 5. 구현과 리뷰
- [ ] 6. 머지·PR 결정
- [ ] 7. PR 만들기
```

### 0. 시작 단계 고르기

인자를 아래 표의 위 행부터 차례로 맞춰 보고 처음 맞는 행의 단계를 고른다. 고른 단계와 근거를 한 줄로 알린 뒤 바로 시작한다. brief와 티켓도 MD 문서라 기획서 행보다 먼저 맞춰 본다.

- brief는 `- 작성일: YYYY-MM-DD` 줄이 있는 문서이고, 티켓은 brief의 `## 티켓` 섹션 링크가 가리키는 문서다.
- docs 티켓은 `- 상태: done`이면, GitHub 티켓은 closed이면 끝난 것이다. `## 티켓` 섹션이 없는 brief는 "남은 일"에 빈 체크박스가 없으면 끝난 것이다.

| 인자 | 시작 단계 |
|---|---|
| `## 티켓` 섹션이 없는 brief | "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 4, 아니면 5 |
| 끝나지 않은 티켓이 있는 brief, 또는 그 brief의 티켓 | 5 |
| 티켓이 모두 끝난 brief | 6 |
| 요구사항 문서(`## 개발 범위`와 `## 요구사항`이 있는 MD), 요청 문장 | 2 |
| 기획서: 위 행에 맞지 않는 PDF·PPT·MD 파일, SharePoint·OneDrive 링크 | 1 |
| 없음 | 끝나지 않은 brief를 찾는다. 하나면 위 표대로 이어 가고, 여럿이면 제목과 남은 티켓 수를 목록으로 보여 주고 고르게 한다. 없으면 무엇을 진행할지 묻는다 |

인자가 없을 때 brief는 docs에서 `command grep -rlE --include='*.md' --exclude-dir=.git --exclude-dir=node_modules '^- 작성일: [0-9]{4}-[0-9]{2}-[0-9]{2}' .`로, GitHub에서 `git remote -v`에 github.com이 있고 `gh auth status`가 성공하면 `gh issue list --label context --state open`으로 찾는다.

### 1. 요구사항 정리

`analyzing-requirements` 스킬을 불러와 기획서를 넘긴다. 스킬이 저장한 요구사항 문서의 경로를 2단계에 넘긴다.

### 2. 구체화

요구사항 문서의 개발 범위가 여럿이면 이번 흐름에서 진행할 범위 하나를 먼저 고르게 한다. brief 하나에는 최종 목적 하나만 담기 때문이다. 고르지 않은 범위는 흐름이 끝난 뒤 요구사항 문서를 인자로 run-flow를 다시 실행하면 된다고 알린다.

`framing-problems` 스킬을 불러와 고른 범위나 요청을 넘기고, 기록이 확정되면 run-flow 3단계로 이어 간다고 함께 지시한다.

### 3. 작업 지시서

`set-brief` 스킬을 불러와 확정한 구체화 기록으로 brief를 남긴다. 게시가 끝나면 brief의 경로나 이슈 번호를 받는다. set-brief의 "티켓 분할 안내"에 쓰인 크기 기준으로, "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 4단계로, 아니면 5단계로 간다.

### 4. 티켓 분할

`set-ticket` 스킬을 불러와 brief를 넘긴다. 게시가 끝나면 5단계로 간다.

### 5. 구현과 리뷰

현재 브랜치가 기본 브랜치(`main` 등)면 먼저 만들 작업 브랜치 이름을 묻고 만든다. run-ticket의 Orca 병렬 실행은 준비 단계에서 brief·티켓 문서를 현재 브랜치에 커밋하므로, 그대로 두면 기본 브랜치에 커밋이 생긴다.

`run-ticket` 스킬을 불러와 이 brief의 끝나지 않은 티켓 전부를 "여러 티켓 실행"으로 실행하게 한다. 티켓이 하나이거나 `## 티켓` 섹션이 없는 brief여도 같은 방법을 쓴다. 구현을 새 컨텍스트의 워커나 서브에이전트가 맡아야 이 대화 없이 brief와 티켓만 보고 작업한다.

- 레포 규칙이 티켓 실행에 다른 스킬을 쓰라고 정해 두었으면 그 스킬을 불러와 따른다. 불러올 수 없는 User-invoked 스킬이면 흐름을 멈추고, 그 스킬을 실행한 뒤 brief를 인자로 run-flow를 다시 실행하라고 알린다.
- run-ticket이 멈추면 흐름도 멈춘다. 완료 기준을 통과하지 못한 티켓이 있으면 실패 보고를 보여 주고, 그 티켓을 다시 나눌지(4단계로 돌아감) 묻는다.

### 6. 머지·PR 결정

run-ticket의 보고에서 티켓별 완료 기준 결과, 고치지 않은 리뷰 지적, 건너뛴 리뷰, 바뀐 파일과 커밋을 한 메시지로 모아 보여 주고 셋 중 하나를 고르게 한다. 6단계부터 시작해 run-ticket의 보고가 없으면 티켓의 `## 완료 기록`(GitHub 티켓은 완료 코멘트)과, 완료 기록의 작업 시작 HEAD부터의 `git log`·`git diff --stat`에서 모은다.

- **PR 만들기**: 다음을 함께 정한다. 커밋하지 않은 변경이 있으면 레포 커밋 규칙대로 커밋 하나로 묶고 그 메시지를 보여 준다. 현재 브랜치가 기본 브랜치면 새로 만들 작업 브랜치 이름을 정한다.
- **고치기**: 받은 지시대로 고친 뒤 `run-ticket` 스킬을 불러와 5단계 리뷰만 다시 하게 하고, 이 단계로 돌아온다.
- **멈추기**: 지금 상태와 남은 일을 보고하고 끝낸다.

### 7. PR 만들기

1. 6단계에서 정한 대로 작업 브랜치를 만들고 커밋한다.
2. PR 본문을 쓴다. 레포나 에이전트 규칙이 PR 설명을 맡을 에이전트를 정해 두었으면 그 에이전트에 brief와 diff 범위(`git diff <기본 브랜치>...HEAD`)를 넘기고, 아니면 직접 쓴다. 바꾼 이유, 바꾼 내용, 확인 방법 순서로 쓰고, 레포에 PR 템플릿(`.github/pull_request_template.md` 등)이 있으면 그 형식을 따른다. 확인 방법에는 brief의 "확인 기준"과 완료 기록의 명령을 옮긴다.
3. `git push -u origin <브랜치>`로 올리고, 본문을 임시 파일에 저장해 `gh pr create --base <기본 브랜치> --title "<제목>" --body-file <임시 파일>`로 PR을 만든 뒤 임시 파일을 지운다. 제목은 레포 규칙이 정한 형식을 따르고, 없으면 brief 제목을 쓴다. github.com 원격이 없거나 `gh auth status`가 실패하면 PR 본문을 보여 주고 멈춘다.
4. 한 메시지로 보고한다. 단계별 결과물(요구사항 문서, brief, 티켓, 커밋), PR URL, 고치지 않은 리뷰 지적, 머지는 사용자가 한다는 안내.
