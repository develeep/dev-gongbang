# Run Flow

이 세션은 조정자다. 개발 단계를 순서대로 진행하면서, 단계가 끝날 때마다 다음 단계를 이어서 시작한다. 이 스킬은 시작 단계를 고르고 단계 사이를 잇는다.

## 핵심 규칙

1. **단계의 일과 확인은 그 단계의 스킬을 따른다.** 스킬을 불러와 그 지시를 따르고, 스킬이 사용자에게 묻는 확인과 질문은 줄이거나 대신 답하지 않고 그대로 묻는다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다.
2. **단계가 끝나면 바로 다음 단계를 시작한다.** 단계 스킬이 끝에서 "다음에 무엇을 실행하라"고 안내하는 부분은 건너뛰고, 다음 단계를 시작한다고 한 줄로 알린다. 4단계 끝의 세션 선택만 예외다.
3. **단계 사이에는 대화 대신 결과물을 넘긴다.** 요구사항 문서 경로, brief 경로나 이슈 번호를 다음 단계 스킬에 준다. 흐름이 끊긴 뒤 다시 실행해도 이 결과물과 상태 파일로 이어 갈 단계를 찾는다.
4. **push와 PR 생성은 6단계에서 사용자가 고른 뒤에만 한다.** push와 PR은 되돌려도 원격 기록과 알림이 남는다.

## 주의할 점

- 상태 파일과 ADR에는 `- 작성일:` 줄을 쓰지 않는다. brief를 찾는 `^- 작성일: ` grep이 저장소 전체를 보므로 brief로 잘못 잡힌다.
- brief 초안도 같은 이유로 저장소 밖 임시 파일에 둔다. 초안에는 `- 작성일:` 줄이 있다.
- run-ticket의 차례 실행은 커밋하지 않지만, 레포 규칙이나 사용자 결정으로 도중에 커밋할 수 있다. 커밋 범위(`<시작 HEAD>..HEAD`)나 작업 트리 한쪽만 보면 구현 일부가 리뷰와 보고에서 빠지므로, 늘 "이번 흐름의 변경" 전체를 본다.
- 티켓은 리뷰보다 먼저 done이 된다. 티켓이 모두 끝났어도 `## 리뷰`가 `- 통합 리뷰: 안 함`이면 5단계는 끝난 것이 아니다.
- Orca나 Paseo 워커의 worktree는 커밋된 문서만 읽는다. 흐름 문서를 커밋하지 않고 5단계를 시작하면 워커가 brief와 티켓을 보지 못한다.

## 상태 파일

흐름마다 상태 파일 하나를 `docs/context/run-flow/YYYY-MM-DD-<slug>.md`에 두고, 단계가 바뀔 때마다 고친다. 대화가 끊겨도 이 파일만 읽으면 어느 단계에서 무엇이 남았는지 알 수 있다. 날짜는 흐름을 시작한 날이고, slug는 요청 문장이나 기획서·brief 제목을 영문 소문자와 하이픈으로 줄인 것이며 흐름이 끝날 때까지 바꾸지 않는다.

- 0단계에서 시작 단계를 고르면 바로 만든다. 이어 가는 흐름이면 새로 만들지 않고 그 파일을 고친다. 6단계부터 시작하는 흐름은 `## 리뷰`를 `- 통합 리뷰: 기록 없음`으로 만든다. 이 흐름 밖에서 구현한 변경이라 리뷰했는지 알 수 없다.
- 단계를 시작할 때 `- 현재 단계:`를 고치고, 마칠 때 `## 단계` 체크리스트와 `## 결과물`·`## 결정`을 고친다. 대화에 보여 주는 체크리스트는 이 `## 단계`와 같다. 7단계를 마치면 `- 현재 단계:`를 `완료`로 고친다.
- 흐름이 멈추면 `- 멈춘 이유:`에 이유와 이어 가는 방법(run-flow를 이 상태 파일을 인자로 다시 실행한다)을 적는다.
- 사용자 답, 구현 중 결정, 리뷰 결과는 단계가 끝나기를 기다리지 않고 생긴 때에 바로 적는다. 리뷰 여러 개를 함께 띄웠으면 모두 끝나기를 기다리지 않고 결과가 하나 올 때마다 적는다. 대화에만 있는 내용은 대화가 끊기거나 압축되면 사라진다.
- 상태 파일과 brief·티켓 상태가 어긋나면 brief·티켓을 따르고 상태 파일을 고친다. 티켓 상태는 다른 worktree의 워커가 run-ticket으로 바꾸기 때문이다.

상태 파일을 만들 때 [assets/state-file.md](assets/state-file.md)를 읽고 그 구조를 그대로 쓴다. 섹션 이름과 줄 이름을 바꾸지 않는다. 이어 가는 세션이 이 이름으로 값을 찾는다.

**이번 흐름의 변경**은 시작 HEAD 이후의 커밋, 커밋하지 않은 변경, 새 파일을 모두 합친 것이다.

**코드 지문**은 흐름 문서를 뺀 지금 작업 트리의 tree 해시다. 커밋하지 않은 변경과 새 파일도 들어가고, 흐름 문서만 바뀌면 값이 그대로다. 리뷰한 코드와 지금 코드가 같은지 볼 때 쓴다. 저장소 루트에서 아래 스크립트를 실행한다. 경로는 이 스킬 폴더 기준이고, 인자는 5단계 2번의 흐름 문서 가운데 저장소 안에 있는 것이다.

```bash
bash scripts/code_fingerprint.sh <흐름 문서 경로들>
```

## 단계

아래 체크리스트를 시작할 때 한 번 보여 주고, 단계를 마칠 때마다 갱신한다. 0단계에서 건너뛴 단계는 `- [-]`로 표시한다.

```
흐름 진행:
- [ ] 0. 시작 단계 고르기
- [ ] 1. 요구사항 정리
- [ ] 2. 구체화
- [ ] 3. 작업 지시서
- [ ] 4. 티켓 분할
- [ ] 5. 구현과 리뷰
- [ ] 6. 머지·PR 결정
- [ ] 7. PR 만들기
```

### 0. 시작 단계 고르기

인자를 아래 표의 위 행부터 차례로 맞춰 보고 처음 맞는 행의 단계를 고른다. 고른 단계와 근거를 한 줄로, 체크리스트와 함께 알린 뒤 바로 시작한다. 상태 파일, brief, 티켓도 MD 문서라 기획서 행보다 먼저 맞춰 본다.

- brief는 `- 작성일: YYYY-MM-DD` 줄이 있는 문서이고, 티켓은 brief의 `## 티켓` 섹션 링크가 가리키는 문서다.
- docs 티켓은 `- 상태: done`이면, GitHub 티켓은 closed이면 끝난 것이다. 레포 규칙이나 상태 파일 `## 결정`이 완료 표시를 다른 값으로 정했으면 그 값도 끝난 것이다. `## 티켓` 섹션이 없는 brief는 "남은 일"에 빈 체크박스가 없으면 끝난 것이다.

| 인자 | 시작 단계 |
|---|---|
| `status` | 끝나지 않은 흐름(상태 파일의 `- 현재 단계:`가 `완료`가 아닌 것)마다 제목, 현재 단계, 멈춘 이유, 남은 티켓 수를 보여 주고 끝낸다. 상태 파일을 고치거나 단계를 시작하지 않는다 |
| 상태 파일 | `- 현재 단계:`의 단계부터 이어 간다 |
| `## 티켓` 섹션이 없는 brief | "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 4, 아니면 5 |
| 끝나지 않은 티켓이 있는 brief, 또는 그 brief의 티켓 | 5 |
| 티켓이 모두 끝난 brief | 이 brief를 `## 결과물`에 적은 끝나지 않은 상태 파일의 `## 리뷰`가 `- 통합 리뷰: 안 함`이면 5, 그 밖에는 6 |
| 흐름 밖에서 진행한 작업을 흐름으로 정리해 달라는 요청 | '없음' 행처럼 brief를 찾고, 끝나지 않은 brief마다 지금 단계를 판정해 상태 파일을 만든 뒤 이어 갈지 묻는다 |
| 요구사항 문서(`## 개발 범위`와 `## 요구사항`이 있는 MD), 요청 문장 | 2 |
| 기획서: 위 행에 맞지 않는 PDF·PPT·MD 파일, SharePoint·OneDrive 링크 | 1 |
| 폴더 | 그 폴더 안에서 '없음' 행대로 찾는다 |
| 없음 | 끝나지 않은 상태 파일을 먼저 찾는다. 하나면 그 단계부터, 여럿이면 목록에서 고르게 한다. 없으면 끝나지 않은 brief를 찾는다. 하나면 위 표대로 이어 가고, 여럿이면 제목과 남은 티켓 수를 목록으로 보여 주고 고르게 한다. 없으면 무엇을 진행할지 묻는다 |

- 인자가 brief나 요구사항 문서이고 그것을 `## 결과물`에 적은 끝나지 않은 상태 파일이 있으면 그 파일을 이어 쓴다. 끝난 상태 파일만 있으면 새 상태 파일을 만든다. 끝난 흐름에 이어 쓰면 두 흐름의 결정과 결과물이 섞인다.
- `## 구체화 기록`이 있고 brief가 없는 흐름은, 기록에 `(확정 전)`이 없으면 3단계부터 이어 가며 그 기록을 set-brief에 넘긴다. `(확정 전)`이 있으면 2단계부터 이어 가며, 적힌 칸을 사용자가 이미 확정한 칸이라고 알려 framing-problems에 넘긴다.
- 진행 중인 흐름에서 요구사항이 바뀌었다는 요청을 받으면 [references/requirement-change.md](references/requirement-change.md)를 읽고 그 절차로 이어 간다.

인자가 없거나 `status`일 때 상태 파일은 `command grep -RlE --include='*.md' --exclude-dir=.git --exclude-dir=node_modules '^- 현재 단계: ' .`로 찾는다. 사용자가 상태 파일을 `docs/context/run-flow/` 밖(brief 옆 등)에 두기로 할 수 있다. brief는 docs에서 `command grep -RlE --include='*.md' --exclude-dir=.git --exclude-dir=node_modules '^- 작성일: [0-9]{4}-[0-9]{2}-[0-9]{2}' .`로, GitHub에서 `git remote -v`에 github.com이 있고 `gh auth status`가 성공하면 `gh issue list --label context --state open`으로 찾는다. `-R`은 `.scratch`처럼 심볼릭 링크로 붙인 폴더도 따라간다.

### 1. 요구사항 정리

`analyzing-requirements` 스킬을 불러와 기획서를 넘긴다. 스킬이 저장한 요구사항 문서의 경로를 2단계에 넘긴다.

스킬이 모호한 부분을 물어 받은 답은 받는 즉시 질문과 함께 상태 파일 `## 요구사항 답변`에 적는다. 요구사항 문서는 스킬의 마지막 단계에서야 저장되므로, 그 전에 끊기면 답이 사라진다. 이어 갈 때 `## 요구사항 답변`이 있으면 이미 받은 답이라고 알려 스킬에 넘긴다.

### 2. 구체화

요구사항 문서의 개발 범위가 여럿이면 이번 흐름에서 진행할 범위 하나를 먼저 고르게 한다. brief 하나에는 최종 목적 하나만 담기 때문이다. 같은 요구사항 문서를 `## 결과물`에 적은 끝난 상태 파일이 있으면, 그 `## 결정`의 고른 범위를 "이미 진행함"으로 표시해 보여 준다. 고르지 않은 범위는 `## 결정`에 적고, 흐름이 끝난 뒤 요구사항 문서를 인자로 run-flow를 다시 실행하면 된다고 알린다.

`framing-problems` 스킬을 불러와 고른 범위나 요청을 넘기고, 기록이 확정되면 run-flow 3단계로 이어 간다고 함께 지시한다. 사용자가 칸을 확정할 때마다 그 칸을 상태 파일 `## 구체화 기록`에 적고 첫 줄에 `(확정 전)`을 둔다. 도중에 끊겨도 받은 답을 다시 묻지 않기 위해서다. 기록 전체가 확정되면 전문으로 바꾸고 `(확정 전)`을 지운 뒤, [references/adr.md](references/adr.md)를 읽고 ADR 후보를 고른다.

### 3. 작업 지시서

`set-brief` 스킬을 불러와 brief를 남긴다. 이 단계에 들어오면 [references/brief-stage.md](references/brief-stage.md)를 읽고 그 절차를 따른다. 초안 작성과 냉독 검증은 서브에이전트에 맡긴다. 이 단계는 출력이 길고 검증 결과가 쌓여, 메인 세션이 하면 이후 모든 턴이 그 내용을 다시 읽는다.

게시가 끝나면 brief의 경로나 이슈 번호를 받는다. set-brief의 "티켓 분할 안내"에 쓰인 크기 기준으로, "남은 일"이 새 컨텍스트 창 하나로 끝나지 않을 크기면 4단계로, 아니면 5단계로 간다.

### 4. 티켓 분할

`set-ticket` 스킬을 불러와 brief를 넘긴다.

게시가 끝나면 5단계를 이 세션에서 이어 갈지, 새 세션에서 run-flow를 상태 파일을 인자로 실행해 이어 갈지 묻는다. 새 세션은 지금까지의 대화를 다시 읽지 않아 비용이 줄고, 5단계에 필요한 것은 brief, 티켓, 상태 파일에 모두 있다. 새 세션을 고르면 `- 현재 단계:`를 5단계로, `- 멈춘 이유:`를 "새 세션에서 이어 감"과 이어 가는 방법으로 고치고 끝낸다.

### 5. 구현과 리뷰

현재 브랜치가 기본 브랜치(`main` 등)면 먼저 만들 작업 브랜치 이름을 묻고 만든다. 이 단계와 run-ticket의 병렬 실행이 흐름 문서를 현재 브랜치에 커밋하므로, 그대로 두면 기본 브랜치에 커밋이 생긴다.

run-ticket을 부르기 전에 두 가지를 차례로 한다.

1. 상태 파일 `## 결과물`의 `- 시작 HEAD:`가 비어 있으면 `git rev-parse HEAD` 값을 적는다. 이미 있으면 그대로 둔다.
2. 커밋하지 않은 흐름 문서(상태 파일, 요구사항 문서, ADR, brief, 티켓, 인덱스 `README.md`)가 있으면 레포 커밋 규칙대로 쓴 메시지를 보여 주고, 커밋 하나로 묶을지 묻는다. run-ticket의 병렬 실행은 작업 트리가 깨끗해야 시작한다. 흐름 문서가 아닌 변경은 이 커밋에 넣지 않는다.

`run-ticket` 스킬을 불러와 이 brief의 끝나지 않은 티켓 전부를 "여러 티켓 실행"으로 실행하게 한다. 티켓이 하나이거나 `## 티켓` 섹션이 없는 brief여도 같은 방법을 쓴다. 구현을 새 컨텍스트의 워커나 서브에이전트가 맡아야 이 대화 없이 brief와 티켓만 보고 작업한다. 끝나지 않은 티켓이 없으면 구현은 끝났고 리뷰만 남은 것이므로, 이번 흐름의 변경에 "여러 티켓 실행"의 통합 리뷰만 하게 한다.

run-ticket에 다음을 넘긴다.

- 리뷰와 보고의 기준 커밋: 상태 파일의 시작 HEAD
- 기록 파일: 상태 파일 경로. 워커 질문에 준 답과 구현 중 새로 정한 설계 결정은 결정, 근거, 걸리는 티켓을 `## 구현 중 결정`에, 워커 식별자는 생긴 때에 바로 적게 한다. Orca Run ID는 `- Orca Run:`에, Paseo 워커는 티켓마다 워크스페이스 ID, 에이전트 ID, 브랜치를 `- Paseo 워커:`에 적는다
- 이미 적힌 것: `## 구현 중 결정`의 결정, `- Orca Run:`과 `- Paseo 워커:` 값, `- 멈춘 이유:`의 앞선 실패 기록

결정을 바로 적지 않으면 뒤 티켓이 같은 질문에 다른 답으로 구현한다. 워커 식별자가 없으면 이어 갈 때 실행 중인 워커를 찾지 못하거나 brief 제목이 같은 다른 Run을 잡는다.

- 레포 규칙이 티켓 실행에 다른 스킬을 쓰라고 정해 두었으면 그 스킬을 불러와 따른다. 불러올 수 없는 User-invoked 스킬이면 흐름을 멈추고, 그 스킬을 실행한 뒤 brief를 인자로 run-flow를 다시 실행하라고 알린다.
- run-ticket이 멈추면 흐름도 멈춘다. 완료 기준을 통과하지 못한 티켓이 있으면 `- 멈춘 이유:`에 그 티켓, 시도한 에이전트와 횟수, 실패 원인을 적는다. 이어 갈 때 같은 시도를 되풀이하지 않기 위해서다. 그다음 실패 보고를 보여 주고, 그 티켓을 다시 나눌지(4단계로 돌아감) 묻는다. 에이전트 규칙의 실패 처리(다시 맡기기, 다른 에이전트로 올리기)는 run-ticket이 멈추기 전에 이미 따른 것이다.
- run-ticket의 통합 리뷰 결과를 받으면 바로 `## 리뷰`에 적은 뒤 6단계로 간다. 코드 지문은 리뷰 지적을 고친 뒤의 값이다. 적을 것:
  - `- 통합 리뷰: 완료 (HEAD <해시>, 코드 지문 <해시>)`
  - 교차 리뷰를 수행한 모델
  - brief "확인 기준" 결과
  - 리뷰별 지적과 고침 여부, 건너뛴 리뷰와 이유, 범위 밖 문제

### 6. 머지·PR 결정

이 단계에 들어오면 [references/merge-stage.md](references/merge-stage.md)를 읽고 그 순서대로 한다. 리뷰가 지금 코드에 유효한지 확인한 뒤 결과를 모아 보여 주고 PR 만들기, 고치기, 멈추기 중 하나를 고르게 한다. 구현 중 새로 정한 설계 결정이 있으면 고르기 전에 [references/adr.md](references/adr.md)를 읽고 ADR 후보를 고른다.

### 7. PR 만들기

6단계에서 "PR 만들기"를 골랐을 때만 한다. 이 단계에 들어오면 [references/pr-stage.md](references/pr-stage.md)를 읽고 그 순서대로 한다. PR 본문은 사용자가 확인하기 전에는 push하지 않는다.
