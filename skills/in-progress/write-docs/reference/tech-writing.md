# 테크니컬 라이팅 원칙

출처: 토스 테크니컬 라이팅 가이드 https://technical-writing.dev/overview.html (원본 저장소 https://github.com/toss/technical-writing). 확인일: 2026-10-26

분야가 기술 문서일 때 적용한다. `clear-writing.md`와 부딪치면 이 파일을 따른다. 단, 사실·수량·근거를 지어내지 않는다는 원칙은 이 파일의 어떤 원칙보다 앞선다.

아래 예시는 합니다체로 적었다. 결과물의 어체는 사용자가 고른 톤을 따른다.

## 목차
- 출발점
- Step 1. 문서 유형 정하기
- Step 2. 정보 구조 만들기
- Step 3. 문장 다듬기

## 출발점

- 테크니컬 라이팅은 기술적인 내용을 정확하고 효과적으로 전달하는 글쓰기다. 목표는 독자가 문제를 해결하고 목표를 이루도록 돕는 것이다.
- 핵심 원칙은 문서 유형을 이해하고(Step 1), 정보를 효과적으로 구조화하고(Step 2), 이해하기 좋은 문장을 쓰는 것(Step 3)이다.
- 모든 원칙은 권장 사항이다. 상황에 맞게 유연하게 적용한다.

## Step 1. 문서 유형 정하기

독자의 목적에 따라 효과적인 문서 유형이 다르고, 유형마다 어느 정도 정해진 구조가 있다. 머릿속 지식을 그 유형의 구조에 맞게 재구성한다.

| 유형 | 언제 쓰나 | 권장 구조 |
|---|---|---|
| 학습 | 새 기술이나 도구를 처음 접해 전체 흐름을 파악할 때 | 제목 → 목표 → 사전 요구사항 → 단계별 가이드 → 최종 결과 확인 |
| 문제 해결 | 배경지식이 있는 독자가 사용 중 생긴 특정 문제를 해결할 때 | 제목 → 문제 정의 → 사전 요구사항 → 해결 방법 → 해결 후 확인 방법 |
| 참조 | 기본 작동법을 아는 독자가 기능이나 API의 매개변수, 반환 값, 예제를 확인할 때 | 제목 → 개요 → 속성·옵션(표) → 시그니처 → 반환 값 → 사용 예제 |
| 설명 | 개념, 원리, 배경, 기술이 등장한 이유를 깊이 이해할 때 | 제목 → 개념 소개 → 등장 배경 → 활용 |

- 학습 문서는 학습 목표를 명확히 제시하고 구체적인 예시, 실행 가능한 코드, 성공 경험을 준다. 예제는 실제로 실행했을 때 작동해야 한다.
- 문제 해결 문서는 다루는 문제나 질문을 명확히 하고 해결 방법을 구체적으로 제시한다.

## Step 2. 정보 구조 만들기

쓰는 사람은 자기가 말하고 싶은 내용 위주로 구조를 짜기 쉽다. 읽는 사람 입장에서 정보를 설계한다.

### 1. 한 페이지에서 하나만 다루기

- 최대한 구체적인 주제 하나만 다룬다.
- 제목 깊이가 H4(`####`) 이상이 되면 문서를 나누는 것을 고려하고, 개요 페이지를 활용한다.

### 2. 가치를 먼저 제공하기

- 기능 중심 설명을 피하고 독자가 얻을 가치를 먼저 전달한다.
- 부가 정보와 세부 사항은 뒤에 둔다.

### 3. 효과적인 제목 쓰기

- 제목에 핵심 키워드를 넣는다.
- 표기를 일관되게 유지한다.
- 30자 이내로 간결하게 쓴다.
- 평서문으로 쓴다.

### 4. 개요 빠트리지 않기

- 개요는 제목 바로 아래, 본문 앞에 둔다.
- 개요만 읽어도 주제와 목적을 알 수 있게 핵심 내용을 요약한다.
- "이 문서를 읽으면 무엇을 할 수 있는가?"에 답해 문서의 목표를 밝힌다.
- 기술적 배경보다 독자가 얻는 직접적인 가치를 먼저 쓴다. 길고 추상적으로 쓰지 않는다.
- 개요는 검색 결과에 함께 노출되고, 먼저 써 두면 쓰는 동안 초점을 지키는 데 도움이 된다.

### 5. 예측 가능하게 하기

- 같은 수준의 개념은 같은 위계로 정리해 제목, 형식, 구조를 일관되게 유지한다.
- 섹션 이름과 순서를 문서 전체에서 통일한다. 같은 내용을 한 문서는 "설치", 다른 문서는 "환경 설정"처럼 부르지 않는다.
- 예제 코드 앞에는 그 코드가 무엇을 하는지 설명하는 문장을 먼저 둔다.
- 정보는 핵심 개념 → 구체적인 사용법 → 예제 코드 → 심화 내용 순서로, 기본 개념부터 점진적으로 확장한다.
- 같은 개념은 같은 용어로 쓰고, 한 문서 안에서 영문 용어와 한글 용어를 섞어 쓰지 않는다. 예: "Error Handling"과 "오류 처리"를 혼용하지 않는다. 필요하면 용어사전이나 용어 가이드라인을 만든다.

### 6. 자세히 설명하기

- 새 개념이 나오면 한두 문장으로 정의하고, 필요하면 왜 알아야 하는지와 어디에 쓰이는지도 안내한다.
- 기능이 어떤 조건에서 어떻게 동작하는지, 입력, 상태, 시간에 따라 결과가 어떻게 달라지는지 설명한다. 필드 설명에는 값이 결정되는 조건과 단위를 함께 적는다.

## Step 3. 문장 다듬기

기술 문서의 독자이자 작업을 하는 사람은 보통 개발자다. 문장에 주어가 없어도 개발자를 주체로 놓고 쓴다. 독자가 운영자, 기획자, 고객처럼 개발자가 아니면 그 독자를 주체로 놓는다. 수동태를 피하거나 해요체를 쓰는 것만으로는 쉬운 글이 되지 않는다. 구조가 좋아도 문장이 어려우면 전달력이 떨어진다.

### 1. 문장의 주체를 분명하게 하기

- 도구, 기술, 시스템을 행동의 주체로 쓰지 않고, 독자가 할 수 있는 일을 중심으로 쓴다.
  - "이 라이브러리는 데이터베이스 초기화를 수행합니다" → "이 명령어를 실행하면 데이터베이스를 초기화할 수 있습니다"
- 예외: 도구의 동작 자체를 설명할 때는 도구를 주어로 쓸 수 있다. 예: "Impression 로그는 두 가지 방식으로 동작합니다"
- 능동형으로 쓴다.
  - "애플리케이션이 실행되기 전에 설정이 완료되어야 합니다" → "애플리케이션을 실행하기 전에 설정을 완료하세요"

### 2. 필요한 정보만 남기기

- 한 문장에는 생각 하나만 담는다. 여러 동작이 이어진 문장은 동작마다 나누고, 길게 늘인 조건문은 명령형으로 줄인다.
- 메타 담화('말에 대한 말')를 줄인다.
  - 문서 흐름 설명: "다음으로", "앞서 설명했듯이", "이제 알아보겠습니다"
  - 불필요한 강조: "사실은", "솔직히 말하면", "결론적으로"
  - 독자 반응 유도: "아시겠지만", "여러분도 아실 것입니다"
  - "아시다시피, 이 설정은 ~" → "이 설정은 성능에 영향을 줍니다"

### 3. 구체적으로 쓰기

받은 자료에 있는 사실로만 구체화한다. 아래 예시의 수치, 경로, 브라우저명은 예시일 뿐이다. 자료에 없는 값이 필요하면 지어내지 말고 `[확인 필요: 타임아웃 기본값]`처럼 표시해 남긴다.

1. 명사 대신 동사를 쓴다. "진행", "수행"처럼 동사에서 나온 명사를 피한다.
   - "코드 최적화 진행 후 배포 수행" → "코드를 최적화한 후 배포하세요"
2. 모호한 표현 대신 확실한 정보를 쓴다. "가능성이 있다", "일부 경우", "필요할 수도 있다"를 피한다.
   - "일부 브라우저에서 동작하지 않을 가능성" → "Internet Explorer에서는 정상적으로 동작하지 않습니다"
3. 누가, 무엇을, 어디에, 어떻게 하는지 빠짐없이 쓴다.
   - "로그를 확인하세요" → "애플리케이션 서버의 에러 로그 파일(`/var/log/app/error.log`)을 확인하세요"
4. 업계 관용 표현 대신 실제 동작이 드러나는 말을 쓴다.
   - "Exception을 던집니다" → "예외(`Exception`)를 일으킵니다"
5. 구체적인 수치와 기준을 쓴다. "많을 때", "빠르게"처럼 문맥에 기대는 말을 피한다.
   - "데이터가 많을 때 성능 저하" → "데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다"
6. 참조하는 내용의 맥락을 밝힌다. 다른 곳에서 나온 변수, 설정값, 개념을 다시 쓸 때는 처음 나온 위치를 알려 준다. 나중에 쓸 정보를 처음 꺼낼 때는 어디서 쓰이는지 알려 준다. 필요하면 링크를 건다.
   - "apiKey를 나중에 사용" → "1단계에서 저장한 API 키로 인증합니다"(1단계 링크)

### 4. 자연스러운 한국어 표현 쓰기

- 불필요한 한자어를 뺀다. "수행하다", "실행하다", "진행하다"는 빼도 뜻이 통하는 경우가 많다.
  - "로그 파일을 삭제하는 작업을 수행합니다" → "로그 파일을 삭제합니다"
- 번역체를 고친다. 영어식 명사형(-tion, -ing, -ment, -ance) 표현 대신 동사로 무엇을 하는지 쓴다.
  - "모니터링 수행을 통해 성능 측정 작업을 실시합니다" → "시스템을 모니터링해서 서버 성능을 측정합니다"
  - "이 API를 통해 데이터를 가져올 수 있습니다" → "이 API로 데이터를 가져올 수 있습니다"

### 5. 일관되게 쓰기

- 공식 기술 용어를 따른다. 위키피디아와 공식 문서의 표기를 따르고 대소문자도 맞춘다.
  - "K8" → "쿠버네티스(Kubernetes)", "자바스크립트" → "JavaScript"
- 같은 개념은 한 가지 표현으로 통일한다.
  - "추가", "첨부", "넣다"를 섞어 쓰지 않고 "업로드"로 통일
- 약어는 처음 나올 때 괄호 안에 전체 이름을 쓴다. 약어와 괄호 사이는 띄우지 않는다.
  - "SSR" → "SSR(Server-Side Rendering)", 또는 "클라이언트 사이드 렌더링(Client-Side Rendering, CSR)"
- 외래어는 맞춤법보다 실제로 많이 쓰는 표기를 따른다. 기준은 구글 트렌드에서 표준 표기보다 5배 이상 많이 쓰이는 표기다.
  - "프런트엔드" → "프론트엔드"
