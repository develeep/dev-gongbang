# 요구사항 정리

기획서를 읽고 요구사항과 개발 범위를 마크다운 문서로 정리한다. 이 문서는 개발자나 에이전트가 읽는다.

## 주의할 점

- 기획서에 없는 디테일이나 구체적인 부분을 채워 넣기 쉽다. 채우지 말고 사용자에게 묻거나 `확인 필요`로 남긴다. 개발자나 에이전트는 기획서 대신 이 문서를 읽으므로, 채워 넣은 내용이 확정된 요구사항처럼 읽힌다.

## 규칙

- 문서에는 기획서에 적힌 것과 사용자가 답한 것만 쓴다.
- 모호한 부분은 문서를 쓰기 전에 사용자에게 묻는다.
- 답을 받지 못한 항목은 해당 자리에 `확인 필요`로 표시하고, 문서 끝 "확인 필요" 목록에도 모은다. 읽는 사람이 정해지지 않은 부분을 알아볼 수 있게 하기 위해서다.
- 출처로 슬라이드 경로나 번호를 적지 않는다.

## 입력

인자로 받은 링크나 경로가 있으면 그 기획서를 읽는다. 인자에도 요청에도 기획서가 없으면 링크나 경로를 묻는다.

- SharePoint·OneDrive 같은 링크: 그 링크를 읽을 수 있는 커넥터나 MCP 도구가 있으면 그것으로 읽는다.
- PDF, PPT(X), MD 파일: 첨부나 경로로 받은 파일을 읽는다.

파일을 읽지 못하면 정리를 시작하지 않고, 그 링크를 읽을 수 있는 커넥터나 MCP 도구를 연결하라고 안내한다.

## 워크플로

아래 체크리스트를 복사해 진행 상황을 표시한다.

```
진행 상황:
- [ ] 1. 기획서 읽기
- [ ] 2. 모호한 부분 질문
- [ ] 3. 문서 작성
- [ ] 4. 검증
- [ ] 5. 저장
```

### 1. 기획서 읽기

기획서를 끝까지 읽고 섹션 구성과 등장하는 서비스, 개발 영역을 파악한다.

### 2. 모호한 부분 질문

모호한 부분을 번호 목록으로 한 메시지에 모아 묻고, 답을 받은 뒤 다음 단계로 넘어간다. 질문마다 무엇이 왜 모호한지 적는다.

### 3. 문서 작성

아래 템플릿을 따른다.

- "개발 범위"와 "요구사항"은 항상 넣는다.
- 그 밖의 섹션(as-is, to-be, 화면 목록, 기능 목록, 일정 등)은 기획서에 있는 것만 기획서 순서대로 넣는다. 기획서에 없는 섹션은 만들지 않는다.
- 개발 범위는 서비스명과 개발 영역(web, api 등)으로 나눈다. 기획서에서 서비스명이나 개발 영역을 알 수 없으면 2단계에서 묻는다.

```markdown
# <기획서 제목> 요구사항

## 개발 범위

| 서비스 | 개발 영역 | 내용 |
|---|---|---|
| <서비스명> | <web, api 등> | <이 영역에서 개발할 것> |

## 요구사항

- <요구사항>

## <기획서에 있는 섹션>

<섹션 내용>

## 확인 필요

- <항목>: <무엇이 정해지지 않았는지>
```

### 4. 검증

문서의 항목마다 기획서나 사용자 답에 근거가 있는지 확인한다. 근거가 없으면 지우거나 `확인 필요`로 바꾸고, 바꾼 문서를 다시 확인한다. 모든 항목에 근거가 있을 때 다음 단계로 넘어간다.

### 5. 저장

저장할 경로를 사용자에게 묻고, 받은 경로에 마크다운 파일로 저장한다.
