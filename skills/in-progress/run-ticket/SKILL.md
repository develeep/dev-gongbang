# Run Ticket

set-ticket이 만든 티켓을 새 세션에서 끝까지 실행한다. 이 세션에는 brief를 만든 대화가 없다. brief, 티켓, 앞 티켓의 완료 기록만 근거로 삼는다.

## 핵심 규칙

1. **brief와 티켓은 경로가 아니라 내용으로 찾는다.** brief는 `- 작성일: YYYY-MM-DD` 줄이 있는 문서이고, 티켓은 brief의 `## 티켓` 섹션 링크가 가리키는 문서다. 레포의 이슈 트래커 규칙이 정한 디렉터리나 파일 이름(`spec.md`, `issues/` 등)은 다른 스킬의 형식이므로 brief를 찾는 데 쓰지 않는다. 그 형식으로 찾으면 지난 작업 폴더를 고를 수 있다.
2. **완료 여부는 티켓 상태로 판단한다.** docs 티켓은 `- 상태: done`이면, GitHub 티켓은 closed이면 끝난 것이다. brief의 `## 티켓` 체크박스는 티켓 상태를 따른다. 둘이 어긋나면 체크박스를 고친다.
3. **커밋하지 않는다.** 레포 규칙이 커밋을 요구해도 사용자에게 맡기고, 커밋하지 않았다는 사실을 완료 기록에 남긴다. 예외는 "Orca 병렬 실행"이다. 자식 worktree는 커밋된 내용만 보므로, 워커가 티켓 브랜치에 커밋하고 이 세션이 현재 브랜치로 머지한다.
4. **티켓의 "하면 안 되는 것"·"작업 경계"가 레포 규칙보다, 레포 규칙이 이 스킬의 기본 동작보다 앞선다.** 티켓과 레포 규칙이 충돌하면 진행하기 전에 묻는다.
5. **앞 티켓의 결과는 다시 만들지 않는다.** 완료 기준이 앞 티켓의 산출물을 참조하는데 찾을 수 없으면 멈추고 알린다. "수정 전 동작"처럼 지금 다시 만들면 값이 달라지는 결과가 있다.

## 단계

아래 체크리스트를 시작할 때 한 번 보여 주고, 단계를 마칠 때마다 갱신한다.

```
티켓 실행:
- [ ] 1. 티켓 고르기
- [ ] 2. 맥락 읽기
- [ ] 3. 구현
- [ ] 4. 완료 기준 확인
- [ ] 5. 리뷰
- [ ] 6. 완료 기록
```

### 1. 티켓 고르기

**brief 목록**

- docs: `command grep -rlE --include='*.md' --exclude-dir=.git --exclude-dir=node_modules '^- 작성일: [0-9]{4}-[0-9]{2}-[0-9]{2}' .`로 찾는다. Grep 도구와 셸 함수(ugrep 등)로 바뀐 Bash `grep`은 `.gitignore`에 걸린 폴더(`.scratch/` 등)를 건너뛰므로 `command grep`으로 찾는다.
- GitHub: `git remote -v`에 github.com이 있고 `gh auth status`가 성공하면 `gh issue list --label context --state open --json number,title,body`도 본다.

**막힘 관계**: docs는 티켓의 `- 막힘 관계:` 줄, GitHub는 `gh api repos/{owner}/{repo}/issues/<번호>/dependencies/blocked_by`와 본문의 "막힘 관계" 섹션이다.

**참조가 있을 때**: 경로, 이슈 번호, URL이 가리키는 문서를 읽는다.

- 티켓이면 그 티켓을 작업한다.
- brief면 그 brief 안에서 아래 "참조가 없을 때"의 2번 규칙으로 고른다.
- 가리키는 문서가 없거나 둘 이상이면(예: 같은 번호의 이슈와 docs 티켓) 후보를 보여 주고 묻는다.
- 이미 done이거나 막힘 관계의 티켓 중 끝나지 않은 것이 있으면 알리고 진행 여부를 묻는다.

**참조가 없을 때**

1. `## 티켓`에 끝나지 않은 티켓이 남은 brief 중 작성일이 가장 늦은 brief를 고른다. 작성일이 같은 brief가 둘 이상이면 묻는다.
2. 그 brief의 끝나지 않은 티켓 중 막힘 관계의 티켓이 모두 끝난 것에서 번호가 가장 앞선 티켓을 고른다. 번호는 docs면 파일 이름의 NN, GitHub면 `## 티켓` 목록 순서다.

고를 brief가 없으면 그렇다고 알리고 멈춘다.

`## 티켓` 섹션이 없는 brief는 brief 전체를 티켓 하나로 본다. "남은 일"이 만들 것, "확인 기준"이 완료 기준이다. "남은 일"에 빈 체크박스가 있으면 끝나지 않은 것이다.

고른 brief와 티켓 제목을 한 줄로 알리고 바로 시작한다.

**작업 트리 확인**: `git status --porcelain`에 brief·티켓 문서 밖의 변경이 있으면, done 티켓의 완료 기록 "바꾼 파일"과 겹치는 것을 보여 주고 커밋한 뒤 진행할지 그대로 진행할지 묻는다. 그대로 진행하면 5단계 리뷰에 이전 변경이 섞인다.

### 2. 맥락 읽기

- 티켓 전문과 부모 brief 전문. GitHub는 `gh issue view <번호> --comments`로 읽는다.
- 같은 brief의 done 티켓에 있는 `## 완료 기록`과 `## 산출물`(GitHub는 완료 코멘트). 완료 기준이 "NN 티켓의 산출물"을 참조하면 여기서 찾는다. 없으면 핵심 규칙 5대로 멈춘다.
- 레포 규칙: 루트와 작업할 디렉터리의 CLAUDE.md·AGENTS.md, 거기서 가리키는 문서, `.claude/skills/`. 테스트 작성 규칙, 검증 명령(타입 검사, 린트, 테스트), 커밋 규칙을 확인한다. 규칙이 특정 스킬을 쓰라고 하면 그 스킬을 불러와 지시를 따른다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다.

### 3. 구현

"만들 것"을 구현한다.

에이전트 규칙이 티켓 구현을 맡을 에이전트를 정해 두었으면 그 에이전트에 맡기고, 4단계는 직접 확인한다. 넘길 것: brief 전문, 티켓 전문, 2단계에서 찾은 레포 규칙 파일 경로와 검증 명령, 앞 티켓의 `## 산출물`. 서브에이전트는 받지 못한 규칙과 산출물을 스스로 찾지 못한다. 정해 둔 에이전트가 없으면 직접 구현한다.

- 테스트는 레포 규칙이 요구하거나 바꾸는 동작에 이미 테스트가 있을 때 함께 쓴다. 레포 규칙이 테스트를 쓰지 않는다고 하면 쓰지 않는다.
- 타입 검사와 바꾼 부분의 테스트를 자주 돌린다.
- 티켓 범위 밖의 문제는 고치지 않고 보고에 남긴다.

### 4. 완료 기준 확인

완료 기준을 하나씩 명령이나 관찰로 확인한다. 전체 테스트 스위트가 있으면 마지막에 한 번 돌린다. 막힘 관계에 `(통합 브랜치 공유)`가 있는 티켓은 전체 테스트 스위트를 돌리지 않는다. 그 묶음의 초록은 마지막 "통합 및 검증" 티켓에서만 약속한다.

화면에서 관찰해야 하는 완료 기준은, 에이전트 규칙이 UI 확인을 맡을 에이전트를 정해 두었으면 그 에이전트에 맡겨 확인한다. 확인하지 못한 항목은 통과로 치지 않고 완료 기록의 "확인 못 한 것"에 적는다.

통과하지 못한 기준은 고친다. 고칠 수 없으면 티켓 상태를 바꾸지 않고, 통과하지 못한 기준과 이유를 보고하고 멈춘다.

### 5. 리뷰

이번 변경을 아래 세 가지로 리뷰한다. 이번 변경은 작업 시작 HEAD 이후의 커밋하지 않은 변경과 새 파일이고, Orca 병렬 실행에서는 시작 HEAD부터 HEAD까지의 커밋이다. 세 리뷰는 서로 기다리지 않으므로 서브에이전트를 띄울 수 있으면 함께 띄운다.

**코드 리뷰**: 아래 순서에서 처음 맞는 방법을 쓴다.

1. 레포 규칙이 지정한 리뷰 스킬을 불러와 그 지시를 따른다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다.
2. 사용 가능한 스킬에 `code-review`나 `<플러그인>:code-review`가 있으면 그 스킬을 불러와 따른다. 여럿이면 설명을 보고 이번 변경을 볼 수 있는 것을 고르고, 그래도 여럿이면 접두사 없는 것을 고른다. 커밋하지 않은 변경은 커밋 범위(`<기준>...HEAD`)만 보는 스킬이 보지 못하고, 커밋 범위는 작업 트리만 보는 스킬이 보지 못한다.
3. 맞는 스킬이 없거나 호출이 실패하면 직접 리뷰한다. `git diff`와 새 파일(커밋 범위면 `git diff <시작 HEAD> HEAD`)을 읽고 버그, 티켓의 "하면 안 되는 것"·"작업 경계" 위반, 레포 규칙 위반을 찾는다.

리뷰 스킬이 서브에이전트를 띄우게 하고, 에이전트 규칙이 그 하위 리뷰를 맡을 에이전트를 정해 두었으면 그 에이전트로 띄운다.

**규칙 검사**: `check-guidelines` 스킬을 불러와 바꾼 파일 경로를 범위로 검사하고 보고까지만 받는다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다. 그 스킬을 찾을 수 없으면 건너뛰고 보고에 적는다.

**교차 리뷰**: 이 세션과 다른 회사의 모델에게 이번 변경의 diff 범위와 brief를 넘겨 리뷰를 맡긴다. 같은 회사의 모델은 같은 실수를 함께 놓치기 쉽다. 아래 순서에서 처음 되는 방법을 쓴다.

1. 레포나 에이전트 규칙이 교차 리뷰를 맡을 에이전트를 정해 두었으면 그 에이전트에 맡긴다.
2. `orchestration` 스킬을 불러올 수 있으면 다른 회사 모델을 쓰는 에이전트(이 세션이 Claude면 Codex, 그 밖이면 Claude Code)를 Orca 워커로 띄워 맡기고 결과를 받는다.
3. 둘 다 안 되면 건너뛰고 보고에 적는다.

리뷰를 실제로 수행한 모델을 확인할 수 있으면 확인한다. 이 세션과 같은 회사의 모델이었으면 교차 리뷰로 치지 않고 "교차 리뷰 건너뜀(같은 회사 모델 <모델 이름>)"으로 보고한다. 모델을 쓸 수 없을 때 다른 모델로 넘어가는 설정이 있으면 리뷰어가 조용히 바뀐다. 확인할 수 없으면 보고에 "교차 리뷰 수행 모델 확인 불가"라고 적는다.

**보안 리뷰**: 이번 변경이 인증, 권한, 결제, 개인정보를 다루고 에이전트 규칙이 보안 리뷰를 맡을 에이전트를 정해 두었으면, 그 에이전트에도 diff 범위와 brief를 넘겨 맡긴다. 아니면 하지 않는다.

맡긴 리뷰의 결과를 모두 받기 전에는 6단계로 넘어가지 않는다. 결과 없이 완료 기록을 쓰면 리뷰 지적이 보고에서 빠진다. 티켓 범위 안의 지적은 고치고 4단계 기준을 다시 확인한다. 범위 밖 지적은 고치지 않고 보고에 남긴다.

### 6. 완료 기록

**산출물**: 다음 결과를 티켓에 남긴다.

- "만들 것"이나 완료 기준이 산출물로 남기라고 한 결과
- 같은 brief의 다른 티켓이 "NN 티켓의 산출물"로 참조하는 결과

체크리스트, 측정값, 조사 내용 같은 텍스트는 내용을 그대로 넣고, 코드나 파일은 저장소 경로를 적는다.

**docs 티켓**

1. `- 상태: ready-for-agent`를 `- 상태: done`으로 바꾼다.
2. 통과한 완료 기준의 `- [ ]`를 `- [x]`로 바꾼다.
3. 파일 끝에 아래 기록을 붙인다. 산출물이 없으면 `## 산출물` 섹션을 지우고, 해당 없는 줄도 지운다.
4. brief `## 티켓`의 해당 줄을 `- [x]`로 바꾼다. brief의 다른 부분은 고치지 않는다. `## 티켓`이 없는 brief면 "남은 일" 체크박스를 바꾸고 기록을 brief 끝에 붙인다.

```markdown
## 완료 기록
- 완료일: YYYY-MM-DD
- 커밋: 안 함 (작업 시작 HEAD `<해시>`)
- 바꾼 파일: `<경로>`, `<경로>`
- 확인한 것: `<명령>` → <결과> (확인한 HEAD `<해시>`, 커밋 전이면 "작업 트리")
- 확인 못 한 것: <기준>: <이유>
- 고치지 않은 지적: <지적>: <이유>

## 산출물
<내용 또는 저장소 경로>
```

**GitHub 티켓**

1. 위 기록을 임시 파일에 저장하고 `gh issue comment <번호> --body-file <임시 파일>`로 남긴 뒤 `gh issue close <번호>`로 닫는다.
2. `gh issue view <brief 번호> --json body --jq .body`로 받은 본문에서 `- [ ] #<번호>`를 `- [x] #<번호>`로 바꾸고 `gh issue edit <brief 번호> --body-file <임시 파일>`로 올린다. 임시 파일을 지운다. `## 티켓`이 없는 brief면 "남은 일" 체크박스를 바꾼 본문을 올리고, 기록은 brief 이슈에 코멘트로 남긴다.

**마지막 티켓이면** brief의 "확인 기준"을 실행해 결과를 보고하고, 남은 티켓이 없으므로 brief를 닫는다. GitHub brief는 `gh issue close <brief 번호>`로 닫는다. docs brief는 닫을 상태가 없으므로 체크박스가 모두 체크된 것으로 끝난 것을 나타낸다. 체크박스와 덧붙인 완료 기록 말고 brief 본문은 고치지 않는다. "여러 티켓 실행"에서는 이 일을 티켓마다 하지 않고 마무리 리뷰 뒤에 한 번 한다.

**보고**: 한 메시지에 다음을 담는다. 끝낸 티켓, 완료 기준 결과, 바꾼 파일, 산출물 위치, 고치지 않은 리뷰 지적, 건너뛴 리뷰와 이유, 다음 티켓, 커밋은 사용자가 한다는 안내.

## 여러 티켓 실행

사용자나 다른 스킬이 번호 범위나 "남은 티켓 전부"처럼 여러 티켓을 요청할 때만 쓴다. 기본은 호출 한 번에 티켓 하나다.

대상 티켓과 막힘 관계를 1단계 규칙으로 모은 뒤 실행 방법을 고른다. 아래를 모두 만족하면 "Orca 병렬 실행"을, 하나라도 아니면 "차례 실행"을 한다.

- `orchestration` 스킬을 불러올 수 있고 그 지시대로 Orca 명령이 실행된다.
- 막힘 관계로 함께 시작할 수 있는 티켓이 둘 이상인 때가 있다. 티켓이 하나이거나 막힘 관계가 일렬이면 병렬 이득 없이 worktree와 머지 비용만 든다.
- 대상 티켓의 막힘 관계 줄에 `(통합 브랜치 공유)`가 없다. 그 티켓들은 티켓별 worktree에서 묶음 하나만으로 4단계를 통과할 수 없다.

두 방법 모두 서브에이전트나 워커에게 이 파일의 절대 경로를 넘긴다. 스킬 도구가 없는 워커도 읽을 수 있고, 수행할 단계만 골라 지시할 수 있다.

### Orca 병렬 실행

티켓마다 Orca 워커가 child worktree의 새 브랜치에서 구현하고 커밋한다. 이 세션은 코디네이터로서 막힘 관계 순서를 지키고, 끝난 브랜치를 현재 브랜치로 머지하고, 완료 기록을 남긴다.

1. **준비**: 작업 트리가 깨끗한지 확인한다. 자식 worktree는 HEAD에서 갈라지므로 커밋하지 않은 brief·티켓 문서를 워커가 읽지 못한다. 커밋하지 않은 것이 brief·티켓 문서뿐이면 커밋할지 묻고, 다른 변경이 있으면 커밋하거나 치운 뒤 다시 실행하라고 알리고 멈춘다.
2. **계획 승인**: 커밋과 머지가 생기므로 시작하기 전에 다음을 보여 주고 승인을 받는다.
   - 실행 묶음: 막힘 관계로 함께 시작할 수 있는 티켓끼리 묶은 순서
   - 머지할 브랜치. 현재 브랜치가 기본 브랜치(`main` 등)면 작업 브랜치를 새로 만들지 함께 묻는다.
   - 동시에 띄울 워커 수: 기본 3개. 워커마다 서브에이전트를 더 띄우므로 많이 띄우면 요청 한도에 걸린다.
   - 시작 HEAD 해시
3. **Task 만들기**: 같은 brief를 목표로 한 Run이 남아 있으면 새로 만들지 않고 이어 받고, 끝난 Task는 다시 띄우지 않는다. 없으면 brief 제목을 목표로 Run 하나를 만들고, 티켓마다 Task를 만들어 막는 티켓의 Task를 deps로 건다.
   - 이어 받은 Run에 끝난 Task가 있는데 그 티켓이 done이 아니면, 워커는 커밋했지만 머지하기 전에 끊긴 것이다. 티켓 브랜치가 `git branch --no-merged`에 있으면 5번의 "통과" 처리부터 한다. 브랜치가 없으면 멈추고 알린다. 다시 띄우면 같은 티켓을 두 번 구현한다.
   - 머지가 진행 중인 채로 끊겼으면(`git status`에 merging 표시) `git merge --abort`로 되돌린 뒤 위와 같이 처리한다.
   - GitHub 티켓이 머지됐는데 열려 있으면 완료 코멘트를 남기고 닫기만 한다.
4. **워커 띄우기**: 막는 티켓이 모두 머지된 Task를 동시 워커 수까지 띄운다. Orca가 deps를 풀어도 머지 전이면 기다린다. 워커는 이 세션과 같은 에이전트로, 현재 브랜치에서 갈라진 새 child worktree에 띄운다. 워커 spec:
   ```
   <이 SKILL.md의 절대 경로>를 읽고 티켓 <참조>에 대해 2, 3, 4단계를 수행하라. 1, 5, 6단계는 건너뛰고 brief와 티켓 문서는 그대로 둔다.
   4단계를 통과하면 레포 커밋 규칙대로 이 worktree의 브랜치에 커밋하라. 통과하지 못하면 커밋하지 말고 실패로 보고하라.
   끝나면 완료 기준 결과, 바꾼 파일, 산출물 내용, 브랜치 이름, 커밋 해시를 보고하라.
   ```
5. **워커가 끝나면** 결과에 따라 처리한다.
   - 통과: 현재 브랜치에서 `git merge --no-ff --no-commit <티켓 브랜치>`로 합치고, 머지 커밋을 만들기 전에 합친 작업 트리에서 레포 검증 명령(타입 검사, 린트, 테스트)을 돌린다. 워커는 갈라진 시점의 worktree에서만 확인했으므로, 텍스트 충돌 없이 앞서 머지한 티켓과 어긋나는 변경은 여기서만 드러난다. 검증을 통과하면 그 티켓의 6단계 완료 기록을 남긴 뒤 레포 커밋 규칙대로 커밋한다. 완료 기록의 커밋 줄은 ``- 커밋: 티켓 브랜치 `<브랜치>`의 `<해시>`를 머지``로 쓴다. 완료 기록이 머지 커밋에 들어가야 뒤 티켓의 worktree가 산출물을 읽는다. 머지한 뒤 워커를 놓아주고 그 worktree를 브랜치와 함께 지운다.
   - 통합 검증 실패: `git merge --abort`로 되돌리고, 실패한 명령과 출력을 보여 준 뒤 새 워커를 띄우지 않고 멈춘다. 실패 원인이 방금 머지한 티켓과 앞서 머지한 티켓 중 어느 쪽인지 알 수 없기 때문이다. 그 티켓의 worktree는 남긴다.
   - 막는 티켓의 교차 리뷰: 머지한 티켓이 다른 티켓을 막으면, 막힌 Task를 띄우기 전에 그 머지 커밋의 diff(`HEAD^..HEAD`)에 5단계의 교차 리뷰만 한다. 지적은 고쳐 레포 커밋 규칙대로 커밋한다. 결함 위에 뒤 티켓이 쌓이면 마무리 리뷰에서 고칠 범위가 여러 티켓으로 커진다.
   - 머지 충돌: `git merge --abort`로 되돌리고, 그 워커에게 현재 브랜치 위로 리베이스해 충돌을 풀고 4단계를 다시 확인한 뒤 커밋하라고 보낸다. 다시 충돌하면 그 티켓을 멈추고 사용자에게 알린다.
   - 실패: 그 티켓과 그 티켓에 막힌 티켓은 띄우지 않는다. 실행 중인 워커는 끝까지 기다려 머지한다. 실패한 티켓의 worktree는 사용자가 볼 수 있게 남긴다.
   - 질문: brief와 티켓으로 답할 수 있으면 답하고, 아니면 사용자에게 물어 답을 전한다.
6. **마무리**: 모든 Task가 끝나면 시작 HEAD부터 HEAD까지에 5단계 리뷰를 한 번 한다. 고친 내용은 레포 커밋 규칙대로 커밋하고, 고친 부분이 걸친 티켓의 완료 기준을 다시 확인한다. 그 뒤 6단계의 "마지막 티켓이면"을 한다. brief의 "확인 기준"은 모든 티켓을 합친 HEAD에서 확인해야 티켓 사이의 어긋남을 잡는다.
7. 티켓별 결과를 6단계 보고 형식으로 모아 알린다. 커밋 안내 대신 만든 커밋 목록을 넣고, push·PR·기본 브랜치 머지는 사용자가 정한다고 알린다.

### 차례 실행

1. 1단계의 작업 트리 확인을 한 번 한다.
2. 대상 티켓의 순서를 1단계 규칙(막힘 관계, 번호)으로 정해 보여 준다.
3. 티켓마다 새 컨텍스트로 서브에이전트 하나를 띄우고, 끝나면 다음 티켓을 띄운다. 띄울 수 없으면 같은 세션에서 티켓을 차례로 2, 3, 4, 6단계대로 한다.
   ```
   <이 SKILL.md의 절대 경로>를 읽고 티켓 <참조>에 대해 2, 3, 4, 6단계를 수행하라. 1단계와 5단계, 6단계의 "마지막 티켓이면"은 건너뛴다. 끝나면 완료 기준 결과, 바꾼 파일, 산출물 위치만 보고하라.
   ```
4. 완료 기준을 통과하지 못한 티켓이 나오면 멈춘다. 뒤 티켓이 그 결과에 기댈 수 있다.
5. 모든 서브에이전트가 끝나면 전체 변경에 5단계 리뷰를 한 번 하고, 고친 부분이 걸친 티켓의 완료 기준을 다시 확인한다. 그 뒤 6단계의 "마지막 티켓이면"을 한다.
6. 티켓별 결과를 6단계 보고 형식으로 모아 알린다.

서브에이전트는 하나씩 띄운다. 커밋하지 않으므로 같은 작업 트리를 동시에 고치면 충돌한다.
