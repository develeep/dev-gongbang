# Run Ticket

set-ticket이 만든 티켓을 끝까지 실행한다. run-flow에서 이어 실행하면 brief를 만든 대화가 같은 세션에 남아 있을 수 있지만, 그래도 brief, 티켓, 앞 티켓의 완료 기록만 근거로 삼는다.

## 핵심 규칙

1. **brief와 티켓은 경로가 아니라 내용으로 찾는다.** brief는 `- 작성일: YYYY-MM-DD` 줄이 있는 문서이고, 티켓은 brief의 `## 티켓` 섹션 링크가 가리키는 문서다. 레포의 이슈 트래커 규칙이 정한 디렉터리나 파일 이름(`spec.md`, `issues/` 등)은 다른 스킬의 형식이므로 brief를 찾는 데 쓰지 않는다. 그 형식으로 찾으면 지난 작업 폴더를 고를 수 있다.
2. **완료 여부는 티켓 상태로 판단한다.** docs 티켓은 `- 상태: done`이면, GitHub 티켓은 closed이면 끝난 것이다. 레포 규칙이나 run-flow 상태 파일의 `## 결정`이 완료 표시를 다른 값으로 정했으면, 이 스킬에서 `done`은 그 값을 뜻하고 읽을 때와 쓸 때 모두 그 값을 쓴다. `done`과 섞어 쓰면 다음 실행이 끝난 티켓을 끝나지 않은 것으로 판정한다. brief의 `## 티켓` 체크박스는 티켓 상태를 따른다. 둘이 어긋나면 체크박스를 고친다.
3. **커밋하지 않는다.** 레포 규칙이 커밋을 요구해도 사용자에게 맡기고, 커밋하지 않았다는 사실을 완료 기록에 남긴다. 예외는 "여러 티켓 실행"의 병렬 실행이다. 워커의 worktree는 커밋된 내용만 보므로, 워커가 티켓 브랜치에 커밋하고 이 세션이 현재 브랜치로 머지한다.
4. **티켓의 "하면 안 되는 것"·"작업 경계"가 레포 규칙보다, 레포 규칙이 이 스킬의 기본 동작보다 앞선다.** 티켓과 레포 규칙이 충돌하면 진행하기 전에 묻는다.
5. **앞 티켓의 결과는 다시 만들지 않는다.** 완료 기준이 앞 티켓의 산출물을 참조하는데 찾을 수 없으면 멈추고 알린다. "수정 전 동작"처럼 지금 다시 만들면 값이 달라지는 결과가 있다.

## 주의할 점

- Grep 도구와 셸 함수(ugrep 등)로 바뀐 Bash `grep`은 `.gitignore`에 걸린 폴더(`.scratch/` 등)를 건너뛴다. brief는 그런 폴더에도 있을 수 있으므로 `command grep`으로 찾는다.
- 교차 리뷰를 맡는 새 컨텍스트와 병렬 실행의 워커는 이 세션의 대화와 에이전트 규칙 파일을 받지 못하고, 넘겨받지 않은 레포 규칙과 산출물을 스스로 찾지 못한다. 맡길 때 필요한 것을 모두 넘긴다.
- 커밋하지 않은 변경은 커밋 범위(`<기준>...HEAD`)만 보는 리뷰 스킬이 보지 못하고, 커밋 범위는 작업 트리만 보는 리뷰 스킬이 보지 못한다. 리뷰 스킬을 고를 때 이번 변경이 어느 쪽인지 먼저 본다.
- 이 세션의 모델을 바꿔 두었거나 모델을 쓸 수 없을 때 다른 모델로 넘어가는 설정이 있으면, 교차 리뷰를 맡기로 정해 둔 수단이 구현한 모델과 같은 회사 모델로 실행될 수 있다. 교차 리뷰는 계획한 모델이 아니라 실제로 수행한 모델로 판정한다.
- 새로 만든 worktree는 커밋된 내용만 본다. 병렬 실행의 워커는 커밋하지 않은 brief, 티켓, 완료 기록을 읽지 못한다.

## 단계

아래 체크리스트를 시작할 때 한 번 보여 주고, 단계를 마칠 때마다 갱신한다.

```
티켓 실행:
- [ ] 1. 티켓 고르기
- [ ] 2. 맥락 읽기
- [ ] 3. 구현
- [ ] 4. 완료 기준 확인
- [ ] 5. 리뷰
- [ ] 6. 완료 기록
```

### 1. 티켓 고르기

**brief 목록**

- docs: `command grep -rlE --include='*.md' --exclude-dir=.git --exclude-dir=node_modules '^- 작성일: [0-9]{4}-[0-9]{2}-[0-9]{2}' .`로 찾는다.
- GitHub: `git remote -v`에 github.com이 있고 `gh auth status`가 성공하면 `gh issue list --label context --state open --json number,title,body`도 본다.

**막힘 관계**: docs는 티켓의 `- 막힘 관계:` 줄, GitHub는 `gh api repos/{owner}/{repo}/issues/<번호>/dependencies/blocked_by`와 본문의 "막힘 관계" 섹션이다.

**참조가 있을 때**: 경로, 이슈 번호, URL이 가리키는 문서를 읽는다.

- 티켓이면 그 티켓을 작업한다.
- brief면 그 brief 안에서 아래 "참조가 없을 때"의 2번 규칙으로 고른다.
- 가리키는 문서가 없거나 둘 이상이면(예: 같은 번호의 이슈와 docs 티켓) 후보를 보여 주고 묻는다.
- 이미 done이거나 막힘 관계의 티켓 중 끝나지 않은 것이 있으면 알리고 진행 여부를 묻는다.

**참조가 없을 때**

1. `## 티켓`에 끝나지 않은 티켓이 남은 brief 중 작성일이 가장 늦은 brief를 고른다. 작성일이 같은 brief가 둘 이상이면 묻는다.
2. 그 brief의 끝나지 않은 티켓 중 막힘 관계의 티켓이 모두 끝난 것에서 번호가 가장 앞선 티켓을 고른다. 번호는 docs면 파일 이름의 NN, GitHub면 `## 티켓` 목록 순서다.

고를 brief가 없으면 그렇다고 알리고 멈춘다.

`## 티켓` 섹션이 없는 brief는 brief 전체를 티켓 하나로 본다. "남은 일"이 만들 것, "확인 기준"이 완료 기준이다. "남은 일"에 빈 체크박스가 있으면 끝나지 않은 것이다.

고른 brief와 티켓 제목을 한 줄로 알리고 바로 시작한다.

**작업 트리 확인**: `git status --porcelain`에 brief·티켓 문서 밖의 변경이 있으면, done 티켓의 완료 기록 "바꾼 파일"과 겹치는 것을 보여 주고 커밋한 뒤 진행할지 그대로 진행할지 묻는다. 그대로 진행하면 5단계 리뷰에 이전 변경이 섞인다. done 티켓의 "바꾼 파일"에 없는 변경은 끊긴 티켓의 미완성 변경일 수 있으므로 따로 보여 주고, 이 티켓이 건드리지 않는 파일이어도 되돌릴지 이어서 쓸지 묻는다. 이어서 쓰면 그 변경을 그대로 두고, 이 티켓이 그 파일을 건드리면 3단계에서 그 변경을 먼저 읽고 그 위에 이어서 구현한다. 구분 없이 진행하면 절반만 된 변경 위에서 처음부터 다시 구현한다.

### 2. 맥락 읽기

- 티켓 전문과 부모 brief 전문. GitHub는 `gh issue view <번호> --comments`로 읽는다.
- 같은 brief의 done 티켓에 있는 `## 완료 기록`과 `## 산출물`(GitHub는 완료 코멘트). 완료 기준이 "NN 티켓의 산출물"을 참조하면 여기서 찾는다. 없으면 핵심 규칙 5대로 멈춘다.
- 레포 규칙: 루트와 작업할 디렉터리의 CLAUDE.md·AGENTS.md, 거기서 가리키는 문서, `.claude/skills/`. 테스트 작성 규칙, 검증 명령(타입 검사, 린트, 테스트), 커밋 규칙을 확인한다. 규칙이 특정 스킬을 쓰라고 하면 그 스킬을 불러와 지시를 따른다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다.

### 3. 구현

"만들 것"을 이 세션이 직접 구현한다. 서브에이전트나 다른 에이전트에 구현을 맡기지 않는다. 맥락을 읽은 세션이 구현해야 도중에 드러난 것을 바로 반영하고, 맡길 때 빠지는 내용이 없다. 예외는 "여러 티켓 실행"의 병렬 실행뿐이고, 그때는 티켓을 받은 워커가 이 단계를 직접 한다. 부른 쪽이 이미 내린 결정이나 앞선 실패 기록을 넘겼으면 그 결정을 따르고, 실패 기록에 있는 시도는 되풀이하지 않고 그다음부터 센다.

- 테스트는 레포 규칙이 요구하거나 바꾸는 동작에 이미 테스트가 있을 때 함께 쓴다. 레포 규칙이 테스트를 쓰지 않는다고 하면 쓰지 않는다.
- 타입 검사와 바꾼 부분의 테스트를 자주 돌린다.
- 티켓 범위 밖의 문제는 고치지 않고 보고에 남긴다.
- 부른 쪽이 보호 경로 검사를 넘겼으면 그 보호 목록의 파일(시작 HEAD에 있던 테스트, 판정용 사례, 앞서 수락한 테스트)은 셸로도 고치지 않는다. 그 파일을 고쳐야만 완료 기준을 통과할 수 있으면 고치지 않고 멈춰 사용자에게 묻는다. 새 테스트 파일은 만들어도 된다.

### 4. 완료 기준 확인

완료 기준을 하나씩 명령이나 관찰로 확인한다. 전체 테스트 스위트가 있으면 마지막에 한 번 돌린다. 막힘 관계에 `(통합 브랜치 공유)`가 있는 티켓은 전체 테스트 스위트를 돌리지 않는다. 그 묶음의 초록은 마지막 "통합 및 검증" 티켓에서만 약속한다.

화면에서 관찰해야 하는 완료 기준도 이 세션이 직접 확인한다. 브라우저를 다루거나 화면을 캡처해 볼 수단이 있으면 화면을 열어 기준을 하나씩 보고, 본 것(연 주소, 한 조작, 캡처 경로)을 근거로 남긴다. 그런 수단이 없거나 확인하지 못한 항목은 통과로 치지 않고 완료 기록의 "확인 못 한 것"에 이유와 함께 적는다.

통과하지 못한 기준은 이 세션이 같은 루프에서 고친다. 실패한 명령과 출력에서 원인을 정리한 뒤 고치고 이 단계를 다시 확인한다. 다른 에이전트에 다시 맡기거나 올리지 않는다. 시도 한 번은 구현하거나 고친 뒤 이 단계를 한 번 확인한 것이고, 최초 시도를 포함해 3회까지 한다. 같은 방법을 되풀이하지 않도록 시도마다 무엇을 바꿨고 왜 실패했는지 적어 둔다. 3회째에도 통과하지 못하면 멈춘다.

멈출 때는 티켓 상태를 바꾸지 않고, 통과하지 못한 기준, 시도 횟수, 시도마다의 실패 원인을 보고한다. 부른 쪽이 기록 파일을 넘겼으면 멈춘 이유를 적는 자리(run-flow 상태 파일은 `- 멈춘 이유:` 줄)에 같은 내용을 바로 적는다. 그다음 그 티켓을 다시 나눌지 묻는다. 부른 스킬이 이 질문을 하게 돼 있으면 그 스킬이 묻는다. 더 강한 모델이 필요해 보이면 사용자가 세션 모델을 바꿔 다시 실행할 수 있다고 함께 알린다.

### 5. 리뷰

이번 변경을 세 가지로 리뷰한다. 코드 리뷰와 규칙 검사는 이 세션이 차례로 직접 하고, 교차 리뷰는 새 컨텍스트에 한 번 맡긴다. 리뷰를 서브에이전트 여럿에 나눠 맡기지 않는다. 새 컨텍스트에 맡기는 리뷰는 교차 리뷰 하나다.

작업 시작 HEAD는 이 실행을 시작할 때의 HEAD이고, 부른 쪽이 기준 커밋을 넘겼으면 그 커밋이다. 이번 변경은 작업 시작 HEAD 이후의 커밋하지 않은 변경과 새 파일이고, 병렬 실행에서는 작업 시작 HEAD부터 HEAD까지의 커밋이다. 부른 쪽이 범위를 정해 주었거나 작업 시작 HEAD 뒤에 커밋과 커밋하지 않은 변경이 함께 있으면, 커밋, 커밋하지 않은 변경, 새 파일을 모두 본다(`git diff <작업 시작 HEAD>`와 `git status --porcelain`의 새 파일).

**코드 리뷰**: 이 세션이 아래 순서에서 처음 맞는 방법으로 한다.

1. 레포 규칙이 지정한 리뷰 스킬을 불러와 그 지시를 따른다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다.
2. 사용 가능한 스킬에 `code-review`나 `<플러그인>:code-review`가 있으면 그 스킬을 불러와 따른다. 여럿이면 설명을 보고 이번 변경을 볼 수 있는 것을 고르고, 그래도 여럿이면 접두사 없는 것을 고른다.
3. 맞는 스킬이 없거나 호출이 실패하면 직접 리뷰한다. `git diff`와 새 파일(커밋 범위면 `git diff <작업 시작 HEAD> HEAD`)을 읽고 버그, 티켓의 "하면 안 되는 것"·"작업 경계" 위반, 레포 규칙 위반을 찾는다.

리뷰 스킬은 하위 리뷰를 맡기지 않는 방식으로 돌린다. 그 스킬이 서브에이전트를 띄워 하위 리뷰를 하라고 하면 띄우지 않고, 하위 리뷰마다 볼 것을 이 세션이 차례로 직접 본다. 하위 리뷰를 맡기지 않고는 실행할 수 없는 스킬이면 그 스킬을 쓰지 않고 3번의 직접 리뷰로 내려가고, 쓰지 않은 스킬과 이유를 보고에 적는다.

**규칙 검사**: 이 세션이 `check-guidelines` 스킬을 불러와 바꾼 파일 경로를 범위로 검사하고 보고까지만 받는다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다. 그 스킬을 찾을 수 없으면 건너뛰고 보고에 적는다.

코드 리뷰와 규칙 검사에서 나온 티켓 범위 안의 지적은 고치고 4단계 기준을 다시 확인한다. 범위 밖 지적은 고치지 않고 보고에 남긴다. 그 뒤에 교차 리뷰를 부른다.

**교차 리뷰**: 이번 변경을 구현한 모델과 다른 회사의 모델에게 읽기 전용 리뷰를 한 번 맡기고, 돌아온 지적을 이 세션이 검증한다. 구현한 모델은 이 세션의 모델이고, 병렬 실행에서 머지한 티켓은 그 티켓을 구현한 워커의 모델이다. 같은 회사의 모델은 같은 실수를 함께 놓치기 쉽다. 리뷰어는 사용자와 대화하지 않고 다음 단계를 정하지 않는다. 결과를 받으면 이 세션이 같은 대화에서 이어 간다. 교차 리뷰를 하지 않고 이 단계를 끝내는 경로는 없다.

- **넘기는 것**: 아래 셋을 넘긴다. 리뷰어는 이 세션의 대화를 모르므로 이것만으로 일할 수 있어야 한다. 비밀값(토큰, 키, 비밀번호)과 원문 로그는 넘기지 않는다.
  - 리뷰할 diff 범위: 작업 시작 HEAD와, 위에서 정한 이번 변경을 읽는 명령
  - brief 전문. 티켓 하나를 리뷰하면 그 티켓 전문도 넘긴다
  - 볼 기준 목록: 버그, 티켓의 "하면 안 되는 것"·"작업 경계" 위반과 레포 규칙 위반(2단계에서 찾은 레포 규칙 파일 경로를 함께 적는다). 이번 변경이 인증, 권한, 결제, 개인정보를 다루면 보안을 더한다. 보안 리뷰를 따로 부르지 않고 이 기준으로 본다
- **권한**: 읽기 전용이다. 파일을 고치거나 커밋하지 말고 저장소 밖에도 쓰지 말라고 지시한다. 지시만으로는 막히지 않으므로, 부르기 직전과 결과를 받은 직후에 코드 지문을 구해 비교한다. 코드 지문은 아래 두 명령의 출력(HEAD 해시, 그리고 커밋하지 않은 변경과 새 파일을 포함한 작업 트리의 tree 해시)이다. 두 번째 명령은 git이 담을 수 없는 특수 파일(장치 파일 등)을 건너뛴다. 그래도 실패하면(명령이 허용되지 않는 때 등) 멈추지 않고 `git rev-parse HEAD`, `git status --porcelain`, `git diff HEAD`의 출력을 지문으로 삼아 같은 방법으로 비교하고, 그렇게 했다고 보고에 적는다. 그 사이에 이 세션은 파일을 고치지 않는다. 지문이 달라졌으면 그 리뷰 결과를 쓰지 않고, 바뀐 것(`git status --porcelain`, `git diff`)을 사용자에게 보여 준 뒤 아래 순서의 다음 수단에 다시 맡긴다.
  ```bash
  git rev-parse HEAD
  GIT_INDEX_FILE="$(git rev-parse --absolute-git-dir)/run-ticket-review-index" sh -c 'git read-tree HEAD && git add -A --ignore-errors 2>/dev/null; git write-tree; rm -f "$GIT_INDEX_FILE"'
  ```
- **돌려받는 것**: 지적 목록과 수행한 모델 이름만 받는다. 지적마다 기준(위 목록 가운데 어느 기준의 지적인지), 심각도(High·Medium·Low), 파일과 줄, 근거(재현 명령이나 코드·규칙 원문), 고칠 방법을 적게 한다. 요약, 총평, 수정 diff는 받지 않는다.
- **지적 검증**: 지적을 하나씩 재현하거나 코드·규칙 원문과 대조해 `수용`, `기각(사유)`, `범위 밖` 가운데 하나로 적는다. 대조하지 않고 받아들이거나 버리지 않는다. 수용한 지적은 고친 뒤 4단계 기준과 검증 명령을 다시 확인한다. 기각한 지적과 범위 밖 지적은 고치지 않고 판정과 사유를 완료 기록과 보고에 남긴다. 지적이 없다는 보고는 수락의 근거가 아니라 입력 하나다. 수락의 근거는 4단계의 확인 결과다.
- **모델과 수단**: 모델 이름을 정해 두지 않는다. 조건은 구현한 모델과 다른 회사의 모델이라는 것 하나다. 부를 때마다 아래 순서에서 처음 되는 것을 쓴다.
  1. 사용자나 부른 쪽이 이번 실행에서 지정한 모델이나 수단
  2. 사용자 설정에 적힌 교차 리뷰 수단. 레포·에이전트 규칙 파일, 하네스 설정, 저장된 에이전트 프로필이 교차 리뷰를 맡을 에이전트나 모델을 정해 둔 것과, 지정되거나 등록된 워커 도구 절차의 "교차 리뷰 워커"가 여기에 든다
  3. 환경 조회. 이 세션에서 쓸 수 있는 provider, 모델, 에이전트 목록을 조회해 다른 회사 모델을 고르고, 무엇을 골랐는지 알린다
  4. 같은 회사 대체 규칙: 다른 회사 모델을 쓸 수 없으면 같은 회사 모델의 새 컨텍스트 리뷰로 대체한다. 넘기는 것, 권한, 돌려받는 것, 지적 검증은 위와 같다. 대체 리뷰는 독립 검증으로 치지 않으므로 대체했다는 것을 아래 "기록"대로 적고 흐름을 계속한다. 다른 회사 모델이 없다는 것은 멈출 이유가 아니다

  부르는 수단은 새 컨텍스트의 읽기 전용 서브에이전트 하나다. 그 서브에이전트에 다른 회사 모델을 줄 수 없으면 4번의 대체가 된다. 서브에이전트를 띄울 때 모델을 정할 수 있으면 같은 회사 대체여도 모델을 정해서 띄운다. 정한 값이 아래 "기록"에서 수행한 모델을 확인하는 그 수단의 설정이 된다. 정하지 않고 띄우면 수행한 모델을 확인하지 못해 대체 기록에 모델 이름이 빠진다. 워커 도구 절차(워커를 띄우는 도구 하나를 쓰는 방법을 적은 문서)를 쓸 때는 그 문서를 읽고, 절차의 "사용 조건"을 만족하면 "교차 리뷰 워커"대로 워커를 띄운다. 워커는 새 worktree가 아니라 지금 작업 트리에 띄우고, 보고는 절차가 정한 알림으로 받고 상태를 되풀이해 조회하지 않는다. 절차가 여럿이면 사용자나 부른 쪽이 정한 도구의 절차를 먼저, 그다음 규칙에 적힌 순서로 해 본다.

  응답이 없거나 결과를 읽을 수 없으면 위 순서의 다음 수단에 다시 맡긴다. 독립 여부는 계획한 모델이 아니라 실제로 수행한 모델로 판정한다. 수행한 모델이 구현한 모델과 같은 회사였으면 교차 리뷰로 치지 않고 다음 수단에 다시 맡긴다. 남은 수단이 4번뿐이면 그 리뷰를 4번의 대체로 친다.

  새 컨텍스트를 하나도 띄울 수 없으면(서브에이전트도 워커도 띄울 수 없으면) 이 세션의 자기 리뷰로 대체한다. 위 기준 목록으로 diff를 처음부터 다시 읽고, 같은 형식으로 지적을 적어 검증한다. 구현한 세션이 자기 변경을 보는 것이라 같은 회사 모델의 새 컨텍스트 리뷰보다 약하다. 그래서 대체 표시를 따로 쓴다.
- **기록**: 실제로 수행한 모델을 확인해 6단계 완료 기록의 `- 교차 리뷰:` 줄에 아래 셋 가운데 하나로 적는다. 수행한 모델은 리뷰어가 본문에 스스로 적은 이름이 아니라 호출 도구가 돌려준 실행 정보나 그 수단의 설정으로 확인한다. 리뷰어는 자기 모델을 모르고 세션 정보를 옮겨 적을 수 있다. 수행한 모델을 확인할 수 없으면 모델 이름 자리에 "수행 모델 확인 불가"와 맡긴 수단을 적는다.
  - 다른 회사 모델이 했으면 `- 교차 리뷰: 완료 (<수행한 모델>)`
  - 4번으로 대체했으면 `- 교차 리뷰: 대체 (같은 회사 모델 <수행한 모델>)`
  - 자기 리뷰로 대체했으면 `- 교차 리뷰: 대체 (새 컨텍스트 없음, 메인 세션 자기 리뷰)`

  보고에는 수행한 모델 이름을 적는다. 대체했으면 "교차 리뷰 대체(같은 회사 모델 <모델 이름>)"이나 "교차 리뷰 대체(새 컨텍스트 없음, 메인 세션 자기 리뷰)"라는 대체 표시를 함께 적는다. 사용자가 독립 검증이 없었다는 것을 보고 판단해야 하기 때문이다. 부른 쪽이 기록 파일을 넘겼으면 교차 리뷰 모델을 적는 자리(run-flow 상태 파일은 `- 교차 리뷰 모델:` 줄)에도 같은 내용을 적는다.

교차 리뷰(대체 포함)의 결과를 받아 지적을 모두 검증하기 전에는 6단계로 넘어가지 않는다. 결과 없이 완료 기록을 쓰면 리뷰 지적이 보고에서 빠진다.

### 6. 완료 기록

**보호 경로 검사**: 부른 쪽이 보호 경로 검사 명령을 넘겼으면 완료 기록을 쓰기 전에 `verify`를 돌린다. 5단계에서 지적을 고쳤으면 고친 뒤의 결과다. 종료 코드가 0이 아니면(1은 보호 경로가 바뀌거나 지워짐, 2는 검사 실패) 이 티켓을 수락하지 않는다. 티켓 상태를 바꾸지 않고, 바뀐 보호 경로를 되돌리지 않고 출력을 보여 준 뒤 멈춘다. 통과하면 이 티켓이 새로 만든 테스트 파일을 `add`로 목록에 더하고, 완료 기록의 "확인한 것"에 `verify` 결과를 적는다.

**산출물**: 다음 결과를 티켓에 남긴다.

- "만들 것"이나 완료 기준이 산출물로 남기라고 한 결과
- 같은 brief의 다른 티켓이 "NN 티켓의 산출물"로 참조하는 결과

체크리스트, 측정값, 조사 내용 같은 텍스트는 내용을 그대로 넣고, 코드나 파일은 저장소 경로를 적는다.

**docs 티켓**

1. `- 상태: ready-for-agent`를 `- 상태: done`으로 바꾼다.
2. 통과한 완료 기준의 `- [ ]`를 `- [x]`로 바꾼다.
3. 파일 끝에 아래 기록을 붙인다. 산출물이 없으면 `## 산출물` 섹션을 지우고, 해당 없는 줄도 지운다. `- 교차 리뷰:` 줄은 지우지 않고 5단계의 "기록"이 정한 값으로 쓴다. "여러 티켓 실행"에서는 `- 교차 리뷰:` 줄과 `- 교차 리뷰 지적:` 줄을 티켓마다 쓰지 않고 그 절차가 정한 때에 더한다.
4. brief `## 티켓`의 해당 줄을 `- [x]`로 바꾼다. brief의 다른 부분은 고치지 않는다. `## 티켓`이 없는 brief면 "남은 일" 체크박스를 바꾸고 기록을 brief 끝에 붙인다.

```markdown
## 완료 기록
- 완료일: YYYY-MM-DD
- 커밋: 안 함 (작업 시작 HEAD `<해시>`)
- 바꾼 파일: `<경로>`, `<경로>`
- 확인한 것: `<명령>` → <결과> (확인한 HEAD `<해시>`, 커밋 전이면 "작업 트리")
- 확인 못 한 것: <기준>: <이유>
- 교차 리뷰: 완료 (<수행한 모델>)
- 교차 리뷰 지적: <지적>: <수용 / 기각(사유) / 범위 밖>
- 고치지 않은 지적: <지적>: <이유>

## 산출물
<내용 또는 저장소 경로>
```

**GitHub 티켓**

1. 위 기록을 임시 파일에 저장하고 `gh issue comment <번호> --body-file <임시 파일>`로 남긴 뒤 `gh issue close <번호>`로 닫는다.
2. `gh issue view <brief 번호> --json body --jq .body`로 받은 본문에서 `- [ ] #<번호>`를 `- [x] #<번호>`로 바꾸고 `gh issue edit <brief 번호> --body-file <임시 파일>`로 올린다. 임시 파일을 지운다. `## 티켓`이 없는 brief면 "남은 일" 체크박스를 바꾼 본문을 올리고, 기록은 brief 이슈에 코멘트로 남긴다.

**마지막 티켓이면** brief의 "확인 기준"을 실행해 결과를 보고하고, 남은 티켓이 없으므로 brief를 닫는다. GitHub brief는 `gh issue close <brief 번호>`로 닫는다. docs brief는 닫을 상태가 없으므로 체크박스가 모두 체크된 것으로 끝난 것을 나타낸다. 체크박스와 덧붙인 완료 기록 말고 brief 본문은 고치지 않는다. "여러 티켓 실행"에서는 이 일을 티켓마다 하지 않고 통합 리뷰 뒤에 한 번 한다.

**보고**: 한 메시지에 다음을 담는다. 끝낸 티켓, 완료 기준 결과, 바꾼 파일, 산출물 위치, 교차 리뷰를 수행한 모델과 대체 표시, 교차 리뷰 지적의 판정, 고치지 않은 리뷰 지적, 건너뛴 리뷰와 이유(규칙 검사를 하지 못했거나 리뷰 스킬을 쓰지 않은 경우다. 교차 리뷰는 여기에 들지 않는다), 다음 티켓, 커밋은 사용자가 한다는 안내.

## 여러 티켓 실행

사용자나 다른 스킬이 번호 범위나 "남은 티켓 전부"처럼 여러 티켓을 요청할 때만 쓴다. 기본은 호출 한 번에 티켓 하나다.

여러 티켓을 요청받았으면 [references/multi-ticket.md](references/multi-ticket.md)를 읽고 그 절차를 따른다. 기본은 이 세션이 티켓을 차례로 직접 실행하는 차례 실행이다. 워커를 쓰는 병렬 실행은 사용자의 선택이 있을 때만 쓴다. 사용자나 부른 쪽이 워커 도구 절차를 지정했거나 레포·에이전트 규칙에 등록해 둔 때다. 실행 방법 고르기, 병렬 실행, 워커 도구 절차가 정해야 할 항목, 차례 실행, 끝에 한 번 하는 통합 리뷰가 거기에 있다. 티켓 하나를 실행할 때와 워커로 일부 단계만 지시받았을 때는 읽지 않는다.
