# Run Ticket

set-ticket이 만든 티켓을 새 세션에서 끝까지 실행한다. 이 세션에는 brief를 만든 대화가 없다. brief, 티켓, 앞 티켓의 완료 기록만 근거로 삼는다.

## 핵심 규칙

1. **brief와 티켓은 경로가 아니라 내용으로 찾는다.** brief는 `- 작성일: YYYY-MM-DD` 줄이 있는 문서이고, 티켓은 brief의 `## 티켓` 섹션 링크가 가리키는 문서다. 레포의 이슈 트래커 규칙이 정한 디렉터리나 파일 이름(`spec.md`, `issues/` 등)은 다른 스킬의 형식이므로 brief를 찾는 데 쓰지 않는다. 그 형식으로 찾으면 지난 작업 폴더를 고를 수 있다.
2. **완료 여부는 티켓 상태로 판단한다.** docs 티켓은 `- 상태: done`이면, GitHub 티켓은 closed이면 끝난 것이다. brief의 `## 티켓` 체크박스는 티켓 상태를 따른다. 둘이 어긋나면 체크박스를 고친다.
3. **커밋하지 않는다.** 레포 규칙이 커밋을 요구해도 사용자에게 맡기고, 커밋하지 않았다는 사실을 완료 기록에 남긴다.
4. **티켓의 "하면 안 되는 것"·"작업 경계"가 레포 규칙보다, 레포 규칙이 이 스킬의 기본 동작보다 앞선다.** 티켓과 레포 규칙이 충돌하면 진행하기 전에 묻는다.
5. **앞 티켓의 결과는 다시 만들지 않는다.** 완료 기준이 앞 티켓의 산출물을 참조하는데 찾을 수 없으면 멈추고 알린다. "수정 전 동작"처럼 지금 다시 만들면 값이 달라지는 결과가 있다.

## 단계

아래 체크리스트를 시작할 때 한 번 보여 주고, 단계를 마칠 때마다 갱신한다.

```
티켓 실행:
- [ ] 1. 티켓 고르기
- [ ] 2. 맥락 읽기
- [ ] 3. 구현
- [ ] 4. 완료 기준 확인
- [ ] 5. 리뷰
- [ ] 6. 완료 기록
```

### 1. 티켓 고르기

**brief 목록**

- docs: `command grep -rlE --include='*.md' --exclude-dir=.git --exclude-dir=node_modules '^- 작성일: [0-9]{4}-[0-9]{2}-[0-9]{2}' .`로 찾는다. Grep 도구와 셸 함수(ugrep 등)로 바뀐 Bash `grep`은 `.gitignore`에 걸린 폴더(`.scratch/` 등)를 건너뛰므로 `command grep`으로 찾는다.
- GitHub: `git remote -v`에 github.com이 있고 `gh auth status`가 성공하면 `gh issue list --label context --state open --json number,title,body`도 본다.

**막힘 관계**: docs는 티켓의 `- 막힘 관계:` 줄, GitHub는 `gh api repos/{owner}/{repo}/issues/<번호>/dependencies/blocked_by`와 본문의 "막힘 관계" 섹션이다.

**참조가 있을 때**: 경로, 이슈 번호, URL이 가리키는 문서를 읽는다.

- 티켓이면 그 티켓을 작업한다.
- brief면 그 brief 안에서 아래 "참조가 없을 때"의 2번 규칙으로 고른다.
- 가리키는 문서가 없거나 둘 이상이면(예: 같은 번호의 이슈와 docs 티켓) 후보를 보여 주고 묻는다.
- 이미 done이거나 막힘 관계의 티켓 중 끝나지 않은 것이 있으면 알리고 진행 여부를 묻는다.

**참조가 없을 때**

1. `## 티켓`에 끝나지 않은 티켓이 남은 brief 중 작성일이 가장 늦은 brief를 고른다. 작성일이 같은 brief가 둘 이상이면 묻는다.
2. 그 brief의 끝나지 않은 티켓 중 막힘 관계의 티켓이 모두 끝난 것에서 번호가 가장 앞선 티켓을 고른다. 번호는 docs면 파일 이름의 NN, GitHub면 `## 티켓` 목록 순서다.

고를 brief가 없으면 그렇다고 알리고 멈춘다.

`## 티켓` 섹션이 없는 brief는 brief 전체를 티켓 하나로 본다. "남은 일"이 만들 것, "확인 기준"이 완료 기준이다. "남은 일"에 빈 체크박스가 있으면 끝나지 않은 것이다.

고른 brief와 티켓 제목을 한 줄로 알리고 바로 시작한다.

**작업 트리 확인**: `git status --porcelain`에 brief·티켓 문서 밖의 변경이 있으면, done 티켓의 완료 기록 "바꾼 파일"과 겹치는 것을 보여 주고 커밋한 뒤 진행할지 그대로 진행할지 묻는다. 그대로 진행하면 5단계 리뷰에 이전 변경이 섞인다.

### 2. 맥락 읽기

- 티켓 전문과 부모 brief 전문. GitHub는 `gh issue view <번호> --comments`로 읽는다.
- 같은 brief의 done 티켓에 있는 `## 완료 기록`과 `## 산출물`(GitHub는 완료 코멘트). 완료 기준이 "NN 티켓의 산출물"을 참조하면 여기서 찾는다. 없으면 핵심 규칙 5대로 멈춘다.
- 레포 규칙: 루트와 작업할 디렉터리의 CLAUDE.md·AGENTS.md, 거기서 가리키는 문서, `.claude/skills/`. 테스트 작성 규칙, 검증 명령(타입 검사, 린트, 테스트), 커밋 규칙을 확인한다. 규칙이 특정 스킬을 쓰라고 하면 Skill 도구로 호출한다.

### 3. 구현

"만들 것"을 구현한다.

- 테스트는 레포 규칙이 요구하거나 바꾸는 동작에 이미 테스트가 있을 때 함께 쓴다. 레포 규칙이 테스트를 쓰지 않는다고 하면 쓰지 않는다.
- 타입 검사와 바꾼 부분의 테스트를 자주 돌린다.
- 티켓 범위 밖의 문제는 고치지 않고 보고에 남긴다.

### 4. 완료 기준 확인

완료 기준을 하나씩 명령이나 관찰로 확인한다. 전체 테스트 스위트가 있으면 마지막에 한 번 돌린다.

통과하지 못한 기준은 고친다. 고칠 수 없으면 티켓 상태를 바꾸지 않고, 통과하지 못한 기준과 이유를 보고하고 멈춘다.

### 5. 리뷰

아래 순서에서 처음 맞는 방법으로 이번 변경을 리뷰한다.

1. 레포 규칙이 지정한 리뷰 스킬을 Skill 도구로 호출한다.
2. 사용 가능한 스킬에 `code-review`나 `<플러그인>:code-review`가 있으면 Skill 도구로 호출한다. 여럿이면 설명을 보고 커밋하지 않은 작업 트리 변경을 리뷰하는 것을 고르고, 그래도 여럿이면 접두사 없는 것을 고른다. 커밋 범위(`<기준>...HEAD`)만 보는 스킬은 이번 변경을 보지 못하므로 고르지 않는다.
3. 맞는 스킬이 없거나 호출이 실패하면 직접 리뷰한다. `git diff`와 새 파일을 읽고 버그, 티켓의 "하면 안 되는 것"·"작업 경계" 위반, 레포 규칙 위반을 찾는다.

티켓 범위 안의 지적은 고치고 4단계 기준을 다시 확인한다. 범위 밖 지적은 고치지 않고 보고에 남긴다.

### 6. 완료 기록

**산출물**: 다음 결과를 티켓에 남긴다.

- "만들 것"이나 완료 기준이 산출물로 남기라고 한 결과
- 같은 brief의 다른 티켓이 "NN 티켓의 산출물"로 참조하는 결과

체크리스트, 측정값, 조사 내용 같은 텍스트는 내용을 그대로 넣고, 코드나 파일은 저장소 경로를 적는다.

**docs 티켓**

1. `- 상태: ready-for-agent`를 `- 상태: done`으로 바꾼다.
2. 통과한 완료 기준의 `- [ ]`를 `- [x]`로 바꾼다.
3. 파일 끝에 아래 기록을 붙인다. 산출물이 없으면 `## 산출물` 섹션을 지운다.
4. brief `## 티켓`의 해당 줄을 `- [x]`로 바꾼다. brief의 다른 부분은 고치지 않는다. `## 티켓`이 없는 brief면 "남은 일" 체크박스를 바꾸고 기록을 brief 끝에 붙인다.

```markdown
## 완료 기록
- 완료일: YYYY-MM-DD
- 커밋: 안 함 (작업 시작 HEAD `<해시>`)
- 바꾼 파일: `<경로>`, `<경로>`

## 산출물
<내용 또는 저장소 경로>
```

**GitHub 티켓**

1. 위 기록을 임시 파일에 저장하고 `gh issue comment <번호> --body-file <임시 파일>`로 남긴 뒤 `gh issue close <번호>`로 닫는다.
2. `gh issue view <brief 번호> --json body --jq .body`로 받은 본문에서 `- [ ] #<번호>`를 `- [x] #<번호>`로 바꾸고 `gh issue edit <brief 번호> --body-file <임시 파일>`로 올린다. 임시 파일을 지운다. `## 티켓`이 없는 brief면 "남은 일" 체크박스를 바꾼 본문을 올리고, 기록은 brief 이슈에 코멘트로 남긴다.

**마지막 티켓이면** brief의 "확인 기준"을 실행해 결과를 보고하고, 남은 티켓이 없으므로 brief를 닫는다. GitHub brief는 `gh issue close <brief 번호>`로 닫는다. docs brief는 닫을 상태가 없으므로 체크박스가 모두 체크된 것으로 끝난 것을 나타낸다. 체크박스와 덧붙인 완료 기록 말고 brief 본문은 고치지 않는다.

**보고**: 한 메시지에 다음을 담는다. 끝낸 티켓, 완료 기준 결과, 바꾼 파일, 산출물 위치, 고치지 않은 리뷰 지적, 다음 티켓, 커밋은 사용자가 한다는 안내.

## 여러 티켓 실행

사용자가 번호 범위나 "남은 티켓 전부"처럼 여러 티켓을 요청할 때만 쓴다. 기본은 호출 한 번에 티켓 하나다.

1. 1단계의 작업 트리 확인을 한 번 한다.
2. 대상 티켓의 순서를 1단계 규칙(막힘 관계, 번호)으로 정해 보여 준다.
3. 티켓마다 Agent 도구로 서브에이전트 하나를 띄우고, 끝나면 다음 티켓을 띄운다. User-invoked 스킬은 서브에이전트가 Skill 도구로 부를 수 없으므로 이 파일의 경로를 넘긴다.
   ```
   <이 SKILL.md의 절대 경로>를 읽고 티켓 <참조>에 대해 2, 3, 4, 6단계를 수행하라. 1단계와 5단계는 건너뛴다. 끝나면 완료 기준 결과, 바꾼 파일, 산출물 위치만 보고하라.
   ```
4. 완료 기준을 통과하지 못한 티켓이 나오면 멈춘다. 뒤 티켓이 그 결과에 기댈 수 있다.
5. 모든 서브에이전트가 끝나면 전체 변경에 5단계 리뷰를 한 번 하고, 고친 부분이 걸친 티켓의 완료 기준을 다시 확인한다.
6. 티켓별 결과를 6단계 보고 형식으로 모아 알린다.

서브에이전트는 병렬로 띄우지 않는다. 커밋하지 않으므로 같은 작업 트리를 동시에 고치면 충돌하고, worktree로 나누면 합칠 때 커밋이 필요하다.
