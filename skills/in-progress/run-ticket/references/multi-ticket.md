# 여러 티켓 실행

run-ticket SKILL.md의 "여러 티켓 실행"에서 읽는 절차다. 여기서 말하는 1~6단계는 SKILL.md의 단계다.

## 목차

1. 기록
2. 실행 방법 고르기
3. 병렬 실행
4. Paseo로 워커 다루기
5. Orca로 워커 다루기
6. 차례 실행

## 기록

실행 도중 생긴 결정과 식별자는 끝날 때 몰아서 보고하지 않고 생긴 때에 바로 남긴다. 세션이 끊기면 대화에만 있던 내용이 사라져, 이어 받은 세션이 같은 질문에 다른 답을 하거나 다른 워커를 잡는다.

- 남길 것: 워커 질문에 준 답과 근거, 구현 중 새로 정한 설계 결정, 걸리는 티켓, 워커 식별자(Paseo는 티켓별 워크스페이스 ID·에이전트 ID·브랜치, Orca는 Run ID), 통과하지 못한 티켓에 시도한 에이전트와 횟수
- 남길 곳: 부른 쪽이 기록 파일과 적을 자리를 넘겼으면 그 자리에 적는다. 넘기지 않았으면 그때 사용자에게 한 줄로 알리고 마지막 보고에 다시 넣는다.

## 실행 방법 고르기

대상 티켓과 막힘 관계를 1단계 규칙으로 모은 뒤 실행 방법을 고른다. 아래를 모두 만족하면 "병렬 실행"을, 하나라도 아니면 "차례 실행"을 한다.

- 막힘 관계로 함께 시작할 수 있는 티켓이 둘 이상인 때가 있다. 티켓이 하나이거나 막힘 관계가 일렬이면 병렬 이득 없이 worktree와 머지 비용만 든다.
- 대상 티켓의 막힘 관계 줄에 `(통합 브랜치 공유)`가 없다. 그 티켓들은 티켓별 worktree에서 묶음 하나만으로 4단계를 통과할 수 없다.
- 워커를 띄울 도구가 있다. 아래 순서에서 처음 되는 것을 쓴다.
  1. Paseo: 이 세션에 Paseo의 워크스페이스·에이전트 관리 도구가 있거나 `paseo ls`가 성공한다. "Paseo로 워커 다루기"를 따른다.
  2. Orca: `orchestration` 스킬을 불러올 수 있고 그 지시대로 Orca 명령이 실행된다. "Orca로 워커 다루기"를 따른다.

사용자나 부른 쪽이 도구를 정해 주었으면 그 도구를 쓴다. 이어 받는 실행은 기록에 남은 워커 식별자의 도구를 쓴다. 도중에 도구를 바꾸면 앞 도구의 워커가 끝난 것을 알 수 없다.

모든 방법에서 서브에이전트나 워커에게 run-ticket SKILL.md의 절대 경로를 넘긴다. 스킬 도구가 없는 워커도 읽을 수 있고, 수행할 단계만 골라 지시할 수 있다.

## 병렬 실행

티켓마다 워커가 현재 브랜치에서 갈라진 worktree의 새 브랜치에서 구현하고 커밋한다. 이 세션은 조정자로서 막힘 관계 순서를 지키고, 끝난 브랜치를 현재 브랜치로 머지하고, 완료 기록을 남긴다. 워커를 만들고, 기다리고, 정리하는 방법은 고른 도구의 절을 따른다.

1. **준비**: 이어 받는 실행이면(기록에 워커 식별자가 있거나, 같은 brief의 Orca Run이 남아 있거나, `git status`에 merging 표시가 있다) 3번의 이어 받기 처리를 먼저 하고 이 검사를 한다. 끊긴 머지가 남아 있으면 이 검사에서 멈춘다. 작업 트리가 깨끗한지 확인한다. 커밋하지 않은 것이 brief·티켓 문서뿐이면 커밋할지 묻고, 다른 변경이 있으면 커밋하거나 치운 뒤 다시 실행하라고 알리고 멈춘다.
2. **계획 승인**: 커밋과 머지가 생기므로 시작하기 전에 다음을 보여 주고 승인을 받는다.
   - 실행 묶음: 막힘 관계로 함께 시작할 수 있는 티켓끼리 묶은 순서
   - 워커를 띄울 도구(Paseo, Orca)
   - 머지할 브랜치. 현재 브랜치가 기본 브랜치(`main` 등)면 작업 브랜치를 새로 만들지 함께 묻는다.
   - 동시에 띄울 워커 수: 기본 3개. 워커마다 서브에이전트를 더 띄우므로 많이 띄우면 요청 한도에 걸린다.
   - 작업 시작 HEAD 해시
3. **이어 받기**: 앞선 실행의 워커가 남아 있으면 새로 만들지 않고 이어 받는다. 남은 워커를 찾는 방법은 도구의 절을 따른다.
   - 실행 중인 워커가 있으면 새로 띄우지 않고, 도구의 절에 적힌 방법으로 상태를 확인하고 기다린다. 워커가 조용하다고 끝난 것으로 보지 않는다. 다시 띄우면 같은 티켓을 두 번 구현한다.
   - 끝난 워커가 있는데 그 티켓이 done이 아니면, 워커는 커밋했지만 머지하기 전에 끊긴 것이다. 티켓 브랜치가 `git branch --no-merged`에 있으면 5번의 "통과" 처리부터 한다. 브랜치가 없으면 멈추고 알린다. 다시 띄우면 같은 티켓을 두 번 구현한다.
   - 머지가 진행 중인 채로 끊겼으면(`git status`에 merging 표시) `git merge --abort`로 되돌린 뒤 위와 같이 처리한다.
   - GitHub 티켓이 머지됐는데 열려 있으면 완료 코멘트를 남기고 닫기만 한다.
   - 다른 티켓을 막는 티켓이 done인데 완료 기록(GitHub는 코멘트)에 `- 교차 리뷰:` 줄이 없으면, 머지한 뒤 교차 리뷰 전에 끊긴 것이다. 막힌 티켓의 워커를 띄우기 전에 5번의 "막는 티켓의 교차 리뷰"부터 한다.
4. **워커 띄우기**: 막는 티켓이 모두 머지된 티켓의 워커를 동시 워커 수까지 띄운다. 막는 티켓의 워커가 끝났어도 머지 전이면 기다린다. 워커는 현재 브랜치에서 갈라진 새 worktree에 띄운다. 워커의 모델과 effort는 도구의 절을 따른다. 워커 spec:
   ```
   <run-ticket SKILL.md의 절대 경로>를 읽고 티켓 <참조>에 대해 2, 3, 4단계를 수행하라. 1, 5, 6단계는 건너뛰고 brief와 티켓 문서는 그대로 둔다.
   4단계를 통과하면 레포 커밋 규칙대로 이 worktree의 브랜치에 커밋하라. 통과하지 못하면 커밋하지 말고 실패로 보고하라.
   끝나면 완료 기준 결과, 바꾼 파일, 산출물 내용, 브랜치 이름, 커밋 해시를 보고하라.
   이미 내린 결정: <결정과 걸리는 티켓. 없으면 이 줄을 뺀다>
   ```
   "이미 내린 결정"에는 부른 쪽이 넘긴 결정과 이 실행에서 워커 질문에 준 답을 넣는다. 워커는 brief, 티켓, 완료 기록만 읽으므로, 넣지 않으면 같은 질문에 다른 답으로 구현한다.
5. **워커가 끝나면** 결과에 따라 처리한다.
   - 통과: 현재 브랜치에서 `git merge --no-ff --no-commit <티켓 브랜치>`로 합치고, 머지 커밋을 만들기 전에 합친 작업 트리에서 레포 검증 명령(타입 검사, 린트, 테스트)을 돌린다. 워커는 갈라진 시점의 worktree에서만 확인했으므로, 텍스트 충돌 없이 앞서 머지한 티켓과 어긋나는 변경은 여기서만 드러난다.
   - 검증 통과: 검증을 통과하면 그 티켓의 6단계 완료 기록을 남긴 뒤 레포 커밋 규칙대로 커밋한다. GitHub 티켓의 완료 코멘트와 닫기는 머지 커밋을 만든 뒤에 한다. 먼저 닫고 끊기면 닫힌 티켓의 코드가 머지되지 않은 채 남는다. 완료 기록의 커밋 줄은 ``- 커밋: 티켓 브랜치 `<브랜치>`의 `<해시>`를 머지``로 쓴다. 완료 기록이 머지 커밋에 들어가야 뒤 티켓의 worktree가 산출물을 읽는다. 머지한 뒤 도구의 절대로 워커와 그 worktree, 브랜치를 정리한다.
   - 통합 검증 실패: `git merge --abort`로 되돌리고, 실패한 명령과 출력을 보여 준 뒤 새 워커를 띄우지 않고 멈춘다. 실패 원인이 방금 머지한 티켓과 앞서 머지한 티켓 중 어느 쪽인지 알 수 없기 때문이다. 그 티켓의 worktree는 남긴다. 에이전트 규칙이 원인을 모르는 실패의 디버깅을 맡을 에이전트를 정해 두었으면, 멈추기 전에 실패한 명령과 출력, 그 티켓 브랜치를 넘겨 원인 보고만 받고 함께 보여 준다. 코드는 고치게 하지 않는다.
   - 막는 티켓의 교차 리뷰: 머지한 티켓이 다른 티켓을 막으면, 막힌 티켓의 워커를 띄우기 전에 그 머지 커밋의 diff(`HEAD^..HEAD`)에 5단계의 교차 리뷰만 한다. 지적은 고쳐 레포 커밋 규칙대로 커밋한다. 결함 위에 뒤 티켓이 쌓이면 통합 리뷰에서 고칠 범위가 여러 티켓으로 커진다. 리뷰가 끝나면 그 티켓의 완료 기록에 ``- 교차 리뷰: 완료 (`<머지 커밋 해시>`, <수행한 모델>)``이나 `- 교차 리뷰: 건너뜀 (<이유>)` 줄을 더해 같은 커밋에 넣는다. 고친 것이 없으면 이 줄만 커밋한다. GitHub 티켓은 코멘트로 남긴다. 이 줄이 있어야 이어 받을 때 리뷰를 했는지 알 수 있다.
   - 머지 충돌: `git merge --abort`로 되돌리고, 그 워커에게 현재 브랜치 위로 리베이스해 충돌을 풀고 4단계를 다시 확인한 뒤 커밋하라고 보낸다. 다시 충돌하면 그 티켓을 멈추고 사용자에게 알린다.
   - 실패: 그 티켓과 그 티켓에 막힌 티켓은 띄우지 않는다. 실행 중인 워커는 끝까지 기다려 머지한다. 실패한 티켓의 worktree는 사용자가 볼 수 있게 남긴다.
   - 질문: brief와 티켓으로 답할 수 있으면 답하고, 아니면 사용자에게 물어 답을 전한다. 답을 전하면 바로 그 답과 근거, 걸리는 티켓을 "기록" 규칙대로 남기고, 뒤에 띄우는 워커의 "이미 내린 결정"에도 넣는다.
6. **통합 리뷰**: 모든 워커가 끝나면 작업 시작 HEAD부터 HEAD까지에 5단계 리뷰를 한 번 한다. 고친 내용은 레포 커밋 규칙대로 커밋하고, 고친 부분이 걸친 티켓의 완료 기준을 다시 확인한다. 그 뒤 6단계의 "마지막 티켓이면"을 한다. brief의 "확인 기준"은 모든 티켓을 합친 HEAD에서 확인해야 티켓 사이의 어긋남을 잡는다.
7. 티켓별 결과를 6단계 보고 형식으로 모아 알린다. 커밋 안내 대신 만든 커밋 목록을 넣고, push·PR·기본 브랜치 머지는 사용자가 정한다고 알린다.

## Paseo로 워커 다루기

Paseo에는 Run이나 Task 같은 실행 단위가 없다. 조정자인 이 세션이 막힘 관계 순서를 직접 지키고, 티켓마다 워크스페이스 하나와 에이전트 하나를 만든다. Paseo 도구가 없고 `paseo` CLI만 있으면 같은 일을 CLI로 한다. 인자는 `paseo workspace create --help`와 `paseo run --help`로 확인한다.

- **워커 만들기**: 티켓의 워커를 띄울 때가 되면 Paseo로 worktree 격리 워크스페이스를 만든다. 새 브랜치로 갈라지게 하고, 기준은 현재 브랜치의 로컬 ref(`refs/heads/<현재 브랜치>`)로 준다. 원격 ref를 주면 push하지 않은 커밋(흐름 문서, 앞서 머지한 티켓)이 빠진 worktree가 생긴다. 워크스페이스 제목은 티켓 번호와 제목으로 한다. 그 워크스페이스에 에이전트를 하나 띄우고 4번의 워커 spec을 첫 프롬프트로 준다. 워크스페이스는 막는 티켓이 모두 머지된 뒤에 만든다. 미리 만들면 막는 티켓의 변경이 없는 커밋에서 갈라진다.
- **워커의 모델**: 저장된 에이전트 프로필이 있으면 프로필마다 설명을 읽고 티켓 구현에 맞는 것을 골라 그 provider, 모델, 모드, thinking 설정으로 띄운다. 맞는 프로필이 없고 에이전트 규칙이 구현 워커의 모델과 effort를 정해 두었으면 그것으로, 그것도 없으면 이 세션과 같은 provider와 모델로 띄우고 무엇으로 띄웠는지 알린다.
- **기록**: 워크스페이스와 에이전트를 만들자마자 티켓 번호, 워크스페이스 ID, 에이전트 ID, 브랜치 이름을 "기록" 규칙대로 남긴다.
- **기다리기**: 워커가 끝나거나, 오류가 나거나, 권한을 요청하면 Paseo가 이 세션에 알린다. 알림을 기다리고 상태를 되풀이해 조회하지 않는다. 알림에 담긴 마지막 응답으로 결과를 읽고, 부족하면 그 에이전트의 최근 활동을 조회한다. 권한 요청은 brief와 티켓 범위 안의 것만 승인하고, 아니면 사용자에게 묻는다.
- **이어 받기**: 기록에 남은 에이전트 ID마다 상태를 한 번 조회한다. 이어 받은 세션이 워커를 띄운 세션이 아니면 완료 알림이 오지 않는다. 실행 중인 워커에는 하던 일을 마치고 결과를 보고하라는 후속 프롬프트를 보내 이 세션이 알림을 받게 한다. 기록에 없는 워커는 찾지 않는다. 워크스페이스 제목만으로 찾으면 다른 실행의 워커를 잡을 수 있다.
- **질문과 리베이스**: 답이나 리베이스 요청은 새 에이전트를 띄우지 않고 같은 에이전트에 후속 프롬프트로 보낸다. 새 에이전트는 워커의 대화를 모른다.
- **정리**: 머지한 뒤 그 티켓의 워크스페이스를 archive한다. Paseo가 그 안의 에이전트를 정리하고 worktree를 지운다. 티켓 브랜치가 남아 있으면 `git branch -d <티켓 브랜치>`로 지운다. 실패한 티켓과 통합 검증에 실패한 티켓의 워크스페이스는 archive하지 않는다.

## Orca로 워커 다루기

`orchestration` 스킬을 불러와 그 지시를 따른다. 스킬 도구가 없으면 그 스킬의 SKILL.md를 읽는다.

- **Run과 Task 만들기**: brief 제목을 목표로 Run 하나를 만들고, 티켓마다 Task를 만들어 막는 티켓의 Task를 deps로 건다. 만든 Run ID는 바로 "기록" 규칙대로 남긴다. Orca가 deps를 풀어도 막는 티켓이 머지되기 전이면 그 Task를 띄우지 않는다.
- **워커 만들기**: 워커는 이 세션과 같은 에이전트로, 현재 브랜치에서 갈라진 새 child worktree에 띄운다. 에이전트 규칙이 구현 워커의 모델과 effort를 정해 두었으면 그것으로 띄운다.
- **이어 받기**: 같은 brief를 목표로 한 Run이 남아 있으면 새로 만들지 않고 이어 받고, 끝난 Task는 다시 띄우지 않는다. 부른 쪽이 Run ID를 넘겼으면 그 Run을 쓴다. brief 제목으로만 찾으면 제목이 같은 다른 Run을 잡을 수 있다. 실행 중인 Task는 orchestration 스킬의 방법으로 워커 상태를 확인하고 기다린다.
- **정리**: 머지한 뒤 워커를 놓아주고 그 worktree를 브랜치와 함께 지운다.

## 차례 실행

1. 1단계의 작업 트리 확인을 한 번 한다.
2. 대상 티켓의 순서를 1단계 규칙(막힘 관계, 번호)으로 정해 보여 준다.
3. 티켓마다 새 컨텍스트로 서브에이전트 하나를 띄우고, 끝나면 다음 티켓을 띄운다. 에이전트 규칙이 티켓 구현을 맡을 에이전트를 정해 두었으면 그 티켓에 맞는 에이전트로 띄운다. 서브에이전트는 에이전트 규칙을 받지 못하므로, 기본 에이전트로 띄우면 규칙이 정한 위임이 빠진다. 띄울 수 없으면 같은 세션에서 티켓을 차례로 2, 3, 4, 6단계대로 한다.
   ```
   <run-ticket SKILL.md의 절대 경로>를 읽고 티켓 <참조>에 대해 2, 3, 4, 6단계를 수행하라. 1단계와 5단계, 6단계의 "마지막 티켓이면"은 건너뛴다. 끝나면 완료 기준 결과, 바꾼 파일, 산출물 위치만 보고하라.
   이미 내린 결정: <결정과 걸리는 티켓. 없으면 이 줄을 뺀다>
   ```
   레포 규칙이 코드를 고치기 전에 사용자 승인(제안 diff 승인 등)을 요구하면, 서브에이전트에는 제안 diff 작성까지만 맡기고 이 세션이 승인을 받아 적용한다. 서브에이전트는 사용자에게 물을 수 없다.
4. 완료 기준을 통과하지 못한 티켓이 나오면, 에이전트 규칙이 실패 처리를 정해 두었으면 그것을 따른다. 실패 보고를 넘겨 다시 띄우거나 규칙이 정한 다른 에이전트로 띄운다. 그래도 통과하지 못하면 멈추고, 시도한 에이전트와 횟수를 보고에 넣는다. 뒤 티켓이 그 결과에 기댈 수 있다.
5. **통합 리뷰**: 모든 서브에이전트가 끝나면 전체 변경(작업 시작 HEAD 이후의 커밋, 커밋하지 않은 변경, 새 파일. 레포 규칙이나 사용자 결정으로 도중에 커밋했을 수 있다)에 5단계 리뷰를 한 번 하고, 고친 부분이 걸친 티켓의 완료 기준을 다시 확인한다. 그 뒤 6단계의 "마지막 티켓이면"을 한다.
6. 티켓별 결과를 6단계 보고 형식으로 모아 알린다.

서브에이전트는 하나씩 띄운다. 커밋하지 않으므로 같은 작업 트리를 동시에 고치면 충돌한다.
