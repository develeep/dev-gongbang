## 원칙 A. 명확성과 맥락

- 규칙의 이유는 사용자에게 받는다. 모르면 질문한다.
- 모델 자기 인식이 필요한 앱이면(A5=예) 현재 모델명과 정확한 모델 문자열을 적는다.

## 원칙 B. 예시

- 예시는 사용자에게 받고 `<examples>` 안의 `<example>`로 감싼다. 사용자가 예시 생성을 요청하면 초안을 보여 주고 승인받은 것만 넣는다.

## 원칙 C. 구조

- 태그 이름은 조립 골격의 이름을 쓰고, 프롬프트 전체에서 같은 이름을 쓴다.
- **긴 컨텍스트(약 20k 토큰 이상)**: 문서는 위, 질문과 지시는 끝에 둔다. 문서마다 `<document>`로 감싸고 `<source>`, `<document_content>` 하위 태그를 쓴다. 필요하면 답하기 전에 관련 구절을 `<quotes>`로 먼저 인용하게 한다.
- 런타임에 바뀌는 값은 `{{VARIABLE_NAME}}` 플레이스홀더로 둔다. 어떤 값이 변수인지는 사용자에게 확인한다.

## 원칙 D. 출력과 서식

- **마지막 assistant 턴 prefill은 Claude 4.6 이후 모델(Opus 4.6+, Sonnet 4.6+, 5.x 전체)에서 400 오류가 난다.** 형식 강제에는 structured outputs, 분류에는 enum 도구, 서두 제거에는 "서두 없이 바로 답하라"는 지시를 쓴다. 이어 쓰기는 user 메시지로 옮긴다. Haiku 4.5처럼 그 이전 모델은 prefill을 받지만, 나중에 모델을 옮길 수 있으면 같은 대안을 먼저 쓰는 편이 이전이 쉽다.
- 도구를 쓴 뒤 요약이 필요하면 명시적으로 요청한다. 최신 모델은 요약을 건너뛸 수 있다.

## 원칙 E. 도구 사용

- 행동을 원하면 명령형으로 쓴다. "바꿔 줄 수 있어?"라고 쓰면 제안만 할 수 있으니 "바꿔라"라고 쓴다.
- 기본 성향은 사용자에게 물어 하나만 넣는다.
  - **적극 실행형**: 기본적으로 제안보다 구현을 하고, 의도가 불분명하면 가장 유용한 행동을 추론해 진행하며, 빠진 정보는 추측하지 말고 도구로 확인하게 한다.
  - **신중형**: 명확한 지시 없이는 파일을 바꾸지 않고, 의도가 모호하면 정보 제공, 조사, 추천에 그치게 한다.
- `CRITICAL`, `MUST` 같은 강한 표현은 과잉 트리거를 부른다. "~할 때 이 도구를 써라" 정도의 평이한 표현을 쓴다.
- 병렬 호출: 서로 의존하지 않는 호출은 한 번에 병렬로 하고, 앞 결과가 뒤 호출의 인자가 되면 순차로 하게 한다. 누락된 인자를 추측하거나 플레이스홀더로 채우지 않게 한다.
- MCP 도구는 `서버명:도구명` 형식의 완전한 이름으로 적는다.

## 원칙 F. 사고와 추론

- 사고 설정은 모델 세대마다 다르다. 실행 설정 권고를 쓰기 전에 대상 모델 가이드를 확인한다.
  - 4.6 이후 모델은 적응형 사고(`thinking: {type: "adaptive"}`)를 쓰고, 사고 깊이는 `effort`로 조절한다.
  - 수동 확장 사고(`thinking: {type: "enabled", budget_tokens: N}`)는 4.6에서 deprecated, 4.7 이후 모델에서는 400 오류다.
  - Haiku 4.5 같은 4.5 이하 모델은 반대로 확장 사고(`budget_tokens`)만 지원하고 `adaptive`는 400 오류다.
- 사고를 이끌 때는 사람이 짠 단계별 계획보다 "철저히 생각하라" 같은 일반 지시가 대개 낫다.
- few-shot 예시에 `<thinking>`을 넣으면 사고 스타일이 전파된다.
- 과잉 사고를 줄이려면 접근법을 하나 정해 밀고 나가게 하고, 모순되는 새 정보가 나올 때만 다시 검토하게 한다. 그보다 먼저 effort를 낮추는 쪽이 확실하다.
- 자체 검증 지시("완료 전에 [기준]으로 검증하라")는 코딩과 수학에서 효과가 있다. Opus 5 계열처럼 스스로 검증하는 모델에서는 모델 가이드를 우선한다.

## 원칙 G. 에이전트 시스템

아래 항목은 괄호 안의 트리거 답이 있을 때만 넣는다. 모델 가이드에 같은 행동을 다루는 스니펫이 있으면(예: 범위 제한, 서브에이전트 위임 기준) 모델 가이드 쪽만 넣고 여기 항목은 넣지 않는다.

- **컨텍스트 압축 안내** (G10=예): 하네스가 자동 압축을 하면 그 사실을 알려서, 토큰 예산 때문에 일찍 멈추지 않고 압축 전에 진행 상태를 저장하게 한다.
- **다중 컨텍스트 윈도우** (G9=파일 또는 git): 첫 윈도우는 뼈대(테스트, 설정 스크립트)를 만들고 이후 윈도우는 할 일 목록을 반복하게 한다. 테스트 상태는 `tests.json` 같은 구조화 파일로, 진행 메모는 `progress.txt` 같은 자유 텍스트로, 체크포인트는 git으로 남긴다. 새 윈도우를 시작하는 절차를 명시한다(예: progress 파일, tests.json, git log 확인).
- **가역성과 안전** (G4 답이 있을 때): 로컬에서 되돌릴 수 있는 작업은 바로 하고, 삭제, force push, 외부 게시처럼 되돌리기 어렵거나 공유 시스템에 영향을 주는 작업은 확인받게 한다. 확인이 필요한 구체적인 목록과, 장애물을 파괴적인 지름길(`--no-verify` 등)로 넘지 말라는 지시를 함께 넣는다. 목록은 G4 답에서 가져온다.
- **리서치** (G11=리서치, 또는 S4=분석·리서치): 성공 기준을 정의하고, 여러 출처로 교차 검증하게 한다. 경쟁 가설과 확신도를 추적하게 한다.
- **서브에이전트** (G7=허용 + 위임 기준): 병렬로 돌릴 수 있거나 격리된 컨텍스트가 필요한 독립 작업에만 위임하게 하고, 단순하거나 순차적인 작업, 단일 파일 편집은 직접 하게 한다.
- **과잉 엔지니어링 방지** (G8=금지하고 제안만): 요청한 것과 명백히 필요한 것만 바꾸게 한다. 안 건드린 코드에 주석이나 타입을 추가하지 않고, 일어날 수 없는 경우의 방어 코드와 일회성 추상화를 만들지 않게 한다.
- **테스트 하드코딩 방지** (G13=테스트 통과가 완료 조건에 포함): 테스트만 통과하는 해법 대신 모든 유효 입력에 맞는 일반 해법을 쓰게 하고, 테스트가 틀렸으면 우회하지 말고 보고하게 한다.
- **환각 최소화** (G13=기존 코드에 대한 질문에 답함): 열어 보지 않은 코드를 추측하지 않고, 언급된 파일은 먼저 읽고 답하게 한다.
- **임시 파일 정리** (G13=반복 작업에 임시 파일을 만듦): 반복 작업용 임시 파일은 끝에 지우게 한다.
- **실행 시 구체화** (C16=예): 작업 지시보다 앞에, 작업을 시작하기 전에 framing-problems 스킬로 요청을 구체화하라는 지시를 넣는다. 다음 네 가지를 함께 넣는다. 이 지시가 없으면 실행하는 모델이 프롬프트에 적힌 해법을 곧바로 정답으로 삼는다.
  1. 이 프롬프트에 적힌 배경, 목적, 규칙은 확인된 사실로 쓰고 다시 묻지 않는다.
  2. 프롬프트나 입력에 적힌 해법은 제안 해법으로 보류하고 다른 후보와 비교한다.
  3. 구체화 기록이 확정되면 그 기록의 목표와 해법(R5)에 따라 작업한다. 기본 성향(G3)은 기록이 확정된 뒤의 실행에 적용한다.
  4. 작업 중 사용자가 전제를 바로잡으면 framing-problems의 되돌아가기 절차로 기록을 갱신한 뒤 이어 간다.

## 원칙 H. 기능별 팁

아래 항목도 괄호 안의 트리거 답이 있을 때만 넣고, 모델 가이드에 같은 주제의 질문이 있으면 그쪽을 따른다.

- **비전** (C15=이미지·차트·스크린샷 입력): 이미지를 잘라 확대하는 crop 도구나, PIL/OpenCV가 있는 컨테이너를 주면 정확도가 오른다. 이것은 프롬프트 문구가 아니라 실행 설정 권고로 적는다.
- **프론트엔드** (C15=프론트엔드 UI 생성): 방향을 주지 않으면 "AI slop" 기본값으로 수렴한다. 서체, 색, 모션, 배경의 방향을 구체적으로 주고, 흔한 기본값(Inter/Roboto/Arial, 흰 배경 보라 그라디언트, 예측 가능한 레이아웃)을 피하게 한다. 구체적인 방향은 사용자에게 받는다.

## 조립 골격

### API 시스템 프롬프트 / 에이전트 프롬프트

```
[역할 1~2문장]

<context>        배경, 목적, 사용자, 이 규칙들이 필요한 이유
<instructions>   작업 방식 (순서가 중요하면 번호 단계)
<constraints>    규칙과 각각의 이유, 범위 밖 요청 처리, 불확실할 때의 행동
<tools>          도구별 사용 시점과 방법 (도구가 있을 때)
<autonomy>       확인이 필요한 행동, 완료 조건, 진행 보고 방식 (에이전트)
<examples>       사용자가 준 예시 3~5개
<output_format>  형식, 길이, 톤
[긴 프롬프트면 끝에 짧은 핵심 리마인더]
```

### 단발 작업 프롬프트

```
<documents>      긴 자료는 맨 위
<context>        배경과 목적
<instructions>   작업 단계
<examples>
<output_format>
[질문 또는 최종 지시는 맨 끝]
```

태그는 받은 값이 있는 것만 쓴다. 빈 태그는 남기지 않는다.

## 공통 검수 목록

- [ ] 모든 내용이 사용자 답변이나 확인받은 초안에서 나왔다 (지어낸 값 없음)
- [ ] 프롬프트에 없는 사실을 추측하게 하는 지시가 없다 (C9 문구 포함)
- [ ] 맥락 없는 동료가 읽어도 이해된다 (황금 규칙)
- [ ] 주요 규칙마다 이유가 있다
- [ ] 금지형 지시를 가능한 한 "할 것" 형태로 바꿨다
- [ ] 태그 이름이 일관되고, 빈 태그가 없다
- [ ] 긴 자료는 위, 질문은 끝에 있다 (해당 시)
- [ ] 예시가 다양하고 `<example>`로 감싸져 있다 (해당 시)
- [ ] `CRITICAL`/`MUST` 같은 과한 강조가 없다
- [ ] 대상 모델이 받지 않는 설정(4.6 이후 모델의 prefill, 4.7 이후 모델의 `budget_tokens`, 4.5 이하 모델의 `adaptive`)에 의존하지 않는다
- [ ] 런타임 변수가 `{{VAR}}`로 표시되어 있고 목록을 확인받았다
- [ ] 완성 프롬프트가 B2에서 고른 언어로 쓰였다
- [ ] 원칙 G·H 항목은 트리거 답이 있는 것만 들어갔고, 모델 가이드 스니펫과 겹치지 않는다
- [ ] 모델 가이드의 검수 항목을 통과했다
