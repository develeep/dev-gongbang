## 인터뷰 항목

필수 여부와 빠른 모드 기본값의 뜻은 [interview.md](interview.md)의 카탈로그와 같다. 라운드 순서도 interview.md에 있다.

| ID | 항목 | 질문 | 형식 | SKILL.md | CLAUDE.md | 빠른 모드 기본값 |
|---|---|---|---|---|---|---|
| K1 | 대상 | 무엇을 만드나요? (SKILL.md / 프로젝트 CLAUDE.md / 사용자 CLAUDE.md) | 선택 | ● | ● | - |
| K2 | 이름 | 스킬 이름은? (소문자·숫자·하이픈, 64자 이하, "anthropic"·"claude" 불가) | 서술 | ● | - | - |
| K3 | 하는 일과 트리거 | 스킬이 하는 일과, 어떤 말이나 상황에서 실행되어야 하는지 알려 주세요. (CLAUDE.md는 프로젝트 규칙과 각 규칙의 이유) | 서술 | ● | ● | - |
| K4 | 자유도 | 작업 성격은? (여러 방법이 가능해 판단이 중요 → 높음 / 선호 패턴이 있음 → 중간 / 실수하면 위험하고 순서가 고정 → 낮음) | 선택 | ● | - | - |
| K5 | 절차 | 반드시 따라야 할 단계와 검증 루프가 있나요? | 서술 | ○ | ○ | 생략 |
| K6 | 번들 파일 | 참조 문서, 스크립트, 템플릿이 필요한가요? | 선택→서술 | ○ | - | 없음 |
| K7 | 사용 모델 | 어떤 모델에서 쓸 예정인가요? (Haiku / Sonnet / Opus / Fable) | 선택(다중) | ● | ○ | 세션 모델 계열 |
| K8 | 평가 시나리오 | 스킬을 테스트할 대표 요청 3개를 알려 주세요. SKILL.md는 비슷해 보이지만 이 스킬을 쓰면 안 되는 요청 2개도 알려 주세요. | 서술 | ● | ● | - |
| K9 | 자주 틀리는 점 | Claude가 이 작업에서 자주 틀리거나, 상식과 다르게 동작하는 환경 사실이 있나요? (예: 이 테이블은 soft delete라 조회에 `deleted_at IS NULL`이 필요하다) | 서술 | ○ | ○ | 생략 |

K7은 0라운드의 B1을 대신한다. 고른 모델마다 해당 모델 가이드의 "제거 검토"와 "검수 항목"을 적용한다. 모델 가이드가 없는 모델은 공통 원칙만 적용한다. K6=필요이면 결과물이 여러 파일이 되므로, [output-format.md](output-format.md)의 "파일 저장" 절차를 따른다.

## SKILL.md 규칙

- **frontmatter**: `name`(64자 이하, 소문자·숫자·하이픈, XML 태그 불가, 예약어 불가), `description`(비어 있으면 안 되고 1,024자 이하, XML 태그 불가).
- **description**은 3인칭으로 쓰고, 무엇을 하는지와 언제 쓰는지("~할 때 사용한다")를 모두 담는다. 언제 쓰는지는 트리거 문구 나열보다 사용자가 처한 상황과 의도로 쓴다. K8의 near-miss 요청에서 경계(쓰지 않는 경우)를 한 문장 넣는다. "도와드립니다"나 "당신은 이것으로" 같은 1인칭·2인칭 표현은 피한다.
- **이름**은 동명사형(`processing-pdfs`)을 권장한다. `helper`, `utils` 같은 모호한 이름은 피한다.
- **본문은 500줄 이하**로 쓰고, 넘을 것 같으면 참조 파일로 분리한다.
- **간결성**: Claude가 이미 아는 설명은 빼고, 문단마다 토큰값을 하는지 따진다.
- **점진적 공개**: SKILL.md는 목차 역할만 하고 세부는 참조 파일에 둔다. 참조는 SKILL.md에서 **한 단계 깊이**로만 연결한다. 참조 파일마다 **언제 읽을지** 조건을 적는다(예: "API가 200이 아니면 `reference/api-errors.md`를 읽는다"). "자세한 내용은 reference/ 참고"처럼 조건 없는 안내는 모델이 언제 읽을지 모른다. 100줄이 넘는 참조 파일은 맨 위에 목차를 둔다.
- **주의할 점(Gotchas)**: K9 답이 있으면 SKILL.md 본문에 "주의할 점" 절을 두고 그대로 적는다. 참조 파일이 아니라 SKILL.md에 두는 이유는, 모델이 그 상황을 만나기 전에 읽어야 하기 때문이다. K9를 생략했으면 절을 만들지 않는다.
- **자유도 맞추기**: 높음이면 휴리스틱을 텍스트로, 중간이면 파라미터가 있는 의사코드나 템플릿으로, 낮음이면 정확한 명령과 "수정 금지"로 쓴다.
- **워크플로**: 복잡한 작업에는 복사해서 쓸 수 있는 체크리스트와 "검증 → 수정 → 반복" 루프를 넣는다.
- **용어 일관성**: 한 개념은 한 용어로만 부른다.
- **시간에 민감한 정보 금지**: 옛 방식은 "이전 패턴" 섹션으로 분리한다.
- **선택지 과다 금지**: 기본값 하나와 예외 경로 하나만 준다.
- **경로는 슬래시(`/`)**로 쓰고, MCP 도구는 `서버:도구` 형식으로 쓴다.
- **스크립트**: 오류를 Claude에게 떠넘기지 말고 직접 처리한다. 상수에는 근거를 적는다. "실행"할 스크립트인지 "참조"할 스크립트인지 명시한다. 필요한 패키지를 적는다.
- **평가 먼저**: 시나리오 3개 이상을 정하고, 스킬 없이 돌린 기준 결과와 비교한다. 사용할 모든 모델에서 테스트한다. K8의 near-miss 요청으로 스킬이 잘못 실행되지 않는지도 확인하게 안내한다.
- **검증**: 저장했고 `skills-ref`를 쓸 수 있으면 `skills-ref validate <스킬 폴더>`로 frontmatter를 검증하라고 안내한다.

## CLAUDE.md 규칙

- 규칙마다 이유를 한 줄 붙인다.
- 코드와 git 기록에서 알 수 있는 내용은 넣지 않는다.
- `CRITICAL`이나 `MUST`를 남발하지 않는다.
- 금지보다 할 일로 쓴다.

## 검수 항목

- [ ] description에 "무엇"과 "언제"가 모두 있고 3인칭이며, 1,024자 이하다
- [ ] name이 스킬 폴더 이름과 같다
- [ ] K8 near-miss를 받았으면 description에 경계가 있다
- [ ] 참조 파일마다 언제 읽을지 조건이 적혀 있다 (K6=필요일 때)
- [ ] K9 답이 있으면 SKILL.md 본문에 "주의할 점" 절이 있다
- [ ] 본문이 500줄 이하이고 참조가 한 단계 깊이다
- [ ] 자유도가 K4 답과 맞는다
- [ ] 평가 시나리오 3개(near-miss 요청을 받았으면 그것까지)가 부록이나 안내에 포함됐다
