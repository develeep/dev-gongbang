## 0라운드: 기본 설정

모든 종류에서 처음에 한 라운드로 묻는다. 요청이나 초안에서 분명한 항목은 묻지 않고 되짚기만 한다. 종류가 불분명하고 답이 CLAUDE.md / SKILL.md일 수 있으면, 종류 문항 하나만 먼저 묻고 나머지를 이어서 묻는다(SKILL.md 종류는 B1 대신 K7을 쓰기 때문이다).

| ID | 항목 | 질문 | 선택지 |
|---|---|---|---|
| B0 | 종류 | 어떤 프롬프트인가요? | API 시스템 / 에이전트·하네스 / 단발 작업 / CLAUDE.md·SKILL.md |
| B1 | 대상 모델 | 이 프롬프트를 실제로 어떤 모델에서 돌리나요? | `<세션 모델> (세션 모델)` / 지원 모델 중 세션 모델이 아닌 것 최대 3개 (Sonnet 5.5, Haiku 4.5, Opus 5.5, Fable 5.1 순으로 고른다). 그 외는 직접 입력 |
| B2 | 프롬프트 언어 | 완성 프롬프트를 어떤 언어로 쓸까요? | 한국어 / 영어 (그 외는 직접 입력) |
| B3 | 진행 방식 | 질문을 얼마나 받을까요? | 빠른 모드: 필수 항목만 묻고 나머지는 기본값 표로 한 번에 승인 / 상세 인터뷰: 모든 항목을 라운드별로 질문 |

B1 선택지에는 "(권장)"을 붙이지 않는다. 대상 모델은 best practice가 아니라 사용자의 배포 환경이 정한다. 세션 모델과 대상 모델이 다르면, 이 세션에서 바로 시험해 보는 결과는 대상 모델의 동작과 다를 수 있다고 한 줄로 알린다.

## 구성 요소 카탈로그

형식: 선택 = AskUserQuestion, 서술 = 번호 텍스트 질문. 필수 여부: ● 필수, ○ 선택(상세 인터뷰에서는 묻고, 빠른 모드에서는 "빠른 모드 기본값"을 표로 승인받는다), - 해당 없음. CLAUDE.md / SKILL.md 종류는 이 표 대신 [skill-authoring.md](skill-authoring.md)의 K1~K10을 쓴다.

| C15 | 특수 입출력 | 해당하는 것을 모두 고르세요. (이미지·차트·스크린샷 입력 / 프론트엔드 UI 생성 / 해당 없음) | 선택(다중) | ○ | ○ | ○ | 해당 없음 |
| C16 | 실행 시 구체화 | 이 프롬프트를 실행하면 작업 전에 framing-problems 스킬로 요청을 먼저 구체화하게 할까요? 실행 환경에 그 스킬이 설치돼 있어야 합니다. (예 / 아니오) | 선택 | - | ● (G2=사람이 대화하며 진행) | ● (S3=템플릿) | - |

C9는 ● 항목으로 물을 때도 종류별 기본값을 "(권장)" 첫 선택지로 둔다. 근거: 에이전트와 단발 작업은 모델 가이드의 범위 지시들이 "일상적인 판단은 스스로 내리고, 해석에 따라 결과물이 실질적으로 달라질 때만 확인한다"를 권장한다. API 챗봇은 답을 받는 사람이 그대로 믿고 따르므로, 프롬프트에 없는 메뉴 경로나 정책을 그럴듯하게 지어내면 바로 피해가 된다. 어느 선택지든 프롬프트에는 다음 뜻으로 넣는다.

- 가정을 밝히고 진행: 해석이 모호하면 가장 그럴듯한 해석을 골라 그 가정을 밝히고 진행한다. 프롬프트와 입력에 없는 사실은 추측하지 않는다.
- 모른다고 답하고 도움 경로 안내: 프롬프트와 입력에 없는 사실은 모른다고 답하고 도움 경로를 안내한다. 경로(상담원 연결, 고객센터 등)는 사용자에게 받고, 받지 못하면 모른다고만 답하게 한다.

C11의 근거: 최신 모델은 길이를 작업에 맞춰 조절한다. C16을 무인 실행과 API 시스템 프롬프트에서 묻지 않는 이유: 구체화는 실행하는 사람에게 의도와 선택을 물어야 하는데, 무인 실행에는 물을 사람이 없고 챗봇은 메시지마다 구체화를 돌릴 일이 아니다. 한 번 쓰는 단발 작업에서 묻지 않는 이유: 프롬프트를 만드는 사람과 실행하는 사람, 작업이 모두 같아서 방금 받은 목적과 배경을 실행할 때 다시 확정받게 된다. 이 작업을 구체화하려면 framing-problems로 먼저 구체화 기록을 확정하고, 그 기록을 초안으로 넘기는 편이 맞다. 요청에서 이미 분명하면("실행하면 문제부터 정리하게 해줘") 묻지 않고 되짚는다.

## 빠른 모드

B3=빠른 모드이면 다음 순서로 진행한다.

1. 위 라운드 순서에서 ● 항목만 남겨 묻는다. 비게 된 라운드는 합쳐서 라운드 수를 줄인다.
2. ○ 항목은 다음 표 하나로 보여 주고 한 번에 승인받는다. 사용자가 고친 행만 반영한다. 표는 ● 질문과 같은 메시지에 함께 보여 준다. 조립이 끝난 뒤에 보여 주면 승인이 아니라 통보가 되기 때문이다.
   ```
   | 항목 | 기본값 | 근거 |
   |---|---|---|
   | C11 출력 길이 | 내용에 맞게 | 최신 모델은 길이를 작업에 맞춰 조절한다 |
   | C13 예시 | 생략 | - |
   ```
3. 서술형 ○ 항목의 기본값은 항상 "생략"이다. 내용을 지어낸 기본값은 두지 않는다.
## 답변 처리 규칙

- "알아서", "적당히", "모름" → 구체적인 후보 2~3개를 보여 주고 고르게 한다. 후보는 best practice상의 선택지여야 하고 도메인 내용을 지어내면 안 된다. 빠른 모드에서 ○ 항목이면 기본값을 후보의 첫째로 둔다.
- 수치나 기준이 없는 형용사("짧게", "자세히", "중요한 것만")에는 구체적인 기준을 되묻는다. 예: "짧게는 몇 문장 또는 몇 단어 정도인가요?"
- 규칙의 이유를 모른다고 하면 이유 없이 넣을지, 빼고 갈지를 묻는다.
- 답끼리 충돌하면(예: "무인 실행"과 "모든 변경 전 확인") 충돌 내용을 보여 주고 어느 쪽을 우선할지 묻는다.
- 사용자가 "생략"이라고 하면 그 항목은 프롬프트에서 뺀다. 필수 항목이면 빠질 경우의 영향을 한 문장으로 알리고 다시 확인한다.
- AskUserQuestion 후보가 4개보다 많으면 묶거나, 덜 쓰이는 후보를 직접 입력으로 돌린다.
