## 특성 요약

- effort가 사고량, 품질, 지연, 비용의 주 조절 수단이다. API 기본 effort는 `high`이다. 수준이 재보정되어 같은 이름이어도 Sonnet 5와 사고량이 다르다.
- 사고 기본값은 켜짐(적응형)이다. `thinking: {type: "disabled"}`는 모든 effort에서 400 오류가 난다. 사전 사고를 끄려면 `thinking: {type: "between_tools"}`를 쓴다. 이 설정은 Sonnet 5.5만 받으며, `high` 이하 effort에서만 쓸 수 있다.
- 수동 확장 사고(`budget_tokens`)는 400 오류가 난다.
- `medium` 이상에서는 인사말에도 짧게 사고해서 첫 토큰이 늦어진다. 시스템 프롬프트로 사고를 줄이라고 해도 확실히 줄지 않는다. 줄이려면 effort를 낮춘다. `low`에서는 단순한 요청 대부분에 사고를 건너뛴다.
- `low`와 `medium`의 긴 에이전트 코딩 작업에서는 끝나기 전에 사용자에게 확인을 구하며 멈추는 경우가 있다. `low`에서는 변경을 검증하지 않고 완료라고 보고할 수 있다.
- 요청하지 않은 테스트, 문서, 작은 보조 파일을 저장소 관례에 맞춰 덧붙이는 경향이 있다. effort가 높을수록 심하다.
- `xhigh`와 `max`에서는 작업을 마친 뒤 스스로 리뷰·검증 라운드를 시작하고, 서브에이전트를 쓰기도 한다.
- 열린 요청("이걸로 뭘 할 수 있는지 보여 줘")에서는 아이디어만 원해도 산출물을 만들기 시작할 수 있다.
- 구조화 출력으로 JSON을 받는 추론 작업에서, 특히 `low`와 `medium`에서는 사고 없이 바로 답해 정확도가 떨어질 수 있다.
- 채팅과 지식 업무에서 검색하면 잡을 수 있는 최신 정보를 학습 지식으로 답하는 경우가 있다.
- 간접 프롬프트 인젝션에 강하게 훈련되어 있어서, 도구 결과 바로 뒤에 붙은 진짜 사용자 메시지를 인젝션으로 오인할 수 있다.
- 도구 이름의 대소문자가 다르거나 파라미터 이름이 조금 다른 호출을 가끔 한다.
- 안전 분류기 대상: `cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms`. 거부되면 `stop_reason: "refusal"`이 반환된다.
- 가장 어려운 장시간 작업에는 Opus 모델이 더 낫다고 공식 가이드가 밝힌다. B1에서 Sonnet 5.5를 고른 사용자가 이런 작업을 설명하면 한 줄로 알린다.

## 프롬프트 반영

**P1. 끝까지 진행과 범위 제한** (M1) 시스템 프롬프트에 넣는다. 중간에 확인하며 멈추는 문제는 effort를 올리는 것이 먼저이므로, effort를 유지해야 할 때만 첫 문단을 넣는다고 알린다. 첫 문단을 넣으면 `low`와 `medium`에서 세션이 길어지고 비용이 는다. 위험하거나 되돌릴 수 없는 행동에 대한 확인 규칙(G4)은 이 스니펫이 대신하지 않으므로 그대로 둔다.
M1=범위 제한만이면 둘째 문단만 넣는다. 요청하지 않은 테스트·문서·보조 파일 추가는 모든 effort에서 일어나고 많은 팀이 반기는 동작이므로, 막을지는 사용자가 정한다. `xhigh`와 `max`에서는 둘째 문단이 이런 추가를 줄이고 변경 전체를 작게 만든다.
```
사용자가 요청한 일을 모두 마칠 때까지 계속한다. 사용자 없이는 더 진행할 수 없을 때나 위험한 단계 직전에만 멈춰서 묻는다.

요청한 일을 마치고 확인까지 끝나면 멈추고 보고한다. 요청하지 않은 기능, 테스트, 파일, 문서, 리팩터링은 추가하지 않는다. 도움이 될 것 같으면 하지 말고 끝에 제안한다.
```
G8=금지하고 제안만이면 원칙 G의 과잉 엔지니어링 방지 문구 대신 이 둘째 문단을 쓴다.

**P2. 자체 리뷰 라운드 억제** (M2=예) 시스템 프롬프트에 넣는다. 일상 작업은 이런 라운드가 드문 `high` 이하로 돌리는 편이 먼저라고 알린다. 공식 테스트(`max` effort 코딩)에서 리뷰 서브에이전트 실행이 멈추고 세션 비용이 약 3분의 1 줄었으며 품질 변화는 없었다. 메인 에이전트가 스스로 시작하는 리뷰는 줄지만 완전히 없어지지는 않는다.
```
요청한 일을 마치고 검사가 통과하면 멈추고 보고한다. 스스로 추가 리뷰나 보강 라운드를 시작하지 않고, 사용자가 리뷰를 요청하지 않았다면 리뷰용 서브에이전트를 띄우지 않는다. 더 깊은 리뷰가 필요하다고 보면 끝에 그렇게 말한다.
```

**P3. 아이디어·계획 요청** (M3=예) 시스템 프롬프트 대신 요청 자체에 "아이디어부터"라고 적는 방법도 있다. 단발 작업 프롬프트라면 그쪽을 쓴다.
```
사용자가 아이디어, 선택지, 계획을 요청하면 그것만 주고 멈춘다. 진행하라고 할 때까지 아무것도 만들거나 바꾸지 않는다.
```

**P4. JSON 추론 작업에서 먼저 생각하기** (M5=structured outputs) 적응형 사고에서 시스템 프롬프트 끝에 넣는다. `between_tools`에서는 효과가 없으므로 이 요청에는 적응형 사고를 쓰라고 실행 설정에 적는다.
```
답하기 전에 문제를 끝까지 생각한다.
```
효과: `high`에서는 출력 토큰이 조금 늘고 정확도가 `xhigh`에 가까워진다. `low`와 `medium`에서도 정확도가 오르지만 `high` 수준에는 못 미치고, 출력 토큰은 더 많이 는다. 스니펫 대신 `xhigh`로 돌리면 정확도가 가장 높지만 출력 토큰이 `high`보다 많다. 이 트레이드오프를 보여 주고 고르게 한다.
M5=프롬프트로 JSON 요청이면 스니펫 대신 하네스 권고를 적는다(실행 설정 권고 참고). 이 경우 모델은 응답 본문에서 문제를 풀고 끝에 JSON을 쓰는 경우가 많다. 적응형 사고에서 `xhigh`로 올리면 풀이가 사고로 옮겨 가 JSON만 돌려주는 경우가 많고, 총 출력 토큰은 `high`와 비슷하다.

**P5. 정해진 시점의 진행 보고** (M6=정해진 시점 원함. 사람이 대화하며 진행하는 작업에 가장 유용하다.)
```
첫 도구 호출 전에 무엇을 할지 한 줄로 말한다. 작업을 마치면 무엇을 찾았고 무엇을 했으며 다음은 무엇인지 짧게 정리한다.
```
M6=그대로 보여 줄 콘텐츠 있음이면, 사용자 메시지 전송 도구를 그런 콘텐츠에만 쓰라는 문장을 넣고 그 도구를 세션 첫 요청부터 `tools`에 선언하라고 실행 설정에 적는다.

**P6. 검색 트리거** (M7=예) 먼저 "꼭 필요할 때만 도구를 써라", "도구 호출을 최소화하라" 같은 문구를 제거한다(제거 검토).
```
학습 이후 바뀌었을 수 있는 세부, 예를 들어 무엇이 허용되고 요구되며 얼마가 부과되는지는 확신이 있어도 검색 도구로 확인한다. 보고서나 비교처럼 조사가 필요한 작업은 학습 지식으로 쓰지 말고 최신 출처를 모은다.
```

**P7. 코딩 변경 검증** (M9=예) 시스템 프롬프트에 넣는다.
```
실행, 빌드, 타입 검사가 가능한 코드를 바꿨으면 완료라고 보고하기 전에 그 변경을 실제로 실행해 보는 검사를 한다. 프로젝트의 테스트, 타입 검사기, 빌드, 또는 바꾼 명령 자체가 해당한다. 문법만 보는 검사나 시작조차 못 한 검사 명령은 검사로 치지 않는다. 빠진 것이 프로젝트에 선언된 의존성뿐이면, 하지 말라는 지시가 없는 한 프로젝트 자체의 패키지 관리자와 잠금 파일로 설치한다(예: npm install, pip install -r requirements.txt). sudo나 시스템 패키지 관리자는 쓰지 않는다. 실제 검사를 돌릴 수 없을 때만, 완료라고 보고하는 대신 어떤 검사를 왜 돌리지 못했는지 말한다.
```

M4와 M8은 프롬프트 문구가 아니라 실행 설정 권고로 반영한다.

## 제거 검토

- `thinking: {type: "disabled"}` 설정. 400 오류가 나므로 `between_tools`로 바꾼다.
- `budget_tokens`를 쓰는 수동 확장 사고. 400 오류가 난다.
- `between_tools`를 쓸 때 "생각하지 마라" 류의 지시. 내부 XML 태그가 응답에 새어 나올 가능성을 높인다.
- 응답 본문에 추론 과정을 쓰라는 지시. `reasoning_extraction` 거부 대상이다. 대신 `display: "summarized"`로 사고 요약을 읽는다.
- "모든 발견 사항은 최종 응답까지 보류하라" 같은 진행 보고 억제 문구
- "꼭 필요할 때만 도구를 써라", "도구 호출을 최소화하라" 같은 도구 사용 억제 문구 (P6 참고)
- 사고를 줄이라는 시스템 프롬프트 지시. 확실히 줄지 않으므로 effort를 낮춘다.

## 실행 설정 권고

- `output_config.effort`: 이전 모델의 값을 가져오지 말고 자체 평가로 다시 고른다.
  - 기본은 `high`에서 시작한다.
  - 에이전트 코딩과 다단계 도구 사용은 잘 정의된 작업이면 `medium`, 어렵거나 긴 작업이면 `high`.
  - 채팅과 지연에 민감한 작업은 `medium` 또는 `low`.
  - `xhigh`와 `max`는 품질 향상이 측정된 작업에만 쓴다.
- `max_tokens`: 사고도 여기에 포함된다. 에이전트 코딩은 최대치인 128,000으로 두고 스트리밍한다.
- `thinking`:
  - 기본(생략 또는 `{type: "adaptive"}`)을 권장한다.
  - M4=between_tools이면 `{type: "between_tools"}`를 쓴다. `high` 이하 effort에서만 쓸 수 있고, 다른 필드(`display`, `budget_tokens`, `block_binding`)를 함께 보내면 400 오류다. 대화 중 effort를 바꿀 수 없다. 도구가 없는 추론 작업에는 쓰지 않는다.
  - 진행 보고를 보이게 하려면 적응형에서 `display: "updates"`(베타 헤더 `thinking-display-updates-2026-08-18`)를 쓴다. `between_tools`에서는 요약 텍스트가 함께 오므로 필요 없다.
- 턴마다 effort를 바꿀 때는 최상위 `effort` 대신 메시지별 effort 변경(베타)을 쓴다. 최상위 값을 바꾸면 캐시가 깨진다. 적응형 사고에서만 된다.
- 조용한 구간: 텍스트도 진행 보고도 없는 도구 단계가 연속 5번쯤 나오면 턴 범위 시스템 메시지(`clear_at: "next_user_message"`, 베타 헤더 `mid-conversation-system-clear-at-2026-08-21`)로 "잠시 소식이 없었으니 무엇을 하는지 짧게 말하고 계속하라"는 알림을 붙인다. 2~3회까지만 보내고, 붙인 알림은 지우지 않는다. 도구 결과 뒤에 하네스 텍스트가 자주 붙으면 모델이 인젝션으로 의심할 수 있으므로, 그런 반응이 보이면 알림 빈도를 줄인다.
- 작업 중 사용자 메시지(M8): 사용자 텍스트를 `tool_result` 블록 안에 넣지 않는다. 마지막 `tool_result` 뒤에 같은 user 메시지의 텍스트 블록으로 붙인다. 하네스 알림은 사용자 말과 다른 블록의 대화 중간 시스템 메시지로 둔다. 사용자가 작업 중 입력할 수 있는 세션에는 도구 결과마다 토큰 카운트다운이나 단계별 지시를 붙이지 않는다. Task budgets(베타)는 이런 오인을 일으킨 사례가 없지만, 오인이 보이면 task budget 없이 시험한다.
- 도구 호출 관대 처리: 대소문자만 다른 도구 이름은 모호하지 않으면 받아들이거나, 정확한 이름을 적은 `is_error: true` 결과를 돌려준다.
- structured outputs(M5): `stop_reason: "max_tokens"`인 응답은 JSON이 유효해도 실패로 보고 재시도한다. `max_tokens`는 사고와 JSON을 담을 만큼 잡되, 한 번의 시도에 쓸 수 있는 비용을 넘지 않게 한다.
- 프롬프트로 JSON 요청(M5): `text` 블록만 읽고, 응답의 **마지막** JSON 값을 파싱한다. 각 `{`·`[`에서 파싱을 시도하고, 성공하면 그 값의 끝에서 이어 가서 중첩 값을 따로 세지 않는다. 첫 `{`부터 마지막 `}`까지를 통째로 잡지 않는다(앞에 초안 JSON이 있을 수 있다). 기대한 필드가 없으면 한 번 재시도한다. `stop_reason: "max_tokens"`이면 실패로 본다.
- 응답 읽기: 블록 타입별로 읽는다. 적응형에서는 첫 블록이 `thinking`일 수 있고, `between_tools`에서는 진행 보고 `thinking` 블록일 수 있다.
- 사고 블록은 받은 그대로 돌려보낸다. `between_tools`의 진행 보고 블록도 마찬가지다(돌려보내면 모델은 요약이 아니라 자기가 쓴 전체 메모를 본다). `block_binding`은 적응형 사고에서만 쓸 수 있다.
- 비전(C15=이미지): crop 도구나 코드 실행 컨테이너를 준다. 차트는 모든 effort에서 효과가 있고 effort를 올리는 것보다 효과가 크다. 기술 도면은 `high` 이상에서 효과가 있고 `xhigh`·`max`에서 가장 크다.
- 거부 대응(A7=예 등): 서버 측 폴백(베타)을 켜면 `cyber`와 `frontier_llm` 거부는 Sonnet 5로 재시도된다. `bio`, `reasoning_extraction`, `general_harms`는 재시도되지 않는다. 조직의 생명과학 업무가 `bio` 분류기에 막히면 Life Sciences Verification Program을 안내한다.
- Sonnet 5에서 옮기는 통합이면, 마이그레이션 가이드의 API 호환성을 깨는 변경 5가지를 확인하라고 안내한다(https://platform.claude.com/docs/en/models/sonnet-5-5/migration-guide).
