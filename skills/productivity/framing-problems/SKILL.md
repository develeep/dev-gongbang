# Framing Problems

요청을 해법으로 옮기기 전에 해법을 고를 근거를 모아 "구체화 기록"으로 남긴다. 기록은 사용자와 함께 확정한다. prompt-builder로 만든 프롬프트는 실행될 때 작업 전에 이 스킬을 호출할 수 있고, 그 작업은 확정된 기록에 따라 이어진다.

## 핵심 규칙

1. **확인할 수 있는 사실은 먼저 조사하고, 의도와 선택만 묻는다.** 코드, 문서, 초안, git 기록, 대화(이 스킬을 호출한 프롬프트 포함)로 답할 수 있는 것은 묻지 않는다. 조사로 찾은 사실은 출처(파일 경로:줄, 문서 이름, URL)와 함께 보여 주고 확인받는다. 왜 하려는지, 무엇을 만족으로 볼지, 무엇을 고를지는 조사로 정하지 않고 사용자에게 묻는다. 조사로도 답으로도 채우지 못한 칸은 "미확인"으로 남기고 지어내지 않는다.
2. **제안된 해법은 보류한다.** 요청이나 호출한 프롬프트에 해법이 들어 있으면("여기 고쳐줘", "이 규칙 넣어줘") 기록의 "R5 제안 해법"에 적어 두고, 그 해법이 풀려는 문제를 R1~R2에서 먼저 맞춘다. 버리지도 바로 채택하지도 않고, R5에서 다른 후보와 함께 비교한다.
3. **외부 근거는 적합성을 따로 판정한다.** 많이 쓰인다는 사실만으로 채택하지 않는다. 항목마다 우리 상황에 맞는지(맞음 / 조건부 / 맞지 않음)와, 그렇게 판단한 근거가 된 기록 항목(R1~R3)을 적는다.
4. **정정되면 바뀐 전제로 돌아간다.** 아래 "되돌아가기" 절차를 따른다.
5. **단계마다 사용자의 "맞다"를 받아야 넘어간다.** 사용자가 맞다고 하기 전에는 다음 단계로 가지 않는다. 조사로 찾은 사실도 사용자가 맞다고 해야 확정된다. 이 스킬을 호출한 프롬프트·스킬이 작업을 지시했더라도 그 지시는 사용자 대신 결정할 권한이 아니다. 질문에 스스로 답하고 넘어가지 않는다.
6. **모호한 점은 전부 묻는다.** 조사한 뒤에도 해석이 둘 이상 가능한 말, 기준 없는 표현("빠르게", "깔끔하게"), 범위가 정해지지 않은 대상, 근거가 약한 추정은 그럴듯한 해석으로 채우지 않고 질문으로 남긴다.
7. **넓은 조사는 서브에이전트로 미리 돌리고, 기다리는 동안 묻는다.** 여러 파일·디렉터리를 훑는 조사(R3 재사용 후보 목록 등)와 웹 조사(R4)는 Agent 도구로 백그라운드에서 돌린다. 파일 하나 읽기나 grep 한 번처럼 작은 조회는 직접 한다.
   - **미리 시작**: R4 웹 조사는 R1을 확정하면 바로 시작한다. 검색은 의도만 있으면 할 수 있다. 적합성 판정은 R3까지 확정한 뒤 R4에서 한다.
   - **막지 않기**: 조사가 끝나지 않았다고 메시지를 미루지 않는다. 그 조사 결과에 기대는 질문만 기다리고, 무관한 질문(의도, 이상적인 결과 등)은 먼저 보낸다.
   - **출처 지시**: 서브에이전트에게 사실마다 출처(`경로:줄`, URL)를 붙여 돌려 달라고 지시한다. 출처 없이 돌아온 내용은 "가설"로 적는다.
   - **도구가 없으면**: Agent 도구가 없으면 직접 조사하고, 순서대로 진행한다.

## 단계

아래 체크리스트를 시작할 때 한 번 보여 주고, 단계를 마칠 때마다 갱신한다.

```
구체화 진행:
- [ ] R1 의도·배경
- [ ] R2 이상·현재·원인
- [ ] R3 제약·자원
- [ ] R4 외부 근거
- [ ] R5 목표·해법
- [ ] R6 부작용·장애물
```

### R1 의도·배경

- **확정할 것**: 왜 이 일을 하려는지, 이야기를 꺼낸 계기(특정 사건 또는 반복되는 상황), 누가 겪는지.
- **먼저 조사**: 요청 문장, 대화 맥락, 관련 코드·문서·이슈.
- **묻기**: 계기와 의도. 요청이나 호출한 프롬프트에 이미 있으면 묻지 않고 "확인됨"으로 되짚기만 한다. 요청이 해법만 말하면 "이걸 바꾸면 무엇이 달라지길 바라나요?"처럼 해법 뒤의 의도를 묻는다.
- **넘어가는 조건**: 의도를 한 문장으로 되짚었고 사용자가 맞다고 했다.

### R2 이상·현재·원인

- **확정할 것**: 이상적인 결과(무엇이 어떻게 달라지면 만족인지, 관찰할 수 있는 기준으로), 현재 상태(지금 실제로 어떤지), 둘 사이의 차이(문제), 그 차이가 생기는 원인.
- 이상과 현재는 따로 묻고 따로 적는다. 섞이면 무엇이 부족한지 말할 수 없다.
- **먼저 조사**: 현재 상태는 코드, 출력, 로그, 재현으로 직접 확인한다. 원인 후보도 조사로 좁힌다.
- **묻기**: 이상적인 결과, 조사로 재현할 수 없는 현재 상태(실패 사례), 원인 후보 중 맞는 것.
- **넘어가는 조건**: 문제를 "이상은 X인데 현재는 Y다" 한 문장으로 쓸 수 있고, 원인이 하나 이상 "확인됨" 또는 "가설"로 적혀 있고.

### R3 제약·자원

- **확정할 것**: 바꿀 수 없는 조건(기술, 일정, 조직, 호환성), 그대로 활용할 기존 코드·도구·문서.
- **먼저 조사**: 이미 있는 구현, 설정, 의존성, 스킬·규칙. 재사용 후보를 목록으로 보여 준다.
- **묻기**: 바꿀 수 없는 조건, 재사용 후보 중 쓰면 안 되는 것.
- **넘어가는 조건**: 제약과 자원이 각각 목록이거나 "없음"으로 확인됐다.

### R4 외부 근거

- **확정할 것**: 이 문제에 이미 알려진 해결 방법이나 표준, 다른 구현들이 움직이는 방향.
- **먼저 조사**: 공식 문서, 표준, 널리 쓰이는 구현. 웹 검색 도구가 없으면 그렇다고 알리고, 모델 지식에서 나온 항목은 출처에 "모델 지식, 미검증"이라고 적는다.
- **판정**: 항목마다 적합성과 근거를 적는다(핵심 규칙 3).
- **묻기**: 적합성 판단에 필요한데 조사로 알 수 없는 것만.
- **건너뛰기**: 이 프로젝트에만 있는 문제라 비교할 외부 사례가 없으면 "해당 없음"과 이유 한 줄로 넘어간다.
- **넘어가는 조건**: 항목마다 적합성이 판정됐거나 "해당 없음"이 확인됐다.

### R5 목표·해법

- **목표**는 R2의 원인 중 무엇을 바꿀지이고, **해법**은 그것을 실제로 어떻게 바꿀지다. 둘을 따로 적는다.
- **후보**: 서로 다른 해법 2~3개를 만든다. 사용자의 제안 해법(있으면), R3 자원을 쓰는 해법, R4 근거에서 온 해법에서 고른다. 후보마다 어떤 원인을 바꾸는지 적는다. 어떤 원인도 바꾸지 않는 후보는 뺀다.
- **묻기**: 바꿀 원인(목표), 고를 해법.
- 목표로 고른 원인이 "가설"이면, 해법 실행 전에 그 가설을 확인할 방법(재현, 측정, 로그)을 R6 장애물에 적는다. 확인 결과 가설이 틀리면 R2로 돌아간다.
- **넘어가는 조건**: 목표와 해법이 각각 확정됐고, 해법이 목표의 원인을 어떻게 바꾸는지 적혀 있다. 고르지 않은 후보는 기각 이유와 함께 남긴다.

### R6 부작용·장애물

- **확정할 것**: 고른 해법이 새로 만드는 비용이나 위험, 실행을 막는 장애물(권한, 의존성, 일정), 다른 후보보다 나은 이유.
- **먼저 조사**: 해법이 건드리는 코드의 다른 호출부, 설정, 이 결과를 쓰는 사람이나 시스템.
- **묻기**: 부작용을 감수할지, 장애물을 어떻게 넘을지.
- 부작용을 감수할 수 없으면 R5로 돌아가 다른 해법을 고른다.
- **넘어가는 조건**: 부작용마다 "감수 / 완화책 / 해법 변경" 중 하나가 정해졌다.

## 질문 방식

- 한 번에 한 단계씩 묻는다. 단계 안의 질문은 번호를 붙여 한 메시지에 모은다.
- 다른 질문의 답에 따라 달라지는 질문은 같은 메시지에 넣지 않는다. 앞 질문의 답을 받은 뒤 다음 메시지에서 묻는다.
- 압축 모드가 아니면 질문 개수에 상한을 두지 않는다. 모호한 점이 남아 있으면 질문이 많아져도 묻고, 메시지를 여러 번 주고받아도 된다.
- **압축 모드**: 사용자나 호출한 프롬프트·스킬이 질문을 줄여 달라고 하면, 조사로 채울 수 있는 칸을 모두 채운 기록 표를 한 번에 보여 주고, 모든 단계의 모호한 점을 "단계 질문 형식"의 질문으로 함께 묻는다. 압축 모드는 질문 횟수만 줄인다. 모든 단계는 여전히 사용자가 맞다고 해야 확정되며, 사용자는 한 번의 답으로 여러 단계를 확정할 수 있다. 확정 전의 칸은 "확인 필요"로 표시한다.
- **중단**: 사용자가 구체화를 멈추라고 하면("그냥 해줘", "그만 묻고 진행해") 더 묻지 않는다. 지금까지의 기록을 보여 주고, 확정하지 못한 칸은 "미확인"으로 둔 채 마무리로 넘어간다. R5 해법이 미확인이면 사용자가 처음 말한 해법(R5 제안 해법)을 따르고, 그렇다고 한 줄로 알린다.

### 단계 질문 형식

단계마다 아래 순서로 한 메시지를 쓴다. 해당 내용이 없는 블록은 뺀다.

```markdown
### R2 이상·현재·원인

**정리한 내용**
- 이상: 배포 전 체크리스트 10개 항목이 모두 확인된다
- 현재: 배포 스크립트가 체크리스트를 읽지 않는다 (`scripts/deploy.sh:12`)
- 문제: 이상은 전 항목 확인인데 현재는 확인 여부를 아무도 검사하지 않는다
- 원인: 스크립트에 확인 단계가 없음 (확인됨)

**모호한 점**

❓ **Q1 - 배포 범위**: 여기서 "배포"는 프로덕션 배포만 가리키나요?

➡️ 네, 프로덕션만. 근거: `docs/deploy-checklist.md:1` 제목이 "프로덕션 배포 체크리스트"

---

❓ **Q2 - 빠지는 항목**: "자꾸 빠진다"는 항목은 매번 같은가요, 매번 다른가요?
(a) 특정 항목 (b) 매번 다름 (c) 모름

**확인**
위 정리와 추천이 맞나요? 맞으면 "맞다", 다르면 번호로 알려 주세요(예: "Q1 아니고 스테이징 포함, Q2 b").
```

- **정리한 내용**: 그 단계에서 확정할 항목을 기록 표의 항목 이름 그대로 한 줄씩 적는다. 조사한 사실에는 출처를 붙인다.
- **질문**: `❓ **Q번호 - 제목**: 본문` 형식으로 쓰고 질문 사이는 `---`로 나눈다. 본문에는 무엇이 모호한지 드러나게 쓰고, 고를 수 있는 해석이 있으면 (a)(b)(c)로 단다. 번호는 단계 안에서 이어 붙여, 사용자가 번호로 답할 수 있게 한다.
- **추천 답**: 조사 결과나 앞 단계 기록에 근거가 있으면 `➡️` 줄에 추천 답과 근거를 적는다. 질문은 "네"나 "맞다"가 추천을 받아들이는 뜻이 되도록 쓴다. 추천이 질문과 반대 방향이 되면 질문을 다시 쓴다.
- **추천을 달지 않는 질문**: R1 의도·계기와, 사용자만 아는 사실(Q2처럼 실패 사례)에는 추천을 달지 않는다. 추천을 주면 사용자는 동의만 하게 되고, 기록에는 사용자의 뜻 대신 모델의 추측이 남는다. 추천 없는 질문은 "맞다"로 넘어가지 않고, 답을 받을 때까지 그 단계를 확정하지 않는다.
- **확인**: 메시지의 마지막 줄은 항상 확인 요청이다. "맞다"는 정리한 내용과 모든 추천 답을 받아들인다는 뜻이다. 답을 받으면 반영한 정리를 다시 보여 주고 확인을 다시 받는다.
- 선택형 질문은 AskUserQuestion이 있으면 그것으로 묻는다. 이때 정리한 내용을 먼저 텍스트로 보여 주고, 질문을 넣는다. 추천 답은 첫 선택지에 두고 라벨 끝에 "(추천)"을 붙인다. 질문이 4개를 넘으면 텍스트 형식으로 묻는다.

## 되돌아가기

사용자가 앞서 확정한 내용을 바로잡으면("그게 아니고", "그런 뜻이 아니라") 다음 순서로 처리한다.

1. 정정된 내용이 어느 단계의 전제인지 찾는다.
2. 그 단계를 바뀐 전제로 다시 확정한다.
3. 그 뒤의 단계를 순서대로 다시 본다. "근거" 열에 바뀐 칸이 있는 결정은 다시 판단하고, 없는 결정도 결론이 여전히 성립하는지 확인한다.
4. 결과를 한 줄씩 보여 준다. 예: `R3 유지: 제약이 의도와 무관함` / `R5 변경: 캐시 추가 → 타임아웃 재시도`.

이미 정한 해법을 지키려고 정정을 조건이나 예외 하나로 덧붙이지 않는다. 그렇게 하면 해법이 바뀐 의도가 아니라 이전 의도를 계속 따르게 된다. 정정이 전제가 아니라 표현에 대한 것이면(용어, 문장) 그 칸만 고친다.

기록을 확정해 다른 작업으로 넘어간 뒤에 정정이 와도 같은 절차를 따른다.

## 구체화 기록 형식

```markdown
## 구체화 기록
| 항목 | 내용 | 출처 | 근거 |
|---|---|---|---|
| R1 의도 | | 사용자 | - |
| R1 계기 | | 사용자 | - |
| R2 이상 | 관찰할 수 있는 기준으로 | 사용자 | R1 의도 |
| R2 현재 | | `경로:줄` / 사용자 | - |
| R2 문제 | 이상은 X인데 현재는 Y다 | - | R2 이상, R2 현재 |
| R2 원인 | (확인됨 / 가설) | | R2 현재 |
| R3 제약 | | | - |
| R3 자원 | | `경로` | - |
| R4 근거 | 항목: 맞음 / 조건부 / 맞지 않음 | URL / 모델 지식, 미검증 | R1~R3 중 해당 칸 |
| R5 제안 해법 | 사용자가 처음 말한 해법 → 채택 / 기각 | 사용자 | - |
| R5 목표 | 바꿀 원인 | 사용자 | R2 원인 |
| R5 해법 | | 사용자 승인 | R5 목표, R3, R4 |
| R5 기각 후보 | 후보: 기각 이유 | - | |
| R6 부작용 | 부작용: 감수 / 완화책 / 해법 변경 | | R5 해법 |
| R6 장애물 | | | R5 해법 |
```

- **출처**: "사용자", 확인한 파일·문서·URL, 또는 "미확인".
- **근거**: 이 칸의 결정이 기대는 다른 칸. 되돌아가기에서 다시 볼 칸을 찾는 데 쓴다.
- 같은 항목에 값이 여럿이면 행을 나눈다(예: R2 원인 두 줄).

## 마무리

1. 완성된 기록 전체를 한 번 보여 주고 확정받는다.
2. 프롬프트나 다른 스킬이 호출했으면, 확정된 기록의 R5 목표와 해법에 따라 그 지시의 작업을 이어 간다.
3. 직접 호출됐으면 R5 해법을 실행할지 묻는다. 답을 받기 전에는 실행하지 않는다.
